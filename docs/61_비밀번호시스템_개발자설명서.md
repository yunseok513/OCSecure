# 비밀번호 시스템 개발자 설명서

## 1. 이 설명서의 대상과 범위

로그인과 회원 관리 화면을 만드시는 분을 위한 문서입니다. 비밀번호를 어떻게 저장하고 어떻게 검증하며 어떤 실수를 피해야 하는지를 다룹니다.

운영 중 관리해야 할 사항과 프로젝트 파일 목록은 `60_비밀번호시스템_관리자설명서.md`에 있습니다. 비밀번호가 아닌 나머지 개인정보의 암복호화는 `50_전자정부프레임워크_사용설명서.md`를 보시면 됩니다.

본문의 자바 코드는 실제로 컴파일하고 시험한 것입니다. 데이터베이스 호출문은 구현과 대조하였으나 오라클에서 실행해 확인하지는 못하였으므로, 처음 적용하실 때 한 건씩 확인하며 진행하시기를 권합니다.

## 2. 먼저 알아야 할 세 가지

### 2.1 되돌릴 수 없습니다

저장된 값에서 원래 비밀번호를 얻는 방법은 없습니다. 함수도 없고 권한도 없으며 우회 경로도 없습니다. 따라서 "비밀번호 찾기" 화면은 알려 주는 기능이 아니라 새로 설정하게 하는 기능이어야 합니다. 이 점을 기획 단계에서 합의해 두지 않으면 개발 막바지에 문제가 됩니다.

### 2.2 세션 문맥이 필요 없습니다

다른 개인정보의 복호화는 접속 증표로 세션 문맥을 세운 뒤에만 동작하지만, 비밀번호 함수는 그렇지 않습니다. 권한 판정도 사용량 집계도 적용되지 않습니다.

이것은 설계상 그래야 합니다. 로그인하기 전에는 사용자가 누구인지 모르므로 문맥을 세울 수 없는데, 비밀번호 검증은 바로 그 시점에 필요하기 때문입니다. 순서를 정리하면 비밀번호를 검증하여 사용자를 확인하고, 그다음에 문맥을 세우고, 그다음부터 개인정보 조회가 가능해집니다.

### 2.3 느린 것이 정상입니다

비밀번호 계산은 일부러 느리게 만들어져 있습니다. 반복 횟수만큼 계산을 되풀이하며, 그 반복이 유출 시의 대량 대입을 어렵게 만드는 유일한 장치입니다. 느리다고 반복 횟수를 낮추자는 요청을 하시기 전에 제4장의 성능 항목을 읽어 보시기 바랍니다.

느리다는 사실이 코드에 영향을 주는 지점이 하나 있습니다. **로그인 한 번에 한 번만 호출해야 합니다.** 목록 조회나 반복문 안에서 호출하면 즉시 문제가 됩니다.

## 3. 저장 형식과 컬럼 정의

저장값은 54바이트의 이진값입니다. 안에 포맷 버전과 키 유도 방식과 반복 횟수와 무작위 값과 계산 결과가 차례로 들어 있습니다. 반복 횟수가 값 안에 있으므로 나중에 기준을 올려도 기존 사용자의 검증이 깨지지 않습니다.

컬럼은 `RAW(64)`로 잡으십시오. 정확히는 54바이트면 되지만 여유를 두는 편이 낫습니다.

```sql
CREATE TABLE TB_USER (
  user_id   VARCHAR2(50) NOT NULL,
  user_nm   VARCHAR2(100),
  user_pwd  RAW(64),          -- 비밀번호 저장값. 54바이트.
  ...
  CONSTRAINT pk_tb_user PRIMARY KEY (user_id)
);
```

문자열 컬럼에 담지 마십시오. 이진값이므로 문자집합 변환 과정에서 손상됩니다. 굳이 문자열로 다루어야 하는 사정이 있다면 16진 문자열로 바꾸어 108자를 담되, 그럴 이유가 있는지 먼저 검토하시기 바랍니다.

컬럼 길이를 짧게 잡으면 값이 잘려 들어가고, 잘린 값은 영원히 검증에 실패합니다. 개발 중에 검증이 계속 실패한다면 컬럼 정의부터 확인하십시오.

## 4. 함수 규격

데이터베이스 쪽에 세 개가 있습니다. 모두 `OCS_OWNER.PKG_SECURE_API`에 들어 있으며, 응용 계정에 실행 권한이 부여되어 있습니다.

```sql
-- 비밀번호를 저장값으로 바꾼다. 반복 횟수는 현재 설정을 따른다.
FUNCTION make_pwd(p_password IN VARCHAR2) RETURN RAW;

-- 입력값이 저장값과 일치하면 1, 아니면 0. SQL 에서 직접 쓸 수 있도록 숫자를 돌려준다.
FUNCTION verify_pwd(p_password IN VARCHAR2, p_stored IN RAW) RETURN NUMBER;

-- 저장값의 반복 횟수가 현재 기준보다 낮으면 1, 아니면 0.
FUNCTION pwd_stale(p_stored IN RAW) RETURN NUMBER;
```

자바 쪽에도 같은 계산을 하는 함수가 있습니다. 데이터베이스가 만든 저장값과 자바가 만든 저장값은 서로 호환되며, 어느 쪽에서 만든 값이든 다른 쪽에서 검증할 수 있습니다. 세 구현이 같은 고정 시험 벡터를 통과하는 것으로 확인하였습니다.

```java
byte[]  stored  = OcsCrypto.passwordHash(password, iterations);
boolean ok      = OcsCrypto.passwordVerify(password, stored);
boolean upgrade = OcsCrypto.passwordNeedsUpgrade(stored, currentIterations);
```

어느 쪽을 쓸지는 제9장에서 다루겠습니다. 특별한 사정이 없으면 데이터베이스 쪽을 쓰십시오.

## 5. 등록

회원 가입이나 사용자 등록에서는 평문을 넘기면 됩니다.

```xml
<insert id="insertUser" parameterType="userVO">
  INSERT INTO TB_USER (user_id, user_nm, user_pwd)
  VALUES (#{userId}, #{userNm}, OCS_OWNER.PKG_SECURE_API.make_pwd(#{userPwd}))
</insert>
```

바인드 변수를 쓰십시오. 문자열을 이어 붙여 구문을 만들면 주입 통로가 되는 것은 물론이고, 비밀번호가 실행 계획 캐시와 추적 파일에 평문으로 남습니다.

빈 값은 거부되며 `ORA-20541` 오류가 납니다. 화면에서 필수 입력 검증을 하셨더라도, 공백만 입력된 경우처럼 걸러지지 않는 경우가 있으니 서버 쪽 검증을 함께 두시는 편이 낫습니다.

비밀번호 복잡도 규칙은 이 시스템이 검사하지 않습니다. 길이와 문자 구성에 대한 규칙이 필요하다면 애플리케이션에서 검사한 뒤 넘기십시오.

## 6. 로그인 검증

### 6.1 기본형

```xml
<select id="selectPasswordMatch" resultType="int">
  SELECT OCS_OWNER.PKG_SECURE_API.verify_pwd(#{inputPwd}, user_pwd)
    FROM TB_USER
   WHERE user_id = #{userId}
</select>
```

결과가 1이면 일치, 0이면 불일치, 조회 결과가 없으면 존재하지 않는 사용자입니다.

### 6.2 존재하지 않는 계정을 다룰 때

여기에 함정이 하나 있습니다. 존재하지 않는 계정이면 조회가 즉시 끝나고, 존재하는 계정이면 반복 계산에 시간이 걸립니다. 이 응답 시간 차이만으로 어떤 계정이 실제로 있는지 알아낼 수 있습니다. 계정 목록을 수집하는 공격에 그대로 노출되는 셈입니다.

막는 방법은 없는 계정에 대해서도 같은 시간만큼 계산해 주는 것입니다. 기동 시점에 더미 저장값을 하나 만들어 두고, 사용자를 찾지 못했을 때 그 값에 대고 검증을 수행한 뒤 실패로 처리합니다.

```java
public class LoginService {

    // 기동 시점에 한 번 만들어 둡니다. 어떤 사용자의 것도 아닌 값입니다.
    private final byte[] dummyStored =
            OcsCrypto.passwordHash("dummy-for-timing-only", currentIterations());

    public boolean authenticate(String userId, String inputPwd) {
        byte[] stored = userMapper.selectPasswordBlob(userId);   // 없으면 null

        if (stored == null) {
            // 없는 계정이어도 같은 시간을 들인다. 결과는 버린다.
            OcsCrypto.passwordVerify(inputPwd, dummyStored);
            return false;
        }
        return OcsCrypto.passwordVerify(inputPwd, stored);
    }
}
```

데이터베이스 쪽 함수로 처리하겠다면 같은 취지로 더미 저장값을 한 건 테이블에 두고 그것을 쓰면 됩니다. 어느 쪽이든 요점은 응답 시간을 맞추는 것입니다.

화면에 돌려주는 메시지도 구분하지 마십시오. 없는 계정과 틀린 비밀번호를 각각 다르게 알리면 응답 시간을 맞춘 보람이 없습니다. 둘 다 같은 문구로 처리하십시오.

### 6.3 로그인 이후

비밀번호 검증에 성공한 뒤에야 세션 문맥을 세울 수 있습니다. 순서를 지키십시오.

```java
Connection con = dataSource.getConnection();
try {
    if (!authenticate(userId, inputPwd)) {
        return LoginResult.FAIL;
    }
    session.establish(con, userId);     // 이제 개인정보 조회가 가능해집니다
    // ...
} finally {
    session.release(con);
    con.close();
}
```

## 7. 반복 횟수 점진 상향

운영 중에 관리자가 반복 횟수를 올릴 수 있습니다. 올린 뒤에도 기존 사용자의 저장값은 옛 횟수 그대로 남아 검증은 정상 동작하지만, 그대로 두면 옛 사용자만 약한 상태로 남습니다.

옮기는 방법은 로그인에 성공한 그 순간, 곧 입력받은 평문이 아직 손에 있는 그때 다시 계산하여 저장하는 것입니다. 그 시점을 놓치면 원문을 알 수 없으므로 영영 불가능합니다.

```xml
<select id="selectPasswordStale" resultType="int">
  SELECT OCS_OWNER.PKG_SECURE_API.pwd_stale(user_pwd)
    FROM TB_USER WHERE user_id = #{userId}
</select>

<update id="updatePasswordBlob">
  UPDATE TB_USER
     SET user_pwd = OCS_OWNER.PKG_SECURE_API.make_pwd(#{inputPwd})
   WHERE user_id = #{userId}
</update>
```

```java
if (authenticate(userId, inputPwd)) {
    if (userMapper.selectPasswordStale(userId) == 1) {
        // 로그인 흐름을 막지 않도록, 실패해도 그냥 넘어갑니다.
        // 다음 로그인 때 다시 시도하면 됩니다.
        try {
            userMapper.updatePasswordBlob(userId, inputPwd);
        } catch (Exception e) {
            log.warn("비밀번호 저장값 갱신 실패: userId={}", userId);
        }
    }
    ...
}
```

갱신에 실패했다고 로그인을 막지 마십시오. 다음 로그인에서 다시 시도하면 되는 일입니다. 다만 실패가 계속 쌓인다면 원인을 봐야 하므로 경고 로그는 남기십시오. 로그에 비밀번호를 찍지 않도록 주의하십시오.

이 처리가 빠져 있으면 관리자가 반복 횟수를 올려도 기존 사용자는 옛 세기에 머뭅니다. 관리자 쪽에서 분포를 확인하고 있으므로, 처리가 누락되면 결국 확인 요청이 옵니다.

## 8. 변경과 초기화

비밀번호 변경 화면에서는 현재 비밀번호를 먼저 검증한 뒤 새 값을 저장합니다. 검증 없이 바꾸게 하면 화면을 열어 둔 채 자리를 비운 사이에 남이 바꿀 수 있습니다.

```java
if (!authenticate(userId, currentPwd)) {
    return Result.fail("현재 비밀번호가 일치하지 않습니다.");
}
userMapper.updatePasswordBlob(userId, newPwd);
```

관리자에 의한 초기화는 현재 비밀번호를 모르는 상태에서 이루어지므로 검증 단계가 없습니다. 그만큼 누가 초기화했는지가 기록되어야 하며, 이 시스템은 그 기록을 남기지 않으므로 애플리케이션이 남겨야 합니다. 초기화된 비밀번호는 최초 로그인 시 반드시 변경하도록 강제하는 편이 낫습니다.

임시 비밀번호를 만들어 전달하는 경우, 그 값을 전자우편이나 문자로 보내면 전달 경로에 평문이 남습니다. 유효 시간이 짧은 재설정 링크를 보내고 사용자가 직접 정하게 하는 방식이 더 안전합니다.

## 9. 자바 계층에서 계산하는 경우

기본은 데이터베이스 쪽 함수를 쓰는 것입니다. 애플리케이션 서버마다 구현이 흩어지지 않고, 반복 횟수 설정이 한곳에서 관리되기 때문입니다.

자바 쪽 계산을 고려할 만한 경우가 하나 있습니다. 반복 횟수를 크게 올렸는데 로그인이 몰리는 시간대에 데이터베이스 부하가 문제가 되는 경우입니다. 계산 자체를 애플리케이션 서버로 옮기면 데이터베이스는 저장값을 읽고 쓰기만 하면 되므로 부하가 분산됩니다. 애플리케이션 서버는 여러 대로 늘리기 쉽지만 데이터베이스는 그렇지 않다는 점도 고려할 만합니다.

옮기더라도 저장 형식은 같으므로 이미 저장된 값을 그대로 검증할 수 있고, 섞여 있어도 문제없습니다. 다만 반복 횟수 설정을 애플리케이션이 따로 들고 있게 되므로 데이터베이스 설정과 어긋나지 않도록 관리가 필요합니다. 기동 시점에 데이터베이스에서 읽어 오는 방식을 권합니다.

```java
// 기동 시점에 한 번 읽어 둡니다.
int iterations = configMapper.selectPwdIterations();   // SEC_CONFIG 조회

byte[] stored = OcsCrypto.passwordHash(inputPwd, iterations);
```

`SEC_CONFIG` 조회 권한이 응용 계정에 부여되어 있지 않다면 키 관리자에게 읽기 권한을 요청하십시오. 반복 횟수는 비밀이 아닙니다.

## 10. 기존 체계에서 옮겨 오기

### 10.1 먼저 기존 방식을 확인합니다

옮겨 오려면 기존 방식을 정확히 알아야 합니다. 확인하는 방법은 세 갈래이고, 마지막 하나만이 확정적입니다.

첫째는 저장값의 생김새로 좁히는 것입니다. 데이터베이스만 있으면 되고 가장 빠릅니다. 조사 스크립트를 마련해 두었습니다.

```
sqlplus <기존 시스템 계정>@대상DB
SQL> @sql/04_admin/410_legacy_pwd_survey.sql
```

컬럼 자료형과 길이 분포와 문자 구성을 보여 줍니다. 길이가 한 가지로 모여 있으면 해시일 가능성이 높고, 16진 표기 기준으로 32는 MD5, 40은 SHA-1, 64는 SHA-256, 128은 SHA-512의 길이입니다. Base64 표기라면 각각 24와 28과 44와 88입니다. 60이면 bcrypt이고 54면 이미 이 시스템의 형식입니다. 길이가 제각각이면 평문이거나 가변 길이 암호화입니다.

이 스크립트의 네 번째 항목이 특히 중요합니다. 서로 다른 사용자가 같은 저장값을 갖고 있는지를 세는데, 중복이 있으면 솔트가 없다는 뜻입니다. 같은 비밀번호를 쓰는 사람이 여럿인 것은 흔한 일이므로, 중복이 전혀 없다면 사용자마다 다른 값이 섞여 들어갔다고 볼 수 있습니다. 조사는 저장값을 화면에 띄우지 않고 세기만 하도록 만들었습니다. 실태 조사가 곧 유출 경로가 되어서는 안 되기 때문입니다.

둘째는 소스 코드를 읽는 것입니다. 확실하지만 시간이 걸립니다. 로그인 처리 서비스에서 비밀번호를 다루는 지점을 찾아 따라가면 되고, `encryptPassword`나 `MessageDigest`나 `PasswordEncoder` 같은 이름으로 검색하면 대개 금방 나옵니다. 비밀번호를 갱신하는 매퍼 구문을 찾아 데이터베이스 함수를 쓰는지 애플리케이션에서 계산한 값을 넣는지 보는 것도 방법입니다.

셋째는 실증 대조이며, 이것만이 확정적입니다. 평문과 그 평문으로 만들어진 저장값 한 쌍을 확보한 뒤 후보 구성들을 재현해 보고 일치하는 것을 찾습니다. 쌍을 얻는 방법은 시험계에 계정을 하나 만들고 비밀번호를 정해 등록한 뒤 그 계정의 저장값을 조회하는 것입니다. **운영계 사용자의 비밀번호로 시도하지 마십시오.**

```
python3 tools/legacy_pwd_probe.py         --plain '정한비밀번호' --stored '조회한저장값' --id '아이디'
```

흔히 쓰이는 구성들을 차례로 재현해 보고 일치하는 것을 알려 줍니다. 해시 알고리즘 여섯 가지와 표기 다섯 가지, 아이디를 섞는 네 가지 배치, 두 번 해싱하는 변형, 그리고 문자집합 두 가지를 조합하여 시도합니다. 아이디를 함께 넣으시는 편이 좋습니다. 솔트를 따로 두지 않고 아이디를 솔트처럼 쓰는 구성이 국내 시스템에서 드물지 않기 때문입니다.

문자집합을 두 가지 시도하는 데에도 이유가 있습니다. 예전에 구축된 시스템은 EUC-KR을 쓰는 경우가 있고, 한글이 섞인 비밀번호에서는 문자집합이 다르면 결과가 완전히 달라집니다. 이 차이를 놓치면 한글 비밀번호를 쓰는 사용자만 검증에 실패하는 현상이 남습니다.

일치하는 것이 나오지 않으면 저장값의 생김새로 판단한 단서를 알려 줍니다. bcrypt이거나 접두사로 알고리즘을 표시하는 형식이면 그 사실을 짚어 주고, 그 밖의 경우에는 소스 코드 확인으로 넘어가시라고 안내합니다. 여기서 시도하는 것은 흔한 구성뿐이므로, 일치하지 않았다고 해서 특별한 방식이라는 뜻은 아닙니다.

평문으로 저장되어 있는 경우도 잡아냅니다. 이때는 이행 문제가 아니라 사고에 가까우므로 보안 담당자에게 먼저 보고하셔야 합니다. 다만 이행 자체는 오히려 쉽습니다. 평문을 알고 있으므로 일괄 변환이 되며, 두 방식을 공존시킬 필요조차 없습니다.

### 10.2 이행 경로

사용자가 모두 공무원이고 최근 1년 접속자가 2만 3천 명 규모이므로, **옛 방식으로 로그인시키되 그 자리에서 비밀번호 변경을 강제하는 방식**을 택하였습니다.

임시 비밀번호를 발급하는 강제 초기화와는 다릅니다. 초기화는 옛 비밀번호를 무효화하므로 본인확인 채널이 따로 필요하고, 임시 비밀번호를 전달하는 경로가 새로운 노출 지점이 됩니다. 반면 강제 변경은 사용자가 옛 비밀번호로 로그인에 성공한 상태에서 이루어지므로 본인확인이 이미 끝나 있고, 전달할 것도 없습니다. 사용자가 겪는 불편도 변경 화면 한 번으로 끝납니다.

### 10.3 컬럼 준비

옛 형식은 Base64 44자이고 새 형식은 16진 108자입니다. 한 컬럼에 섞여 있어도 길이와 문자 구성으로 구분되므로, 컬럼을 넓히기만 하면 됩니다. 오라클에서 문자열 컬럼의 길이를 늘리는 것은 테이블을 다시 쓰지 않으므로 서비스 중에도 가능합니다.

```sql
ALTER TABLE TB_USER MODIFY (user_pwd VARCHAR2(108));
```

이행이 끝난 뒤 옛 값이 하나도 남지 않았음을 확인하면 `RAW(64)`로 정리할 수 있습니다. 그때는 한 번의 변환이 필요하므로 서비스 중단 시간을 확보하십시오. 급한 일은 아닙니다.

### 10.4 배포 전 관문

가정이 틀린 채로 배포하면 전 사용자가 로그인하지 못합니다. 실제 계정으로 확인한 뒤에 배포하십시오.

```sql
SELECT OCS_OWNER.PKG_LEGACY_PWD.self_check('아는 평문', '그 계정의 저장값') FROM DUAL;
```

`일치 (문자집합 ...)`가 나와야 합니다. 나온 문자집합이 `AL32UTF8`이 아니라면 `SEC_CONFIG`의 `LEGACY_PWD_CHARSET`을 그 값으로 바꾸셔야 합니다. 예전에 구축된 시스템은 문자집합이 갈리는 경우가 있고, 어긋나면 한글이 섞인 비밀번호를 쓰는 사용자만 로그인하지 못하는 현상이 남습니다.

`불일치`가 나오면 조사가 틀린 것입니다. 배포하지 마시고 `tools/legacy_pwd_probe.py`로 다시 확인하십시오.

### 10.5 로그인 흐름

판정 함수 하나로 옛 형식과 새 형식을 함께 처리합니다.

```sql
-- 0 = 불일치, 1 = 일치(현재 형식), 2 = 일치(옛 형식, 변경 강제)
SELECT OCS_OWNER.PKG_SECURE_API.check_pwd(#{inputPwd}, user_pwd)
  FROM TB_USER WHERE user_id = #{userId}
```

```java
public LoginResult authenticate(String userId, String inputPwd) {
    String stored = userMapper.selectPasswordText(userId);

    if (stored == null) {
        // 없는 계정이어도 같은 시간을 들인다. 응답 시간으로 계정 목록이
        // 새어 나가지 않게 하기 위함이다.
        OcsCrypto.passwordVerify(inputPwd, dummyStored);
        return LoginResult.FAIL;
    }

    int r = userMapper.checkPassword(userId, inputPwd);
    if (r == 0) {
        return LoginResult.FAIL;
    }
    if (r == 2) {
        // 옛 형식이다. 로그인은 시키되 비밀번호 변경 화면으로 보낸다.
        // 여기서 곧바로 새 형식으로 저장하지 않는다. 같은 비밀번호를 그대로
        // 새 형식에 담으면 형식만 바뀔 뿐, 이미 유출되었을지 모르는 비밀번호는
        // 그대로 남기 때문이다.
        return LoginResult.MUST_CHANGE_PASSWORD;
    }
    return LoginResult.OK;
}
```

여기서 한 가지를 주의하셔야 합니다. 옛 형식으로 검증에 성공했을 때 **같은 비밀번호를 새 형식으로 다시 저장하고 끝내고 싶은 유혹**이 있습니다. 사용자를 귀찮게 하지 않으니 편해 보입니다. 그러나 옛 방식은 솔트 없는 단일 해시라 이미 유출되었을 가능성을 배제할 수 없고, 유출되었다면 그 비밀번호는 이미 알려진 값입니다. 형식만 바꾸어 담으면 알려진 비밀번호를 그대로 쓰는 셈이 됩니다. 그래서 변경을 강제합니다.

### 10.6 비밀번호 변경 화면

변경 화면에서는 새 형식으로만 저장합니다.

```xml
<update id="updatePasswordText">
  UPDATE TB_USER
     SET user_pwd = OCS_OWNER.PKG_SECURE_API.make_pwd_str(#{newPwd}),
         pwd_chg_dt = SYSDATE
   WHERE user_id = #{userId}
</update>
```

변경을 마치기 전에는 다른 화면으로 나가지 못하게 막으십시오. 막지 않으면 대부분 건너뛰고, 이행이 끝나지 않습니다. 세션에 변경 필요 표시를 두고 모든 요청에서 확인하는 방식이 무난합니다.

이 기회에 비밀번호 복잡도 규칙도 함께 적용하십시오. 기존 시스템에 규칙이 없었다면 지금이 넣기 가장 좋은 때입니다. 사용자가 어차피 새로 정해야 하므로 추가 불편이 없습니다.

### 10.7 이행 완료

옛 형식이 하나도 남지 않으면 `PKG_LEGACY_PWD`와 `PKG_SECURE_API`의 `check_pwd`, `make_pwd_str`을 제거하십시오. 남겨 두면 약한 검증 경로가 계속 남습니다. 제거 시점과 절차는 관리자 설명서에 있습니다.

## 11. 시험하기

직접 구현을 손대셨다면 고정 시험 벡터로 확인할 수 있습니다. 파이썬 참조 구현이 만들어 낸 값이 기준이며, 데이터베이스와 자바 구현이 같은 값을 내는지 대조합니다.

```
./tools/run_checks.sh
```

데이터베이스 쪽은 인스턴스에서 자체 시험을 돌립니다. 설치 직후와 변경 배포 직후에 반드시 실행하십시오.

```
sqlplus OCS_OWNER/…@대상DB
SQL> @sql/09_test/900_kat_setup.sql
SQL> @sql/09_test/901_kat_data.sql
SQL> @sql/09_test/902_selftest.sql
```

비밀번호 관련 항목으로는 저장값이 참조 구현과 일치하는지, 한글 비밀번호가 제대로 처리되는지, 올바른 값은 통과하고 틀린 값은 통과하지 못하는지, 같은 비밀번호라도 저장값이 매번 달라지는지, 빈 값이 거부되는지를 확인합니다.

업무 화면을 시험하실 때는 한글과 특수 문자가 섞인 비밀번호를 반드시 넣어 보십시오. 문자집합 처리가 어긋나 있으면 여기서 드러납니다.

## 12. 오류가 났을 때

`ORA-20541`은 인자 오류이며, 비밀번호 쪽에서는 빈 값을 저장하려 한 경우입니다. 화면 검증을 보완하십시오.

검증이 계속 실패한다면 컬럼 길이를 먼저 확인하십시오. `RAW(64)`보다 짧게 잡혀 있으면 저장값이 잘려 들어가고, 잘린 값은 절대 통과하지 못합니다. 저장 직후 `SELECT UTL_RAW.LENGTH(user_pwd) FROM TB_USER WHERE ...`로 54가 나오는지 보시면 바로 판별됩니다.

한글 비밀번호만 실패한다면 문자집합 문제입니다. 화면에서 데이터베이스까지 오는 경로 어딘가에서 변환이 일어나고 있는지 확인하십시오. 등록할 때와 검증할 때 같은 경로를 거치면 문제가 없지만, 두 경로가 다르면 어긋납니다.

로그인이 느리다면 반복 횟수 때문일 가능성이 큽니다. 관리자에게 현재 설정값을 문의하십시오. 다만 느린 것이 정상이라는 점을 먼저 감안하시기 바랍니다.

## 13. 하지 말아야 할 것

비밀번호를 로그에 남기지 마십시오. 디버그 로그, 예외 발생 시 파라미터 덤프, 접근 로그의 질의 문자열이 모두 위험합니다. 특히 공통 예외 처리에서 파라미터 전체를 찍는 코드가 있다면 반드시 확인하십시오.

비밀번호를 세션이나 캐시에 담지 마십시오. 검증이 끝나면 즉시 버려야 합니다.

문자열 연결로 구문을 만들지 마십시오. 바인드 변수를 쓰십시오.

검증 함수를 목록 조회나 반복문에서 호출하지 마십시오. 일부러 느리게 만든 계산이므로 한 번에 여러 건을 처리하면 즉시 문제가 됩니다.

저장값을 비교하여 같은 비밀번호인지 판별하려 하지 마십시오. 같은 비밀번호라도 저장값은 매번 다릅니다. 이는 결함이 아니라 의도된 성질입니다.

반복 횟수를 애플리케이션이 임의로 낮추어 호출하지 마십시오. 함수에 반복 횟수를 지정하는 인자가 있지만 이는 시험용이며, 업무 코드에서는 설정값을 따라야 합니다.

비밀번호를 다른 개인정보처럼 양방향으로 암호화하려 하지 마십시오. 복구할 수 있다는 것은 누군가 꺼내 볼 수 있다는 뜻입니다.

## 14. 참고 근거와 신뢰도 자체 평가

저장 형식과 함수 규격에 관한 서술은 신뢰도 높음입니다. 구현 코드와 직접 대조하였고, 자바 구현은 컴파일하여 고정 시험 벡터로 확인하였습니다.

비밀번호 함수에 세션 문맥과 권한 판정이 적용되지 않는다는 서술은 신뢰도 높음입니다. 구현을 확인하였습니다.

응답 시간 차이로 계정 존재 여부가 드러난다는 서술은 신뢰도 높음입니다. 널리 알려진 취약점 유형입니다.

데이터베이스 호출문에 관한 서술은 신뢰도 중간입니다. 함수 이름과 인자는 구현과 대조하였으나 오라클에서 실행해 확인하지는 못하였습니다.

전자정부 표준프레임워크의 기존 비밀번호 처리 관행에 관한 서술은 신뢰도 중간입니다. 실제 사용 중인 코드를 확인하셔야 합니다.

## 15. 결론 요약

비밀번호는 되돌릴 수 없으므로 찾기 기능은 재설정이어야 하고, 검증에는 세션 문맥이 필요 없으므로 로그인 전에 호출할 수 있으며, 일부러 느리게 만들어져 있으므로 로그인 한 번에 한 번만 호출해야 합니다. 저장 컬럼은 `RAW(64)`로 잡고, 검증이 계속 실패하면 컬럼 길이부터 확인하십시오. 존재하지 않는 계정에 대해서도 같은 시간을 들여 검증해야 응답 시간으로 계정 목록이 새어 나가지 않으며, 화면 메시지도 구분하지 말아야 합니다. 관리자가 반복 횟수를 올렸을 때 기존 사용자를 옮기는 일은 로그인 성공 그 순간에만 가능하므로, 그 처리를 반드시 넣으십시오. 기존 단일 해시 체계에서 옮겨 올 때는 저장값의 길이와 첫 바이트로 방식을 판별하여 두 방식을 한동안 공존시키고, 기간을 정해 정리한 뒤 옛 검증 코드를 제거하십시오.
