## 1. 이 문서의 범위

저장소에 들어 있는 파이썬 코드와 자바 코드를 어떻게 준비하고 돌리고 배포하는지를 다룹니다. 지금까지의 설명서들이 "무엇을 어떻게 쓰는가"를 다루었다면 이 문서는 "그것을 어떻게 만들어 내는가"를 다룹니다.

본문의 모든 명령은 실제로 실행하여 결과를 확인한 것입니다. 확인하지 못한 것은 그렇다고 적어 두었습니다.

## 2. 준비물

자바는 8 이상이면 됩니다. 연동 모듈이 8을 대상으로 컴파일되도록 해 두었기 때문이며, 그 이유는 전자정부 표준프레임워크 3.x 환경까지 고려했기 때문입니다. 개발 환경의 자바가 더 높아도 상관없습니다.

파이썬은 3.6 이상이면 동작할 것으로 보이나, 확인은 3.11에서만 하였습니다. 정확도: 중간.

**명령 이름이 운영체제마다 다릅니다.** 리눅스와 맥에서는 `python3`이지만 윈도우에서는 `python` 또는 `py`입니다. 윈도우에는 `python3`라는 명령이 대개 없습니다. 이 문서는 `python`으로 적었으니, 리눅스나 맥에서 동작하지 않으면 `python3`으로 바꾸어 보십시오. 제2.1절에 진단 방법이 있습니다.

**외부 패키지는 파이썬 쪽에도 자바 쪽에도 필요하지 않습니다.** 모두 표준 라이브러리만으로 돌아갑니다. 폐쇄망을 염두에 둔 결정이며, 자세한 것은 제4.2절과 제9장에서 다루겠습니다.

오라클 쪽 자체 시험을 돌리려면 인스턴스와 접속 도구가 필요하나, 그것 없이도 파이썬과 자바 점검은 전부 돌아갑니다.

### 2.1 파이썬이 제대로 잡혔는지 확인하기

무엇보다 먼저 이것을 확인하십시오. 아래가 판 번호를 제대로 찍어야 나머지가 의미가 있습니다.

윈도우에서는 다음과 같이 확인합니다.

```
py -0
py -3 --version
where python
```

`py -0`은 설치된 파이썬 판의 목록을 보여 줍니다. 아무것도 나오지 않으면 파이썬이 설치되어 있지 않은 것입니다.

리눅스와 맥에서는 다음과 같이 확인합니다.

```
python3 --version
type python3
```

### 2.2 명령을 실행했는데 `Python`만 찍히고 끝난다면

윈도우에서 겪기 쉬운 증상입니다. 윈도우 10과 11에는 앱 실행 별칭이라는 기능이 있어서, 파이썬이 설치되어 있지 않아도 `python`이나 `python3`이라는 이름의 껍데기가 자리를 차지하고 있습니다. 그것을 실행하면 아무 일도 하지 않고 끝나거나 마이크로소프트 스토어가 열립니다. 추측입니다만, 뒤에 붙인 인자가 모두 무시되고 짧은 문구만 찍히는 증상은 대개 이 경우입니다.

확인은 제2.1절의 `py -0`으로 합니다. 목록이 나오면 파이썬은 설치되어 있고 명령 이름만 잘못 고른 것이므로 `py -3`으로 바꾸면 해결됩니다.

```
py -3 -m unittest discover -s tests -q
```

목록이 나오지 않으면 파이썬을 설치하셔야 합니다. 설치할 때 경로 추가 항목을 켜 두시고, 설치 후에는 설정에서 앱 실행 별칭을 꺼 두시면 이 혼동이 사라집니다. 시작 메뉴에서 앱 실행 별칭을 찾으면 해당 설정 화면이 나옵니다.

리눅스나 맥에서 같은 증상이 난다면 별칭이나 껍데기 스크립트가 끼어 있는 경우이므로 `type python3`으로 무엇이 실행되는지 확인하십시오.

## 3. 한 번에 점검하기

평소에는 이것 하나면 됩니다. 어느 운영체제에서나 같은 일을 합니다.

```
python tools/run_checks.py
```

운영체제에 맞춘 껍데기도 두었습니다. 리눅스와 맥에서는 다음과 같이 쓰고,

```
./tools/run_checks.sh
```

윈도우에서는 다음과 같이 씁니다.

```
tools\run_checks.bat
```

껍데기는 파이썬을 찾아 `tools/run_checks.py`를 부르는 일만 합니다. 실제 점검은 전부 그 파이썬 파일이 하므로, 어느 방법으로 실행하든 결과는 같습니다. 껍데기가 파이썬을 찾지 못하면 그 사실을 알려 주고 멈춥니다.

네 가지를 차례로 수행합니다. 참조 구현 시험을 돌리고, 고정 시험 벡터가 참조 구현과 여전히 일치하는지 확인하고, PL/SQL 정적 점검을 하고, 자바 모듈을 컴파일하여 자체 시험을 돌립니다.

마지막 줄에 `모든 점검 통과`가 나와야 합니다. 커밋하기 전에 돌리는 습관을 들이시면 좋습니다.

한 가지만 돌리고 싶으면 `--only`를 씁니다.

```
python tools/run_checks.py --only java
```

`python`, `vectors`, `plsql`, `java` 중에서 고를 수 있습니다.

건너뛴 항목이 있으면 마지막에 무엇을 건너뛰었는지 알려 주고, 기본적으로는 실패로 보지 않습니다. `cryptography` 패키지가 없거나 JDK가 없는 경우가 이에 해당하며, 폐쇄망에서 흔한 상황이기 때문입니다. 지속 통합처럼 하나도 빠짐없이 돌아야 하는 자리에서는 `--strict`를 붙이면 건너뛴 것도 실패로 처리합니다.

여기서 확인하지 못하는 것이 하나 있습니다. **오라클에서의 컴파일과 실행입니다.** 이 점검은 인스턴스를 필요로 하지 않으므로, PL/SQL은 정적 점검까지만 이루어집니다. 실 인스턴스 확인은 제6장을 보십시오.

## 4. 파이썬 쪽

### 4.1 무엇이 들어 있는가

`tools/refimpl/ocsecure_ref.py`가 참조 구현입니다. 암호문 포맷의 실행 가능한 정의이며, 문서의 서술과 실제 구현이 어긋나는 것을 막는 역할을 합니다. PL/SQL과 자바가 이것과 같은 값을 내는지로 정확성을 판정하므로, 이 파일이 세 구현의 기준점입니다.

`tools/refimpl/gen_vectors.py`는 참조 구현이 만들어 낸 값을 고정 시험 벡터로 떨어뜨립니다. 세 가지 형식으로 나오는데, JSON은 범용, `.properties`는 자바용, `.sql`은 오라클용입니다.

`tools/legacy_pwd_probe.py`는 기존 비밀번호 저장 방식을 식별합니다. 이 도구만은 외부 패키지 없이 돌아갑니다.

`tools/lint_plsql.py`는 오라클 없이 잡을 수 있는 PL/SQL 오류를 걸러 냅니다.

`tests/`에는 참조 구현 시험과 식별기 시험이 있습니다. `tests/vectors/`에는 생성된 고정 시험 벡터가 있으며, 이 둘은 손으로 고치지 않습니다.

### 4.2 준비

준비할 것이 없습니다. 파이썬만 있으면 모든 도구가 그대로 돌아갑니다.

예전 판에서는 참조 구현이 암호 연산에 외부 패키지를 썼습니다. 지금은 표준 라이브러리만으로 만든 AES 구현을 함께 담고 있어 그 의존이 사라졌습니다. 폐쇄망으로 옮길 때마다 설치 파일을 챙기고 운영체제와 파이썬 판을 맞춰야 하는 부담이 컸기 때문에 내린 결정입니다.

직접 만든 암호 구현은 검증이 생명이므로 두 가지로 대조합니다. 하나는 미국 표준문서 FIPS-197 부록 C.3의 AES-256 공인 시험 벡터이고, 다른 하나는 검증된 라이브러리가 설치되어 있을 때 무작위 입력 이백 건으로 결과를 맞춰 보는 것입니다. 두 대조 모두 `tests/test_aes_pure.py`에 있습니다. 어느 경로로 돌든 참조 구현이 같은 시험 벡터를 만들어 내는지도 함께 확인합니다.

**이 구현은 참조 구현 전용입니다.** 운영에서 실제 암복호화를 수행하는 것은 오라클과 자바의 검증된 구현이며, 직접 만든 것은 그것들이 내놓은 값이 규격과 맞는지 확인하는 기준으로만 씁니다.

검증된 라이브러리를 설치하면 참조 구현이 그쪽을 씁니다. 개발 환경에서는 설치하는 편이 낫습니다. 검증된 구현이고 더 빠르며, 무엇보다 직접 만든 구현을 계속 대조할 수 있게 해 주기 때문입니다.

```
pip install -r requirements.txt
```

### 4.3 시험 실행

전부 돌리려면 이렇게 합니다. 저장소 최상위에서 실행합니다. 리눅스와 맥에서는 `python3`을, 윈도우에서는 `py -3`을 쓰십시오.

```
python -m unittest discover -s tests -q
```

명령 이름이 헷갈리면 제3장의 점검 실행기를 쓰는 편이 낫습니다. 파이썬을 알아서 찾습니다.

```
python tools/run_checks.py --only python
```

무엇이 통과했는지 하나씩 보고 싶으면 `-q` 대신 `-v`를 씁니다. 시험 이름을 한글로 달아 두었으므로 무엇을 확인하는 시험인지 이름만 보아도 알 수 있습니다.

파일 하나만 돌리려면 이렇게 합니다.

```
python -m unittest discover -s tests -p "test_refimpl.py"
```

시험 묶음 하나만 돌리려면 `tests` 디렉터리로 들어가서 실행합니다.

```
cd tests
python -m unittest test_refimpl.TestPassword
```

### 4.4 시험 벡터 다시 만들기

참조 구현을 고쳤다면 벡터를 다시 만들어야 합니다.

```
python tools/refimpl/gen_vectors.py
```

세 파일이 함께 갱신됩니다. **반드시 참조 구현 수정과 같은 커밋에 넣으십시오.** 벡터만 옛것으로 남아 있으면 PL/SQL과 자바 쪽 시험이 엉뚱한 기준과 대조하게 됩니다.

이 사고를 막으려고 점검 실행기가 벡터를 임시로 다시 만들어 기존 파일과 대조합니다. 어긋나면 거기서 멈추므로 잊고 커밋하는 일은 생기지 않습니다. 대조가 끝나면 원래 파일을 되돌려 놓으므로 점검 자체는 작업 파일을 바꾸지 않습니다. 갱신은 위 명령을 직접 돌려 의도적으로 하셔야 합니다.

줄바꿈 차이는 내용 차이로 보지 않습니다. 생성기가 운영체제와 무관하게 같은 줄바꿈으로 쓰도록 해 두었고, 형상 관리 설정 때문에 내려받은 파일이 다를 수 있으므로 대조에서도 그 차이는 무시합니다.

벡터를 손으로 고치지 마십시오. 생성 파일이며, 다음 생성 때 덮어써집니다.

### 4.5 저장 방식 식별기

기존 시스템의 비밀번호 저장 방식을 알아낼 때 씁니다. 자세한 사용법은 `개발자_매뉴얼.md` 제9.7절에 있습니다.

```
python tools/legacy_pwd_probe.py --plain '평문' --stored '저장값' --id '아이디'
```

### 4.6 PL/SQL 정적 점검기

```
python tools/lint_plsql.py
```

패키지 명세와 본문의 대응, 종결자 누락, 그리고 패키지 사이의 호출이 실제로 존재하는 이름을 가리키는지를 확인합니다. 오타로 인한 컴파일 실패를 미리 잡아 주지만 컴파일을 대신하지는 못합니다.

## 5. 자바 쪽

### 5.1 무엇이 들어 있는가

`java/src/main/java/ocsecure/client/` 아래가 연동 모듈의 본체입니다. `OcsCrypto`가 암호문 포맷 구현이고, `OcsKeySet`이 키 묶음, `OcsAppProof`가 접속 증표 생성기, `OcsSessionSupport`가 세션 문맥 확립 도우미, `OcsLegacyPassword`가 이행 기간용 기존 방식 검증, `OcsCryptoException`이 예외 정의입니다.

`java/src/test/java/ocsecure/client/OcsSelfTest.java`가 자체 시험입니다. 고정 시험 벡터와 대조하여 참조 구현과 바이트 단위로 같은 값을 내는지 확인합니다.

`java/pom.xml`이 빌드 정의입니다.

### 5.2 의존성이 없다는 것

외부 라이브러리를 하나도 쓰지 않습니다. JDK 표준 라이브러리만으로 만들었습니다.

의도한 설계입니다. 암호 모듈이 다른 라이브러리를 끌고 들어오면 그 라이브러리의 취약점이 곧 암호 모듈의 취약점이 되고, 대상 프로젝트가 이미 쓰고 있는 것과 버전이 충돌하면 적용 자체가 막힙니다. 전자정부 표준프레임워크 프로젝트는 의존성이 이미 촘촘하게 얽혀 있는 경우가 많아 이 점이 특히 중요합니다.

덕분에 빌드 도구 없이 `javac`만으로도 컴파일되고, 소스를 그대로 복사해 넣어도 동작합니다.

### 5.3 빌드 도구 없이 컴파일하기

가장 간단한 방법입니다. 저장소 최상위에서 실행합니다.

```
javac -encoding UTF-8 -d out $(find java/src -name '*.java')
java -Dstdout.encoding=UTF-8 -cp out ocsecure.client.OcsSelfTest tests/vectors/kat.properties
```

`-encoding UTF-8`은 어느 환경에서나 필요합니다. 원본 파일이 UTF-8 이므로 이것을 빠뜨리면 주석의 한글 때문에 컴파일에 실패할 수 있습니다.

`-Dstdout.encoding=UTF-8`은 환경에 따라 다릅니다. 여기가 헷갈리는 지점이라 따로 적겠습니다.

리눅스와 맥에서 로캘이 UTF-8 이 아니면 한글이 물음표로 나오므로 붙이는 편이 낫습니다. 반면 **한글 윈도우 콘솔에서는 붙이면 오히려 글자가 깨집니다.** 콘솔의 코드 페이지가 949 인데 UTF-8 바이트를 내보내면 콘솔이 그것을 949 로 읽어 엉뚱한 글자가 되기 때문입니다. 윈도우에서 직접 실행하실 때는 이 인자를 빼시거나, 먼저 `chcp 65001` 로 콘솔을 UTF-8 로 바꾸십시오.

이 번거로움을 피하려면 제3장의 점검 실행기를 쓰십시오. 자바의 출력을 UTF-8 로 받아 파이썬을 거쳐 다시 찍으므로, 콘솔에 맞추는 일은 파이썬이 알아서 합니다. 어느 운영체제에서나 한글이 제대로 나옵니다.

이 과정을 묶어 둔 것이 점검 실행기의 자바 항목입니다. 경고까지 모두 켜고 컴파일하며, 자바 파일 목록도 알아서 모으므로 평소에는 이것을 쓰시면 됩니다. 어느 운영체제에서나 같습니다.

```
python tools/run_checks.py --only java
```

리눅스와 맥에서는 `./tools/build_java.sh`도 같은 일을 합니다. 윈도우에서는 `tools\run_checks.bat --only java`를 쓰십시오.

위에 적은 `javac` 명령의 `$(find ...)` 부분은 리눅스와 맥에서만 동작합니다. 윈도우에서 직접 컴파일하시려면 파일 목록을 따로 만들어 넘겨야 하므로, 점검 실행기를 쓰는 편이 간단합니다.

### 5.3의2 연동 확인 프로그램

`OcsConnectDemo` 는 실제 데이터베이스에 붙어 연동이 되는지 확인합니다. 설치 직후 한 번 돌려 보는 용도이며 업무 코드가 아닙니다. 문맥 없이는 거부되는지, 증표를 제출하면 암호화가 되는지, 색인이 구분자와 무관하게 같은 값을 내는지, 복호화 자격에 따라 거부와 평문이 갈리는지를 봅니다.

덧붙이는 선택지가 셋 있습니다. `--data` 는 투명화 뷰에 자료를 넣고 꺼내 본 다음 지웁니다. `--keep` 은 같은 일을 하되 지우지 않고 남기며, 키 교체 리허설에 옮길 자료가 있어야 할 때 씁니다. `--read` 는 남은 자료를 읽기만 하고 넣지도 지우지도 않으며, 키를 교체한 직후와 옛 키를 폐기한 직후에 옛 자료가 그대로 읽히는지 보는 데 씁니다. 복호화 자격이 있는지는 먼저 물어보고 그에 맞추어 판정하므로, 자격을 주기 전과 준 뒤에 같은 명령을 그대로 다시 돌릴 수 있고 통과 건수는 어느 쪽이든 같습니다.

이 프로그램만은 JDBC 드라이버가 필요합니다. 오라클 설치 폴더의 `jdbc/lib/ojdbc8.jar` 에 있습니다. 라이브러리 자체에는 여전히 외부 의존성이 없습니다.

```
javac -encoding UTF-8 -cp ojdbc8.jar -d out @srcs.txt
java  -cp out;ojdbc8.jar ocsecure.client.OcsConnectDemo \
      "jdbc:oracle:thin:@호스트:포트/서비스명" <응용계정> - -
```

증표용 키를 명령행에 적으면 명령 이력에 남습니다. 확인이 끝나면 이력을 지우십시오. 운영 코드에서는 키 관리 제품이나 기동 시점에 주입되는 값에서 읽어야 하며, 소스나 설정 파일에 평문으로 두어서는 안 됩니다.

### 5.4 Maven 으로 빌드하기

배포용 jar를 만들 때 씁니다.

```
cd java && mvn -B package
```

`java/target/ocsecure-client-1.0.0.jar`가 나옵니다. 처음 실행할 때는 Maven이 플러그인을 내려받으므로 시간이 걸리고 망 접속이 필요합니다.

이 명령과 산출물은 실제로 확인하였습니다. 만들어진 jar를 사용해 자체 시험을 돌려 68건이 모두 통과하는 것까지 확인하였습니다.

```
javac -encoding UTF-8 -cp java/target/ocsecure-client-1.0.0.jar \
      -d out-test java/src/test/java/ocsecure/client/OcsSelfTest.java
java -Dstdout.encoding=UTF-8 \
     -cp "java/target/ocsecure-client-1.0.0.jar:out-test" \
     ocsecure.client.OcsSelfTest tests/vectors/kat.properties
```

`target/` 디렉터리는 형상 관리에서 제외해 두었습니다. 빌드 산출물이므로 커밋하지 마십시오.

Gradle 빌드 스크립트는 제공하지 않습니다. 필요하시면 만들어 드릴 수 있으나, 의존성이 없으므로 굳이 필요하지 않을 것입니다.

### 5.5 자바 8 을 대상으로 하는 이유

전자정부 표준프레임워크 3.x 환경이 자바 8을 쓰는 경우가 있어 그에 맞추었습니다. 정확도: 중간이며 실제 대상 환경을 확인하셔야 합니다.

더 낮은 버전을 대상으로 컴파일하려면 다음과 같이 확인할 수 있습니다. 실제로 확인한 명령입니다.

```
javac --release 8 -encoding UTF-8 -d out $(find java/src/main -name '*.java')
```

`source value 8 is obsolete` 경고가 나오지만 컴파일은 정상입니다. 최근 JDK가 옛 대상 버전에 대해 내는 경고이며 결과에는 영향이 없습니다.

### 5.6 업무 프로젝트에 반입하기

세 가지 방법이 있습니다.

첫째는 jar를 직접 넣는 방법입니다. 만들어진 jar를 프로젝트의 라이브러리 디렉터리에 두고 클래스패스에 추가합니다. 폐쇄망 환경에서 가장 간단합니다.

둘째는 사내 저장소에 올려 두고 의존성으로 선언하는 방법입니다. Maven을 쓰는 프로젝트라면 이 편이 관리하기 좋습니다.

```xml
<dependency>
  <groupId>ocsecure</groupId>
  <artifactId>ocsecure-client</artifactId>
  <version>1.0.0</version>
</dependency>
```

셋째는 소스를 그대로 복사해 넣는 방법입니다. 의존성이 없으므로 `ocsecure/client` 패키지를 통째로 옮기면 그대로 동작합니다. 빌드 절차를 하나 더 두고 싶지 않을 때 쓸 만합니다. 다만 나중에 모듈이 고쳐졌을 때 반영이 누락되기 쉬우므로, 복사해 넣었다는 사실과 어느 판을 가져왔는지를 기록해 두십시오.

어느 방법이든 반입한 뒤에는 그 환경에서 자체 시험을 한 번 돌려 보시기를 권합니다. 문자집합이나 보안 정책이 달라 결과가 달라지는 일이 드물게 있습니다.

## 6. 오라클 쪽 시험

인스턴스가 필요합니다. 설치 직후와 변경 배포 직후에 반드시 돌립니다.

명령 프롬프트에서 접속합니다.

```
sqlplus OCS_OWNER@localhost:1521/<서비스명>
```

접속된 `sqlplus` 안에서 한 줄씩 실행합니다.

```
@sql/09_test/900_kat_setup.sql
@sql/09_test/901_kat_data.sql
@sql/09_test/902_selftest.sql
```

`901_kat_data.sql`은 생성 파일입니다. 참조 구현을 고쳤다면 `gen_vectors.py`를 먼저 돌려 갱신한 뒤에 올리십시오.

자체 시험은 설정을 개발 모드로 잠시 바꾸었다가 되돌립니다. **운영계에서 실행하지 마십시오.**

### 6.1 스크립트 인코딩과 데이터베이스 문자집합

저장소의 오라클 스크립트는 모두 UTF-8 로 저장되어 있습니다. 주석과 오류 문구에 한글이 들어 있으므로, 데이터베이스 문자집합이 `KO16MSWIN949` 인 곳에서는 이 점을 반드시 맞추어야 합니다. 맞추지 않으면 일부 패키지가 컴파일되지 않습니다.

이유는 이렇습니다. SQL\*Plus 는 파일에서 읽은 바이트를 `NLS_LANG` 이 가리키는 문자집합으로 해석하여 데이터베이스로 보냅니다. 한글 윈도우의 기본값은 CP949 이므로, UTF-8 로 저장된 한글 한 글자(3바이트)가 CP949 로 읽히면 두 글자하고도 한 바이트가 남는 꼴이 됩니다. CP949 는 선행 바이트가 오면 반드시 후행 바이트 하나를 더 먹으므로, 남은 한 바이트가 뒤따르는 줄바꿈이나 작은따옴표를 자기 짝으로 삼켜 버립니다. 그 결과 한 줄 주석이 다음 줄까지 먹어 치우거나 문자열이 닫히지 않은 채로 넘어가고, 컴파일이 깨집니다. 한글이 짝수 개만 들어 있는 줄에서는 우연히 아무 일도 일어나지 않기 때문에, 전부가 아니라 몇몇 패키지에서만 오류가 나는 것처럼 보입니다.

해결 방법은 두 가지이며 둘 중 하나만 택해야 합니다. 섞으면 같은 문제가 반대 방향으로 생깁니다.

첫째 방법은 파일을 CP949 로 바꾸어 실행하는 것입니다. 변환 도구가 있습니다.

```
python tools/to_cp949.py
sqlplus OCS_OWNER/…@대상DB @sql_cp949/02_packages/210_pkg_rekey.sql
```

`sql/` 을 읽어 `sql_cp949/` 를 만들며, 내용은 같고 인코딩만 다릅니다. `--check` 를 붙이면 변환할 수 없는 글자가 있는지만 확인합니다. 폐쇄망 반입 꾸러미에는 이 사본이 `sql_cp949/` 로 이미 들어 있으므로 따로 돌릴 필요가 없습니다. 편집기로 한 파일씩 다른 이름으로 저장하며 ANSI 를 고르는 것도 결과는 같습니다.

둘째 방법은 파일을 그대로 두고 클라이언트에 원본이 UTF-8 임을 알리는 것입니다.

```
rem 윈도우
set NLS_LANG=KOREAN_KOREA.AL32UTF8
chcp 65001
sqlplus OCS_OWNER/…@대상DB

# 리눅스
export NLS_LANG=KOREAN_KOREA.AL32UTF8
sqlplus OCS_OWNER/…@대상DB
```

이러면 SQL\*Plus 가 보낸 UTF-8 을 데이터베이스가 `KO16MSWIN949` 로 옮겨 담으므로 파일을 건드릴 필요가 없습니다. 다만 화면 출력도 UTF-8 이 되므로 `chcp 65001` 을 함께 하지 않으면 결과 메시지가 깨져 보입니다. 명령 프롬프트를 새로 열면 `NLS_LANG` 은 사라지므로 매번 설정해야 합니다.

어느 쪽을 택하든 저장되는 자료는 같습니다. 데이터베이스가 받는 문자가 같기 때문입니다. 고정 시험 벡터의 한글 평문도 두 방법 모두에서 같은 값으로 들어갑니다.

## 7. 무엇을 고치면 무엇을 다시 돌려야 하는가

참조 구현을 고쳤다면 벡터를 다시 만들고, 세 구현의 시험을 모두 돌려야 합니다. 포맷이 바뀐 것이므로 PL/SQL과 자바가 따라오지 못하면 거기서 드러납니다.

PL/SQL만 고쳤다면 정적 점검을 돌리고 인스턴스에서 자체 시험을 돌립니다.

자바만 고쳤다면 `build_java.sh` 하나면 됩니다.

문서만 고쳤다면 아무것도 돌릴 필요가 없습니다. 다만 문서에 적은 명령을 바꾸었다면 그 명령이 실제로 동작하는지 한 번 실행해 보십시오.

어느 경우든 커밋 전에 `run_checks.sh`를 돌리면 위 판단을 대신해 줍니다.

## 8. 자주 겪는 문제

명령을 실행했는데 `Python`만 찍히고 끝난다면 파이썬이 아니라 껍데기가 실행된 것입니다. 윈도우의 앱 실행 별칭이 가장 흔한 원인이며, 제2.2절에 진단과 해결이 있습니다.

`python3`이 없다는 오류가 나면 윈도우입니다. `py -3`으로 바꾸거나 제3장의 점검 실행기를 쓰십시오.

`./tools/run_checks.sh`가 실행되지 않으면 윈도우 명령 프롬프트에서 셸 스크립트를 부른 것입니다. `tools\run_checks.bat`을 쓰십시오.

컴파일 단계에서 한글이 깨진다면 `-encoding UTF-8`이 빠진 것입니다.

오라클 패키지 일부에서만 컴파일 오류가 나고 오류 위치가 주석이나 문자열 근처라면 스크립트 인코딩 문제입니다. 제6.1절에 원인과 두 가지 해결 방법이 있습니다.

실행 결과의 한글이 물음표로 나오면 리눅스나 맥에서 로캘이 UTF-8 이 아닌 경우이므로 `-Dstdout.encoding=UTF-8`을 붙이십시오. 반대로 한글 윈도우 콘솔에서 글자가 깨진다면 그 인자를 붙였기 때문이므로 빼시거나 `chcp 65001` 을 먼저 실행하십시오. 제5.3절에 자세히 적었습니다. 점검 실행기를 쓰면 이 문제가 생기지 않습니다.

`cryptography 패키지가 없다`는 메시지가 나오던 증상은 사라졌습니다. 참조 구현이 더 이상 그 패키지를 필요로 하지 않기 때문입니다. 설치하고 싶다면 `pip install -r requirements.txt`로 하되, 하지 않아도 모든 점검이 수행됩니다. 설치 중 `_cffi_backend`를 찾지 못한다는 오류가 나면 `pip install cffi`를 함께 하십시오.

`시험 벡터가 참조 구현과 어긋난다`는 참조 구현을 고치고 벡터를 다시 만들지 않은 것입니다. `gen_vectors.py`를 돌리고 결과를 함께 커밋하십시오.

참조 구현을 건드린 적이 없는데도 이 오류가 난다면 줄바꿈 문자 때문일 수 있습니다. 예전 판의 생성기는 운영체제의 기본 줄바꿈을 따랐기 때문에, 윈도우에서 다시 만들면 내용이 같아도 바이트가 달라졌습니다. 지금은 생성기가 어디서 돌든 같은 줄바꿈으로 쓰고 점검도 줄바꿈 차이는 무시하므로 이 증상은 사라졌습니다. 그래도 난다면 내용이 실제로 다른 것이니 재생성 결과를 확인하십시오.

Maven 빌드가 멈춰 있다면 플러그인을 내려받는 중일 수 있습니다. 폐쇄망이라면 `javac`로 컴파일하거나 사내 저장소를 거울로 두셔야 합니다.

`target/`이나 `out/`이 형상 관리에 올라왔다면 제외 설정을 확인하십시오. 빌드 산출물은 커밋하지 않습니다.

## 9. 폐쇄망으로 옮기기

관공서 환경은 망이 분리되어 있는 경우가 많으므로 따로 다루겠습니다.

### 9.1 무엇을 옮겨야 하는가

전부 옮길 필요는 없습니다. 먼저 폐쇄망에서 실제로 무엇을 해야 하는지 정하면 범위가 크게 줄어듭니다.

운영에 필요한 것은 오라클 스크립트와 자바 라이브러리 둘뿐입니다. 스크립트는 글자 파일이고 라이브러리는 미리 컴파일해 두면 되므로, 이 둘만 놓고 보면 옮기는 일에 어려움이 없습니다.

조사에 필요한 것이 하나 더 있습니다. 기존 비밀번호 저장 방식을 알아내는 식별기입니다. 대상 자료가 폐쇄망 안에 있으므로 거기서 돌려야 합니다.

**어느 것도 외부 패키지를 필요로 하지 않습니다.** 자바는 의존성이 아예 없고, 파이썬 도구도 전부 표준 라이브러리만 씁니다. 따라서 파일을 옮기고 파이썬과 JDK만 있으면 그대로 돌아갑니다.

Maven은 필요하지 않습니다. 고집하면 플러그인을 내려받아야 하므로 사내 저장소를 거울로 두거나 지역 저장소를 통째로 옮겨야 하는데, 얻는 것이 없습니다. JDK가 있으면 `javac`로 충분하고, 그마저 없으면 미리 컴파일한 라이브러리를 쓰면 됩니다.

### 9.2 설치 패키지 만들기

외부에 전달할 설치 패키지는 한 번 실행하여 만듭니다.

```
python tools/make_install_package.py
```

`dist/` 아래에 날짜가 붙은 디렉터리와 압축 파일이 만들어집니다. 안에는 설치 매뉴얼(`설치_매뉴얼.md`), 오라클 설치 스크립트와 그 CP949 사본, 자바 원본과 미리 컴파일한 라이브러리, 패키지 확인 도구, 파일 해시 목록(`MANIFEST.sha256`), 판 정보(`VERSION`)가 들어갑니다.

담을 파일은 `tools/make_install_package.py` 안의 목록에 하나하나 적혀 있고, 목록에 없는 파일(`internal/`, 다른 문서, 조사 도구, 시험 코드 등)은 저장소에 있어도 들어가지 않습니다. 새 파일을 패키지에 넣으려면 그 목록에 적으십시오. 관리자·개발자 매뉴얼을 함께 담아야 하면 `--with-ops-docs` 를 붙입니다.

만든 뒤에는 `tools/check_manual_paths.py` 가 설치 매뉴얼이 언급하는 경로가 패키지에 있는지, 패키지에 없는 문서를 가리키지 않는지를 자동으로 대조하며, 어긋나면 빌드가 실패합니다. 자바 라이브러리는 자바 8을 대상으로 컴파일합니다.

### 9.3 해시 목록

꾸러미에는 `MANIFEST.sha256` 이 함께 들어갑니다. 모든 파일의 해시 목록이며 두 가지 쓸모가 있습니다.

첫째는 반입 심사입니다. 폐쇄망 반입 시 파일 목록과 무결성 증빙을 요구하는 경우가 흔하므로, 이 목록을 그대로 제출하시면 됩니다.

둘째는 손상 확인입니다. 옮기는 도중 파일이 빠지거나 깨지지 않았는지 확인합니다.

### 9.4 옮긴 뒤에 할 일

먼저 파일이 온전한지 확인합니다.

```
python tools/verify_manifest.py
```

빠진 파일과 손상된 파일을 알려 주고, 목록에 없는 파일이 섞여 있으면 그것도 알려 줍니다. 마지막 항목은 반입 심사에서 문제가 되는 쪽이므로 함께 봅니다. 하나라도 빠지거나 손상되었으면 종료 코드 1을 돌려줍니다.

설치 패키지에는 점검 도구와 시험 벡터가 들어 있지 않습니다(`tools/run_checks.py` 는 저장소에서만 돌립니다). 받은 쪽의 설치 확인은 설치 매뉴얼의 단계별 기대값으로 합니다.

## 10. 참고 근거와 신뢰도 자체 평가

직접 만든 AES 구현에 관한 서술은 신뢰도 높음입니다. FIPS-197 부록 C.3 공인 시험 벡터와 일치하고, 검증된 라이브러리와 무작위 삼백 건을 대조하여 모두 일치하며, 두 경로가 만들어 내는 시험 벡터가 바이트 단위로 같음을 확인하였습니다. 다만 부수 경로 방어는 하지 않았으므로 운영에 쓰지 마십시오.

반입 꾸러미에 관한 서술은 신뢰도 높음입니다. 외부 패키지를 차단한 상태에서 꾸러미를 풀어 네 단계가 모두 통과하는 것까지 확인하였습니다. 꾸러미를 만들고, 다른 자리에 풀어 그 안에서 점검을 돌려 통과하는 것과, 미리 컴파일한 라이브러리로 자체 시험이 통과하는 것과, 파일을 일부러 손상시켰을 때 탐지되고 종료 코드가 1이 되는 것을 모두 확인하였습니다. 윈도우 대상 설치 파일 내려받기도 확인하였습니다.

본문의 명령은 리눅스에서 모두 실제로 실행하여 확인하였습니다. 파이썬 시험 실행, 벡터 생성, 정적 점검, `javac` 컴파일, 자바 8 대상 컴파일, Maven 패키징, 산출된 jar로 자체 시험 실행, 그리고 점검 실행기의 건너뜀 경로까지 확인하였으므로 신뢰도 높음입니다.

**윈도우에서는 직접 확인하지 못하였습니다.** 윈도우 환경이 없어 `tools\run_checks.bat`을 실행해 보지 못하였습니다. 다만 사용자가 실행하여 네 단계가 모두 돌아가는 것과, 자바 단계의 한글만 깨지던 것을 확인해 주셨습니다. 그 원인인 출력 문자집합 문제는 고쳤으나 고친 뒤의 확인은 아직 받지 못하였습니다. 문법을 검토하고 메시지를 아스키로만 적어 문자집합 문제를 피했으며, 처음 판에 있던 종료 코드 전달 결함도 고쳤습니다. 괄호로 묶은 조건문 안에 적은 `%errorlevel%`은 블록을 해석하는 시점에 값이 정해지므로 점검의 종료 코드가 아니라 그 앞 명령의 것이 반환되는 문제였고, 각 종료문을 블록 밖으로 빼는 방식으로 해결하였습니다. 그럼에도 실행 확인은 되지 않았으므로 신뢰도 중간입니다. 처음 쓰실 때 문제가 있으면 알려 주십시오.

윈도우에서 파이썬 명령이 `python3`이 아니라 `python` 또는 `py`라는 사실은 신뢰도 높음입니다. 사용자 환경에서 `py -3`으로 시험 51건이 통과하는 것을 확인하였습니다.

윈도우 앱 실행 별칭이 `Python`만 찍고 끝나는 원인이라는 진단은 여전히 추측입니다. `py -3`으로 바꾸면 해결된다는 것은 확인되었으나, 껍데기가 그 문구를 찍은 것인지 다른 이유인지는 환경을 직접 보아야 알 수 있습니다. 해결에는 영향이 없습니다.

파이썬 3.6 이상에서 동작한다는 서술은 신뢰도 중간입니다. 3.11에서만 확인하였습니다.

전자정부 표준프레임워크 3.x가 자바 8을 쓴다는 서술은 신뢰도 중간입니다. 대상 환경을 확인하셔야 합니다.

오라클 쪽 자체 시험 실행 절차는 신뢰도 중간입니다. 스크립트의 내용은 확인하였으나 인스턴스에서 실행해 보지는 못하였습니다.

## 11. 결론 요약

평소에는 `python tools/run_checks.py` 하나면 됩니다. 리눅스와 맥에서는 `./tools/run_checks.sh`, 윈도우에서는 `tools\run_checks.bat`도 같은 일을 합니다. 명령 이름이 운영체제마다 다르다는 점에 주의하십시오. 윈도우에는 `python3`이 대개 없고 `py -3`을 씁니다. 참조 구현 시험과 벡터 최신 여부, PL/SQL 정적 점검, 자바 컴파일과 자체 시험을 한 번에 수행하며, 오라클 인스턴스 없이 돌아갑니다. 파이썬 쪽은 `cryptography` 하나만 있으면 되고 없으면 참조 구현 시험만 건너뛰면 됩니다. 자바 쪽은 외부 의존성이 전혀 없어 `javac`만으로 컴파일되고, 배포용 jar가 필요하면 `cd java && mvn -B package`로 만듭니다. 업무 프로젝트에는 jar를 넣거나 사내 저장소를 거치거나 소스를 복사해 넣는 세 가지 방법이 있으며, 어느 쪽이든 반입 후 그 환경에서 자체 시험을 한 번 돌려 보시기 바랍니다. 참조 구현을 고쳤다면 시험 벡터를 다시 만들어 같은 커밋에 넣어야 하고, 잊더라도 점검 스크립트가 잡아 줍니다.
