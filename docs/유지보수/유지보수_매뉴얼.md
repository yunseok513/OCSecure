## 0. 이 문서를 읽는 법

대상은 키 관리자, 감사자, 보안 담당자, 시스템 운영자입니다. 이 문서는 두 부분입니다. **제0~13장은 평소의 운영과 변경**(키, 자격, 감사, 설정)이고, **제14~21장은 업무 프로그램에서 `OCSecure:` 오류가 났을 때 운영담당자가 보는 대응**입니다. 오류를 받았다면 제14장부터 보십시오. 제22~25장은 개통 전 확인, 부록, 근거, 요약입니다. 개발자는 `개발자_매뉴얼.md` 를, 처음 설치하는 분은 `설치_매뉴얼.md` 를 보십시오.

파일 이름에 「비밀번호」가 들어 있으나 이 문서는 비밀번호만이 아니라 **암호화 시스템 전체의 운영**을 다룹니다. 파일 이름은 다른 문서가 참조하므로 바꾸지 않았습니다.

각 절은 같은 틀로 되어 있습니다.

| 표시 | 뜻 |
|---|---|
| **접속** | 어느 계정으로 붙는가 |
| **실행** | 무엇을 치는가. 코드 블록이 곧 실행할 것입니다 |
| **확인** | 무엇이 나와야 정상인가. 아니면 멈추고 제12장을 보십시오 |
| **주의** | 어기면 사고가 나는 것. 건너뛰지 마십시오 |
| 인용 표시(`>`) 「설명」 | 이유와 배경. **읽지 않아도 업무는 됩니다** |

실행 예시의 `<…>` 는 현장에서 채울 자리입니다. **마스터 키와 증표용 키의 실제 값은 어떤 문서나 메신저에도 적지 마십시오.**

## 1. 한눈에 보기

### 1.1 계정과 역할

| 계정 | 하는 일 | 하지 못하는 일 |
|---|---|---|
| `OCS_OWNER` | 패키지와 키 정보를 소유. 설정(`SEC_CONFIG`) 변경 | 키 생성, 자격 부여. **운영 전환 뒤에는 잠금** |
| `OCS_KEYADM` | 도메인·키·복호화 자격·재암호화 | 감사 기록 조회 |
| `OCS_AUDITOR` | 감사 기록과 현황 조회 | 어떤 변경도 못 함 |
| 응용(업무) 계정 | 이미 있는 업무 계정을 `480_connect_app_schema.sql` 로 연결. `PKG_SECURE_API` 와 `FN_` 함수만 호출 | 키 관리, 하위 계층 호출 |

> **설명.** 소유 계정이 혼자 키까지 만들 수 있으면 계정을 나눈 뜻이 없으므로 권한을 갈라 두었습니다. 한 계정이 새어도 혼자서는 자료를 풀 수 없다는 것이 설계 목적입니다. 상세는 `보안관리_접근통제설계.md`.

### 1.2 정기 업무 일람

| 주기 | 업무 | 계정 | 절 |
|---|---|---|---|
| 상시 | 암복호화 가능 상태(`ready`) 감시 | 감시 도구 | 3.1 |
| 매일 | 키 유지 프로그램 로그, `ALERT` 사건 확인 | 운영자, `OCS_AUDITOR` | 3.3, 9.2 |
| 매주 | 복호화 거부와 임계치 사건, 사용량 추이 | `OCS_AUDITOR` | 9.3 |
| 분기 | 복호화 자격 대장, 관리 권한 대장, 하위 패키지 권한 누출 점검 | `OCS_AUDITOR`, `OCS_OWNER` | 6.3, 9.4 |
| 분기 | 비밀번호 반복 횟수 재검토 | `OCS_OWNER` | 10.4 |
| 정기 | 마스터 키 백업 복구 시험과 기록 | 키 관리자 | 3.4 |

### 1.3 운영 담당자 두 분을 위한 최소 점검표

위 일람은 담당자가 충분할 때의 전부입니다. 운영 담당자가 두 분이라면 아래만 하십시오. 줄여도 되는 것은 이 절 끝에 따로 적었습니다. 주기와 분담은 제안이며 업무 방식에 맞게 조정하십시오.

| 주기 | 할 일 | 누가 | 절 |
|---|---|---|---|
| 매일 | 암복호화가 되는 상태인지 `ready` 가 1 인지 봅니다. 감시 도구가 없으면 이 조회를 한 번 칩니다 | 담당 1 | 3.1 |
| 매일 | 키 유지 프로그램이 도는지, 로그의 마지막 줄이 「종료한다」나 「주입했으나 열려 있지 않다」가 아닌지 봅니다 | 담당 1 | 3.3 |
| 매일 | 어제 이후의 `ALERT` 사건을 봅니다. 계획 없는 `KEYSTORE_CLOSE`, `INTEGRITY_FAIL`, 낯선 주소의 `KEYSTORE_OPEN` 만 즉시 확인합니다 | 담당 2 (감사 열람) | 9.2 |
| 매주 | 감사 기록을 데이터베이스 밖의 다른 장비나 매체에 내려받아 보관합니다. 보관처는 데이터베이스 관리를 맡은 쪽이 지울 수 없어야 합니다 | 담당 2 | 설치 매뉴얼 운영 편 제8.6.5절(리눅스는 제10.6.5절) |
| 분기 | 복호화 자격 대장과 관리 권한 대장을 점검하고, 근거 없는 자격을 회수합니다 | 담당 2 확인, 담당 1 실행 | 6.3, 9.4 |
| 연 1회 | 마스터 키 백업으로 복구가 되는지 시험하고 기록합니다. 이때 평소 하지 않던 분이 직접 해 봐서, 한 분이 없어도 복구되는지 확인합니다 | 두 분 | 3.4 |
| 개통 전, 이후 연 1회 | 키 교체 절차를 연습합니다. 교체 주기 자체는 책임자가 정해 문서로 남깁니다 | 두 분 | 5 |

**일이 생겼을 때.** 오류가 나면 제14~21장(오류 대응)을 따르십시오. 특히 `ready` 가 0 이거나 여러 곳에서 `ORA-20513` 이 나면 암복호화가 전체 정지한 것이므로 제4.1절 대응을 먼저 하십시오.

**줄여도 되는 것(제안).**

| 항목 | 이유 |
|---|---|
| 비밀번호 반복 횟수의 분기 재검토 | 장비를 바꾸거나 증설했을 때만 다시 재도 됩니다. 매 분기 재는 것은 부담이 큰 데 비해 얻는 것이 적습니다 |
| 사용량 추이 점검 | 정상 업무량이 변하지 않는다면 이상 징후가 의심될 때만 봅니다. 매주 감사 기록을 내려받을 때 함께 눈으로 훑는 정도로 충분합니다 |

이 두 가지를 줄이는 것은 제 제안이며 책임자의 확인이 필요합니다. 줄이지 않고 1.2의 일람대로 해도 됩니다.

> **설명.** 키 교체 주기는 이 문서가 정하지 않습니다. 설계서에서 확인하지 못하였으므로 보안 담당자가 정해 문서로 남기십시오. 어떤 주기든 **개통 전에 교체 절차를 한 번 실제로 돌려 본 상태**여야 합니다(제5장).

## 2. 이 시스템이 하는 일과 하지 않는 일

| 구분 | 내용 |
|---|---|
| 양방향 암호화 | 평문을 AES-256 암호문으로 저장하고, 자격이 있는 세션에만 평문을 돌려줌 |
| 검색용 색인 | 같은 평문이면 같은 색인값. 암호문과 별도 컬럼으로 저장 |
| 마스킹 | 자격이 없으면 가린 값을 돌려줌 |
| 단방향(비밀번호) | 되돌릴 수 없는 저장값. 키를 쓰지 않음 |
| 통제 | 접속 증표, 복호화 자격 대장, 사용량 임계치, 감사 기록 |
| **하지 않는 것** | 로그인 시도 제한, 계정 잠금, 비밀번호 복잡도·재사용·만료, 재설정 절차. 모두 응용이 맡음 |

**주의.** 양방향 암호화에는 마스터 키가 필요하고, 비밀번호에는 필요 없습니다. 장애 때 원인을 좁히는 단서가 되므로 기억해 두십시오. 마스터 키를 잃어도 비밀번호 자료는 무사하고, **양방향 자료는 하나도 되살릴 수 없습니다.**

## 3. 마스터 키와 키 저장소

### 3.1 상태 확인

**접속.** 아무 응용 계정. 감시 도구의 상태 점검에도 같은 구문을 씁니다.

**실행.**

```sql
SELECT OCS_OWNER.PKG_SECURE_API.ready FROM DUAL;
```

**확인.** `1` 이면 암복호화 가능, `0` 이면 불가입니다. 키 값은 나오지 않습니다. `0` 이 이어지면 제3.3절로 가십시오.

**주의.** `OCS_KEYADM` 에는 이 패키지의 실행 권한이 없어 `ORA-00904` 가 납니다. 키 관리 계정에서는 `OCS_OWNER.PKG_KEK_PROVIDER.is_open` 으로 보십시오.

### 3.2 마스터 키가 사라지는 경우

| 상황 | 결과 | 조치 |
|---|---|---|
| 데이터베이스 재기동 | 전역 문맥이 비워져 `0` | 유지 프로그램이 다시 주입. 안 되면 3.3 |
| 누군가 저장소를 닫음 | `0`, `KEYSTORE_CLOSE` 사건. **이미 붙어 있던 세션도 다음 호출부터 `ORA-20513`.** 유지 프로그램이 확인 주기 안에 다시 넣음(시험 확인) | 닫은 사람 확인 후 3.3. 의도한 비상 정지라면 13.4 |
| 자체 시험(`902_selftest.sql`) 실행 | 끝에 저장소가 닫힘 | **운영계에서 실행 금지** |

> **설명.** 시험 인스턴스를 재부팅한 뒤 `ready` 가 0 으로 나오는 것을 확인하였습니다(한 번의 관찰). 재부팅 뒤에는 PDB 도 `MOUNTED` 로만 올라오므로 먼저 열어야 합니다(제12장).

### 3.3 키 저장소 유지 프로그램

`OcsKeystoreKeeper` 가 정해진 주기로 저장소를 확인하고, 닫혀 있으면 마스터 키를 다시 넣습니다.

**확인.** 로그에서 아래 문구를 봅니다.

| 로그 문구 | 뜻 | 조치 |
|---|---|---|
| 접속하고 마스터 키를 주입하였다 | 정상 시작 | 없음 |
| 저장소가 닫혀 있다. 다시 주입한다 | 닫힘을 감지해 복구 중 | 이어서 「정상으로 돌아왔다」가 나오는지 확인 |
| 끊겼다. 다시 붙기를 되풀이한다 | 데이터베이스 접속 불가 | 데이터베이스와 네트워크 확인 |
| 주입했으나 열려 있지 않다 | **설정의 마스터 키가 틀림** | 설정 파일의 키 확인 |
| 설정 파일을 소유자 외에도 읽을 수 있다 | 파일 권한 부실 | 3.5 |
| 종료한다 | **이 시점부터 암복호화가 멈춤** | 즉시 재기동 |

윈도우는 `%OCS_HOME%\java\log\keeper.log` 입니다. 주기는 설정 파일의 `check.seconds` 이며 최소 5초입니다. 재기동 때 이 주기만큼 암복호화가 멈출 수 있으므로 짧을수록 공백이 줄어듭니다.

**주의.** 윈도우 시험 인스턴스에서 저장소를 닫았을 때, 데이터베이스를 재기동했을 때, 장비를 재부팅했을 때 모두 사람 손 없이 복구되는 것을 확인하였습니다. **운영 장비에서는 개통 전에 같은 세 시험을 다시 하십시오**(`docs/설치/설치_매뉴얼.md` 운영 편 제8.5절, 리눅스는 제10.5절). 작업 스케줄러는 `/rp *` 로 암호를 저장하여 등록해야 로그인 없이 뜹니다.

### 3.4 마스터 키 보관

| 항목 | 기준 |
|---|---|
| 보관 | 열람 통제가 되는 곳에 **두 벌 이상**. 꺼낸 사람과 시각이 남는 절차 |
| 복구 시험 | 백업본으로 복구가 되는지 시험하고 결과를 기록 |
| 분실 | 양방향 자료 전부 복구 불가. 제13.1절 |

> **설명.** 개발과 시험은 `KEK_SOURCE=GLOBAL_CTX` 로 마스터 키를 직접 주입하는 방식이고, 외부 키 관리 서버나 하드웨어 보안 모듈이 없는 운영은 `SCOPED_CTX` 를 씁니다. `SCOPED_CTX` 는 업무 계정이 마스터 키를 읽지 못하게 하지만 `SYS` 와 키 유지 프로그램 장비의 관리자는 막지 못하므로, 개통 판정에는 책임자의 수용 기록이 필요합니다(설치 매뉴얼 운영 편 제8.6.5절). 마스터 키는 데이터 키를 감싸는 데만 쓰이므로 나중에 외부 키 관리 방식(`EXTERNAL`)으로 바꾸더라도 **자료를 다시 암호화할 필요는 없습니다.** 감싼 값만 다시 만들면 됩니다.

### 3.5 설정 파일 보호

설정 파일(`keeper.properties`)에는 마스터 키와 계정 암호가 들어 있습니다. 형상 관리에는 값이 빈 `keeper.properties.sample` 만 두십시오.

| 운영체제 | 실행 |
|---|---|
| 리눅스 | `chown <서비스계정> keeper.properties` 후 `chmod 600 keeper.properties` |
| 윈도우 | `icacls <파일> /inheritance:r` 로 상속을 끊고 전용 계정과 관리자에게만 권한 |

**주의.** 윈도우에서는 프로그램의 권한 경고가 동작하지 않으므로 `icacls` 로 사람이 확인해야 합니다. 상속을 끊지 않으면 `Users` 읽기가 남습니다.

## 4. 도메인 관리

도메인은 컬럼의 성격별 정책 묶음입니다. 도메인마다 키가 따로 있어 한 키가 새도 다른 도메인으로 번지지 않습니다.

### 4.1 현재 등록된 도메인

| 코드 | 정규화 | 마스킹 | 문맥 요구 | 임계치(구간당) | 감사 |
|---|---|---|---|---|---|
| `RRN` 주민등록번호 | `DIGITS` | `RRN` | Y | 200 | `SUMMARY` |
| `NAME` 성명 | `TRIM` | `NAME` | Y | 없음(0) | `SUMMARY` |
| `PHONE` 연락처 | `DIGITS` | `PHONE` | Y | 없음(0) | `SUMMARY` |
| `ACCOUNT` 계좌번호 | `DIGITS` | `ACCOUNT` | Y | 50 | `FULL` |

위는 `450_bootstrap_domains.sql` 의 초기 등록값입니다. 현재 값은 `SEC_DOMAIN` 을 조회하십시오(`OCS_AUDITOR` 가 볼 수 있습니다). 코드에는 `EMAIL`, `ADDR` 상수도 있으나 **초기 등록 대상이 아니므로** 쓰려면 먼저 등록해야 합니다.

### 4.2 도메인 설정값의 뜻

| 항목 | 값 | 뜻 |
|---|---|---|
| 정규화 `norm_mode` | `NONE` `TRIM` `UPPER_TRIM` `DIGITS` | 색인 계산 전에 입력을 다듬는 방식. 구분자 유무와 무관하게 같은 행을 찾게 함 |
| 마스킹 `mask_type` | `ALL` `RRN` `NAME` `ACCOUNT` `EMAIL` `PHONE` | 자격 없는 조회에 보일 모양 |
| 문맥 요구 `require_app_ctx` | `Y` `N` | `Y` 면 접속 증표를 낸 세션만 허용. **운영은 `Y`** |
| 임계치 `reveal_limit` | 0 이상 | 집계 구간당 복호화 허용 건수. 0 은 무제한 |
| 감사 `audit_level` | `NONE` `SUMMARY` `FULL` | `FULL` 은 복호화마다 기록, `SUMMARY` 는 구간 누계만 |

마스킹 결과의 예: `RRN` 은 앞 8자리 뒤에 `******`, `NAME` 은 첫 글자와 끝 글자만 남김, `ACCOUNT` 는 끝 4자리만 남김, `ALL` 은 길이와 무관하게 `********`.

### 4.3 새 도메인 추가

**접속.** `OCS_KEYADM`. 마스터 키가 열려 있어야 합니다.

**실행.** 인자는 차례로 코드, 설명, 정규화, 마스킹, 문맥 요구, 임계치, 감사 수준입니다. 이어서 운영 키를 만들어 활성으로 올립니다.

```sql
BEGIN
  OCS_OWNER.PKG_KEY_ADMIN.upsert_domain('EMAIL', '전자우편', 'UPPER_TRIM', 'EMAIL', 'Y', 0, 'SUMMARY');
  COMMIT;
END;
/
DECLARE v PLS_INTEGER; BEGIN
  v := OCS_OWNER.PKG_KEY_ADMIN.create_key('EMAIL', TRUE, '개통 초기 키');
  COMMIT;
  DBMS_OUTPUT.PUT_LINE('key_id = ' || v);
END;
/
```

**확인.** 해당 도메인에 `ACTIVE` 키가 하나 있어야 합니다.

```sql
SELECT key_id, key_state FROM OCS_OWNER.V_SEC_KEY_STATUS WHERE domain_code = 'EMAIL';
```

**주의.** 도메인 코드는 응용이 임의로 지을 수 없습니다. 여기서 등록한 코드만 쓸 수 있고, 없는 코드를 넘기면 `ORA-20530` 이 납니다. **조인할 두 컬럼은 같은 도메인이어야** 색인값이 맞습니다. 나중에 바꾸려면 재암호화가 필요하므로 컬럼 분류 단계에서 확정하십시오.

> **설명.** 임계치는 정상 사용량을 관측한 뒤에 정합니다. 처음부터 낮게 잡으면 정상 업무가 막히고, 높게 잡으면 장치가 의미를 잃습니다. 도메인 설정을 바꾸는 호출은 `POLICY_ADMIN` 관리 권한이 있어야 하며, 없으면 `ORA-20523` 과 `ADMIN_DENIED` 경보가 남습니다.

## 5. 키 교체

서비스를 멈추지 않고 하는 절차입니다. 새 키를 활성으로 올리면 옛 키는 복호화 전용(`RETIRING`)이 되고, 이후 신규 자료는 새 키로 암호화됩니다. 기존 자료는 암호문 머리의 키 번호로 옛 키를 찾아 읽으므로 아무 일도 일어나지 않습니다.

**주의.** **개통 전에 이 절차를 한 번 실제로 돌려 보십시오.** 한 번도 돌려 보지 않은 교체는 정작 필요한 순간에 실패합니다. 단계별 기대값이 있는 리허설은 `docs/설치/설치_매뉴얼.md` 개발·시험 편의 키 교체 연습(윈도우는 제4.4절, 리눅스는 제6.4절)에 있습니다.

### 5.1 절차 한눈에

| 단계 | 계정 | 하는 일 | 건너뛰면 |
|---|---|---|---|
| 1 | `OCS_OWNER` | 대상 업무 테이블 `SELECT`, `UPDATE` 를 `OCS_OWNER` 에 **직접** 부여 | 재암호화에서 `ORA-00942` |
| 2 | `OCS_KEYADM` | `rotate` 로 새 키 생성·활성. **옛 `key_id` 를 적어 둠** | 폐기할 키를 못 찾음 |
| 3 | 응용 | 교체 직후 기존 자료가 읽히는지 확인 | 무중단이 깨졌는데 모름 |
| 4 | `OCS_KEYADM` | 재암호화 작업 생성·실행(제8장) | 옛 키 자료가 남음 |
| 5 | `OCS_KEYADM` | `remaining` 이 **0** 인지 확인 | 폐기하면 남은 자료는 영구 손실 |
| 6 | `OCS_KEYADM` | 옛 키 폐기, 읽기 재확인 | 옛 키가 계속 살아 있음 |
| 7 | `OCS_OWNER` | 1단계 권한 회수 | 소유 계정이 업무 자료에 상시 접근 |

### 5.2 교체와 폐기

**접속.** `OCS_KEYADM`.

**실행.**

```sql
SET SERVEROUTPUT ON
DECLARE
  v_old PLS_INTEGER;
  v_new PLS_INTEGER;
BEGIN
  SELECT key_id INTO v_old FROM OCS_OWNER.V_SEC_KEY_STATUS
   WHERE domain_code = 'RRN' AND key_state = 'ACTIVE';
  v_new := OCS_OWNER.PKG_KEY_ADMIN.rotate('RRN', '정기 교체');
  COMMIT;
  DBMS_OUTPUT.PUT_LINE('옛 key_id = ' || v_old || ' , 새 key_id = ' || v_new);
END;
/
```

재암호화(제8장)로 `remaining` 이 0 이 된 것을 확인한 뒤에만 폐기합니다. 폐기할 키는 상태가 아니라 **번호**로 지목합니다.

```sql
BEGIN
  OCS_OWNER.PKG_KEY_ADMIN.retire(<옛 key_id>);
  COMMIT;
END;
/
```

**확인.** 폐기 뒤에도 응용에서 기존 자료가 그대로 읽혀야 합니다. 읽히지 않고 「사용할 수 없는 키」 오류가 나면 옮기지 못한 자료가 남아 있던 것이고, 이것이 리허설에서 건질 가장 중요한 발견입니다.

> **설명.** 폐기는 키 값을 지우는 것이 아니라 그 키로는 복호화도 못 하게 막는 것입니다. 상태로 찾지 않고 번호로 지목하는 까닭은 폐기 대기 키가 도메인마다 여럿일 수 있어 상태로 찾는 조회가 `ORA-01422` 로 멈출 수 있기 때문입니다.

### 5.3 리허설이 어긋났을 때

자료 없이 교체부터 해 버려 빈 `RETIRING` 키가 남았다면 설치 매뉴얼 참고 사항의 「자료 없이 교체한 키 정리」(제11.2절)를 쓰십시오. **업무 테이블 건수가 0 일 때에만** 폐기합니다.

## 6. 복호화 자격

기본은 불허입니다. 대장(`SEC_REVEAL_GRANT`)에 있는 항목만 평문을 볼 수 있습니다.

### 6.1 부여와 회수

**접속.** `OCS_KEYADM`. 다른 계정으로 치면 `PLS-00201` 이 납니다.

**실행.** 인자는 도메인, 대상, 대상 종류(`ROLE` 또는 `USER`), 만료 시각, 사유입니다.

```sql
BEGIN
  OCS_OWNER.PKG_KEY_ADMIN.grant_reveal('RRN', 'ROLE_HR_VIEW', 'ROLE',
                                       SYSTIMESTAMP + INTERVAL '30' DAY, '인사 조회 업무');
  COMMIT;
END;
/

BEGIN
  OCS_OWNER.PKG_KEY_ADMIN.revoke_reveal('RRN', 'ROLE_HR_VIEW', 'ROLE');
  COMMIT;
END;
/
```

**주의.** 회수할 때 인자 셋(도메인, 대상, 종류)은 부여할 때와 똑같아야 합니다. 주고 거둔 사실은 `REVEAL_GRANT`, `REVEAL_REVOKE` 로 감사 기록에 남습니다.

### 6.2 부여 원칙

| 원칙 | 이유 |
|---|---|
| 사람이 아니라 **업무 역할**에 준다 | 인사 이동마다 흔적이 쌓이지 않음 |
| **만료 시각**을 둔다 | 장애 대응용 임시 권한이 회수되지 않고 누적되는 것을 막음 |
| **사유**를 적는다 | 분기 점검 때 존속 여부를 판단할 근거 |
| 특정 계정에 기한 없이 주지 않는다 | 확인 목적에 한함 |

### 6.3 분기 점검

**접속.** `OCS_AUDITOR`. 자격 대장은 키 관리 계정에도 열려 있지 않아 감사 계정이 유효 자격 뷰로 봅니다.

**실행.**

```sql
SELECT domain_code, grantee_type, grantee_name, expires_at, reason
  FROM OCS_OWNER.V_SEC_EFFECTIVE_REVEAL ORDER BY domain_code, grantee_name;
```

**확인.** 만료일 없는 항목, 사유가 빈 항목, 퇴직·전출한 사람의 항목이 없어야 합니다. 있으면 키 관리자에게 회수를 요청합니다. 만료된 한시 권한은 뷰에서 자동으로 빠집니다.

## 7. 관리 권한

키 생성, 정책 변경, 재암호화를 누가 할 수 있는지는 `SEC_ADMIN_GRANT` 대장이 정합니다. 권한 종류는 `KEY_ADMIN`, `POLICY_ADMIN`, `REKEY` 셋이며, **복호화 자격과는 별개**입니다. 관리 권한이 없으면 `ORA-20523` 이 나고 `ADMIN_DENIED` 경보가 남습니다.

**접속.** `OCS_AUDITOR`.

**실행.**

```sql
SELECT privilege, grantee_type, grantee_name, expires_at, reason
  FROM OCS_OWNER.SEC_ADMIN_GRANT ORDER BY privilege, grantee_name;
```

**확인.** 설치 때 등록한 역할(`OCS_ROLE_KEYADM`) 외의 항목이 있으면 근거를 확인하십시오. 이 대장의 변경은 그 자체가 감사 대상이어야 합니다.

## 8. 재암호화 배치

키 교체와 알고리즘 교체에 공통으로 씁니다. 중단되어도 이어서 수행할 수 있고, 일정 건수마다 커밋하여 되돌리기 구간을 짧게 유지합니다.

### 8.1 제약

| 제약 | 확인 방법 |
|---|---|
| 대상 테이블은 **숫자형 단일 기본 키**만 지원 | 문자형·복합 기본 키는 별도 확장 필요 |
| 호출 계정이 아니라 **`OCS_OWNER` 의 권한**으로 돈다 | 업무 테이블 권한을 `OCS_OWNER` 에 직접 부여. 역할로 준 권한은 인정되지 않음 |

### 8.2 실행

**접속.** `OCS_KEYADM`. 작업 이름은 한 번 쓰면 남으므로 다시 할 때는 다른 이름을 쓰십시오.

**실행.** 인자는 작업명, 소유 스키마, 테이블, 기본 키, 암호문 컬럼, 도메인, 색인 컬럼, 묶음 크기입니다.

```sql
BEGIN
  OCS_OWNER.PKG_REKEY.create_job('REKEY_2026Q4', '<업무스키마>', '<테이블>',
                                 '<기본키컬럼>', '<암호문컬럼>', 'RRN', '<색인컬럼>', 1000);
  COMMIT;
END;
/
SET SERVEROUTPUT ON
BEGIN
  DBMS_OUTPUT.PUT_LINE('옮길 건수(전) = ' || OCS_OWNER.PKG_REKEY.remaining('REKEY_2026Q4'));
  OCS_OWNER.PKG_REKEY.run_job('REKEY_2026Q4');
  DBMS_OUTPUT.PUT_LINE('옮길 건수(후) = ' || OCS_OWNER.PKG_REKEY.remaining('REKEY_2026Q4'));
END;
/
```

**확인.** 후가 0 이면 끝입니다. 0 이 아니면 `run_job` 을 다시 부르십시오. 한 번 부를 때 정해진 묶음 수(기본 10)만 처리하고 돌아오므로, 큰 테이블은 여러 번 불러야 합니다. 업무 시간대를 피해 나누어 돌리는 구조입니다.

> **설명.** `remaining` 은 암호문을 하나씩 읽어 머리의 키 번호가 목표 키와 다른 것을 센 값입니다. 전부 읽으므로 큰 테이블에서는 시간이 걸립니다. 진행 지점은 작업 테이블에 남으므로 중단해도 처음부터 다시 하지 않습니다. `reset_job` 은 진행 지점만 되돌릴 뿐 목표 키는 처음 값 그대로이므로 새 교체에는 새 작업을 만드십시오.

**주의.** 배치가 끝나면 `OCS_OWNER` 에 준 업무 테이블 권한을 **반드시 회수**하십시오. 비밀번호 저장값은 재계산이 불가능하므로 재암호화 대상이 아닙니다.

## 9. 감사와 모니터링

### 9.1 어디에 무엇이 남는가

| 기록 | 위치 | 내용 | 볼 수 있는 계정 |
|---|---|---|---|
| 사건 기록 | `SEC_AUDIT_LOG` | 시각, 사건 유형, 심각도, 도메인, 접속 정보, 응용 사용자, 건수 | `OCS_AUDITOR` |
| 복호화 사용량 | `SEC_REVEAL_USAGE` | 계정·도메인·구간별 복호화 건수와 거부 건수 | `OCS_AUDITOR` |
| 데이터베이스 통합 감사 | `UNIFIED_AUDIT_TRAIL` | 소유 계정 접속, DDL, 키 표 접근, 권한 변경 | 감사 정책 |

**주의.** 기록에는 평문, 키, 암호문 전체가 남지 않습니다. 감사 기록이 감사 대상과 같은 시스템 안에만 있으면 통제가 성립하지 않으므로, **통합 감사를 외부 보안 관제로 즉시 전송**하고 있는지 따로 확인하십시오.

### 9.2 매일: 경보 확인

**실행.**

SELECT event_ts, event_type, domain_code, db_user, app_user, ip_address, detail

### 9.3 사건 유형 해석

| 사건 | 심각도 | 뜻 | 보아야 할 것 |
|---|---|---|---|
| `REVEAL` | INFO | 복호화 1건(`FULL` 도메인만) | 계좌번호 조회 패턴 |
| `REVEAL_DENIED` | ALERT | 문맥 없음 또는 자격 없음 복호화 시도 | **누적되는 양상이 침해 시도의 첫 신호** |
| `PROTECT_DENIED` `INDEX_DENIED` | ALERT | 문맥 없이 암호화·색인 시도 | 조회 도구로 직접 붙은 흔적 |
| `RATE_EXCEEDED` | ALERT | 구간 사용량이 임계치 도달 | 정상 업무인지 계정 탈취인지 |
| `APPCTX_DENIED` | ALERT | 증표 없음·불일치·시간 초과 | 서버 시각 어긋남, 증표 키 불일치, 위조 시도 |
| `INTEGRITY_FAIL` | ALERT | 암호문 변조 또는 키 불일치 | **조용히 넘기지 말고 즉시 보안 담당자에게** |
| `MASK_FAIL` | WARN | 마스킹 중 복호화 실패. `********` 로 대체됨 | 반복되면 자료 손상 의심 |
| `ADMIN_DENIED` | ALERT | 관리 권한 없는 관리 호출 | 권한 없는 계정의 시도 |
| `KEY_CREATE` `KEY_IMPORT` `KEY_ACTIVATE` `KEY_RETIRE` | ALERT | 키 변경 | 승인된 작업과 대조 |
| `REVEAL_GRANT` `REVEAL_REVOKE` | ALERT | 자격 변경 | 승인된 작업과 대조 |
| `KEYSTORE_OPEN` `KEYSTORE_CLOSE` | ALERT | 저장소 열림·닫힘 | 닫힘은 즉시 확인 |
| `REKEY_CREATE` `REKEY_DONE` `REKEY_ERROR` `REKEY_RESET` | ALERT | 재암호화 작업 | 오류는 `last_error` 확인 |
| `DOMAIN_UPSERT` | INFO | 도메인 설정 변경 | 임계치 변경은 승인 확인 |

> **설명.** `ALERT` 에 변경 사건이 많은 것은 **키와 자격의 모든 변경을 눈에 띄게 하려는** 설계입니다. 승인된 작업이면 정상입니다. 비교할 승인 기록이 없다면 그것이 문제입니다.

## 10. 설정값 (`SEC_CONFIG`)

| 키 | 운영값 | 뜻 | 바꾸면 |
|---|---|---|---|
| `KEK_SOURCE` | 개통 전 `EXTERNAL` 로 전환 | 마스터 키 반입 방식. `GLOBAL_CTX` 는 개발 전용 | 자료 재암호화 불필요 |
| `APPCTX_MODE` | **`PROOF`** | 접속 증표 검증. `SIMPLE` 이면 검증이 통째로 사라짐 | `SIMPLE` 이 남으면 통제가 없는 것과 같음 |
| `APPCTX_WINDOW_SEC` | 300 | 증표 유효 시간(초) | 서버 시각 차이가 크면 `APPCTX_DENIED` |
| `USAGE_BUCKET_MIN` | 60 | 사용량 집계 구간(분). 임계치 판정 단위 | 구간이 길수록 임계치를 크게 잡아야 함 |
| `FAIL_DELAY_CS` | 0 | 복호화 거부 시 지연(1/100초). 대량 시도 억제 | 올리면 거부된 호출이 느려짐 |
| `PWD_ITERATIONS` | 실측 후 설정 | 비밀번호 반복 횟수 | **올리기만 하고 내리지 않음** |
| `LEGACY_PWD_CHARSET` | `AL32UTF8` | 기존 비밀번호 체계의 문자집합 | 이행 전에 확정 |

**접속.** `OCS_OWNER`. 운영 전환으로 잠겼다면 승인 절차를 거쳐 일시 해제하고, 작업 뒤 다시 잠급니다. 해제와 재잠금은 통합 감사에 남습니다.

**실행.**

```sql
UPDATE SEC_CONFIG SET cfg_value = '<값>', updated_at = SYSTIMESTAMP WHERE cfg_key = '<키>';
COMMIT;
```

`SEC_CONFIG` 의 조회와 변경은 통합 감사 정책에 들어 있으므로 변경은 기록으로 남습니다. 변경은 즉시 반영되며 재기동이 필요 없습니다.

## 11. 비밀번호 운영

되돌릴 수 없는 저장값입니다. 키를 쓰지 않고, 복호화처럼 감사되지도 않으며, 같은 비밀번호도 저장값이 사용자마다 다릅니다. 관리자가 정하는 값은 **반복 횟수 하나**입니다.

### 11.1 반복 횟수 측정

**접속.** `OCS_OWNER`. 다른 계정으로는 측정할 수 없습니다.

**실행.**

```
@sql/04_admin/400_pwd_iteration_tune.sql
```

**확인.** 반복 횟수별 소요 시간과 초당 처리 횟수가 나옵니다. 허용할 로그인 응답 시간을 먼저 정하고 그 안에 드는 가장 큰 값을 고르십시오. **한산한 때와 붐비는 때에 각각 재어 나쁜 쪽을 기준**으로 삼습니다.

| 참고 | 값 |
|---|---|
| 개발 서버 실측 | 1,000회당 약 8.7밀리초, 50,000회에 약 444밀리초 |
| 운영 규모 가정 | 최근 1년 접속자 약 2만 3천 명. 피크 시간 초당 4건 가량 |

> **설명.** 개발 서버 한 대에서 잰 값이며 운영 장비는 다릅니다. 반드시 다시 재십시오. 50,000회는 국제 권고 수준에 못 미치는데, 원인은 PL/SQL 로 계산하기 때문입니다. 자바에서 같은 계산을 하면 훨씬 빠르며 저장값은 호환됩니다. 계산 위치를 응용으로 옮길지는 개통 전에 정하십시오.

### 11.2 변경과 이행 현황

**실행.** 변경합니다. 새로 저장되는 값부터 적용되며, 기존 값은 옛 횟수 그대로 검증됩니다.

```sql
UPDATE SEC_CONFIG SET cfg_value = '50000', updated_at = SYSTIMESTAMP WHERE cfg_key = 'PWD_ITERATIONS';
COMMIT;
```

**주의.** **내리지 마십시오.** 내리면 이후 저장값이 기존보다 약해집니다. 로그인이 너무 느려 내려야 한다면 감당할 수 없는 값으로 올린 것이므로 측정부터 다시 하십시오.

**확인.** 로그인 성공 시점에 응용이 다시 계산해 저장하는지를 분포로 봅니다.

```
@sql/04_admin/401_pwd_iteration_dist.sql
```

현재 설정보다 낮은 횟수의 사용자가 줄지 않으면 응용에 갱신 처리가 빠진 것입니다. 개발자에게 확인을 요청하십시오. 오래 접속하지 않는 사용자는 끝내 옮겨 가지 않으므로 일정 기간 뒤 재설정을 요구해 정리하는 방안을 검토하십시오.

### 11.3 기존 체계에서의 이행

기존 시스템은 솔트 없는 단일 해시입니다. 일괄 변환이 불가능하므로 **옛 비밀번호로 로그인시키되 그 자리에서 변경을 강제**하는 방식을 택했습니다.

**실행.** 개통 전에 실제 계정으로 가정을 확인합니다.

```sql
SELECT OCS_OWNER.PKG_LEGACY_PWD.self_check('아는 평문', '그 계정의 저장값') FROM DUAL;
```

**확인.** `일치` 가 나와야 개통할 수 있습니다. 괄호의 문자집합이 `AL32UTF8` 이 아니면 `SEC_CONFIG` 의 `LEGACY_PWD_CHARSET` 을 그 값으로 바꾸십시오. 어긋나면 한글이 섞인 비밀번호를 쓰는 사용자만 로그인하지 못합니다. **`불일치` 면 배포하지 마십시오.**

**실행.** 개통 뒤 이행 현황을 봅니다. 옛 형식은 44자, 새 형식은 108자입니다.

```sql
SELECT CASE LENGTH(user_pwd) WHEN 44 THEN '옛 형식' WHEN 108 THEN '새 형식' ELSE '알 수 없음' END AS fmt,
       COUNT(*) AS cnt
  FROM TB_USER WHERE user_pwd IS NOT NULL GROUP BY LENGTH(user_pwd);
```

| 결과 | 판단 |
|---|---|
| 첫 주에 가파르게 줄고 이후 완만 | 정상 |
| 줄지 않음 | 응용의 변경 강제가 화면에서 동작하지 않음 |
| `알 수 없음` 이 나옴 | 조사에서 놓친 형식. 그 계정들을 따로 조사 |

기한(석 달 정도)을 정하고, 지나면 남은 계정을 잠그고 필요한 사람만 정식 절차로 되살립니다. 옛 형식이 하나도 남지 않으면 `PKG_LEGACY_PWD` 와 `PKG_SECURE_API` 의 `check_pwd`, `make_pwd_str` 을 제거하고 자체 시험을 다시 돌려 이행용 항목이 함께 빠졌는지 확인하십시오. 남겨 두면 약한 검증 경로가 계속 남습니다.

### 11.4 유출 의심 시

| 순서 | 조치 |
|---|---|
| 1 | 전체 사용자에게 비밀번호 **재설정 강제**. 유출된 저장값을 무용지물로 만드는 유일한 방법 |
| 2 | 동시에 반복 횟수 상향 |
| 3 | 유출 경로 차단, 같은 경로로 다른 자료가 나가지 않았는지 확인 |
| 4 | 사용자 안내. 유출된 것은 비밀번호가 아니라 되돌릴 수 없는 형태의 값임과 재설정이 필요한 이유를 함께 설명 |

로그인 실패 급증은 이 시스템에서 탐지되지 않습니다(실패를 기록하지 않음). 애플리케이션 로그와 응용의 시도 제한·계정 잠금이 동작하는지 먼저 보십시오.

## 12. 증상별 조치

운영담당자가 업무 프로그램의 오류를 받았을 때의 절차는 이 문서의 제14~21장에 오류 번호별로 있습니다. 아래 표는 관리자 관점의 요약입니다.

| 증상 | 원인 | 조치 |
|---|---|---|
| `ORA-20513` 키 저장소가 열려 있지 않음 | 재기동, 자체 시험 직후, 저장소 닫힘 | 3.3. 유지 프로그램 상태 확인, 안 되면 마스터 키 재주입 |
| `ORA-20512` 사용할 수 없는 키 | 폐기된 키, 키 없음 | 폐기 전 `remaining` 이 0 이었는지 확인. 응용 계정이 읽던 자료가 옛 키였을 가능성 |
| `ORA-20511` 무결성 검증 실패 | 암호문 변조, 키 불일치, **컬럼 길이 부족으로 잘림** | 개발 중이면 컬럼 정의 확인. 운영이면 **즉시 보안 담당자에게** |
| `ORA-20521` 인증 문맥 없음 | 문맥 미설정, 세운 연결과 조회 연결이 다름, 서버 시각 어긋남 | 증표 불일치면 `_APPCTX` 키 확인(재설치 때마다 새로 만드는 값). 조회 도구로 직접 붙은 경우는 **정상 동작** |
| `ORA-20520` 복호화 권한 없음 | 자격 대장에 없음, 한시 권한 만료 | 6.3 으로 대장 확인 후 정당하면 부여 |
| `ORA-20522` 임계치 초과 | 전 행 복호화 쿼리 또는 정상 업무량 초과 | 9.5. 쿼리 개선이 먼저 |
| `ORA-20523` 관리 권한 없음 | 관리 권한 대장에 없음 | 7 |
| `ORA-20530` 정의되지 않은 도메인 | 코드 오타 또는 미등록 | 4.3 |
| `ORA-20541` 인자 오류 | 빈 비밀번호 저장 시도 등 | 응용의 입력 검증 보완. 보안상 위험은 아님 |
| 접속 시 `ORA-01109` | PDB 가 `MOUNTED`(재부팅·재기동 뒤) | `SYS` 로 `ALTER PLUGGABLE DATABASE <PDB> OPEN;` 후 `SAVE STATE`. 연 뒤 마스터 키 재주입 |
| 재암호화 작업 생성 시 `ORA-00001` `UK_SEC_REKEY_JOB` | 같은 이름의 옛 작업이 있음. **뒤의 `remaining` 이 0 이어도 믿지 말 것** | 이름을 바꿔 다시 만들고 전이 건수인지 확인. 확인 전에는 옛 키 폐기 금지 |
| `ORA-01422` 폐기 후 조회 | 폐기 대기 키가 둘 이상 | 설치 매뉴얼 제11.2절 |
| `PLS-00201` | `OCS_KEYADM` 이 아닌 계정으로 관리 호출, 또는 `300_grants.sql` 누락 | 계정 확인, 설치 매뉴얼 제11.1절 |
| 로그인이 갑자기 느려짐 | 반복 횟수를 최근 올림 | 11.1 로 재측정. 바꾼 적이 없으면 데이터베이스 부하 확인 |
| 한글 비밀번호만 실패 | 문자집합 문제 | 11.3 `LEGACY_PWD_CHARSET`, 등록 경로와 검증 경로 일치 여부 |
| `ORA-20521` 이 로그에 매우 많음 | 조회 도구 직접 접속 시도 또는 서버 시각 문제 | 9.3 `APPCTX_DENIED` 의 접속 정보 확인 |

## 13. 사고 대응

### 13.1 마스터 키 분실

**양방향 암호화 자료를 하나도 되살릴 수 없습니다.** 백업본을 찾는 것이 유일한 길입니다.

| 순서 | 조치 |
|---|---|
| 1 | 보관 두 벌 이상을 모두 확인. 복구 시험 기록이 있으면 그 절차로 복구 |
| 2 | 복구 불가면 해당 자료는 원천 시스템에서 다시 받아 새로 암호화(데이터 전환 재수행) |
| 3 | 분실 경위 조사. 보관 절차와 열람 기록 점검 |

비밀번호 저장값은 영향을 받지 않습니다.

### 13.2 접속 정보 유출 의심 (응용 계정 등)

| 순서 | 조치 |
|---|---|
| 1 | `APPCTX_DENIED`, `REVEAL_DENIED`, `INDEX_DENIED`, `PROTECT_DENIED` 의 접속 정보(IP, 호스트) 확인 |
| 2 | 계정 암호 변경, 접속 지점 제한(`sqlnet.ora` 노드 검증) 확인 |
| 3 | 증표 키 유출이 의심되면 `_APPCTX` 키를 새로 들여옴(설치 매뉴얼의 증표용 키 절, 윈도우 운영은 제7.10절, 리눅스 운영은 제9.10절, 기존 키는 폐기). **응용 서버 설정과 함께 바꿔야 하므로 개발 담당자와 시점 합의** |

> **설명.** 접속 정보만으로는 암호화·색인·복호화가 되지 않는 것이 설계의 핵심입니다(증표 키가 데이터베이스 밖에 있음). 그래도 거부 기록이 쌓이는 양상이 침해 시도의 첫 신호이므로 매주 확인합니다.

### 13.3 소유 계정 접속 감지

`OCS_OWNER` 의 `LOGON` 은 통합 감사 대상입니다. 승인된 배포 작업이 아니면 즉시 보안 담당자에게 알리십시오.

### 13.4 비상 정지: 저장소 닫기

사고 때 암복호화를 즉시 멈추는 방법입니다. 저장소를 닫으면 **이미 붙어 있는 응용 세션도 다음 호출부터** `ORA-20513` 으로 멈춥니다(시험 확인). **유지 프로그램이 돌고 있으면 10초 안에 다시 열리므로 반드시 먼저 멈추십시오.**

| 순서 | 계정 | 실행 |
|---|---|---|
| 1 | 관리자 | 유지 프로그램 멈춤(윈도우 `schtasks /end /tn "OCSecure Keystore Keeper"`, 리눅스 `systemctl stop ocs-keeper`) |
| 2 | `OCS_KEYADM` | `EXEC OCS_OWNER.PKG_KEK_PROVIDER.close_keystore;` |
| 3 | `OCS_KEYADM` | `@sql/04_admin/470_keystore_check.sql` 로 `전역 문맥 없음 / 저장소 닫힘` 확인 |

**복구.** 원인을 조사하고 승인을 받은 뒤 유지 프로그램을 다시 띄웁니다(`schtasks /run /tn "OCSecure Keystore Keeper"` 또는 `systemctl start ocs-keeper`). 몇십 초 안에 마스터 키가 다시 들어갑니다.

> **설명.** 이전 판은 이미 키를 올려 둔 세션이 담아 둔 값을 그대로 믿어, 저장소를 닫아도 연결 풀의 응용 세션은 계속 암복호화가 되었습니다. 쓸 때마다 전역 문맥에 같은 값이 있는지 확인하도록 고쳤고, 같은 세션 번호로 닫힘을 확인하였습니다. 이 동작은 마스터 키를 `GLOBAL_CTX` 로 반입할 때에 한합니다. `EXTERNAL`(키 관리 서버나 HSM)은 구현 전이라 닫기의 의미를 따로 정해야 합니다.

## 14. 오류가 났을 때: 읽는 법 (운영담당자용)

업무 프로그램을 쓰다가 화면이나 로그에 `OCSecure:` 로 시작하는 오류가 나왔을 때, 운영담당자가 무엇을 확인하고 누구에게 무엇을 요청해야 하는지를 정리한 부분입니다. 평소의 운영(키 교체, 자격 부여, 감사 점검)은 이 문서의 제0~13장이 다루고, 제14~21장은 **오류가 났을 때**에 한정합니다.

오류 메시지는 다음 모양입니다. 괄호 안은 원인을 좁히는 짧은 설명이며 값 자체는 담지 않습니다.

```
ORA-20521: OCSecure: 애플리케이션 인증 문맥 없음 (증표 불일치)
```

업무 프로그램이 이 오류를 자기 오류로 감싸서 보여 주는 경우에도 로그에는 `ORA-205xx` 번호와 `OCSecure:` 문구가 남아 있습니다. 먼저 그 번호를 찾으십시오. 번호를 찾으면 제16장의 한눈표에서 줄을 고르고, 제17장에서 그 번호의 절차를 따릅니다. 번호를 모르겠거나 여러 번호가 한꺼번에 나오면 제15장의 3분 점검부터 하십시오.

운영담당자가 직접 할 수 있는 일과 키 관리자나 보안 담당자에게 요청해야 하는 일을 구분해 적었습니다. **요청해야 하는 일을 운영담당자가 직접 하지 마십시오.** 키와 자격을 다루는 작업은 승인과 기록이 남아야 하며, 임의로 하면 감사에서 침해 시도와 구별되지 않습니다.

### 14.1 역할

| 역할 | 하는 일 | 이 문서에서의 쓰임 |
|---|---|---|
| 운영담당자 | 업무 프로그램과 서버 운영 | 오류 접수, 상태 확인, 유지 프로그램 확인, 보고 |
| 키 관리자 | `OCS_KEYADM` 계정 사용. 키, 복호화 자격, 마스터 키 주입 | 키와 자격과 설정 변경, 마스터 키 재주입 |
| 감사 담당자 | `OCS_AUDITOR` 계정 사용. 감사 기록 조회 | 사건 기록 조회 |
| 보안 담당자 | 침해 판단과 승인 | 무결성 오류와 의심 사건의 판단 |
| 개발 담당자 | 업무 프로그램 개발 | 문맥 설정, 쿼리 수정 |
| 데이터베이스 관리자 | `SYS` 권한 | PDB 열기, 권한 점검 |

한 사람이 여러 역할을 맡은 곳에서도 **위 구분대로 기록을 남기십시오.**

## 15. 먼저 할 일 (3분 점검)

오류를 받으면 원인을 짐작하기 전에 아래 세 가지를 먼저 확인합니다. 어느 오류든 이 순서입니다.

### 15.1 범위 확인

| 확인 | 판단 |
|---|---|
| 한 사용자나 한 화면에서만 나는가, 여러 사용자와 여러 화면에서 함께 나는가 | **여러 곳에서 함께** 나면 시스템 상태(키 저장소, 서버 시각, 데이터베이스) 문제일 가능성이 큽니다. 제15.2절로 가십시오 |
| 방금 시작된 일인가, 계속되던 일인가 | 방금이면 직전 변경(배포, 재기동, 키 교체, 설정 변경)을 찾으십시오 |
| 암호화나 복호화나 검색 중 무엇이 실패하는가 | 셋 다 실패하면 시스템 상태, 복호화만 실패하면 자격이나 사용량 문제입니다 |

### 15.2 암복호화 가능 상태 확인

**접속.** 업무 계정이나 응용 계정으로 접속합니다. 키 값은 나오지 않습니다.

```sql
SELECT FN_READY FROM DUAL;
```

함수 이름이 풀리지 않으면(`ORA-00904`) 아래로 바꾸십시오.

```sql
SELECT OCS_OWNER.PKG_SECURE_API.ready FROM DUAL;
```

| 결과 | 뜻 | 다음 |
|---|---|---|
| `1` | 암복호화 가능. 키 저장소는 열려 있음 | 오류 번호별 절차(제17장)로 |
| `0` | 암복호화 불가. 키 저장소가 닫혀 있음 | **제18.1절** 전체 정지 절차로 |
| 조회 자체가 실패 | 접속 문제 또는 권한 문제 | 제17.12절 |

### 15.3 키 저장소 유지 프로그램 확인

마스터 키가 사라지면 이 프로그램이 자동으로 다시 넣습니다. 이 프로그램이 멈춰 있으면 데이터베이스를 재기동한 뒤에 복구되지 않습니다.

| 운영체제 | 상태 확인 | 로그 확인 |
|---|---|---|
| 윈도우 | `schtasks /query /tn "OCSecure Keystore Keeper" /v /fo list` 의 「상태」가 「실행 중」 | `type "%OCS_HOME%\java\log\keeper.log"` 의 마지막 줄 |
| RHEL | `systemctl status ocs-keeper` 가 `active (running)` | `journalctl -u ocs-keeper -n 50` |

RHEL 절차는 설치 매뉴얼에 밝힌 대로 실제 리눅스에서 확인하지 못했습니다. 로그 문구의 뜻은 제3.3절의 표를 보십시오.

| `ORA-20540` | 설정값 오류 | 주의 | `KEK_SOURCE`, `APPCTX_MODE` 등 설정값이 잘못됨 | 키 관리자 | 17.10 |
| `ORA-20541` | 인자 오류 | 낮음 | 빈 비밀번호 저장 시도 등 입력 검증 부족 | 개발 담당자 | 17.11 |
| `ORA-00904`, `ORA-00942`, `PLS-00201` | 암호 모듈이 아닌 오라클 오류 | 주의 | 함수 이름이나 권한이 연결되지 않음 | 데이터베이스 관리자 | 17.12 |
| `ORA-01109` | 데이터베이스가 개방되지 않음 | **긴급** | 재부팅 뒤 PDB 가 닫힌 채 | 데이터베이스 관리자 | 17.12 |

번호가 위에 없으면(`ORA-20500` 대 중 알 수 없는 번호 등) 메시지가 「암호 모듈 오류」로 나옵니다. 제20장의 정보를 모아 보안 담당자와 키 관리자에게 보고하십시오.

## 17. 오류별 대응

### 17.1 `ORA-20513` 키 저장소가 열려 있지 않음

**뜻.** 마스터 키가 데이터베이스 안에 없습니다. 이 상태에서는 **모든 암호화, 복호화, 색인 생성이 멈춥니다.** 이미 접속해 있던 업무 세션도 다음 호출부터 이 오류가 납니다.

**원인과 확인.**

| 원인 | 확인 | 조치 |
|---|---|---|
| 데이터베이스를 재기동했거나 장비를 재부팅함 | 데이터베이스 기동 시각, `v$instance` 의 `startup_time`. 유지 프로그램 로그에 「끊겼다」가 있는지 | 유지 프로그램이 곧 다시 넣습니다(제15.3절). 확인 주기의 두 배쯤 기다린 뒤 제15.2절을 다시 하십시오 |
| 유지 프로그램이 멈춰 있음 | 제15.3절의 상태가 「실행 중」이 아님 | 윈도우 `schtasks /run /tn "OCSecure Keystore Keeper"`, RHEL `systemctl start ocs-keeper`. 시작 뒤 로그에 「주입하였다」가 나오는지 확인 |
| 누군가 저장소를 닫음 | 감사 담당자가 `KEYSTORE_CLOSE` 사건을 조회(제19.1절) | **닫은 사람과 사유를 확인하십시오.** 승인된 비상 정지가 아니면 보안 담당자에게 보고하고 그 뒤에 복구하십시오 |
| 유지 프로그램은 도는데 열리지 않음 | 로그에 「주입했으나 열려 있지 않다」 | 설정 파일의 마스터 키가 틀린 것입니다. 키 관리자가 설정 파일을 확인합니다. 운영담당자는 키 값을 열어 보거나 전달하지 마십시오 |
| 재부팅 뒤 PDB 가 닫혀 있음 | 접속이 `ORA-01109` | 제17.12절. 연 뒤에 마스터 키는 비어 있으므로 위 항목으로 이어집니다 |

**복구 확인.** 제15.2절에서 `1` 이 나오고, 업무 프로그램에서 같은 동작이 되는지 확인합니다. 키 관리자는 `@sql/04_admin/470_keystore_check.sql` 로 「전역 문맥 있음」과 「저장소 열림」을 확인할 수 있습니다.

**하지 마십시오.** 마스터 키를 대화나 메신저로 주고받지 마십시오. 키 저장소가 닫힌 원인을 확인하기 전에 설정을 개발용으로 바꾸지 마십시오.

### 17.2 `ORA-20511` 무결성 검증 실패

**뜻.** 저장된 암호문이 복호화 과정의 검증을 통과하지 못했습니다. 암호문이 바뀌었거나, 맞지 않는 키로 풀려 했거나, 컬럼에 저장되면서 잘렸다는 뜻입니다. **조용히 넘기지 말고 즉시 보안 담당자에게 알리십시오.**

| 가능성 | 확인 | 조치 |
|---|---|---|
| 컬럼 길이 부족으로 암호문이 잘림 | 새로 만든 컬럼이나 새로 넣은 자료에서만 나는가. 컬럼이 `RAW(256)` 이상인가. 암호문 길이는 52 + 16×(평문 바이트 수÷16 의 몫+1) 바이트이며 `RAW(256)` 은 평문 191바이트까지 담음 | 개발 담당자가 컬럼 정의를 고칩니다. 잘린 행은 원본에서 다시 암호화해야 합니다 |
| 암호문을 사람이 수정함 | 감사 담당자가 통합 감사에서 해당 표의 갱신과 `INTEGRITY_FAIL` 사건을 대조 | 보안 담당자가 판단합니다 |
| 다른 설치의 암호문이나 옛 키로 만든 암호문 | 설치를 다시 했거나 마스터 키를 바꾼 이력이 있는가 | 키 관리자가 키 이력(제19.2절)을 확인합니다 |
| 키 유지 프로그램이 옛 마스터 키를 다시 넣고 있음(재설치 뒤 연동 확인이 어제까지는 통과했는데 `login` 에서 막힘) | `470_keystore_check.sql` 은 키가 있기만 하면 「있음 / 열림」이어서 가려지지 않음. `keeper.properties` 의 마스터 키가 이번 설치의 것인지, 옛 프로세스가 아직 떠 있는지 확인 | 옛 프로그램을 멈추고 프로세스가 없는지 확인한 뒤 `keeper.properties` 를 고치고 `--once` 로 덮어씀. 자세한 순서는 설치 매뉴얼 제11.1절(증상별 조치)과 제11.4절(재설치 뒤 복구 순서) |
| 자료가 손상됨 | 같은 행에서만 반복되는가 | 백업에서 복구할 수 있는지 확인합니다 |

**조치 순서.**

1. 오류가 난 행의 식별자와 시각, 호출한 응용 사용자를 기록합니다. **암호문 값 전체를 옮기지 마십시오.**
2. 같은 행으로 반복 호출하지 마십시오. 호출마다 감사 기록이 쌓이고 다른 원인을 가립니다.
3. 오류가 한 행인지, 여러 행인지 개발 담당자와 확인합니다. 여러 행이면 키 불일치나 컬럼 길이 문제일 가능성이 큽니다.
4. 보안 담당자에게 위 기록을 전달합니다.

**하지 마십시오.** 오류가 난 행을 임의로 지우거나 고치지 마십시오. 증거가 사라지고 원본을 복구할 수 없게 됩니다.

### 17.3 `ORA-20512` 사용할 수 없는 키

**뜻.** 암호문이 가리키는 키를 찾을 수 없거나 쓸 수 없는 상태입니다. 메시지 괄호 안의 설명으로 원인이 갈립니다.

| 괄호 안 설명 | 뜻 | 조치 |
|---|---|---|
| `폐기된 키: <번호>` | 옛 키를 폐기했는데 그 키로 암호화된 자료가 남아 있음 | **키 관리자에게 즉시 알리십시오.** 키 교체 뒤 재암호화가 끝나기 전에 폐기했을 가능성이 큽니다. 폐기한 키를 되살려 자료를 읽어야 할 수 있으므로 임의로 다른 조치를 하지 마십시오 |
| `키 식별자 없음: <번호>` | 그 번호의 키가 없음 | 다른 설치의 암호문이거나 설치를 다시 한 경우입니다. 키 관리자와 보안 담당자가 확인합니다 |
| `활성 키 없음: 도메인 <코드>` | 그 도메인에 새로 암호화할 활성 키가 없음 | 키 관리자가 키 상태를 확인하고 키를 활성화합니다(제19.2절) |

**확인.** 키 관리자나 감사 담당자가 아래로 현재 키 상태를 봅니다.

```sql
SELECT domain_code, key_id, key_state FROM OCS_OWNER.V_SEC_KEY_STATUS
 ORDER BY domain_code, key_id;
```

**하지 마십시오.** 폐기된 키 번호를 근거로 임의로 키를 다시 만들거나 상태를 바꾸지 마십시오. 키 교체와 폐기는 제5장의 절차(재암호화 건수 확인 뒤 폐기)대로만 합니다.

### 17.4 `ORA-20521` 애플리케이션 인증 문맥 없음

**뜻.** 암호화, 복호화, 색인 생성을 하려면 업무 프로그램이 먼저 접속 문맥(증표)을 세워야 하는데, 지금 세션에는 문맥이 없거나 증표가 맞지 않습니다. **통제가 작동한 결과이므로 항상 고장은 아닙니다.**

**먼저 구분합니다.**

| 어디서 났는가 | 판단 |
|---|---|
| 업무 프로그램이 아니라 `SQL*Plus` 나 조회 도구로 직접 접속해 암호화나 복호화를 시도했을 때 | **정상 동작입니다.** 조회 도구에서는 문맥을 세울 수 없습니다. 의도한 시도가 아니었다면 누가 했는지 확인하십시오 |
| 업무 프로그램에서, 여러 사용자가 한꺼번에 | 서버 시각 어긋남이나 증표 키 불일치일 가능성이 큽니다 |
| 업무 프로그램에서, 특정 화면에서만 | 그 화면의 코드가 문맥을 세우지 않았거나, 세운 연결과 조회한 연결이 다름 |

메시지 괄호 안의 설명으로 원인이 갈립니다.

| 괄호 안 설명 | 뜻 | 조치 |
|---|---|---|
| (설명 없음) | 세션에 문맥이 세워지지 않음 | 개발 담당자가 문맥을 세우는 코드가 이 경로에서 실행되는지, 연결 풀에서 연결을 돌려받을 때 문맥이 유지되는지 확인 |
| `증표가 제출되지 않음` | 증표를 넘기지 않고 문맥 설정을 시도함 | 개발 담당자가 문맥 설정 호출의 인자를 확인 |
| `증표 유효 시간 초과` | 증표의 시각과 데이터베이스 서버 시각의 차이가 허용 범위(설치 시 300초)를 넘음 | **응용 서버와 데이터베이스 서버의 시각을 맞추십시오.** NTP 등의 동기화 상태를 확인합니다. 운영담당자가 직접 확인할 수 있는 항목입니다 |
| `증표 불일치` | 응용 서버가 가진 증표 키가 데이터베이스의 `_APPCTX` 키와 다름 | 재설치나 `_APPCTX` 키 교체 뒤에 응용 서버 설정이 바뀌지 않은 경우가 흔합니다. 키 관리자와 개발 담당자가 시점을 합의하여 맞춥니다. 증표 키 값을 문서나 메신저에 적지 마십시오 |

**확인.**

1. 응용 서버와 데이터베이스 서버의 현재 시각을 비교합니다.
2. 감사 담당자가 `APPCTX_DENIED` 사건의 접속 정보(`ip_address`, `host_name`, `app_user`)를 조회합니다(제19.1절). 정상 응용 서버의 주소가 아니면 **침해 시도일 수 있으므로** 보안 담당자에게 알립니다.
3. 오류가 매우 많이 쌓이면(`ORA-20521` 폭주) 조회 도구 직접 접속 시도이거나 서버 시각 문제입니다. 위 표에서 시각부터 확인하십시오.

**하지 마십시오.** 문제를 피하려고 응용 문맥 모드를 개발용(`SIMPLE`)으로 바꾸지 마십시오. 증표 검증이 통째로 사라져 접속 정보만으로 복호화가 가능해집니다.

### 17.5 `ORA-20520` 복호화 권한 없음

**뜻.** 문맥은 있으나 그 계정이나 역할에 해당 도메인을 평문으로 볼 자격이 없습니다. 자격 대장에 없거나, 한시 자격이 만료되었습니다.

**확인.** 감사 담당자가 지금 유효한 자격을 조회합니다.

```sql
SELECT domain_code, grantee_type, grantee_name, expires_at
  FROM OCS_OWNER.V_SEC_EFFECTIVE_REVEAL
 ORDER BY domain_code, grantee_name;
```

| 상황 | 조치 |
|---|---|
| 해당 업무가 원래 평문 조회 대상이 아님 | 화면이 목록용 함수(`FN_SHOW` 나 `FN_MASKED`)를 써야 하는 곳입니다. 개발 담당자에게 알립니다. 자격을 부여할 문제가 아닙니다 |
| 자격이 필요한 업무인데 대장에 없음 | **키 관리자가 승인 절차를 거쳐서만** 부여합니다. 운영담당자가 자격을 직접 달라고 요청하기 전에 업무 필요성과 승인 기록을 먼저 갖추십시오 |
| 한시 자격이 만료됨 | 연장이 필요한지 승인 후 키 관리자가 다시 부여합니다 |

**하지 마십시오.** 장애를 해결하려고 자격을 폭넓게(모든 계정, 기한 없음으로) 부여하지 마십시오. 자격 부여와 회수는 감사 기록에 남으며 분기 점검 대상입니다.

### 17.6 `ORA-20522` 복호화 사용량 임계치 초과

**뜻.** 한 구간 안에서 그 도메인의 복호화 건수가 설정한 임계치에 닿았습니다. 대량 복호화를 막는 장치입니다. 구간의 길이는 설정(`USAGE_BUCKET_MIN`, 설치 시 60분)이며 구간 단위로 건수를 셉니다.

**확인.** 감사 담당자가 거부가 있었던 계정과 구간을 조회합니다.

```sql
SELECT db_user, domain_code, bucket_ts, reveal_cnt, denied_cnt
  FROM OCS_OWNER.SEC_REVEAL_USAGE
 WHERE bucket_ts > SYSDATE - 7 AND denied_cnt > 0
 ORDER BY bucket_ts DESC;
```

| 판단 | 조치 |
|---|---|
| 암호화 컬럼을 조건절에 직접 써서 **전 행을 복호화**하는 쿼리가 있음 | 개발 담당자가 쿼리를 색인 컬럼으로 고칩니다. 임계치를 올리는 것은 해결이 아닙니다 |
| 목록 화면이 행마다 평문을 복호화함 | 목록은 마스킹 함수로, 상세 화면에서만 복호화하도록 고칩니다 |
| 정상 업무량이 늘어서 닿음 | 키 관리자가 승인 후 도메인의 임계치를 조정합니다. 변경은 `DOMAIN_UPSERT` 사건으로 남습니다 |
| 평소에 없던 시각이나 계정에서 갑자기 많음 | 계정 탈취 가능성입니다. 보안 담당자에게 알립니다 |

**하지 마십시오.** 오류가 났다고 임계치를 0(제한 없음)으로 하지 마십시오.

### 17.7 `ORA-20510` 암호문 형식 오류

**뜻.** 복호화하려는 값이 이 모듈의 암호문 형식이 아닙니다. 괄호 안 설명은 `암호문이 비어 있음`, `길이 부족`, `알 수 없는 포맷 버전` 중 하나입니다.

| 원인 | 조치 |
|---|---|
| 암호화되지 않은 평문이 암호문 컬럼에 들어 있음. 자료 이행이 덜 끝났거나 새 프로그램이 암호화 없이 저장함 | 개발 담당자가 저장 경로를 확인하고 해당 행을 암호화합니다. **평문이 DB 에 있다는 뜻이므로 보안 담당자에게도 알리십시오** |
| 암호문이 잘림 | 제17.2절의 컬럼 길이 확인 |
| 다른 컬럼의 값을 넘김 | 개발 담당자가 호출 인자를 확인 |
| 값이 비어 있음 | 업무상 비어 있어도 되는 컬럼이면 응용이 널을 먼저 처리해야 합니다 |

### 17.8 `ORA-20530` 정의되지 않은 도메인

**뜻.** 호출에 쓴 도메인 코드가 등록되어 있지 않습니다. 대문자 코드(`RRN`, `NAME`, `PHONE`, `ACCOUNT` 등)의 오타가 가장 흔합니다.

**확인.** 감사 담당자가 등록된 도메인을 봅니다.

```sql
SELECT domain_code FROM OCS_OWNER.SEC_DOMAIN ORDER BY domain_code;
```

| 상황 | 조치 |
|---|---|
| 코드 오타 | 개발 담당자가 코드를 고칩니다 |
| 새 업무 도메인이 필요함 | 키 관리자가 제4.3절의 절차로 등록합니다 |

### 17.9 `ORA-20523` 관리 권한 없음

**뜻.** 키나 자격이나 설정을 바꾸는 관리 호출을 관리 권한 대장에 없는 계정이 했습니다. 업무 프로그램에서는 나지 않아야 하는 오류입니다.

| 상황 | 조치 |
|---|---|
| 키 관리자가 관리 작업 중 | 키 관리 계정(`OCS_KEYADM`)으로 접속했는지 확인 |
| 업무 계정이나 다른 계정이 시도함 | `ADMIN_DENIED` 사건의 계정과 접속 정보를 보안 담당자에게 알립니다 |

### 17.10 `ORA-20540` 설정값 오류

**뜻.** 설정값이 이 모듈이 받아들이는 값이 아닙니다. 괄호 안 설명이 어떤 설정인지 알려 줍니다. 대부분 개통 전에 나며 운영 중에 새로 나면 **누군가 설정을 바꾼 것**입니다.

| 괄호 안 설명 | 조치 |
|---|---|
| `KEK_SOURCE 설정값 오류` | 키 관리자가 설정을 확인합니다. 값은 `GLOBAL_CTX` 나 `EXTERNAL` 이어야 합니다 |
| `외부 키 반입이 구현되지 않았다` | `KEK_SOURCE` 가 `EXTERNAL` 인데 외부 키 반입이 구현되어 있지 않은 것입니다. 이 패키지에서는 알려진 한계입니다(설치 매뉴얼 제11.7절). 키 관리자와 보안 담당자가 대응합니다 |
| `GLOBAL_CTX 모드가 아니면 마스터 키를 직접 주입할 수 없다` | 설정과 주입 방식이 맞지 않음. 키 관리자가 확인 |
| `APPCTX_MODE 설정값 오류` | 값은 운영에서는 `PROOF` 여야 합니다(`SIMPLE` 은 개발 전용). 키 관리자가 확인 |
| `반복 횟수가 1보다 작음` | 비밀번호 반복 횟수 설정이 잘못됨. 키 관리자가 확인 |

설정은 `SEC_CONFIG` 표의 값으로만 바뀌며, 운영 전환 때 켠 통합 감사 정책이 그 표의 갱신을 기록합니다. 승인된 변경이 아니면 보안 담당자에게 알립니다.

### 17.11 `ORA-20541` 인자 오류

**뜻.** 호출에 넘긴 값이 규칙에 맞지 않습니다. 빈 비밀번호 저장 시도, 응용 사용자 식별자가 비어 있음 등입니다. 보안상 위험이 아니라 응용의 입력 검증이 부족한 것입니다. 개발 담당자에게 알립니다.

### 17.12 암호 모듈 오류가 아닌 오라클 오류

| 오류 | 뜻 | 조치 |
|---|---|---|
| `ORA-00904`(`FN_...` 식별자) | 짧은 함수 이름이 풀리지 않음. 그 계정에 시노님이 없음 | 데이터베이스 관리자가 업무 계정 연결(`480_connect_app_schema.sql`)을 합니다. 임시로는 `OCS_OWNER.PKG_SECURE_API.함수이름` 으로 호출합니다 |
| `ORA-00942` | 객체가 없거나 권한이 없음 | 시노님이나 실행 권한이 없는 경우가 흔합니다. 같은 조치 |
| `PLS-00201` | 식별자를 찾을 수 없음. 뷰나 저장 프로시저 안에서 쓰려면 실행 권한이 **역할이 아니라 계정에 직접** 있어야 함 | 데이터베이스 관리자가 `480_connect_app_schema.sql` 을 실행(직접 권한을 줌) |
| `ORA-01109` | 대상 PDB 가 닫혀 있음. 재부팅이나 재기동 뒤에 흔함 | 데이터베이스 관리자가 `sqlplus / as sysdba` 로 `SELECT name, open_mode FROM v$pdbs;` 를 보고 `MOUNTED` 이면 `ALTER PLUGGABLE DATABASE <PDB이름> OPEN;` 과 `SAVE STATE;`. **연 뒤에는 마스터 키가 비어 있으므로** 제17.1절로 이어집니다 |
| 업무 프로그램에서 `ORA-04068`, `ORA-06508` 등 패키지 상태 오류 | 이 문서에서는 확인하지 않았습니다 | 오류 번호와 함께 보안 담당자와 개발 담당자에게 문의하십시오 |

## 18. 상황별 절차

### 18.1 전체 암복호화 정지 (`FN_READY` 가 `0`, 여러 곳에서 `ORA-20513`)

| 순서 | 담당 | 할 일 |
|---|---|---|
| 1 | 운영담당자 | 제15.2절로 `0` 을 확인하고 영향받는 업무를 파악해 알림 |
| 2 | 운영담당자 | 제15.3절의 유지 프로그램 상태 확인. 멈춰 있으면 시작 |
| 3 | 운영담당자 | 확인 주기의 두 배쯤 기다린 뒤 제15.2절 재확인. `1` 이면 업무를 재개하고 4 로 |
| 4 | 감사 담당자 | `KEYSTORE_CLOSE` 사건이 있었는지 조회. 승인 없는 닫힘이면 보안 담당자에게 보고 |
| 5 | 키 관리자 | 유지 프로그램이 돌고 있는데도 열리지 않으면 설정 파일의 마스터 키와 계정을 확인. 필요하면 마스터 키를 직접 주입(제3장) |
| 6 | 운영담당자 | 접속이 `ORA-01109` 이면 먼저 제17.12절로 PDB 를 열고 2 로 |

### 18.2 일부 화면이나 일부 사용자만 실패

| 순서 | 할 일 |
|---|---|
| 1 | 제15.2절로 `1` 임을 확인(시스템 문제가 아님) |
| 2 | 오류 번호로 제17장을 찾습니다. 이 경우는 `ORA-20521`(문맥), `ORA-20520`(자격), `ORA-20522`(사용량), `ORA-20530`(도메인 코드)이 흔합니다 |
| 3 | 실패한 사용자의 업무 권한과 자격이 같은 업무의 다른 사용자와 같은지 비교 |

### 18.3 특정 행만 실패

`ORA-20511` 이나 `ORA-20510` 이 같은 행에서만 반복되면 그 행의 자료 문제입니다. 제17.2절과 제17.7절을 따르고, **그 행을 고치거나 지우지 마십시오.**

### 18.4 화면에 `********` 가 많이 보임

목록 화면의 마스킹 값(`********`)은 정상 마스킹일 수도, 마스킹 중 복호화 실패로 대체된 것일 수도 있습니다. 마스킹 형식은 도메인마다 다르며, 복호화 실패로 대체된 값은 전부 별표입니다. 감사 담당자가 `MASK_FAIL` 사건이 쌓이는지 조회하고(제19.1절), 반복되면 자료 손상을 의심하여 제17.2절로 가십시오.

### 18.5 오류가 갑자기 폭주

| 순서 | 할 일 |
|---|---|
| 1 | 오류 번호별 건수를 센다(`ORA-20521`, `ORA-20520`, `ORA-20511` 중 무엇이 많은가) |
| 2 | `ORA-20521` 폭주: 서버 시각, 증표 키, 조회 도구 직접 접속 시도 순서로 확인(제17.4절) |
| 3 | `ORA-20520`, `ORA-20522` 폭주: 침해 시도일 수 있으므로 감사 담당자가 계정과 접속 정보를 확인하고 보안 담당자에게 알림 |
| 4 | 침해가 의심되면 보안 담당자의 판단에 따라 비상 정지(제13.4절)를 합니다. **운영담당자가 임의로 저장소를 닫지 마십시오.** 닫으려면 유지 프로그램을 먼저 멈춰야 하며, 그 순서를 지키지 않으면 10초 안에 다시 열립니다 |

## 19. 확인에 쓰는 조회

감사 기록에는 평문, 키, 암호문 전체가 남지 않습니다. 아래 조회는 `OCS_AUDITOR` 로 합니다.

### 19.1 최근 사건

```sql
SELECT event_ts, event_type, severity, domain_code, db_user, app_user, ip_address, detail
  FROM OCS_OWNER.SEC_AUDIT_LOG
 WHERE event_ts > SYSTIMESTAMP - INTERVAL '1' DAY
   AND severity IN ('ALERT', 'WARN')
 ORDER BY event_ts DESC;
```

사건 이름과 오류의 대응은 다음과 같습니다.

| 오류 | 같이 보아야 할 사건 |
|---|---|
| `ORA-20513` | `KEYSTORE_CLOSE`, `KEYSTORE_OPEN` |
| `ORA-20511` | `INTEGRITY_FAIL`, `MASK_FAIL` |
| `ORA-20512` | `KEY_RETIRE`, `KEY_ACTIVATE` |
| `ORA-20521` | `APPCTX_DENIED`, `REVEAL_DENIED`, `PROTECT_DENIED`, `INDEX_DENIED` |
| `ORA-20520` | `REVEAL_DENIED`, `REVEAL_GRANT`, `REVEAL_REVOKE` |
| `ORA-20522` | `RATE_EXCEEDED` |
| `ORA-20523` | `ADMIN_DENIED` |

특정 사건만 보려면 `AND event_type = 'APPCTX_DENIED'` 처럼 조건을 더합니다.

### 19.2 키 상태와 변경 이력

```sql
SELECT domain_code, key_id, key_state FROM OCS_OWNER.V_SEC_KEY_STATUS
 ORDER BY domain_code, key_id;

SELECT event_ts, event_type, domain_code, db_user, detail
  FROM OCS_OWNER.SEC_AUDIT_LOG
 WHERE event_type IN ('KEY_CREATE', 'KEY_IMPORT', 'KEY_ACTIVATE', 'KEY_RETIRE')
 ORDER BY event_ts DESC;
```

### 19.3 사용량

제17.6절의 조회를 씁니다.

## 22. 개통 직전과 운영 전환

개통 직전의 절차와 판정은 설치 매뉴얼의 운영 편에 있습니다. 윈도우는 제8.6절, 리눅스는 제10.6절이며, 시험 객체 확인, 소유 계정 잠금(`310_lockdown.sql`), 개통 판정(`320_golive_check.sql`), 위험 수용 기록(`490_kek_risk_ack.sql`), 데이터베이스 밖에서 챙길 일, 운영 담당자 두 분 기준의 운영 지침이 모두 거기에 있습니다. 이 장은 운영 중에 기억해 둘 것만 남깁니다.

**마스터 키 반입 방식.** 외부 키 관리 서버나 하드웨어 보안 모듈을 쓸 수 없는 운영에서는 `KEK_SOURCE` 를 `SCOPED_CTX` 로 둡니다. 개통 판정은 이 방식에서 위험 수용 기록(`KEK_RISK_ACK`)이 있을 때만 통과합니다. `EXTERNAL` 은 아직 구현되어 있지 않으며, 구현되기 전에는 `GLOBAL_CTX` 를 운영에 쓰지 마십시오(`GLOBAL_CTX` 는 업무 계정도 마스터 키를 볼 수 있는 방식입니다).

**설정 점검.** `APPCTX_MODE` 는 `PROOF` 여야 합니다. 개발 모드(`910_dev_mode_on.sql`)를 켠 채 두면 접속 정보만으로 암복호화가 됩니다.

스크립트가 처리하지 못하는 **데이터베이스 밖의 일**이 남습니다.

| 외부 조치 | 하지 않으면 |
|---|---|
| 감사 기록(`SEC_AUDIT_LOG`, 통합 감사)을 데이터베이스 밖에 보관하거나 외부 보안 관제로 전송 | 감사 대상이 감사 기록을 지울 수 있음 |
| 응용 계정 접속 지점을 `sqlnet.ora` 노드 검증으로 제한 | 어디서든 응용 계정으로 접속 가능 |
| 패키지 소스 해시를 밖에 보관하고 정기 대조 | 패키지가 바뀌어도 모름 |
| 마스터 키 백업 복구 시험과 기록 | 필요한 순간에 복구 실패 |
| `keeper.properties` 를 일반 백업에서 제외하고 접근 제한 유지 | 마스터 키가 백업 매체를 통해 새어 나감 |

**운영계에서 실행하지 마십시오.** `sql/09_test/902_selftest.sql`(저장소를 닫고 설정을 바꿈)과 `sql/99_uninstall/990_drop_all.sql`(키와 감사 기록을 지워 자료를 영구히 되살릴 수 없게 함).

## 24. 근거와 신뢰도

이 문서의 표와 구문은 저장소의 패키지 명세와 본문, 표 정의, 설치·잠금 스크립트를 직접 읽고 대조한 것입니다. 신뢰도: 높음. 사건 유형과 심각도는 `PKG_AUDIT.log` 호출을 열거한 결과입니다.

본문의 **새 조회 구문**(제6.3절, 제7장, 제9.2절, 제9.5절 등)은 컬럼 이름을 표 정의와 대조하였으나 **오라클에서 실행해 확인하지 않았습니다.** 신뢰도: 중간. 처음 쓰실 때 한 건씩 확인하십시오.

데이터베이스 재기동 시 전역 문맥이 비워진다는 서술은 시험 인스턴스에서 한 번 관찰하였습니다. 정확도: 높음. 키 유지 프로그램의 상주 실행과 세 가지 복구 시험, 윈도우의 `icacls` 와 작업 스케줄러 절차는 시험 인스턴스에서 직접 확인하였습니다. 정확도: 높음. 리눅스 systemd 와 운영 장비는 확인하지 않았습니다.

반복 횟수 측정값은 개발 서버 한 대의 값입니다. 정확도: 그 장비에 한해 높음. 반복 횟수의 국제 권고 수준은 해마다 바뀌므로 인증 대응 시에는 최신 문서로 확인하십시오. 정확도: 중간.

제14~21장(오류 대응)의 근거입니다. 오류 번호, 메시지, 괄호 안 설명, 발생 조건은 암호 모듈의 소스(`PKG_SEC_ERR` 와 각 패키지의 `raise_err` 호출)를 읽어 정리했습니다(정확도: 높음). 아래는 시험 인스턴스에서 실제로 확인한 것입니다. 윈도우 + 오라클 19c 시험 인스턴스에서 키 저장소를 닫았을 때 `ORA-20513` 이 나고 유지 프로그램이 복구하는 것, 응용 문맥 없이 직접 호출하면 `ORA-20521` 로 거부되는 것, 문맥 없는 복호화 거부와 자격 없는 복호화 거부와 사용량 임계치가 자체 시험에서 통과하는 것(정확도: 높음, 신뢰도: 높음).

확인하지 않은 것은 다음과 같습니다. `ORA-20511`, `ORA-20512`, `ORA-20510` 을 운영과 같은 조건에서 일으켜 본 적이 없으며 원인 분류는 소스와 일반적인 동작에 근거한 추정입니다(정확도: 중간). 리눅스(RHEL)의 명령은 확인하지 않았습니다. 패키지 상태 오류(`ORA-04068`, `ORA-06508`)는 다루지 않았습니다. 다음 구간에서 건수가 다시 시작하는 방식은 이 문서에서 코드로 확인하지 않았습니다.

## 25. 결론 요약

운영에서 가장 먼저 지킬 것은 마스터 키 보관(두 벌 이상, 복구 시험)과 `ready` 감시, 그리고 개통 전 `APPCTX_MODE=PROOF` 확인입니다. 키 교체와 복호화 자격 변경은 모두 `OCS_KEYADM` 만 하며 감사 기록에 `ALERT` 로 남으므로 승인된 작업과 대조하십시오. 옛 키는 `remaining` 이 0 임을 확인한 뒤에만 폐기합니다. 정기 점검의 중심은 `REVEAL_DENIED`·`APPCTX_DENIED`·`RATE_EXCEEDED` 추이와 복호화 자격 대장, 하위 패키지 권한 누출 점검입니다. 비밀번호는 키를 쓰지 않고 반복 횟수 하나만 관리하며, 올리기만 하고 내리지 않습니다. 로그인 시도 제한과 계정 잠금은 이 시스템이 제공하지 않으므로 응용이 맡아야 합니다.

제14~21장(오류 대응)의 요약입니다. 오류를 받으면 번호를 찾고, 여러 곳에서 함께 나는지 보고, `FN_READY` 로 시스템 상태를 먼저 확인합니다. `0` 이면 키 저장소 문제이므로 유지 프로그램을 확인하고 PDB 가 닫혀 있는지 봅니다. `1` 인데 특정 화면에서만 나면 문맥(`ORA-20521`), 자격(`ORA-20520`), 사용량(`ORA-20522`), 도메인 코드(`ORA-20530`) 중 하나입니다.

`ORA-20511` 과 `ORA-20512` 는 자료나 키에 이상이 있다는 신호이므로 **임의로 고치거나 재시도하지 말고 즉시 보안 담당자와 키 관리자에게 알리십시오.** `ORA-20521` 과 `ORA-20520` 은 통제가 제대로 작동한 결과일 수 있으니, 오류를 피하려고 통제를 낮추는 조치는 하지 마십시오. 키와 자격과 설정을 바꾸는 일은 승인을 받아 키 관리자만 합니다.
