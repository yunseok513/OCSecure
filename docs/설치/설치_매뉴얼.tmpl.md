# OCSecure 설치 매뉴얼

## 0. 이 문서에 대하여

이 문서는 오라클 19c 데이터베이스에 OCSecure 컬럼 암호화 모듈을 설치하고, 설치가 제대로 되었는지 확인하는 절차를 담고 있습니다. 설치 패키지와 함께 제공되며, 문서의 순서는 작업의 순서와 같습니다. 제1장에서 설치할 것을 소개하고, 제2장에서 설치 전에 확인할 것을 점검합니다. 이어서 설치 진행과 설치 후 확인이 운영체제별로 나뉘어 있습니다. **윈도우에 설치하면 제3장과 제4장을, 리눅스(RHEL)에 설치하면 제5장과 제6장을 읽으십시오.** 두 편은 같은 순서로 쓰여 있고 각각 처음부터 끝까지 이어서 읽을 수 있으므로 다른 편을 오갈 필요가 없습니다. 제7장에 모든 설치에 공통인 참고 사항을 모았습니다.

읽는 분은 오라클 데이터베이스 관리자이거나 그에 준하는 권한을 가진 담당자를 전제합니다. 설치 대상은 오라클 19c 멀티테넌트의 PDB 이며 데이터베이스 문자집합이 `KO16MSWIN949` 인 환경을 기준으로 작성하였습니다. 설치 대상 운영체제는 윈도우와 리눅스(RHEL)이며 아래와 같이 나누어 적었습니다.

| 구분 | 상태 |
|---|---|
| 윈도우 + 오라클 19c 멀티테넌트 (제3장, 제4장) | 새 PC 에서 이 판의 패키지로 제3장과 제4장을 단계별로 진행하며 기대값을 확인했음(제4.5절 복구 시험은 저장소 닫기만 함). 시험 중 찾은 결함을 고쳤으므로 **고친 판으로 처음부터 한 번에 이어서 다시 설치한 시험은 아직 하지 않음** |
| 리눅스(RHEL, systemd) (제5장, 제6장) | 명령을 참고로 적었으나 **검증되지 않음.** 운영 적용 전에 별도 검증이 필요함 |
| 마스터 키 `GLOBAL_CTX` 방식 | **개발·시험 전용.** 운영 개통에는 쓸 수 없음(제{I}.8절, 제7.7절) |
| 마스터 키 `SCOPED_CTX` 방식 | 외부 키 관리 서버나 하드웨어 보안 모듈을 쓸 수 없는 운영용. **시험 PC 한 대에서 확인했으나 운영 장비에서는 하지 않음.** 남는 위험을 수용한다는 기록이 있어야 개통 판정을 통과함(제{I}.8절, 제7.7절) |

검증 범위의 자세한 내용은 제7.7절에 있습니다.

### 0.1 표기법

설치 절차의 각 단계는 **접속**, **실행**, **확인**의 세 토막으로 적었습니다. 접속은 어느 계정으로 붙어야 하는지를, 실행은 무엇을 치는지를, 확인은 무엇이 나와야 하는지를 말합니다. 확인에서 기대값이 나오지 않으면 **다음 단계로 넘어가지 말고** 제7.1절에서 해당 증상을 찾으십시오. 뒤에서 드러나는 오류는 원인을 찾기가 훨씬 어렵습니다.

코드 블록은 그대로 복사하여 붙여 넣으면 됩니다. `@` 로 시작하는 줄은 `sqlplus` 안에서 치고, `sqlplus` 나 `python` 이나 `java` 로 시작하는 줄은 윈도우에서는 명령 프롬프트에서, 리눅스에서는 셸에서 칩니다. 꺾쇠로 둘러싼 `<대상PDB>` 같은 부분은 현장의 값으로 바꾸어 넣습니다.

본문에서 굵게 표시한 문장은 지시이므로 건너뛰지 마십시오. 인용 표시로 묶고 「참고」라고 단 대목은 이유를 설명한 것이며 읽지 않고 건너뛰어도 설치는 완료됩니다.

### 0.2 문서에서 쓰는 이름

설치 패키지를 푼 폴더를 이 문서에서는 `OCS_HOME` 이라 부릅니다. 윈도우에서는 `C:\ocsecure`, 리눅스에서는 `/opt/ocsecure` 에 푼 것으로 적습니다. 이 위치는 제{I}.1절에서 환경 변수에 한 번 담으며, 뒤의 명령은 모두 그 변수를 기준으로 합니다.

## 1. 소개

### 1.1 설치하는 것

OCSecure 는 오라클 테이블의 컬럼을 응용 프로그램이 쓰기 쉬운 형태로 암호화하는 모듈입니다. 설치 대상은 세 부분입니다.

| 부분 | 내용 | 설치 장소 |
|---|---|---|
| 데이터베이스 모듈 | 계정 3개, 역할 3개, 테이블 8개, 뷰 3개, 패키지 14개. 암호화와 복호화, 검색용 색인, 비밀번호 해시, 키 교체와 감사를 담당 | 대상 PDB |
| 자바 연동 모듈 | 응용 서버가 데이터베이스에 접속할 때 접속 증표를 계산하여 제출하고 문맥을 세우는 라이브러리 | 응용 서버 |
| 키 저장소 유지 프로그램 | 마스터 키가 데이터베이스 안에서 사라졌을 때 사람 손 없이 다시 넣는 상주 프로그램 | 전용 계정이 있는 장비 |

### 1.2 설치 후의 모습

설치가 끝나면 데이터베이스에 암호 모듈의 세 계정이 생기고, 이미 있는 업무 계정 하나 이상이 거기에 연결됩니다. 계정마다 하는 일이 다릅니다. 계정을 나눈 것이 이 모듈의 통제 구조의 토대이므로 한 사람이 둘 이상의 역할을 겸하지 않도록 운영하는 것이 바람직합니다.

| 계정 | 하는 일 | 설치 후 상태 |
|---|---|---|
| `OCS_OWNER` | 패키지와 키 정보를 소유 | 설치를 마친 뒤 잠금 |
| `OCS_KEYADM` | 키 생성과 교체, 복호화 자격 부여, 마스터 키 주입 | 사용 |
| `OCS_AUDITOR` | 감사 기록과 자격 현황 조회 | 사용 |
| `<응용계정>` | 이미 있는 업무 계정. 응용이 사용하며 암호화 API 를 호출. **설치가 새로 만들지 않고 권한만 연결하며 비밀번호와 기존 권한은 건드리지 않음** | 사용 |

암호화 대상 업무 구분은 도메인으로 관리하며, 설치할 때 주민등록번호(`RRN`), 성명(`NAME`), 연락처(`PHONE`), 계좌번호(`ACCOUNT`)의 네 도메인이 만들어집니다.

### 1.3 이 문서가 다루는 범위

이 문서는 설치와 설치 확인까지를 다룹니다. 운영 중의 키 교체와 감사 조회, 응용 개발 방법은 범위 밖이며 별도의 관리자 매뉴얼과 개발자 매뉴얼에서 다룹니다. 기존 업무 테이블의 자료를 암호화 구조로 옮기는 일, 그리고 외부 키 관리 서버나 하드웨어 보안 모듈과의 연동도 이 문서의 범위가 아닙니다.

### 1.4 설치에 걸리는 일

설치는 크게 열두 단계이며 한 사람이 이어서 하면 반나절 안팎이 걸릴 것으로 예상합니다. 다만 제{I}.7절의 반복 횟수 결정과 제{I}.10절의 증표용 키 전달은 다른 담당자와의 협의가 필요하므로 미리 준비하십시오. 설치가 끝난 뒤의 확인(제4장)에는 장비 재부팅을 포함한 시험이 있어 별도 시간이 필요합니다.

## 2. 설치 전 확인 사항

### 2.1 환경 요건

| 항목 | 요건 | 확인 방법 |
|---|---|---|
| 데이터베이스 | 오라클 19c, 멀티테넌트 | 제{I}.2절에서 확인 |
| 대상 PDB | 업무 자료가 있는 PDB 에 설치. 문자집합 `KO16MSWIN949` 기준 | 제{I}.2절에서 확인 |
| 접속 도구 | SQL\*Plus | `sqlplus -V` |
| 파이썬 | 3.x. 패키지 확인, CP949 사본 만들기, 키 만들기에 사용. 외부 패키지는 필요 없음 | `python --version` |
| 자바 | JDK 8 이상(`javac` 포함). 자바 연동 모듈의 컴파일에 사용. 소스는 자바 8 호환으로 작성됨 | `javac -version` |
| JDBC 드라이버 | `ojdbc8.jar`. 오라클 설치 폴더의 `jdbc/lib` 에 있음 | 제{I}.1절에서 복사 |
| 운영체제 권한 | 관리자(윈도우) 또는 root(리눅스). 환경 변수, 전용 계정, 작업 스케줄러 등록에 필요 | |
| 시간 동기화 | 데이터베이스 서버와 응용 서버의 시계가 NTP 등으로 맞추어져 있어야 함. 증표에 현재 시각이 들어 있고 기본 유효 시간이 300초이므로, 시계가 크게 어긋나면 정상 응용도 인증에 실패함 | 두 장비의 현재 시각을 비교 |

### 2.2 데이터베이스 접속 권한

대상 PDB 에 `SYS` 로 접속할 수 있어야 합니다. 일반 DBA 계정으로는 일부 부여가 조용히 실패할 수 있으므로 `SYS` 를 쓰십시오. 접속 문자열의 모양은 다음과 같습니다.

```
sqlplus <계정>@<호스트>:<포트>/<서비스명>
```

접속 문자열의 서비스명은 최상위 컨테이너가 아니라 **대상 PDB 의 서비스명**입니다. 호스트와 포트와 서비스명을 미리 확인해 두십시오.

### 2.3 사람이 미리 준비할 것

| 준비물 | 내용 | 비고 |
|---|---|---|
| 계정 비밀번호 3개 | `OCS_OWNER`, `OCS_KEYADM`, `OCS_AUDITOR` | 제{I}.3절에서 입력. 정책에 맞는 강도로 정해 두고 열람 통제가 되는 곳에 보관 |
| 연결할 업무 계정 | 이미 있는 업무 계정의 이름(이 문서의 `<응용계정>`). 여러 개이면 모두 | 설치 전에 정해 둘 것. 설치는 이 계정을 만들지 않으며, 계정이 없으면 연결 단계(제{I}.5.1절)가 거부함. 연동 확인을 하려면 그 계정으로 접속할 수 있어야 함 |
| 마스터 키 보관처 | 제{I}.8절에서 만들어지는 64자리 16진 문자열을 보관할 곳 | 열람 통제가 되고, 두 벌 이상 보관하며, 꺼낸 사람과 시각이 남는 곳. **잃으면 암호화한 자료를 하나도 되살릴 수 없음** |
| 증표용 키 전달 경로 | 제{I}.10절에서 만드는 키를 응용 서버 담당자에게 전달할 방법 | 응용 서버 설정에 들어갈 값이므로 안전한 경로로 전달 |
| 키 저장소 유지 프로그램을 둘 장비 | 전용 운영체제 계정을 만들 수 있는 장비 | 제{I}.12절. 마스터 키를 쥐는 프로그램이므로 데이터베이스 관리자의 손이 덜 닿는 장비가 바람직하나, 데이터베이스가 재기동된 뒤 빨리 다시 넣으려면 네트워크로 닿기 쉬워야 함 |
| 설치 전 백업과 복구 지점 | 대상 PDB 의 백업 또는 조직 표준의 복구 지점, 복구 책임자, 복구 여부를 판단할 기준 | 오라클 DDL 은 한 번에 되돌릴 수 없으므로 운영 인스턴스에서는 설치 전에 반드시 준비. 제7.4절의 제거 스크립트는 운영계에서 쓰지 못하므로 복구 수단이 아님 |
| 로그인 한 건에 허용할 시간 | 비밀번호 검증 한 번에 허용할 응답 시간 | 제{I}.7절의 반복 횟수를 정하는 기준 |

### 2.4 주의가 필요한 파일

설치 패키지에는 운영계에서 실행하면 안 되는 스크립트가 둘 들어 있습니다. `sql/09_test/902_selftest.sql` 은 설정을 개발용으로 바꾸었다가 되돌리고 끝에 키 저장소를 닫으므로 **운영 중인 시스템에서 실행하지 마십시오.** `sql/99_uninstall/990_drop_all.sql` 은 암호 모듈과 모든 키와 감사 기록을 지우므로 **운영계에서는 절대 실행하지 마십시오.** 키를 지우면 그 키로 암호화한 자료를 영구히 되살릴 수 없습니다.

#### {I}.1.4 대상 PDB 열림 확인

오라클에 처음 접속하기 전에 대상 PDB 가 열려 있는지 확인합니다. 재부팅이나 재기동 뒤에 PDB 는 `MOUNTED` 로만 올라오는 것이 기본이며, 새로 설치한 장비에서는 열려 있지 않아 접속이 `ORA-01109` 로 거부되는 일이 흔합니다.

**접속.** 데이터베이스 서버에서 운영체제 인증으로 컨테이너 최상위에 붙습니다.

@@win
관리자 권한 명령 프롬프트가 필요할 수 있습니다.

```
sqlplus / as sysdba
```
@@rhel
오라클 소프트웨어 소유 계정(보통 `oracle`)으로 붙습니다.

```
sqlplus / as sysdba
```
@@end

**확인.** 대상 PDB 의 `OPEN_MODE` 를 봅니다.

```sql
SELECT name, open_mode FROM v$pdbs;
```

| `OPEN_MODE` | 뜻 | 조치 |
|---|---|---|
| `READ WRITE` | 열려 있음 | 이 문제가 아님. 접속 문자열의 서비스명과 호스트, 포트, 리스너를 확인 |
| `MOUNTED` | 닫혀 있음 | 아래로 열기 |
| `READ ONLY` | 읽기 전용으로 열려 있음 | 설치는 쓰기가 필요하므로 닫은 뒤 다시 열기 |

**실행.** `MOUNTED` 이면 열고, 재기동 뒤에도 자동으로 열리도록 상태를 저장합니다. `ORCLPDB` 는 대상 PDB 이름으로 바꾸십시오.

```sql
ALTER PLUGGABLE DATABASE ORCLPDB OPEN;
ALTER PLUGGABLE DATABASE ORCLPDB SAVE STATE;
SELECT name, open_mode FROM v$pdbs;
```

**확인.** 마지막 조회에서 `READ WRITE` 가 나와야 합니다. `SAVE STATE` 는 CDB 가 재기동될 때 PDB 를 같은 상태로 열라는 설정입니다. 이미 설치가 끝난 시스템에서 PDB 를 다시 연 경우에는 마스터 키가 비어 있으므로 제{I}.8절의 주입이나 키 저장소 유지 프로그램의 재주입을 확인하십시오.

```sql
SELECT grantee, table_name, privilege FROM USER_TAB_PRIVS_MADE
 WHERE grantee LIKE 'OCS%' ORDER BY 1, 2;
```

`OCS_ROLE_APP` 에 `PKG_SECURE_API` 와 `FN_` 으로 시작하는 함수 25개의 실행 권한이, `OCS_ROLE_KEYADM` 에 `PKG_KEY_ADMIN` 과 `PKG_REKEY` 와 `PKG_KEK_PROVIDER` 실행 권한이, `OCS_KEYADM` 에 `V_SEC_KEY_STATUS` 조회 권한이 보여야 합니다.

> **참고.** 이 스크립트는 최상위 인터페이스 패키지에만 실행 권한을 주고 그 아래 계층에는 어떤 계정에도 주지 않습니다. 정책 계층을 우회한 복호화가 막히는 근거가 전적으로 이 원칙입니다. 키 관리 계정에 키 현황 뷰를 역할이 아니라 계정으로 직접 주는 까닭은, 역할로 준 권한이 소유자 권한 패키지 안에서는 인정되지 않기 때문입니다.

### {I}.8 마스터 키

**접속.** 먼저 `OCS_OWNER`.

**실행.** 마스터 키 반입 방식을 정하고 키를 만듭니다.

```sql
UPDATE SEC_CONFIG SET cfg_value = 'GLOBAL_CTX', updated_at = SYSTIMESTAMP
 WHERE cfg_key = 'KEK_SOURCE';
COMMIT;

SET SERVEROUTPUT ON
DECLARE v RAW(32); BEGIN
  v := DBMS_CRYPTO.RANDOMBYTES(32);
  DBMS_OUTPUT.PUT_LINE('MASTER KEY = ' || RAWTOHEX(v));
END;
/
```

**찍힌 64자리 16진 문자열을 화면에서 지우기 전에 반드시 제2.3절에서 정한 보관처에 기록하십시오.** 열람 통제가 되는 곳에 두 벌 이상 보관하고, 누가 언제 꺼냈는지 남는 절차를 함께 두십시오. **이것을 잃으면 암호화한 자료를 하나도 되살릴 수 없습니다.**

**접속.** 이어서 `OCS_KEYADM`.

**실행.** `<64자리>` 에 위에서 기록한 값을 넣습니다.

```sql
BEGIN OCS_OWNER.PKG_KEK_PROVIDER.set_master_key(HEXTORAW('<64자리>')); END;
/
```

**확인.** 「키 저장소 열림」이 나와야 합니다.

```sql
SET SERVEROUTPUT ON
BEGIN
  IF OCS_OWNER.PKG_KEK_PROVIDER.is_open THEN
    DBMS_OUTPUT.PUT_LINE('키 저장소 열림');
  ELSE
    DBMS_OUTPUT.PUT_LINE('키 저장소 닫힘');
  END IF;
END;
/
```

> **참고.** 마스터 키는 데이터 키를 감싸는 데만 쓰는 최상위 키입니다. 주입한 값은 데이터베이스의 전역 문맥에 들어가며 주입한 세션이 끝나도 남습니다. 다만 **데이터베이스를 재기동하거나 누군가 키 저장소를 닫으면 사라집니다.** 사람이 다시 넣지 않아도 되도록 제{I}.12절의 키 저장소 유지 프로그램을 둡니다.

> **경고.** `GLOBAL_CTX` 방식은 마스터 키 값을 데이터베이스의 전역 문맥에 넣으며, 이 구현은 특정 사용자나 클라이언트를 지정하지 않으므로 **다른 데이터베이스 계정도 `SYS_CONTEXT('OCS_KEK_CTX','MASTER')` 로 그 값을 읽을 수 있습니다.** 따라서 이 방식은 개발과 시험에만 쓰고 운영 개통에는 쓸 수 없습니다. 운영에서는 `EXTERNAL` 방식이 필요하며 그 구현(`PKG_KEK_PROVIDER.load_from_external`)은 이 패키지에 포함되어 있지 않습니다(제7.7절). 외부 키 관리 서버나 하드웨어 보안 모듈을 쓸 수 없다면 아래의 `SCOPED_CTX` 를 검토하십시오.

> **운영용: 외부 키 관리 서버가 없을 때(`SCOPED_CTX`).** 위의 `UPDATE` 에서 `GLOBAL_CTX` 대신 `SCOPED_CTX` 를 넣고 나머지는 같습니다. 마스터 키는 같은 전역 문맥에 올라가지만 값을 넣을 때 **설치마다 다른 무작위 토큰을 클라이언트 식별자로 지정**합니다. 토큰은 소유 계정만 읽는 `SEC_CONFIG` 에 있고 이 패키지만 잠깐 써서 읽으므로, 응용 계정이 `SYS_CONTEXT('OCS_KEK_CTX','MASTER')` 로 직접 읽으면 빈 값이 나옵니다. **그러나 `SYS` 와 소유 계정을 쥔 사람, 키 유지 프로그램이 있는 장비의 관리자는 막지 못합니다.** 이 잔여 위험을 책임자가 문서로 수용했다는 기록(제{V}.6.3절의 `490_kek_risk_ack.sql`)이 있어야 개통 판정이 통과합니다. 이 방식은 시험 PC 한 대에서 확인한 것이므로(제7.7절), 운영에 쓰기 전에 운영 장비에서 제{V}장의 전 과정을 이 방식으로 다시 확인하십시오.

### {I}.10 증표용 키

이 키는 응용 서버가 데이터베이스에 접속할 때 자기가 정당한 응용임을 증명하는 데 쓰입니다. 응용 계정의 접속 정보를 알아낸 사람이 조회 도구로 직접 붙더라도 아무것도 하지 못하게 하는 장치입니다.

**실행.** 이 키는 데이터베이스 **밖에서** 만듭니다. 애플리케이션 담당자가 만들어 전달하는 것이 가장 낫습니다.

@@win
```
python -c "import secrets,hashlib; k=[secrets.token_hex(32) for _ in range(3)]; print('\n'.join(k)); print('지문(세 번째 값):', hashlib.sha256(bytes.fromhex(k[2])).hexdigest()[:8])"
```
@@rhel
```
python3 -c "import secrets,hashlib; k=[secrets.token_hex(32) for _ in range(3)]; print('\n'.join(k)); print('지문(세 번째 값):', hashlib.sha256(bytes.fromhex(k[2])).hexdigest()[:8])"
```
@@end

키 세 줄과 그 아래 「지문(세 번째 값)」 한 줄이 나옵니다. 앞의 키 둘은 규격을 맞추기 위한 예비값이고 **세 번째가 실제 증표 계산에 쓰이는 값이며 응용 서버 설정에 들어갑니다. 반드시 기록해 두십시오.** 지문은 세 번째 값의 짧은 확인용 값(8자리)이며 키를 되살릴 수 없습니다. 뒤에서 증표 키를 입력할 때 화면에 지문이 나오므로, **키와 함께 지문을 적어 두십시오.**

**접속.** `OCS_KEYADM`.

**실행.** 세 값을 차례로 물어봅니다. 먼저 입력을 화면에 보이게 할지 묻습니다. 기본(엔터)은 보이지 않게 받는 것입니다. 이 경우 붙여 넣어도 아무것도 보이지 않는 것이 정상입니다. 붙여 넣기가 되지 않는 환경이면 `Y` 를 골라 보이게 입력할 수 있으나, 키가 화면과 스크롤백에 남으므로 개발·시험에서만 쓰십시오. 세 값을 모두 넣으면 값 자체는 보여 주지 않고 칸마다 「길이, 형식, 지문(SHA-256 앞 4바이트)」을 보여 줍니다. 각각 64자·형식 정상이어야 하며, 128자가 나오면 두 번 붙여 넣은 것이므로 다시 실행하십시오. 입력에 문제가 있으면 키를 등록하기 전에 스크립트가 끝나 SQL*Plus 도 종료됩니다. **증표용 키(셋째)의 지문을 적어 두십시오.** 제{V}.2절 자바 연동 확인에서 나오는 지문과 같아야 같은 키를 넣은 것입니다.

@@end

> **참고.** 패키지를 JDK 가 있는 장비에서 만들었다면 미리 컴파일한 `java/ocsecure-client-1.0.0.jar` 가 들어 있고, 그렇지 않으면 들어 있지 않습니다. 이것은 응용 서버의 업무 프로젝트에 넣어 쓰는 라이브러리이며, 이 설치 절차의 연동 확인(제{V}.2절)과 유지 프로그램은 위에서 컴파일한 `out` 폴더를 씁니다. jar 가 필요한데 없으면 `out` 의 `ocsecure/client` 클래스를 묶어 쓰거나 JDK 가 있는 장비에서 패키지를 다시 만들어 달라고 요청하십시오.

### {I}.12 키 저장소 유지 프로그램

마스터 키는 데이터베이스를 재기동하면 사라지므로, 사람이 와서 다시 넣어 주지 않아도 되도록 상주 프로그램이 주기적으로 확인하여 닫혀 있으면 다시 넣습니다. 이 절은 그 프로그램을 설치하는 일입니다.

#### {I}.12.1 전용 계정 만들기

유지 프로그램은 사람이 쓰는 계정이 아닌 전용 계정으로 돌려야 합니다. 사람이 쓰는 계정으로 돌리면 그 사람이 떠나거나 암호를 바꿀 때 암복호화가 함께 멈춥니다. 아래에서는 `ocskeeper` 라는 이름으로 적었습니다. 이 계정은 데이터베이스 계정이 아니라 운영체제 계정이며, 데이터베이스 쪽에서 쓰는 계정은 설정 파일에 적는 `OCS_KEYADM` 입니다.

@@win
**실행.** 관리자 권한 명령 프롬프트에서 만듭니다. 별표를 적으면 암호를 물어보므로 명령 이력에 남지 않습니다. 암호는 길고 임의로 정하고 열람 통제가 되는 곳에 보관하십시오.

```
net user ocskeeper * /add /comment:"OCSecure 키 저장소 유지 프로그램 전용"
mkdir "%OCS_HOME%\java\log"
```

이어서 암호 만료를 끕니다. **창을 관리자 권한으로 띄우셔야 합니다.** 시작 단추에서 `cmd` 또는 `powershell` 을 찾아 오른쪽 단추로 「관리자 권한으로 실행」을 고르십시오. 창 제목에 「관리자」가 붙어 있으면 맞습니다. 암호 만료를 꺼 두는 까닭은, 만료되면 작업 스케줄러에 저장된 암호가 맞지 않게 되어 어느 날 재기동 뒤에 조용히 뜨지 않기 때문입니다. 대신 이 계정의 암호를 바꿀 때에는 제{I}.12.5절의 작업 등록도 함께 다시 해야 합니다.

장비의 윈도우 판과 셸에 따라 되는 명령이 다르므로 세 가지를 적습니다. 어느 하나만 되면 됩니다.

화면으로 하는 방법이 가장 확실합니다. `lusrmgr.msc` 를 열어 사용자 목록에서 `ocskeeper` 의 속성을 열고 「암호 사용 기간 제한 없음」에 체크한 뒤 확인을 누르십시오.

```
lusrmgr.msc
```

PowerShell 창에서 하는 방법입니다. 감싸지 말고 그대로 치십시오.

```
Set-LocalUser -Name ocskeeper -PasswordNeverExpires $true
```

명령 프롬프트에서 하는 방법입니다. 첫 줄이 없는 장비에서는 둘째 줄의 `wmic` 을 쓰십시오.

```
powershell -Command "Set-LocalUser -Name ocskeeper -PasswordNeverExpires $true"
wmic useraccount where "name='ocskeeper'" set PasswordExpires=FALSE
```

세 가지를 두는 까닭은 어느 하나가 모든 장비에서 되지는 않기 때문입니다. `Set-LocalUser` 는 PowerShell 5.1 부터(Windows 10, Server 2016 이상) 있고 그 이전 장비에는 없으며, `wmic` 은 오래된 장비에는 있으나 최근 윈도우에서는 빠졌습니다. 또 `powershell -Command "... $true"` 형태는 명령 프롬프트에서만 맞고, 같은 줄을 PowerShell 창에서 치면 바깥 셸이 `$true` 를 먼저 바꿔 넣어 형 변환 오류가 납니다.

이어서 이 계정의 권한을 조입니다. **아래는 명령이 아니라 화면에서 하는 단계이며, 건너뛰면 작업 스케줄러가 시작되지 못합니다.** 관리자 권한으로 `secpol.msc` 를 열고, 왼쪽의 「로컬 정책」, 「사용자 권한 할당」에서 아래 세 항목을 손봅니다.

| 항목 | 할 일 | 이유 |
|---|---|---|
| 일괄 작업으로 로그온 | `ocskeeper` **추가** | 작업 스케줄러가 이 계정으로 프로그램을 돌리는 데 필요. 없으면 작업이 시작되지 않고 이벤트 로그에 오류 값 `0x80070569` 가 남음 |
| 로컬 로그온 거부 | `ocskeeper` 추가 | 사람이 이 계정으로 장비 화면에 로그인하지 못하게 막음 |
| 원격 데스크톱 서비스를 통한 로그온 거부 | `ocskeeper` 추가 | 사람이 이 계정으로 원격 접속하지 못하게 막음 |

「일괄 작업으로 로그온 거부」 항목에 `ocskeeper` 가 들어 있으면 제거하십시오. 장비가 도메인에 속해 있으면 도메인 정책이 로컬 정책을 덮어쓸 수 있으므로, 적용되지 않으면 도메인 관리자와 협의하십시오. 이 단계를 했는지는 제{I}.12.5절에서 작업을 한 번 돌려 보면 드러납니다.

**확인.** 「계정 활성」이 `Yes` 또는 「예」이고 **「암호 만료 날짜」가 「안 함」 또는 `Never`** 여야 합니다. 실제 날짜가 보이면 만료를 끄는 명령이 먹지 않은 것입니다.

```
net user ocskeeper
```
@@rhel
**실행.** 로그인할 수 없고 홈 디렉터리도 없는 시스템 계정으로 만들고, 프로그램을 둘 디렉터리의 소유자를 넘깁니다.

```
useradd --system --no-create-home --shell /sbin/nologin ocskeeper
mkdir -p $OCS_HOME/java/log
chown -R ocskeeper:ocskeeper $OCS_HOME/java
chmod 750 $OCS_HOME/java
```

**확인.** 계정이 보이고, 로그인 셸이 `/sbin/nologin` 이어야 합니다.

```
id ocskeeper
getent passwd ocskeeper
```
@@end

#### {I}.12.2 프로그램 둘 장비

유지 프로그램을 돌릴 장비가 제{I}.11절에서 컴파일한 장비와 다르다면, `java` 폴더에서 `out` 폴더와 `ojdbc8.jar` 를 그 장비의 같은 모양의 폴더로 옮기십시오. `out` 은 통째로 옮기면 되고 소스와 SQL 스크립트까지 옮길 필요는 없습니다. 그 장비에도 같은 이름의 `OCS_HOME` 변수가 있어야 합니다(제{I}.1.1절).

> **참고.** 이 프로그램은 마스터 키를 쥐고 있으므로 데이터베이스 관리자의 손이 닿는 곳에 두면 키를 나누어 맡긴 뜻이 옅어집니다. 그러나 데이터베이스가 재기동된 뒤 빨리 다시 넣으려면 네트워크로 닿기 쉬워야 하므로 두 요건을 함께 보고 장비를 정하십시오.

#### {I}.12.3 설정 파일 만들기

**실행.** 예시 파일을 복사하여 이름을 `keeper.properties` 로 바꾸고 값을 채웁니다. 반드시 `java` 폴더에 두십시오.

@@win
```
copy "%OCS_HOME%\java\keeper.properties.sample" "%OCS_HOME%\java\keeper.properties"
notepad "%OCS_HOME%\java\keeper.properties"
```
@@rhel
```
cp $OCS_HOME/java/keeper.properties.sample $OCS_HOME/java/keeper.properties
vi $OCS_HOME/java/keeper.properties
```
@@end

채울 값은 넷입니다. `jdbc.url` 에 접속 문자열을, `jdbc.user` 와 `jdbc.password` 에 `OCS_KEYADM` 의 계정과 암호를, `master.key` 에 제{I}.8절에서 기록해 둔 16진 64자를 넣으십시오. `check.seconds` 는 저장소가 열려 있는지 확인하는 주기이며 기본값 30 이면 충분합니다.

**이 파일에는 마스터 키와 계정 암호가 평문으로 들어갑니다.** 만드는 즉시 다음 절로 잠그십시오. 값이 채워진 파일은 형상 관리나 공유 저장소에 올리지 마십시오.

#### {I}.12.4 설정 파일 보호

설정 파일을 전용 계정만 읽을 수 있도록 막습니다.

@@win
**실행.** 관리자 권한 명령 프롬프트에서 `icacls` 로 접근 제어 목록을 다시 짭니다. **첫 줄의 상속 제거가 핵심입니다.** 이것을 빠뜨리면 상위 폴더에서 내려온 `Users` 읽기 권한이 그대로 남아 장비에 로그인할 수 있는 누구나 마스터 키를 읽습니다.

```
icacls "%OCS_HOME%\java\keeper.properties" /inheritance:r
icacls "%OCS_HOME%\java\keeper.properties" /grant:r "ocskeeper:(R)"
icacls "%OCS_HOME%\java\keeper.properties" /grant:r "Administrators:(F)"
```

**확인.** 두 줄만 나와야 합니다. `ocskeeper:(R)` 과 `BUILTIN\Administrators:(F)` 이며, `Users` 나 `Everyone` 이나 `Authenticated Users` 가 보이면 상속 제거가 되지 않은 것입니다.

```
icacls "%OCS_HOME%\java\keeper.properties"
```

> **참고.** 윈도우에서는 프로그램이 이 보호를 대신 확인해 주지 못합니다. 유지 프로그램에는 설정 파일이 남에게 읽히면 경고를 찍는 장치가 있으나 그것은 POSIX 권한을 읽는 방식이라 윈도우에서는 아무 말 없이 지나갑니다. 그러므로 윈도우에서는 위 `icacls` 확인을 사람이 눈으로 해야 합니다. 접근 제어로 막아도 그 장비의 관리자는 소유권을 가져와 읽을 수 있으며, 이것은 파일 권한으로 해결되는 문제가 아닙니다. 관리자 수를 줄이고 누가 언제 그 장비에 들어갔는지 남기는 쪽으로 다루십시오.
>
> **잠근 뒤에 수정하려면** 일반 권한으로는 읽기도 저장도 되지 않는 것이 정상입니다. **관리자 권한 명령 프롬프트**에서 `notepad "%OCS_HOME%\java\keeper.properties"` 로 여십시오. 관리자 그룹에는 모든 권한이 있어 수정과 저장이 되고 권한은 그대로 유지됩니다. 관리자 권한 창에서도 거부되면 `takeown /f <파일>` 과 `icacls <파일> /grant:r "%USERNAME%:(M)"` 로 권한을 얻어 고친 뒤, 위 세 줄의 `icacls` 로 **반드시 다시 잠그십시오.**
@@rhel
**실행.** 소유자를 전용 계정으로 바꾼 뒤 소유자만 읽도록 막습니다.

```
chown ocskeeper:ocskeeper $OCS_HOME/java/keeper.properties
chmod 600 $OCS_HOME/java/keeper.properties
```

**확인.** `-rw-------` 와 `ocskeeper` 가 나와야 합니다.

```
ls -l $OCS_HOME/java/keeper.properties
```

> **참고.** 소유자만 읽도록 막아도 그 장비의 root 는 읽을 수 있습니다. 이것은 파일 권한으로 해결되는 문제가 아닙니다. 관리자 수를 줄이고 누가 언제 그 장비에 들어갔는지 남기는 쪽으로 다루십시오.
@@end

#### {I}.12.5 한 번 돌려 보고 상주 등록

**실행.** 상주 등록 전에 한 번만 돌려 보십시오. 설정이 틀렸으면 여기서 드러납니다. **프로그램을 둔 `java` 폴더로 옮긴 뒤에 치십시오.** `out` 과 `ojdbc8.jar` 와 `keeper.properties` 는 현재 디렉터리를 기준으로 찾습니다.

@@win
```
cd /d "%OCS_HOME%\java"
java -cp out;ojdbc8.jar ocsecure.keeper.OcsKeystoreKeeper keeper.properties --once
```
@@rhel
```
cd $OCS_HOME/java
java -cp out:ojdbc8.jar ocsecure.keeper.OcsKeystoreKeeper keeper.properties --once
```
@@end

**확인.** 저장소를 열고 바로 끝납니다. 이어서 제{I}.8절의 열림 확인이 「키 저장소 열림」으로 나와야 합니다.

@@win
**실행.** 윈도우에는 명령 프롬프트에서 띄운 프로그램이 로그아웃하면 함께 죽으므로 **작업 스케줄러에 등록합니다.** 스케줄러가 부를 배치 파일 `%OCS_HOME%\java\keeper.bat` 은 패키지에 들어 있으며 손수 만들 것이 없습니다. 이 파일은 돌기 전에 `OCS_HOME` 이 비어 있지 않은지, `java` 폴더가 있는지, 컴파일 결과물이 있는지, 드라이버와 설정 파일이 있는지를 보고, 하나라도 어긋나면 무엇이 없는지를 찍고 멈춥니다. 등록하기 전에 손으로 한 번 돌려 보십시오.

```
"%OCS_HOME%\java\keeper.bat" --once
```

아무것도 찍히지 않으면 정상이며 결과는 `log\keeper.log` 에 들어갑니다. `[ERROR]` 로 시작하는 줄이 찍히면 그 줄이 말하는 것을 먼저 갖추십시오.

이 배치 파일과 `out` 폴더도 `keeper.properties` 와 같은 요령으로 전용 계정과 관리자만 접근하도록 막으십시오. 그런 다음 관리자 권한 명령 프롬프트에서 등록합니다. 암호를 묻거든 전용 계정의 암호를 넣으십시오.

```
schtasks /create /tn "OCSecure Keystore Keeper" /tr "%OCS_HOME%\java\keeper.bat" ^
         /sc onstart /ru ocskeeper /rp * /rl HIGHEST /f
```

**`/rp *` 를 반드시 적으십시오.** 이것을 빼면 암호가 저장되지 않아 로그온 모드가 「대화형만」이 되고, 그러면 전용 계정이 로그인해 있을 때만 돌 수 있어 `schtasks /run` 이 「실행하도록 시도했습니다」라고만 하고 실제로는 뜨지 않습니다. 등록 직후 아래로 확인하십시오. 「로그온 모드」가 「대화형만」이 아니라 **「대화형/백그라운드」** 여야 합니다.

```
schtasks /query /tn "OCSecure Keystore Keeper" /v /fo list | findstr /i "로그온 상태 마지막"
```

등록이 「액세스가 거부되었습니다」로 막히면 전용 계정에 「일괄 작업으로 로그온」 권한이 없는 것이니 제{I}.12.1절의 사용자 권한 할당을 다시 보십시오.

**등록한 뒤에 반드시 한 가지를 더 고치십시오. 이것도 명령이 아니라 화면에서 하는 단계입니다.** 작업 스케줄러는 작업이 일정 시간 넘게 돌면 강제로 끝내는 설정을 기본으로 두는데, 이 프로그램은 끝나지 않고 계속 도는 것이 정상이므로 그대로 두면 며칠 뒤에 조용히 멈춥니다.

| 순서 | 할 일 |
|---|---|
| 1 | 시작 단추에서 `작업 스케줄러` 를 열고 왼쪽의 「작업 스케줄러 라이브러리」에서 `OCSecure Keystore Keeper` 를 두 번 누름 |
| 2 | 「설정」 탭에서 「작업이 다음 시간 이상 실행되면 중지」의 **체크를 해제** |
| 3 | 같은 탭에서 「작업이 실패하면 다시 시작」을 켜 두면 좋음 |
| 4 | 「확인」을 눌러 저장. 암호를 물으면 전용 계정 암호를 입력 |

해제했는지는 아래 명령으로 확인합니다. 「다음 시간 동안 실행되면 작업 중지」가 `72:00:00` 이 아니라 사용 안 함으로 나와야 합니다.

```
schtasks /query /tn "OCSecure Keystore Keeper" /v /fo list | findstr /i "중지"
```

**실행.** 지금 바로 한 번 띄워 봅니다.


```sql
 WHERE table_name = 'TB_MEMBER_ENC' ORDER BY 1, 2;
```

**전이 2 가 아니면 멈추고 제{V}.4.4절의 폐기를 하지 마십시오.** 작업을 만들 때 `ORA-00001` 이 났다면 같은 이름의 옛 작업이 있다는 뜻이고, 뒤의 건수는 그 옛 작업의 것이라 자료가 옛 키에 남아 있어도 0 으로 나올 수 있습니다. 제7.1절에서 해당 증상을 찾으십시오.

> **참고.** 작업 이름은 한 번 쓰면 남으므로 연습을 다시 할 때에는 `REHEARSAL2` 처럼 다른 이름을 쓰십시오.

**실행.**

```
ALTER SESSION SET CONTAINER = <대상PDB>;
@sql/03_grants/310_lockdown.sql
```

**확인.** 스크립트가 설정 점검 결과를 찍습니다. `APPCTX_MODE` 는 `정상` 이어야 합니다. `KEK_SOURCE` 가 `위험` 으로 나오면 마스터 키가 `GLOBAL_CTX` 방식인 것입니다. 이 표시는 시험 설치에서는 예상되지만 **운영 개통을 막는 사유**입니다. `KEK_SOURCE` 가 `EXTERNAL` 이 되기 전에는 이 시스템을 운영에 쓰지 마십시오. `SCOPED_CTX` 라면 `조건부(위험 수용 확인 필요)` 로 나오며, 제{V}.6.3절의 수용 기록이 있어야 합니다(제7.7절). 이어서 계정 상태와 감사 정책을 봅니다.

**확인.** 잠근 뒤에는 `OCS_OWNER` 로 설정을 조회할 수 없으므로 **`SYS` 로** 마지막 설정을 봅니다. `APPCTX_MODE` 가 `PROOF` 여야 합니다.

**확인.** 잠근 뒤에도 시스템이 정상으로 도는지 제{V}.3.2절의 `--data` 를 한 번 돌립니다. 소유 계정이 잠겨도 패키지는 소유자 권한으로 돌기 때문에 영향이 없어야 합니다. 예시 스키마를 만들지 않았다면 제{V}.2절의 기본 확인(통과 5)을 대신 돌리십시오. **통과 9, 실패 0** 이 기대값입니다.

#### {V}.6.5 마스터 키 운영 지침: 분리 운영과 감사 연계

외부 키 관리 서버나 하드웨어 보안 모듈을 쓸 수 없어 `SCOPED_CTX` 로 운영하고 장비를 재부팅한 뒤에도 사람이 암호를 입력할 수 없는 경우를 위한 지침입니다. 이 구조에서는 키 유지 프로그램이 읽는 설정 파일에 마스터 키가 있고, 주입한 뒤에는 데이터베이스 메모리에도 있으므로 **그 장비의 관리자와 `SYS` 는 마스터 키에 닿을 수 있습니다.** 코드로는 막을 수 없는 위험이므로, 아래 두 가지로 줄이고 사고가 났을 때 알아챌 수 있게 하며, 책임자가 제{V}.6.3절의 수용 기록에 서명하기 전에 이 지침의 현재 상태를 알려야 합니다.

**분리 운영.** 한 사람이나 한 장비가 마스터 키와 암호문을 함께 쥐지 않게 나눕니다.

| 항목 | 내용 | 확인 |
|---|---|---|
| 장비 분리 | 키 유지 프로그램은 데이터베이스 서버와 **다른 장비**에 둡니다. 데이터베이스 서버를 얻어도 설정 파일의 마스터 키는 얻지 못하게 하려는 것입니다 | 두 장비의 이름이 다른지 |
| 사람 분리 | 키 유지 프로그램 장비의 관리자, 데이터베이스 관리자(`SYS`), 키 관리 담당(`OCS_KEYADM`), 감사 담당(`OCS_AUDITOR`)을 서로 다른 사람으로 정합니다. 한 사람이 둘 이상을 맡아야 한다면 그 사실을 수용 기록에 함께 적습니다 | 담당자 명단이 겹치지 않는지 |
| 접속 경로 제한 | `OCS_KEYADM` 은 키 유지 프로그램 장비와 키 관리 작업용으로 지정한 장비에서만 접속하게 합니다. 방법으로는 접속 노드를 검증하는 리스너 설정과, 이 계정의 접속 주소를 검사하는 로그온 트리거가 있습니다. 앞의 것은 모든 계정에 한꺼번에 걸리는 거친 제한입니다. **둘 다 이 프로젝트에서 시험하지 않았으므로** 운영에 적용하기 전에 시험 환경에서 먼저 확인하고, 관리 작업이 막히지 않는지 보십시오 | 지정하지 않은 장비에서 `OCS_KEYADM` 접속이 거부되는지 |
| 설정 파일과 백업 | `keeper.properties` 에는 마스터 키가 평문으로 있습니다. 이 파일을 일반 백업에서 빼거나, 백업 매체를 암호화하고 접근을 통제합니다. 복사본을 만들거나 메신저와 메일로 보내지 마십시오 | 백업 목록에 이 파일이 없거나 보호되는지 |
| 마스터 키 이중 보관 | 제{I}.8절의 보관을 그대로 지킵니다. 이것과 별개의 일입니다 | 제{V}.6.4절 |

**감사 연계.** 마스터 키가 열리고 닫히는 일과 그 주변의 접근은 세 곳에 남습니다.

| 어디에 | 무엇이 남나 | 누가 보나 |
|---|---|---|
| `OCS_OWNER.SEC_AUDIT_LOG` | `KEYSTORE_OPEN`(저장소 열림, 마스터 키 주입)과 `KEYSTORE_CLOSE`(닫힘) 사건이 `ALERT` 수준으로 남습니다. 접속 계정, 운영체제 사용자, 장비 이름, 주소 컬럼이 함께 기록됩니다. 소스상 그렇게 되어 있으며, 이번 시험에서 이 표를 직접 조회해 확인하지는 않았습니다 | `OCS_AUDITOR` |
| 통합 감사 | `OCS_POL_KEY_TABLE`(키 표와 설정 표의 조회와 변경), `OCS_POL_OWNER_ACCESS`(소유 계정의 접속과 종료), `OCS_POL_PRIV_CHANGE`(권한 부여), `OCS_POL_DDL`(객체 변경). 소유 계정은 잠겨 있으므로 평소에는 이 계정의 접속 기록이 없어야 하고, 있다면 그 자체가 경보 대상입니다. 잠긴 계정으로의 **실패한** 접속 시도가 이 정책에 기록되는지는 확인하지 못했습니다 | `OCS_AUDITOR`, 보안 관제 |
| 키 유지 프로그램의 로그 | 「시작한다」, 「접속하고 마스터 키를 주입하였다」, 「저장소가 닫혀 있다. 다시 주입한다」, 「끊겼다」가 상태가 바뀔 때 남습니다. 키 값은 찍히지 않습니다 | 장비 관리자와 운영 담당자 |

감사 기록은 **외부 보안 관제로 즉시 전송**해야 의미가 있습니다. 감사 대상이 기록을 지울 수 있기 때문입니다(`310_lockdown.sql` 이 알리는 데이터베이스 밖의 일 가항). 이 전송은 스크립트가 해 주지 않으며 현장에서 구성해야 합니다. 감사 담당자는 아래 조회로 최근 열림과 닫힘을 볼 수 있습니다. `OCS_AUDITOR` 로 접속해 실행합니다. 조회만 합니다.

```sql
SELECT event_ts, event_type, db_user, os_user, host_name, ip_address
  FROM OCS_OWNER.SEC_AUDIT_LOG
 WHERE event_type IN ('KEYSTORE_OPEN', 'KEYSTORE_CLOSE')
 ORDER BY log_id DESC FETCH FIRST 20 ROWS ONLY;
```

**무엇을 경보로 보는가.** 아래는 출발점이며 현장의 업무 방식에 맞게 조정하십시오.

| 사건 | 정상 | 의심하고 확인할 것 |
|---|---|---|
| `KEYSTORE_CLOSE` | 계획된 점검이나 복구 시험 | 계획 없는 닫힘. 닫으면 암복호화가 멈추고 키 유지 프로그램이 다시 열기 전까지 서비스가 중단되므로 즉시 확인 |
| `KEYSTORE_OPEN` | 키 유지 프로그램 장비의 주소와 `OCS_KEYADM` 에서 찍힘. 닫힘이나 재연결 뒤에 찍힘 | 다른 주소나 다른 계정에서의 주입. 평소 하루에 몇 번 찍히는지 기준선을 먼저 파악 |
| `OCS_OWNER` 접속 | 승인된 배포나 설정 변경 때만 | 그 밖의 접속 기록 |
| `SEC_CONFIG` 변경, 특히 `KEK_SOURCE` 와 `KEK_RISK_ACK` | 승인된 변경 | 승인 문서와 대조되지 않는 변경 |

**한계.** 감사는 사고를 막지 않고 알려 줄 뿐입니다. `SYS` 가 문맥에서 값을 읽는 일처럼 위 사건으로 남지 않는 접근이 있을 수 있고, `SYS` 의 작업이 어디까지 기록되는지는 이 프로젝트에서 확인하지 않았으므로 운영 환경의 감사 설정을 따로 확인하십시오. 위 분리 운영과 감사 연계는 모두 **지침이며 이 패키지가 갖춰 주는 것이 아닙니다.** 갖추지 못한 항목은 수용 기록에 남기십시오.

### 7.2 자료 없이 교체한 키 정리

제{V}.4절의 순서가 어긋나 자료 없이 교체부터 한 경우에 제{V}.4절만 되돌리는 절차입니다. 설치를 처음부터 다시 할 일은 아닙니다. 이 절차는 제7.7절에 밝힌 대로 실제 인스턴스에서 돌려 보지 않았으므로, 운영계에서는 절차를 검토한 뒤에 진행하십시오.

**접속.** `OCS_KEYADM`. 지금 키 상태를 봅니다.

```sql
SELECT key_id, key_state, created_at FROM OCS_OWNER.V_SEC_KEY_STATUS
 WHERE domain_code = 'RRN' ORDER BY key_id;
```

**접속.** `<응용계정>`. **반드시 먼저 하십시오.** 0 이 나와야 합니다.

```sql
SELECT COUNT(*) FROM TB_MEMBER_ENC;
```

**접속.** `OCS_KEYADM`. **위가 0 일 때에만 실행하십시오.** 자료가 있는데 폐기하면 그 자료는 영영 읽을 수 없게 됩니다.

```sql
BEGIN
  FOR r IN (SELECT key_id FROM OCS_OWNER.V_SEC_KEY_STATUS
             WHERE domain_code = 'RRN' AND key_state = 'RETIRING') LOOP
    OCS_OWNER.PKG_KEY_ADMIN.retire(r.key_id);
  END LOOP;
  COMMIT;
END;
/
```

`ACTIVE` 키 하나만 남아야 합니다. 그 뒤에는 제{V}.3.3절의 `--keep` 으로 시험 자료 두 건을 다시 넣고 제{V}.4절을 처음부터 하되 재암호화 작업 이름만 `REHEARSAL2` 처럼 바꾸십시오.

### 7.3 설치 중간에 실패했을 때

SQL\*Plus 는 한 구문이 실패해도 다음 구문으로 넘어가므로, 각 단계 끝의 확인에서 기대값이 나오지 않으면 그 단계 안에서 원인을 고치고 다시 하십시오. 단계마다 다시 실행할 수 있는지가 다릅니다.

| 단계 | 다시 실행 |
|---|---|
| {I}.4 패키지(`090`~`220`) | 가능. `CREATE OR REPLACE` 이므로 실패한 파일만 다시 돌리면 됨 |
| {I}.4 테이블과 뷰(`020`, `030`) | 일부만 만들어진 상태에서는 그대로 다시 돌리면 `ORA-00955` 가 남. 만들어진 것과 빠진 것을 확인하고 빠진 구문만 실행 |
| {I}.3 계정(`010`) | 이미 있는 계정에서 `ORA-01920` 이 남. 빠진 것만 점검 조회로 찾아 실행 |
| {I}.5 권한(`300`) | 가능. 부여는 겹쳐도 무해 |
| {I}.9, {I}.10 도메인과 키 | 도메인은 가능, 증표용 키는 이미 `ACTIVE` 키가 있으면 새로 넣기 전에 폐기 여부를 판단 |

**실수로 `SYS` 에서 {I}.4 의 스크립트를 실행한 경우.** 같은 이름의 표와 뷰와 패키지와 함수가 `SYS` 스키마에 만들어진 것입니다. `OCS_OWNER` 에는 아무것도 만들어지지 않았습니다. `SYS` 로 대상 PDB 에서 아래 스크립트를 실행하면 이름 목록에 있는 `SYS` 소유 객체만 지웁니다. 지우기 전에 대상 목록을 보여 주고 `DROP` 입력을 받습니다. 목록이 이 설치에서 잘못 만든 것이 맞는지 보고 진행하십시오. 계정이나 문맥이나 역할은 건드리지 않습니다.

```
@sql/99_uninstall/991_cleanup_sys_objects.sql
```

끝의 「남은 SYS 의 암호 모듈 객체」 조회가 비어 있으면 정리가 끝난 것입니다. 이어서 `OCS_OWNER` 로 접속하여 제{I}.4절을 처음부터 다시 실행하십시오.

운영 인스턴스에서 되돌릴 수 없는 상태가 되었으면 제2.3절에서 준비한 백업·복구 지점으로 복구하십시오. 제7.4절의 제거 스크립트는 시험 인스턴스용입니다.

### 7.4 처음부터 다시 설치하기

**접속.** `SYS`.

**실행.** `DROP` 이라고 입력해야 진행됩니다. **이 스크립트는 암호 모듈과 그 아래의 모든 키와 감사 기록을 지웁니다. 키를 지우면 그 키로 암호화한 자료를 영구히 되살릴 수 없으므로 운영계에서는 절대 실행하지 마십시오.** 업무 계정(응용 스키마)과 그 안의 표와 예시 객체는 건드리지 않습니다. 예시 객체는 그 업무 계정에서 `sql/08_sample/890_drop_samples.sql` 로 따로 지웁니다.

```
@sql/99_uninstall/990_drop_all.sql
```

이 스크립트는 통합 감사 정책(`OCS_POL_...`)과 문맥과 다른 스키마의 `FN_` 시노님을 지우고, 접속 중인 세션이 있는 계정은 잠근 뒤 세션을 끊고 `OCS_OWNER`, `OCS_KEYADM`, `OCS_AUDITOR` 를 지웁니다(`SEC_CONFIG` 등 표는 `OCS_OWNER` 와 함께 사라집니다). 키 저장소 유지 프로그램이 `OCS_KEYADM` 으로 접속해 있는 경우에도 같습니다.

**확인.** 끝에 남은 계정, 역할, 문맥, 통합 감사 정책, 시노님을 보여 주며 **다섯 조회가 모두 비어 있으면** 설치 전 상태입니다. 위쪽에 `[실패]` 줄이 있으면 그 이유(오라클 오류 문구)를 풀고 같은 스크립트를 다시 실행하십시오. 다시 실행해도 안전합니다. 제{I}장부터 다시 하십시오.

데이터베이스 밖의 자원은 지워지지 않습니다. 재설치 전에 키 저장소 유지 프로그램(작업 스케줄러 작업이나 `systemd` 서비스)을 멈추고, 새 마스터 키와 새 `OCS_KEYADM` 암호에 맞게 `keeper.properties` 를 고치십시오.

**재설치 뒤 유지 프로그램을 되살리는 순서.** 순서를 바꾸지 마십시오. 파일만 고치고 프로세스를 그대로 두면 옛 마스터 키가 다시 주입됩니다.

1. 유지 프로그램을 멈춥니다. 윈도우는 관리자 권한 명령 프롬프트에서 `schtasks /end /tn "OCSecure Keystore Keeper"` 를 칩니다. 리눅스는 `sudo systemctl stop ocs-keeper` 입니다.
2. 프로세스가 정말 없는지 확인합니다. 윈도우 PowerShell 에서 `Get-CimInstance Win32_Process -Filter "Name='java.exe'" | Select-Object ProcessId,CommandLine | Format-List` 를 쳐서 `OcsKeystoreKeeper` 가 들어 있는 줄이 없어야 합니다. 있으면 그 `ProcessId` 를 `taskkill /f /pid <번호>` 로 끝냅니다. 리눅스는 `pgrep -af OcsKeystoreKeeper` 입니다. (일부 윈도우에서는 `wmic` 이 없으므로 PowerShell 을 쓰십시오. 창이 이미 PowerShell 이면 `powershell -Command` 로 감싸지 마십시오. `$_` 가 사라집니다.)
3. `keeper.properties` 의 마스터 키와 `OCS_KEYADM` 암호를 이번 설치의 값으로 고칩니다. 값은 화면에 옮겨 적지 말고 눈으로만 비교하십시오.
4. `java` 폴더에서 `--once` 로 한 번 주입합니다(제{I}.12.5절). 이 명령은 저장소가 이미 열려 있어도 무조건 덮어씁니다. 결과는 창에 「저장소가 열렸다. 설정이 올바르다.」로 나와야 합니다.
5. 제{I}.8절의 열림 확인과 제{V}.2절의 연동 확인이 통과하는지 봅니다.
6. 통과하면 그때 유지 프로그램을 다시 띄웁니다. 윈도우는 `schtasks /run /tn "OCSecure Keystore Keeper"`, 리눅스는 `sudo systemctl start ocs-keeper` 입니다. 띄운 뒤 연동 확인을 한 번 더 하여, 상주 프로그램이 이번 설정으로 돌고 있음을 확인하십시오. 재설치한 뒤에는 증표용 키(제{I}.10절)도 새로 만들어 응용 서버에 다시 전달해야 합니다.

### 7.6 설정값

설정은 `OCS_OWNER` 의 `SEC_CONFIG` 테이블에 있으며 `OCS_OWNER` 를 잠근 뒤에는 `SYS` 로 조회합니다. 설치 중에 바꾸는 것은 `KEK_SOURCE` 와 `PWD_ITERATIONS` 둘이고, 나머지는 기본값으로 둡니다. 값의 뜻과 운영 중의 변경은 별도의 관리자 매뉴얼을 보십시오.

| 설정 | 설치 시 기본값 | 설치 중 변경 | 뜻 |
|---|---|---|---|
| `KEK_SOURCE` | `EXTERNAL` | `GLOBAL_CTX`(개발·시험) 또는 `SCOPED_CTX`(운영, 외부 키 서버 없음)로 변경(제{I}.8절) | 마스터 키 반입 방식 |
| `PWD_ITERATIONS` | `10000` | 장비에 맞게 올림(제{I}.7절) | 비밀번호 키 유도 반복 횟수 |
| `APPCTX_MODE` | `PROOF` | 변경하지 않음 | 응용 문맥 설정 방식. `PROOF` 가 운영, `SIMPLE` 은 개발 전용 |
| `FAIL_DELAY_CS` | `0` | 변경하지 않음 | 복호화 실패 시 지연(1/100초) |
| `LEGACY_PWD_CHARSET` | `AL32UTF8` | 변경하지 않음 | 기존 비밀번호 체계의 문자집합. 기존 체계를 이행할 때 확정 |

이 밖에 `APPCTX_WINDOW_SEC` 과 `USAGE_BUCKET_MIN` 이 설정에 있습니다. 모든 설정의 목록은 `SELECT cfg_key, cfg_value, description FROM SEC_CONFIG` 로 볼 수 있습니다.

### 7.7 검증 범위와 알려진 제한

| 구분 | 내용 |
|---|---|
| 확인한 것 | 윈도우에서 오라클 19c 멀티테넌트(`KO16MSWIN949`)에 단계별로 설치하며 기대값을 확인했습니다. 가장 최근의 시험(새 PC, 이 판의 패키지)에서는 증표용 키 입력 점검, 마스터 키 복구, 자바 연동 확인, 업무 스키마 예시, 키 교체와 재암호화와 옛 키 폐기, 복호화 자격 부여와 회수, 예시 객체 제거, 소유 계정 잠금과 감사 정책, 개통 판정(`320`, 마스터 키 방식만 「불가」)까지 결과를 확인했습니다. 업무 계정에는 `FN_` 시노님 25개가 연결되어 있었고(`480` 의 결과), 개발 모드를 켜고 끄는 `910`·`911` 도 정상이었으며 껐을 때 연동 확인(통과 5)과 개통 판정(`320`)이 다시 통과했습니다. 키 유지 프로그램의 복구 시험은 이 판에서는 저장소 닫기만 확인했고, 데이터베이스 재기동과 장비 재부팅은 이전 판에서 확인했습니다. 시험 중 찾은 결함을 고친 판으로 처음부터 한 번에 이어서 다시 설치한 시험은 하지 않았습니다 |
| 운영용 한정 | `OCS_OWNER` 의 `USERS QUOTA UNLIMITED` 는 개발·시험 기본값입니다. 운영 배포에서는 현장의 테이블스페이스와 quota 로 바꾸어야 합니다 |
| 검증되지 않은 것 | 리눅스(RHEL)에서의 설치 전체(제5장, 제6장)와 systemd 단위. 운영 장비. 이 판에서 결과를 확인하지 못한 스크립트(사용 예시 `810`, 자체 시험 `902`, 제거 `990`·`991`). 함수 이름 호출(`FN_ENC_…`)은 개발 모드(`910`)에서 문맥을 세운 SQL*Plus 세션으로만 확인했고, 운영 방식(증표 제출)으로 문맥을 세운 응용 세션에서 `FN_` 함수를 부르는 경로는 확인하지 못했습니다. 이 판에서의 복구 시험 중 데이터베이스 재기동과 장비 재부팅. 외부 키 관리 서버(`EXTERNAL`)에서 마스터 키를 읽는 경로(구현되어 있지 않음). 제7.2절의 되돌리기 절차. `810_usage_examples.sql` 중 복호화 자격이 있는 상태에서 도는 부분 |
| `GLOBAL_CTX` 방식 | 마스터 키를 사람이 만들어 직접 주입하는 방식이며 **개발과 시험 전용으로, 운영 개통에는 쓸 수 없습니다.** 마스터 키가 데이터베이스 전역 문맥에 올라가며 이 구현은 사용자를 한정하지 않아 다른 데이터베이스 계정도 읽을 수 있고, 유지 프로그램의 설정 파일에도 평문으로 남습니다. `310_lockdown.sql` 이 `위험` 으로 표시합니다. `EXTERNAL` 방식의 키 읽기 구현은 이 패키지에 없으므로, **현재 패키지는 개발·시험 설치용이며 운영용 키 관리까지 완성된 것이 아닙니다.** 키 관리 서버나 하드웨어 보안 모듈이 준비되면 `EXTERNAL` 로 바꾸고 `PKG_KEK_PROVIDER.load_from_external` 을 구현하면 되며, 그때 자료를 다시 암호화할 필요는 없습니다. 마스터 키는 데이터 키를 감싸는 데만 쓰므로 감싼 값만 다시 만들면 됩니다 |
| `SCOPED_CTX` 방식 | 외부 키 관리 서버나 하드웨어 보안 모듈을 도입할 수 없는 운영을 위한 방식입니다. 마스터 키를 전역 문맥에 올리되 설치마다 다른 무작위 토큰을 클라이언트 식별자로 지정해, 토큰을 모르는 응용 계정이 읽지 못하게 합니다. **시험 PC 한 대에서 다음을 확인했습니다.** 이전 방식(`GLOBAL_CTX`)에서는 업무 계정이 `SYS_CONTEXT` 로 마스터 키의 존재를 볼 수 있었고, 이 방식으로 올린 뒤에는 보이지 않았습니다. 패키지는 오류 없이 컴파일되었고 업무 확인(통과 5)이 정상이었으며, 저장소를 닫았을 때 키 유지 프로그램이 약 1분 안에 다시 열고 그 뒤에도 업무 계정에 보이지 않았습니다. 개통 판정은 위험 수용 기록이 없을 때 「불가」, 기록이 있을 때 「통과」였습니다. **확인하지 못한 것:** 운영 장비에서의 동작, 데이터베이스 재기동과 장비 재부팅 뒤의 복구, 리눅스, 외부 인증이나 점검에서 이 방식이 인정되는지. **이 방식은 `SYS` 와 소유 계정을 쥔 사람, 키 유지 프로그램이 있는 장비의 관리자를 막지 못하며, 설정 파일에 마스터 키가 평문으로 남는 한계도 그대로입니다.** 개통 판정은 위험 수용 기록(`KEK_RISK_ACK`)이 있을 때만 통과합니다 |
| 비밀번호 반복 횟수 | 비밀번호 해시는 PL/SQL 로 계산하므로 같은 계산을 자바에서 하는 것보다 느립니다. 그래서 장비에 따라 허용 시간 안에 들어오는 반복 횟수가 국제적으로 권고되는 수준에 못 미칠 수 있습니다. 권고 수준은 해마다 바뀌므로 인증 대응 시에는 최신 문서로 확인하십시오. 자바 연동 모듈이 PL/SQL 과 바이트 단위로 같은 값을 내므로 계산을 응용 쪽으로 옮기는 선택지가 있고, 개통 전에 결정하십시오 |
| 키 유지 프로그램의 윈도우 등록 | 작업 스케줄러 방식입니다. 진짜 윈도우 서비스로 등록하려면 자바 프로그램을 서비스로 감싸 주는 별도 도구가 필요합니다 |
| 마스터 키의 한계 | 접근 제어로 막아도 설정 파일이 있는 장비의 관리자는 소유권을 가져와 읽을 수 있습니다. 이것은 파일 권한으로 해결되는 문제가 아니며 근본적으로는 `EXTERNAL` 로 옮겨야 합니다 |

### 7.10 개발자가 함수 이름으로 호출하게 하기

업무 계정을 연결하면(제{I}.5.1절) 그 계정에서는 `OCS_OWNER.PKG_SECURE_API.enc_rrn(...)` 처럼 소유자와 패키지 이름을 붙여 부르는 방법과, `FN_ENC_RRN(...)` 처럼 **짧은 함수 이름**만으로 부르는 방법을 모두 쓸 수 있습니다. 짧은 이름은 설치가 만든 단독 함수(`FN_` 으로 시작, 25개)이며 `PKG_SECURE_API` 의 같은 이름 함수를 그대로 부를 뿐이므로, 증표 검증과 복호화 자격과 마스킹과 감사는 달라지지 않습니다. 이름 규칙은 `FN_` 뒤에 패키지 함수 이름을 대문자로 붙인 것입니다.

| 패키지 함수 | 짧은 함수 이름 | 하는 일 |
|---|---|---|
| `enc_rrn`, `dec_rrn`, `mask_rrn`, `idx_rrn` | `FN_ENC_RRN`, `FN_DEC_RRN`, `FN_MASK_RRN`, `FN_IDX_RRN` | 주민등록번호 암호화, 복호화, 마스킹, 검색용 색인 |
| `enc_name`, `dec_name`, `mask_name`, `idx_name` | `FN_ENC_NAME`, `FN_DEC_NAME`, `FN_MASK_NAME`, `FN_IDX_NAME` | 성명 |
| `enc_account`, `dec_account`, `mask_account`, `idx_account` | `FN_ENC_ACCOUNT`, `FN_DEC_ACCOUNT`, `FN_MASK_ACCOUNT`, `FN_IDX_ACCOUNT` | 계좌번호 |
| `protect`, `reveal`, `masked`, `show`, `search_of`, `allowed` | `FN_PROTECT`, `FN_REVEAL`, `FN_MASKED`, `FN_SHOW`, `FN_SEARCH_OF`, `FN_ALLOWED` | 도메인 코드를 인자로 받는 일반형 |
| `make_pwd`, `verify_pwd`, `pwd_stale`, `make_pwd_str`, `check_pwd`, `pwd_state` | `FN_MAKE_PWD`, `FN_VERIFY_PWD`, `FN_PWD_STALE`, `FN_MAKE_PWD_STR`, `FN_CHECK_PWD`, `FN_PWD_STATE` | 비밀번호 해시와 검증 |
| `ready` | `FN_READY` | 암복호화가 가능한 상태인지 |

세션을 세우는 `login`, `logout` 은 함수가 아니라 프로시저이므로 패키지 이름으로 부릅니다.

**업무 계정을 더 연결하려면** 제{I}.5.1절의 `480_connect_app_schema.sql` 을 그 계정마다 한 번씩 실행합니다. 다시 실행해도 안전합니다.

연결 직후 그 계정으로 접속해 호출이 이름만으로 풀리는지 봅니다. 응용 문맥이 아직 없으면 `-20521` 로 거부되는 것이 정상이며, 이 오류가 나왔다는 것은 함수 이름이 풀려 `PKG_SECURE_API` 까지 도달했다는 뜻입니다. `ORA-00904` 나 `ORA-00942` 가 나오면 시노님이나 권한이 없는 것입니다.

```sql
SELECT FN_ALLOWED('RRN') FROM DUAL;
```

개발자는 이렇게 씁니다. 응용 문맥을 세운 세션에서의 예입니다.

```sql
INSERT INTO 내테이블 (id, rrn_enc, rrn_idx)
VALUES (1, FN_ENC_RRN(:rrn), FN_IDX_RRN(:rrn));

SELECT FN_SHOW('RRN', rrn_enc) FROM 내테이블 WHERE rrn_idx = FN_IDX_RRN(:rrn);
```

연결을 거두려면 그 계정에서 `DROP SYNONYM <함수 이름>` 을 하고 `SYS` 로 `REVOKE EXECUTE ON OCS_OWNER.<함수 이름> FROM <응용계정>`, `REVOKE EXECUTE ON OCS_OWNER.PKG_SECURE_API FROM <응용계정>`, `REVOKE OCS_ROLE_APP FROM <응용계정>` 을 합니다. 제7.4절의 제거 스크립트는 다른 스키마의 이 시노님도 함께 지웁니다.

> **참고.** 호출마다 단독 함수에서 패키지로 PL/SQL 호출이 한 번 더 들어갑니다. 한 쿼리가 많은 행에 `FN_DEC_` 나 `FN_SHOW` 를 부르는 곳은 필요한 행과 컬럼만 대상으로 줄이십시오. 이 점은 패키지를 직접 부를 때와 같습니다.

### 7.11 개발·시험 인스턴스에서 빠르게 시험하기

증표 키를 쓰는 운영 방식은 시험하기에 까다로우므로, 시험 인스턴스에서는 `sql/09_test/910_dev_mode_on.sql` 로 증표 검증을 잠시 끄고 `login('이름')` 한 줄로 문맥을 세워 바로 암복호화를 해 볼 수 있습니다. 끝나면 `911_dev_mode_off.sql` 로 반드시 되돌립니다. **운영 인스턴스에서는 쓰지 마십시오.** 켜 둔 채로는 운영 개통 판정(`320_golive_check.sql`)이 「불가」로 나옵니다. 개발 모드의 사용법은 별도의 개발 모드 빠른 시작 문서에 있습니다.

## 8. 요약

설치는 대상 확인과 환경 점검, 계정과 역할, 스키마와 패키지, 권한 부여, 자체 시험, 반복 횟수, 마스터 키, 도메인과 키, 증표용 키, 자바 모듈 준비, 키 저장소 유지 프로그램의 순서로 진행하며, 각 단계마다 기대값이 정해져 있어 맞지 않으면 다음으로 넘어가지 않는 것이 원칙입니다. 설치가 끝나면 통제 확인, 연동 확인, 예시 스키마 확인, 키 교체 연습, 복구 시험을 거쳐 시험용 표를 지우고 소유 계정을 잠급니다.

가장 빠뜨리기 쉬운 것은 제{I}.5절의 권한 부여입니다. 건너뛰면 뒤의 거의 모든 단계가 막히는데 증상이 권한 문제로 보이지 않아 원인을 찾기 어렵습니다. 가장 중요한 것은 제{I}.8절의 마스터 키 보관입니다. 잃으면 암호화한 자료를 되살릴 방법이 없습니다. 운영계에서는 `902_selftest.sql` 과 `990_drop_all.sql` 을 실행하지 마십시오.
