## 0. 이 문서를 읽는 법

대상은 이 시스템을 이용해 **자바 프로그램 또는 PL/SQL 프로그램**을 개발하는 사람이다. 개인정보(주민등록번호, 성명, 연락처, 계좌번호 등)를 저장하고 조회하고 검색하는 일, 그리고 비밀번호를 다루는 일을 모두 포함한다. 운영과 키 관리는 유지보수 매뉴얼에, 설치는 설치 매뉴얼에 있다.

이 문서는 **작업의 순서**로 쓰였다. 처음 쓰는 사람은 제1장부터 제3장까지 읽고 제3장의 예제를 한 번 돌려 보면 전체 모양이 잡힌다. 그다음에는 만들 기능에 맞는 절을 찾아 읽으면 된다.

| 하려는 일 | 읽을 곳 |
|---|---|
| 처음이라 전체 모양을 알고 싶다 | 제1장, 제3장 |
| 개발을 시작하기 전에 받아야 할 것을 알고 싶다 | 제2장 |
| 새 테이블에 암호화 컬럼을 넣는다 | 제4.1절 |
| 회원 가입, 상세 보기, 목록, 검색, 수정, 삭제를 만든다 | 제4.2절 ~ 제4.6절 |
| 조인, 집계, 대량 처리를 만든다 | 제4.7절, 제4.8절 |
| 로그인과 비밀번호 변경을 만든다 | 제5장 |
| 연결 풀이나 스프링에 세션 등록 처리를 넣는다 | 제6장 |
| 전자정부 표준프레임워크와 MyBatis 로 개발한다 | 제7장 |
| 저장 프로시저를 만든다 | 제8장 |
| 오류가 났다 | 제9장 |
| 금지 사항을 확인한다 | 제10장 |
| 함수 목록과 규격이 필요하다 | 제11장 |
| 기존 시스템의 비밀번호를 옮겨 와야 한다 | 제13장 |
| 개발용 인스턴스에서 증표 키 없이 빨리 해 보고 싶다 | 제14장 |

본문의 표시는 다음과 같다.

| 표시 | 뜻 |
|---|---|
| **할 일** | 개발할 때 실제로 해야 하는 것 |
| **확인** | 무엇이 나와야 정상인가 |
| **주의** | 어기면 사고가 나는 것 |
| 인용 표시(`>`) 「설명」 | 이유와 배경. **읽지 않아도 개발은 된다** |

예시의 함수 호출은 **짧은 이름(`FN_` 으로 시작하는 함수)을 기본**으로 적었다. 패키지 이름을 붙인 긴 호출(`OCS_OWNER.PKG_SECURE_API.enc_rrn(...)`)은 같은 동작의 보조 방법이다(제11.3절).

## 1. 먼저 알아둘 것

### 1.1 개발자가 하는 일

이 시스템은 오라클 테이블의 컬럼을 암호화하는 기능을 **데이터베이스 함수**로 제공한다. 개발자는 SQL 안에서 `FN_ENC_RRN(...)` 처럼 함수를 부르기만 하면 된다. 암호화에 쓰는 키는 데이터베이스가 쥐고 있으며 **애플리케이션은 키를 갖지 않는다.** 그래서 앱 서버가 침해되어도 키는 나가지 않는다.

대신 정당한 응용만 이 함수를 쓰게 하려고 **세션 등록**이라는 절차가 하나 있다. 데이터베이스 연결을 쓰기 전에 "이 연결은 정당한 응용이 쓰고, 지금 쓰는 업무 사용자는 이 사람이다"라고 한 번 알려 주는 일이다. 출입증을 한 번 찍고 들어가는 것과 같다. 등록하지 않은 연결에서는 암호화와 복호화가 거부된다(`ORA-20521`). 코드에서는 `establish` 한 줄로 등록하고 `release` 한 줄로 해제한다. 자바에서는 연동 모듈이 이 일을 대신한다.

```
응용 서버
 ① 연결 풀에서 DB 연결을 얻는다     dataSource.getConnection()
 ② 세션을 등록한다                  session.establish(con, 업무사용자)    ← 이 연결에서만 유효하다
 ③ 평소처럼 SQL 을 실행한다          INSERT ... FN_ENC_RRN(?)  /  SELECT FN_SHOW('RRN', ...)
 ④ 등록을 해제하고 연결을 닫는다     session.release(con) 다음에 con.close()   ← finally 에서 반드시
```

개발자가 만드는 것은 대부분 ③이다. ②와 ④는 한곳에 모아 두면 업무 코드에서는 신경 쓸 일이 없다(제6장).

### 1.2 반드시 지킬 여덟 가지

| # | 규칙 | 어기면 |
|---|---|---|
| 1 | 호출할 패키지는 `OCS_OWNER.PKG_SECURE_API` **하나뿐**이다 | 하위 계층은 권한이 없어 호출 불가 |
| 2 | 암복호화는 **데이터베이스가 한다**. 애플리케이션은 키를 갖지 않는다 | 앱 서버가 침해되면 키까지 잃음 |
| 3 | 세션마다 **세션 등록**을 하고, 연결을 닫기 전에 **`finally` 에서 등록을 해제한다** | 암호화·복호화 거부(`ORA-20521`) 또는 **앞 사용자의 등록을 이어받음** |
| 4 | 암호문 컬럼과 **색인 컬럼을 함께** 채운다 | 그 행은 이후 검색되지 않음 |
| 5 | 검색은 **색인 컬럼**으로 한다. 암호화 컬럼을 조건절에 쓰지 않는다 | 전 행 복호화 → 성능 붕괴, 임계치 차단 |
| 6 | 암복호화 호출의 **예외를 삼키지 않는다** | 암호문 자리에 널이 들어가고 뒤늦게 발견됨 |
| 7 | 로그·세션·캐시에 **평문을 남기지 않는다** | 암호화의 의미가 사라짐 |
| 8 | 비밀번호는 **양방향으로 암호화하지 않는다**. 전용 함수를 쓴다 | 복구 가능 = 누군가 꺼내 볼 수 있음 |

> **설명.** 규칙 1·2 는 설계의 토대이다. 복호화 요청이 정책 계층(세션 등록, 자격, 사용량 판정)을 우회할 수 없는 것은 하위 계층에 어떤 계정도 실행 권한이 없기 때문이다. 편의를 위해 이 구조를 우회하는 코드를 만들면 통제가 통째로 무너진다.

## 2. 개발을 시작하기 전에

### 2.1 받아야 할 것

**할 일.** 개발을 시작하기 전에 아래를 확인하고, 없는 것은 해당 담당자에게 요청하라.

| 필요한 것 | 누구에게 | 확인 방법 |
|---|---|---|
| 응용 계정이 `PKG_SECURE_API` 를 **직접** 실행할 수 있음 | 키 관리자 | `SELECT OCS_OWNER.PKG_SECURE_API.ready FROM DUAL;` 가 `1` |
| 쓸 **도메인**이 등록되어 있음 | 키 관리자 | 도메인 코드(`RRN`, `NAME`, `PHONE`, `ACCOUNT` 등)를 문의 |
| 업무 계정에 **짧은 이름 함수가 연결**되어 있음 | 키 관리자·설치 담당자 | `SELECT COUNT(*) FROM user_synonyms WHERE synonym_name LIKE 'FN\_%' ESCAPE '\';` 가 `25` (설치 매뉴얼의 업무 계정 연결 `480`) |
| 복호화가 필요하면 **복호화 자격** | 키 관리자 | 자격이 없으면 마스킹된 값만 나옴(오류 아님) |
| **증표 키**(운영) | 키 관리자·보안 담당자 | 앱 서버 설정에 안전하게 주입. 소스·설정 파일 평문 금지 |
| 개발 환경의 `APPCTX_MODE` | 키 관리자 | 개발은 `SIMPLE`(증표 없이 세션 등록), 운영은 `PROOF` |

**주의.** 응용 계정이 PL/SQL 객체(뷰, 프로시저, 트리거)에서 `PKG_SECURE_API` 를 부르려면 실행 권한이 **역할이 아니라 계정에 직접** 부여되어 있어야 한다. 역할로 받은 권한은 저장 객체 안에서 인정되지 않는다. 설치 스크립트가 이를 이미 직접 부여한다. 컴파일 오류 `PLS-00201` 이 나면 키 관리자에게 알리라.

### 2.2 확인

준비가 되었는지는 업무 계정으로 접속해 아래 세 줄로 본다. 모두 기대값이 나와야 개발을 시작할 수 있다.

```sql
SELECT OCS_OWNER.PKG_SECURE_API.ready FROM DUAL;                                  -- 1
SELECT COUNT(*) FROM user_synonyms WHERE synonym_name LIKE 'FN\_%' ESCAPE '\';    -- 25
SELECT FN_ALLOWED('RRN') FROM DUAL;                                               -- Y 또는 N
```

첫째가 `0` 이면 마스터 키가 닫혀 있는 것이므로 키 관리자에게 알린다. 둘째가 `25` 가 아니면 업무 계정이 아직 연결되지 않은 것이다. 셋째는 세션 등록이 없으면 `N` 으로 나오는 것이 정상이며 오류가 아니다.

## 3. 첫 프로그램: 저장하고 읽기

가입, 상세 보기, 목록, 검색, 수정, 비밀번호 확인, 삭제를 한 파일에 담은 예제다. 이것을 돌려 보면 이 시스템으로 개발하는 일의 전체 흐름을 한 번에 볼 수 있다. 업무 코드는 이 파일의 메서드를 그대로 가져다 고쳐 쓰면 된다.

### 3.1 준비

예제는 업무 계정에 시험용 회원 테이블 `TB_MEMBER` 가 있다고 전제한다. 키 관리자 또는 설치 담당자가 업무 계정으로 아래 스크립트를 한 번 실행해 두면 된다. 이 스크립트는 암호문을 담는 실제 테이블 `TB_MEMBER_ENC`, 옛 이름 그대로 쓰는 투명화 뷰 `TB_MEMBER`, 평문을 넣으면 암호화해 주는 트리거를 만든다.

```
@sql/08_sample/800_sample_member.sql
```

이미 같은 이름의 객체가 있으면 실행하지 마라. 실제 업무 테이블에 적용하는 방법은 제4.1절에 있다.

### 3.2 예제 프로그램

파일 위치는 `java/src/example/java/ocsecure/example/MemberExample.java` 이다. 전체는 아래와 같다.

```java
package ocsecure.example;

import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;

import ocsecure.client.OcsAppProof;
import ocsecure.client.OcsCrypto;
import ocsecure.client.OcsSessionSupport;

/**
 * 개발자 매뉴얼 제3장의 예제. 연결을 얻고, 세션을 등록하고, 저장하고, 읽고, 찾고, 고치고,
 * 지우고, 등록을 해제하는 흐름을 한 파일에 담았다.
 *
 * <p>전제. 업무 계정에 sql/08_sample/800_sample_member.sql 로 TB_MEMBER 가 만들어져 있어야 한다.
 * 이 예제는 TB_MEMBER 의 투명화 뷰와 원본 표 TB_MEMBER_ENC 를 쓴다. 값은 모두 시험용으로 만든
 * 값이며 실제 개인정보가 아니다.
 *
 * <p>실행. 암호와 증표 키 자리의 하이픈(-)은 화면에 보이지 않게 입력받는다는 뜻이다.
 * <pre>
 *   java -cp out;ojdbc8.jar ocsecure.example.MemberExample "jdbc:oracle:thin:@호스트:포트/서비스명" 계정 - -
 * </pre>
 *
 * <p>실제 응용에서는 DriverManager 대신 연결 풀(DataSource)에서 DB 연결을 얻고, 증표 키는
 * 키 관리 제품이나 기동 시점에 주입되는 값에서 읽는다. 세션 등록과 해제 부분(establish,
 * release)이 이 예제의 핵심이다.
 */
public final class MemberExample {

    private static final long ID = 9301L;

    private static String secret(String arg, String prompt) {
        if (!"-".equals(arg)) {
            return arg;
        }
        java.io.Console c = System.console();
        if (c == null) {
            throw new IllegalStateException("콘솔이 없어 비밀값을 입력받을 수 없다. 명령 프롬프트에서 실행하라.");
        }
        return new String(c.readPassword("%s", prompt));
    }

    /** 가입. 뷰에 평문을 넣으면 트리거가 암호화와 색인 생성을 대신한다. 비밀번호는 전용 함수로 만든다. */
    static int insertMember(Connection con, long id, String name, String rrn, String phone, String pwd)
            throws SQLException {
        String sql = "INSERT INTO TB_MEMBER (mbr_id, mbr_name, mbr_rrn, mbr_phone, mbr_pwd)"
                   + " VALUES (?, ?, ?, ?, FN_MAKE_PWD(?))";
        try (PreparedStatement ps = con.prepareStatement(sql)) {
            ps.setLong(1, id);
            ps.setString(2, name);
            ps.setString(3, rrn);
            ps.setString(4, phone);
            ps.setString(5, pwd);
            return ps.executeUpdate();
        }
    }

    /** 상세. 평문 컬럼은 복호화 자격이 있으면 평문, 없으면 마스킹 값이다. 오류가 아니다. */
    static void printDetail(Connection con, long id) throws SQLException {
        String sql = "SELECT mbr_name, mbr_rrn, mbr_phone FROM TB_MEMBER WHERE mbr_id = ?";
        try (PreparedStatement ps = con.prepareStatement(sql)) {
            ps.setLong(1, id);
            try (ResultSet rs = ps.executeQuery()) {
                while (rs.next()) {
                    System.out.println("  상세  성명=" + rs.getString(1) + "  주민등록번호=" + rs.getString(2)
                            + "  연락처=" + rs.getString(3));
                }
            }
        }
    }

    /** 목록. 안쪽에서 먼저 자르고 바깥에서 마스킹 함수를 건다. 행마다 복호화하지 않는다. */
    static void printList(Connection con, int first, int size) throws SQLException {
        String sql = "SELECT t.mbr_id, FN_MASKED('RRN', t.mbr_rrn_enc) AS rrn_masked"
                   + "  FROM (SELECT mbr_id, mbr_rrn_enc FROM TB_MEMBER_ENC"
                   + "         ORDER BY mbr_id OFFSET ? ROWS FETCH NEXT ? ROWS ONLY) t"
                   + " ORDER BY t.mbr_id";
        try (PreparedStatement ps = con.prepareStatement(sql)) {
            ps.setInt(1, first);
            ps.setInt(2, size);
            try (ResultSet rs = ps.executeQuery()) {
                while (rs.next()) {
                    System.out.println("  목록  번호=" + rs.getLong(1) + "  주민등록번호=" + rs.getString(2));
                }
            }
        }
    }

    /** 검색. 암호화 컬럼이 아니라 색인 컬럼으로 찾는다. 구분자가 있든 없든 같은 행이 나온다. */
    static int countByRrn(Connection con, String rrn) throws SQLException {
        String sql = "SELECT COUNT(*) FROM TB_MEMBER_ENC WHERE mbr_rrn_idx = FN_IDX_RRN(?)";
        try (PreparedStatement ps = con.prepareStatement(sql)) {
            ps.setString(1, rrn);
            try (ResultSet rs = ps.executeQuery()) {
                rs.next();
                return rs.getInt(1);
            }
        }
    }

    /** 수정. 바뀐 컬럼만 트리거가 다시 암호화한다. */
    static int updatePhone(Connection con, long id, String phone) throws SQLException {
        try (PreparedStatement ps = con.prepareStatement("UPDATE TB_MEMBER SET mbr_phone = ? WHERE mbr_id = ?")) {
            ps.setString(1, phone);
            ps.setLong(2, id);
            return ps.executeUpdate();
        }
    }

    /** 로그인 검증. 1 일치, 0 불일치, 조회 결과 없음은 없는 사용자. */
    static int checkPassword(Connection con, long id, String input) throws SQLException {
        try (PreparedStatement ps = con.prepareStatement(
                "SELECT FN_VERIFY_PWD(?, mbr_pwd) FROM TB_MEMBER_ENC WHERE mbr_id = ?")) {
            ps.setString(1, input);
            ps.setLong(2, id);
            try (ResultSet rs = ps.executeQuery()) {
                return rs.next() ? rs.getInt(1) : -1;
            }
        }
    }

    static int delete(Connection con, long id) throws SQLException {
        try (PreparedStatement ps = con.prepareStatement("DELETE FROM TB_MEMBER WHERE mbr_id = ?")) {
            ps.setLong(1, id);
            return ps.executeUpdate();
        }
    }

    public static void main(String[] args) throws Exception {
        if (args.length < 4) {
            System.out.println("사용법: MemberExample <jdbcUrl> <사용자> <암호|-> <증표키16진|->");
            System.exit(2);
        }
        String pwd = secret(args[2], "응용 계정 암호: ");
        String keyHex = secret(args[3], "증표 키(16진 64자): ").trim();

        // 기동 시 한 번 만든다.
        OcsSessionSupport session = new OcsSessionSupport(new OcsAppProof(OcsCrypto.fromHex(keyHex)));

        try (Connection con = DriverManager.getConnection(args[0], args[1], pwd)) {
            con.setAutoCommit(false);
            // DB 연결을 얻을 때마다 세션을 등록한다. 업무 사용자 식별자는 데이터베이스 계정이 아니라 실제 사용자다.
            session.establish(con, "member.admin");
            try {
                delete(con, ID);   // 이전 실행이 남긴 자료가 있으면 지운다.

                System.out.println("  가입  " + insertMember(con, ID, "홍길동", "880101-1234567", "010-1234-5678", "Pw#12345") + "건");
                con.commit();

                printDetail(con, ID);
                printList(con, 0, 10);

                System.out.println("  검색  구분자 있음=" + countByRrn(con, "880101-1234567")
                        + "건  구분자 없음=" + countByRrn(con, "8801011234567") + "건");

                System.out.println("  수정  " + updatePhone(con, ID, "010-9999-8888") + "건");
                con.commit();

                System.out.println("  비밀번호  맞는 값=" + checkPassword(con, ID, "Pw#12345")
                        + "  틀린 값=" + checkPassword(con, ID, "wrong") + "  없는 사용자=" + checkPassword(con, ID + 1, "x"));

                System.out.println("  삭제  " + delete(con, ID) + "건");
                con.commit();
            } catch (SQLException e) {
                // 삼키지 않는다. 되돌리고 다시 던진다.
                con.rollback();
                throw e;
            } finally {
                // 연결을 닫기 전에 반드시 등록을 해제한다. 해제하지 않으면 풀의 다음 사용자가 앞 사용자의 등록을 이어받는다.
                if (!session.release(con)) {
                    System.out.println("  [경고] 세션 등록을 해제하지 못하였다.");
                }
            }
        }
    }
}
```

설치 매뉴얼에서 자바 프로그램을 컴파일해 두었다면 `out` 폴더가 있다. 예제 파일만 추가로 컴파일해 실행한다. 윈도우 기준이며 `java` 폴더에서 친다.

```
cd /d C:\ocsecure\java
javac -encoding UTF-8 -cp out;ojdbc8.jar -d out src\example\java\ocsecure\example\MemberExample.java
java -cp out;ojdbc8.jar ocsecure.example.MemberExample "jdbc:oracle:thin:@호스트:포트/서비스명" <업무계정> - -
```

끝의 하이픈 두 개는 업무 계정 암호와 증표 키를 화면에 보이지 않게 물어보라는 뜻이다. 차례로 입력한다. 증표 키는 설치 때 응용 서버 담당자에게 전달된 세 번째 값이다.

### 3.4 결과 읽기

복호화 자격이 없는 계정이면 아래와 같이 나온다.

```
  가입  1건
  상세  성명=홍*동  주민등록번호=880101-1******  연락처=010******5678
  목록  번호=9301  주민등록번호=880101-1******
  검색  구분자 있음=1건  구분자 없음=1건
  수정  1건
  비밀번호  맞는 값=1  틀린 값=0  없는 사용자=-1
  삭제  1건
```

**상세의 값이 마스킹으로 나오는 것은 오류가 아니다.** 평문을 볼 자격이 없으면 `FN_SHOW` 가 자동으로 마스킹된 값을 돌려준다. 평문이 필요한 화면이라면 키 관리자에게 그 도메인의 복호화 자격을 요청한다(제4.3절). 자격을 받고 다시 돌리면 상세에 평문이 나온다.

**검색**은 구분자 있는 값과 없는 값이 같은 한 건을 찾는다. 색인이 입력을 다듬은 뒤 계산하기 때문이다. **비밀번호**는 맞는 값이 `1`, 틀린 값이 `0`, 조회 결과가 없는 사용자가 `-1` 이다(예제에서만 쓰는 표시이며 제5장 참조).

### 3.5 이 예제에서 볼 곳

| 보는 곳 | 의미 | 자세한 설명 |
|---|---|---|
| `new OcsSessionSupport(new OcsAppProof(키))` | 기동 시 한 번 만든다. 증표 키를 키 관리 제품에서 읽는 자리다 | 제6.1절 |
| `session.establish(con, ...)` | DB 연결을 얻을 때마다 세션을 등록한다 | 제6.1절 |
| `INSERT INTO TB_MEMBER ... FN_MAKE_PWD(?)` | 평문을 바인드 변수로 넣는다. 트리거가 암호화와 색인을 채운다. 비밀번호는 전용 함수 | 제4.2절, 제5장 |
| `SELECT mbr_name, mbr_rrn ... FROM TB_MEMBER` | 상세. 자격이 있으면 평문, 없으면 마스킹 | 제4.3절 |
| 안쪽에서 `OFFSET ... FETCH`, 바깥에서 `FN_MASKED` | 목록. 먼저 자르고 나서 함수를 건다 | 제4.4절 |
| `WHERE mbr_rrn_idx = FN_IDX_RRN(?)` | 검색. 암호화 컬럼이 아니라 색인 컬럼 | 제4.5절 |
| `catch ... rollback ... throw` | 예외를 삼키지 않는다 | 제9.1절 |
| `finally ... release` | 연결을 닫기 전에 반드시 등록을 해제한다 | 제6.1절 |

## 4. 기능별 구현

### 4.1 테이블을 설계할 때

업무 테이블의 개인정보 컬럼은 **암호문 컬럼과 색인 컬럼 한 쌍**으로 바꾼다. 평문 컬럼은 두지 않는다.

| 평문이던 컬럼 | 바꾼 모양 | 비고 |
|---|---|---|
| `mbr_rrn VARCHAR2(14)` | `mbr_rrn_enc RAW(256)`, `mbr_rrn_idx RAW(32)` | 검색할 일이 있으면 색인을 둔다 |
| `mbr_name VARCHAR2(30)` | `mbr_name_enc RAW(256)`, `mbr_name_idx RAW(32)` | 성명으로 찾을 일이 있으면 색인 |
| `mbr_phone VARCHAR2(20)` | `mbr_phone_enc RAW(256)` | 찾을 일이 없으면 색인을 두지 않는다 |
| `mbr_pwd VARCHAR2(50)` | `mbr_pwd RAW(64)` | 비밀번호는 암호문이 아니라 일방향 저장값(제5장) |

**할 일.** 암호문과 색인과 비밀번호의 크기는 아래로 잡는다.

| 컬럼 | 형 | 근거 |
|---|---|---|
| 암호문 | `RAW(256)` | 평문 **191바이트(UTF-8)** 까지 담음 |
| 색인 | `RAW(32)` | 고정 32바이트 |
| 비밀번호 저장값 | `RAW(64)` | 고정 54바이트 |

암호문 길이는 `52 + 16 × (⌊n / 16⌋ + 1)` 바이트이며 `n` 은 평문의 UTF-8 바이트 수이다(한글 한 글자는 3바이트). 주민등록번호 13자리는 68바이트이다.

**주의.** 암호문은 **문자열 컬럼에 담지 마라.** 이진값이라 문자집합 변환에서 손상된다. 컬럼이 짧으면 암호문이 잘려 들어가고, 잘린 값은 영원히 복호화에 실패(`ORA-20511`)한다. 개발 중 복호화가 계속 실패하면 컬럼 정의부터 보라.

> **설명.** 길이 산식은 파이썬 참조 구현으로 직접 확인했다(0, 13, 16, 207, 208바이트에서 68, 68, 84, 260, 276). 데이터베이스와 자바 구현은 같은 고정 시험 벡터로 대조되므로 같은 길이를 낸다.

**할 일.** 색인 컬럼에만 인덱스를 만든다. 암호문 컬럼에는 인덱스를 만들지 마라(값이 매번 달라 쓸 수 없고 비용만 든다). 같은 사람을 한 번만 허용해야 하는 컬럼(주민등록번호)은 색인에 유일 인덱스를 둔다.

```sql
CREATE UNIQUE INDEX ux_tb_member_rrn  ON TB_MEMBER_ENC (mbr_rrn_idx);
CREATE INDEX        ix_tb_member_name ON TB_MEMBER_ENC (mbr_name_idx);
```

**할 일.** 도메인은 키 관리자가 등록한 것만 쓴다. 표준 도메인은 `RRN`(주민등록번호), `NAME`(성명), `PHONE`(연락처), `ACCOUNT`(계좌번호)이다. 컬럼마다 어느 도메인인지 정해서 적어 둔다. 도메인을 정하는 일은 기능을 만들기 전에 끝내야 한다. 나중에 바꾸면 자료를 다시 암호화해야 한다.

**주의.** 입력은 **형식을 하나로 통일해서** 넣는다. 색인은 입력을 다듬은 뒤 계산하므로 하이픈이 있든 없든 같은 값이 나오지만, **암호문에는 넣은 그대로 들어가고 마스킹은 저장된 모양을 기준으로** 만들어진다. 주민등록번호를 `880101-1234567` 로 넣으면 마스킹이 `880101-1******` 이 되고, `8801011234567` 로 넣으면 `88010112******` 가 된다. 화면 표시가 일정해야 하면 입력 형식부터 정해라.

**선택.** 응용 쿼리를 거의 고치지 않으려면 원래 테이블 이름으로 **투명화 뷰**를 만든다. 뷰는 평문 컬럼을 `FN_SHOW` 로 보여 주고, `INSTEAD OF` 트리거가 평문을 받아 암호화와 색인 생성을 대신한다. 만드는 방법은 `sql/08_sample/800_sample_member.sql` 이 최소 구성이고, `sql/08_sample/810_usage_examples.sql` 이 비밀번호까지 포함한 더 완전한 본보기다. 업무 테이블에 적용할 때 바꿀 것은 테이블과 컬럼의 이름, 도메인 코드뿐이다.

트리거를 직접 쓸 때의 규칙은 제4.6절에 있다.

### 4.2 저장

저장하는 길은 두 가지다. 투명화 뷰를 쓰면 평문을 그대로 넣고, 뷰 없이 쓰면 함수를 직접 부른다. **두 경우 모두 암호문과 색인을 함께 채워야 한다.** 색인을 빠뜨리면 그 행은 이후 검색되지 않는다.

**투명화 뷰로 저장한다(권장).**

```java
String sql = "INSERT INTO TB_MEMBER (mbr_id, mbr_name, mbr_rrn, mbr_phone, mbr_pwd) "
           + "VALUES (?, ?, ?, ?, FN_MAKE_PWD(?))";
```

**뷰 없이 원본 테이블에 직접 저장한다.**

```java
String sql = "INSERT INTO TB_MEMBER_ENC (mbr_id, mbr_name_enc, mbr_name_idx, mbr_rrn_enc, mbr_rrn_idx, mbr_phone_enc, mbr_pwd) "
           + "VALUES (?, FN_ENC_NAME(?), FN_IDX_NAME(?), FN_ENC_RRN(?), FN_IDX_RRN(?), FN_PROTECT('PHONE', ?), FN_MAKE_PWD(?))";
// 같은 값을 두 번 바인드한다: 이름(2번), 주민등록번호(2번)
```

**주의.** 값은 반드시 **바인드 변수**로 넣어라. 문자열을 이어 붙이면 주입 통로가 되고, 평문이 실행 계획 캐시와 추적 파일에 남는다.

**확인.** 저장 직후 암호문 길이를 본다. 주민등록번호 13자리는 68바이트가 나와야 한다.

```sql
SELECT UTL_RAW.LENGTH(mbr_rrn_enc) FROM TB_MEMBER_ENC WHERE mbr_id = ?
```

길이가 다르거나 컬럼이 짧으면 암호문이 잘려 들어가며, 잘린 값은 영원히 복호화에 실패한다(`ORA-20511`).

### 4.3 상세 조회

상세 화면은 한 건의 평문을 보여 준다. 평문을 볼 자격이 있는 사용자만 평문을 보고, 아닌 사용자는 마스킹된 값을 보게 할지, 아예 오류로 막을지에 따라 함수를 고른다.

| 화면 요구 | 쓰는 함수 | 자격이 없을 때 |
|---|---|---|
| 자격이 있으면 평문, 없으면 가려서 보여 준다 | `FN_SHOW('도메인', 암호문)` | 오류 없이 마스킹된 값 |
| 자격이 없으면 화면 자체를 막아야 한다 | `FN_REVEAL('도메인', 암호문)` 또는 `FN_DEC_RRN` 등 | `ORA-20520` |
| 평문 대신 마스킹만 보여 준다 | `FN_MASKED('도메인', 암호문)` | 항상 마스킹 |
| 화면을 그리기 전에 자격을 먼저 안다 | `FN_ALLOWED('도메인')` | 판정만(`Y`/`N`) |

```java
// 투명화 뷰: 평문 컬럼이 이미 FN_SHOW 를 거친다.
"SELECT mbr_name, mbr_rrn, mbr_phone FROM TB_MEMBER WHERE mbr_id = ?"

// 원본 테이블: 함수를 직접 건다.
"SELECT FN_SHOW('NAME', mbr_name_enc), FN_SHOW('RRN', mbr_rrn_enc) FROM TB_MEMBER_ENC WHERE mbr_id = ?"
```

**주의.** 복호화는 호출마다 **사용량으로 집계**되고 도메인별 임계치가 있다(주민등록번호는 한 구간 200건, 계좌번호는 50건이 기본이다). 상세 화면에서 한 건씩 보는 것은 문제가 없지만, 목록 화면에서 행마다 평문을 읽으면 임계치에 걸린다. 목록은 제4.4절을 따른다.

**주의.** 읽은 평문을 세션이나 화면 캐시에 담아 다음 화면에서 쓰지 마라. 필요할 때 다시 조회한다.

### 4.4 목록과 페이징

목록에는 평문이 아니라 **마스킹된 값**을 쓴다. 그리고 마스킹이든 복호화든 함수를 건 채로 페이징하면 **전체 행에 함수가 적용된 뒤** 잘린다. 안쪽 조회에서 먼저 자르고, 바깥에서 함수를 걸어라.

```sql
SELECT t.mbr_id, FN_MASKED('RRN', t.mbr_rrn_enc) AS mbr_rrn
  FROM ( SELECT mbr_id, mbr_rrn_enc FROM TB_MEMBER_ENC
          WHERE dept_cd = ?
          ORDER BY mbr_id OFFSET ? ROWS FETCH NEXT ? ROWS ONLY ) t
 ORDER BY t.mbr_id
```

투명화 뷰에는 마스킹 전용 컬럼(`mbr_rrn_masked`)이 있으므로 목록에서는 그것을 쓰고, 평문 컬럼은 상세에서만 읽는다. 마스킹 함수도 내부에서는 복호화를 하므로 **비용은 든다.** 대량 목록이라면 마스킹된 값을 별도 컬럼에 저장해 두는 편이 낫다. 암호문 컬럼이나 마스킹 결과로 정렬하지 마라(제4.5절).

**확인.** 한 번에 읽는 행 수가 화면에 보이는 행 수와 같아야 한다. 화면에 20건을 보여 주면서 전체를 복호화하고 있다면 이 절을 놓친 것이다.

### 4.5 검색

암호문은 같은 평문이라도 **매번 다르게** 만들어지므로 예전처럼 `WHERE mbr_rrn = '...'` 로 찾을 수 없다. 조건절의 평문 비교를 **색인 비교**로 바꾼다.

```sql
-- 고치기 전: 전 행을 복호화한 뒤 비교한다. 성능이 무너지고 임계치에 걸린다.
SELECT * FROM TB_MEMBER WHERE mbr_rrn = '880101-1234567';

-- 고친 뒤: 인덱스를 타고 한 건만 찾는다.
SELECT * FROM TB_MEMBER_ENC WHERE mbr_rrn_idx = FN_IDX_RRN('880101-1234567');
```

색인값은 입력을 도메인별로 다듬은 뒤 계산하므로 **하이픈이 있든 없든 같은 행**을 찾는다. 성명은 앞뒤 공백을 무시한다. 연락처도 숫자만 남겨 비교한다.

| 하려는 일 | 지원 | 방법 |
|---|---|---|
| 일치 검색 | 가능 | 색인 컬럼 |
| 부분 일치(`LIKE`), 범위 검색 | **불가** | 업무 협의로 요건 조정 |
| 정렬 | **불가** | 다른 컬럼(등록일시, 식별자)으로 정렬 |

부분 일치와 범위와 정렬은 기술적 한계가 아니라 **그렇게 만들면 안 되는 것**이다. 순서를 보존하면 순서 정보가 새고, 앞 몇 글자씩 따로 색인을 만들면 만든 만큼 노출이 늘어난다. 요건이 있으면 아래처럼 바꾸어 협의한다.

| 요건 | 대안 |
|---|---|
| 성명 부분 검색 | 사번, 회원번호 같은 다른 식별자로 검색 |
| 전체 목록에서 찾기 | 조회 범위를 부서, 담당 건으로 좁힘 |
| 이름순 정렬 | 등록일시, 식별자순. 꼭 필요하면 정렬용 컬럼을 따로 두되 **노출 범위를 문서로 남기고 승인을 받는다** |

### 4.6 수정과 삭제

**수정.** 투명화 뷰에 평문으로 `UPDATE` 하면 트리거가 바뀐 컬럼만 다시 암호화한다.

```java
"UPDATE TB_MEMBER SET mbr_phone = ? WHERE mbr_id = ?"
```

원본 테이블에 직접 고칠 때에는 암호문과 색인을 **둘 다** 바꾼다.

```java
"UPDATE TB_MEMBER_ENC SET mbr_rrn_enc = FN_ENC_RRN(?), mbr_rrn_idx = FN_IDX_RRN(?) WHERE mbr_id = ?"
```

**트리거를 직접 쓸 때의 규칙.** `INSTEAD OF` 트리거를 손수 쓰면 아래 네 가지를 지켜라.

| 규칙 | 이유 |
|---|---|
| 뷰에 보이는 컬럼은 **하나도 빠짐없이** `UPDATE` 분기에 둔다 | 빠진 컬럼은 오류 없이 **갱신이 조용히 사라짐**(한 행 갱신됨으로 나옴) |
| `UPDATING('컬럼명')` 은 **`IF` 같은 PL/SQL 조건식에서만** 쓴다. `UPDATE` 구문 안의 `CASE` 에 넣지 않는다 | `PLS-00231` 로 트리거가 컴파일되지 않음 |
| 바뀐 컬럼만 다시 암호화한다 | 조건 없이 전부 다시 암호화하면 값이 같아도 초기화 벡터가 새로 생겨 암호문이 바뀜 |
| 읽기 전용 컬럼(마스킹·색인 컬럼)은 일부러 빼고 주석으로 남긴다 | 의도를 구분 |

```sql
ELSIF UPDATING THEN
  UPDATE TB_MEMBER_ENC SET mbr_pwd = :NEW.mbr_pwd, join_dt = :NEW.join_dt
   WHERE mbr_id = :OLD.mbr_id;

  IF UPDATING('MBR_RRN') THEN
    UPDATE TB_MEMBER_ENC
       SET mbr_rrn_enc = FN_ENC_RRN(:NEW.mbr_rrn),
           mbr_rrn_idx = FN_IDX_RRN(:NEW.mbr_rrn)
     WHERE mbr_id = :OLD.mbr_id;
  END IF;
```

**삭제.** 평문이 필요 없으므로 일반 `DELETE` 와 같다.

```java
"DELETE FROM TB_MEMBER WHERE mbr_id = ?"
```

**주의.** 뷰는 원본 테이블에 대한 **직접 접근을 막지 못한다.** 원본(`…_ENC`) 테이블의 권한은 필요한 계정에만 두라. 뷰를 제3자에게 넘기려 하면 `ORA-01720` 이 날 수 있는데, 응용 계정에 재부여 권한을 주지 않는 것이 맞으므로 **자료를 넣고 꺼내는 일은 조회 도구가 아니라 애플리케이션이 하도록** 하라.

### 4.7 조인과 집계

조인과 집계는 **색인 컬럼끼리** 한다. 복호화가 필요 없다.

```sql
-- 조인: 양쪽에 색인 컬럼을 두고 색인끼리 비교
SELECT a.*, b.* FROM TB_MEMBER_ENC a JOIN TB_ORDER_ENC b ON a.mbr_rrn_idx = b.ord_rrn_idx;

-- 집계: 색인으로 묶으면 복호화 없이 된다
SELECT mbr_rrn_idx, COUNT(*) FROM TB_ORDER_ENC GROUP BY mbr_rrn_idx;
```

**주의.** **도메인이 다르면 키가 달라 색인값이 맞지 않는다.** 조인할 두 컬럼은 같은 도메인으로 등록되어야 한다. 컬럼을 분류하는 단계에서 확인하고, 나중에 바꾸려면 재암호화가 필요하다. 합계와 평균은 암호화 대상이 아니다. 그런 컬럼이 암호화 대상인지 다시 따져라.

### 4.8 대량 처리와 사용량 임계치

복호화에는 **사용량 임계치**가 걸려 있다. 평소보다 현저히 많은 복호화는 차단(`ORA-20522`)되고 경보가 올라간다. 계정 탈취 시 피해를 줄이기 위한 장치다.

| 상황 | 해야 할 일 |
|---|---|
| 업무상 대량 추출, 엑셀 내려받기 | 일반 조회 경로로 만들지 말고 **승인된 별도 작업**으로 분리하고 키 관리자와 협의한다. 마스킹된 값으로 충분한지 먼저 검토한다 |
| 임계치에 걸림 | 대개 암호화 컬럼을 조건절에 쓴 쿼리가 전 행을 복호화하는 중이다. 제4.5절로 고친다. 정상 업무량이면 키 관리자와 협의한다 |
| 배치 | **배치 전용 사용자 식별자**로 세션을 등록해 감사 기록에서 사람과 구분한다. 행마다 호출하지 말고 묶어서 처리한다 |
| 평문 컬럼을 암호문 컬럼으로 이관 | 건수씩 묶어서 `UPDATE` 하고 매번 커밋한다. 아래 예 |

```java
PreparedStatement ps = con.prepareStatement(
  "UPDATE 내테이블 SET rrn_enc = FN_ENC_RRN(rrn_plain), rrn_idx = FN_IDX_RRN(rrn_plain) " +
  " WHERE rrn_enc IS NULL AND ROWNUM <= ?");
ps.setInt(1, 5000);
int n;
do { n = ps.executeUpdate(); con.commit(); } while (n > 0);
```

`WHERE rrn_enc IS NULL` 이 처리 완료 지점을 데이터에 남기므로 중간에 멈춰도 다시 실행하면 이어진다. 끝난 뒤에는 건수와 표본 복호화와 색인 검색 결과를 평문 검색과 견주어 검증한다. 이관에 쓰는 시험 자료는 실제 개인정보가 아닌 값으로 하라.

## 5. 비밀번호

비밀번호는 다른 개인정보와 **전혀 다른 경로**이다.

| 비교 | 개인정보 | 비밀번호 |
|---|---|---|
| 복구 | 자격이 있으면 가능 | **불가능**(되돌릴 수 없음) |
| 세션 등록·자격 | 필요 | **불필요**(로그인 전에 검증해야 하므로) |
| 마스터 키 | 필요 | **쓰지 않음** |
| 감사 기록 | 남음 | 남지 않음 |
| 속도 | 빠름 | **일부러 느림**(반복 계산) |

따라서 **「비밀번호 찾기」는 알려 주는 기능이 아니라 새로 설정하게 하는 기능**이어야 한다. 기획 단계에서 합의해 두지 않으면 개발 막바지에 문제가 된다.

### 5.1 함수와 저장

| 함수 | 용도 | 반환 |
|---|---|---|
| `make_pwd(평문)` | 저장값 생성 | `RAW`(54바이트) |
| `verify_pwd(평문, 저장값)` | 검증 | `1` 일치, `0` 불일치 |
| `pwd_stale(저장값)` | 반복 횟수가 현재 기준보다 낮은가 | `1` 갱신 필요, `0` 아님 |

**할 일.** 컬럼은 `RAW(64)` 로 잡고, 등록은 평문을 바인드 변수로 넘긴다.

```xml
<insert id="insertUser" parameterType="userVO">
  INSERT INTO TB_USER (user_id, user_nm, user_pwd)
  VALUES (#{userId}, #{userNm}, FN_MAKE_PWD(#{userPwd}))
</insert>
```

**확인.** 저장 직후 `SELECT UTL_RAW.LENGTH(user_pwd) FROM TB_USER WHERE …` 가 `54` 여야 한다. 검증이 계속 실패하면 컬럼 길이부터 의심하라(잘린 값은 절대 통과하지 못한다).

| 규칙 | 이유 |
|---|---|
| 빈 값은 거부(`ORA-20541`). 화면·서버에서 **필수 입력 검증**을 둔다 | 공백만 입력된 경우처럼 걸러지지 않는 경우가 있다 |
| **복잡도 규칙은 이 시스템이 검사하지 않는다.** 응용에서 검사한 뒤 넘긴다 | 한 글자 비밀번호도 저장됨 |
| 저장값 안에 포맷·반복 횟수·솔트가 들어 있다 | 별도 컬럼 불필요, 반복 횟수를 올려도 기존 값 검증이 깨지지 않음 |

### 5.2 로그인 검증

**할 일.** 기본형이다. 결과 `1` 일치, `0` 불일치, **조회 결과 없음은 존재하지 않는 사용자**이다.

```xml
<select id="selectPasswordMatch" resultType="int">
  SELECT FN_VERIFY_PWD(#{inputPwd}, user_pwd) FROM TB_USER WHERE user_id = #{userId}
</select>
```

**주의.** **없는 계정에도 같은 시간을 들이라.** 존재하지 않는 계정은 즉시 끝나고 존재하는 계정은 반복 계산에 시간이 걸려, 응답 시간만으로 어떤 계정이 있는지 알아낼 수 있다. 기동 때 더미 저장값을 만들어 두고 없는 계정에 대해 그 값으로 검증한 뒤 실패로 처리한다. **화면 메시지도 구분하지 마라**(없는 계정과 틀린 비밀번호를 같은 문구로).

```java
private final byte[] dummyStored = OcsCrypto.passwordHash("dummy-for-timing-only", currentIterations());

public boolean authenticate(String userId, String inputPwd) {
    byte[] stored = userMapper.selectPasswordBlob(userId);   // 없으면 null
    if (stored == null) {
        OcsCrypto.passwordVerify(inputPwd, dummyStored);     // 같은 시간을 들이고 결과는 버린다
        return false;
    }
    return OcsCrypto.passwordVerify(inputPwd, stored);
}
```

| 규칙 | 이유 |
|---|---|
| **로그인 한 번에 한 번만** 호출 | 일부러 느린 계산. 목록·반복문 안에서 부르면 즉시 문제 |
| 검증 **성공 후에** 세션을 등록한다 | 로그인 전에는 사용자를 몰라 세션을 등록할 수 없음 |
| 로그인 실패 추적·계정 잠금은 **응용이 구현** | 이 시스템은 제공하지 않음 |

### 5.3 반복 횟수 점진 상향

관리자가 반복 횟수를 올려도 기존 사용자의 저장값은 옛 횟수 그대로이다. 옮기는 방법은 **로그인에 성공한 그 순간**, 평문이 손에 있을 때 다시 계산해 저장하는 것이다. 그 시점을 놓치면 영영 불가능하다.

**할 일.**

```java
if (authenticate(userId, inputPwd)) {
    if (userMapper.selectPasswordStale(userId) == 1) {          // pwd_stale
        try {
            userMapper.updatePasswordBlob(userId, inputPwd);     // make_pwd 로 다시 저장
        } catch (Exception e) {
            log.warn("비밀번호 저장값 갱신 실패: userId={}", userId);   // 비밀번호는 로그에 찍지 않는다
        }
    }
}
```

갱신에 실패해도 **로그인을 막지 마라.** 다음 로그인에서 다시 시도하면 된다. 이 처리가 빠져 있으면 관리자 쪽 분포 확인에서 드러난다.

### 5.4 변경과 초기화

| 상황 | 처리 |
|---|---|
| 사용자 변경 | **현재 비밀번호를 먼저 검증**한 뒤 새 값을 저장(화면을 열어 둔 채 자리를 비운 사이의 변경 방지) |
| 관리자 초기화 | 현재 비밀번호를 모르므로 검증 없음. **누가 초기화했는지는 응용이 기록**(이 시스템은 남기지 않음). 최초 로그인 때 변경 강제 |
| 임시 비밀번호 | 전자우편·문자로 보내면 평문이 경로에 남는다. **유효 시간이 짧은 재설정 링크**로 사용자가 직접 정하게 한다 |

### 5.5 자바 계층에서 계산하는 경우

기본은 데이터베이스 함수이다. 반복 횟수를 크게 올렸는데 로그인이 몰리는 시간대에 DB 부하가 문제가 될 때만 계산을 앱 서버로 옮긴다. **저장 형식이 같아 섞여 있어도 문제없다.**

```java
int iterations = configMapper.selectPwdIterations();            // 기동 시 SEC_CONFIG 에서 읽는다
byte[] stored = OcsCrypto.passwordHash(inputPwd, iterations);
```

**주의.** 반복 횟수를 앱이 따로 들면 DB 설정과 어긋날 수 있으므로 기동 시 DB에서 읽으라. `SEC_CONFIG` 조회 권한이 응용 계정에 없으면 키 관리자에게 읽기 권한을 요청하라(반복 횟수는 비밀이 아니다). 함수에 반복 횟수를 직접 지정하는 인자가 있으나 **시험용**이며, 업무 코드에서 임의로 낮추어 호출하지 마라.

## 6. 연결과 세션 등록

### 6.1 자바에서 등록하고 해제하기

복호화뿐 아니라 **암호화와 색인 생성에도** 세션 등록이 필요하다. 등록 없이 부르면 `ORA-20521` 이다.

> **설명.** 색인은 같은 평문이면 항상 같은 값이 나온다. 응용 계정 접속 정보를 가진 사람이 후보 평문을 넣어 색인을 계산하고 저장된 색인과 맞춰 보면 평문을 알아낼 수 있다(주민등록번호는 생년월일을 알면 후보가 백만 개 수준이다). 그래서 복호화만 막고 색인을 열어 두면 통제가 성립하지 않는다.

**할 일.** 앱 기동 때 한 번 만들고, DB 연결을 얻을 때마다 세션을 등록하고, 연결을 닫기 전에 `finally` 에서 등록을 해제한다.

```java
// 기동 시 한 번. 증표 키는 소스·설정 파일에 평문으로 두지 말 것.
OcsAppProof proof = new OcsAppProof(loadAppCtxKeyFromSecureStore());   // 32바이트
OcsSessionSupport session = new OcsSessionSupport(proof);

Connection con = dataSource.getConnection();
try {
    session.establish(con, currentUserId());   // 업무 사용자 식별자(DB 계정이 아님)
    // ... 이 연결로 수행하는 모든 조회와 갱신 ...
} finally {
    boolean ok = session.release(con);          // 실패해도 업무를 되돌릴 수는 없으므로 로그만
    if (!ok) { log.warn("세션 등록 해제 실패"); }
    con.close();
}
```

**확인.** `session.establish` 가 예외 없이 돌아오고, 같은 연결에서 `SELECT FN_ALLOWED('RRN') FROM DUAL` 이 오류 없이 `Y` 또는 `N` 을 돌려준다.

**업무 사용자 ID.** `establish(con, "업무사용자ID")` 의 두 번째 인자는 오라클 계정(USERNAME)이 아니라 **응용에 로그인한 실제 사용자의 식별자**다. 응용 서버는 연결 풀을 통해 오라클 계정 하나로 접속하므로 데이터베이스는 화면을 쓰는 사람을 알 수 없다. 그래서 이 값으로 알려 준다.

| 구분 | 무엇인가 | 예 |
|---|---|---|
| 오라클 계정 | 응용 서버가 데이터베이스에 접속할 때 쓰는 계정. 보통 모든 사용자가 공유한다 | `SFIS`, `DEV01` |
| 업무 사용자 ID | 응용에 로그인한 실제 사람의 사번이나 로그인 ID | `hong01`, `20231045` |

이 값은 **감사 기록**(`SEC_AUDIT_LOG` 의 `APP_USER` 컬럼)에만 쓰인다. 누가 평문을 봤고 누가 막혔는지를 추적하는 용도다. **복호화 자격의 판정에는 쓰이지 않는다.** 자격은 오라클 계정 기준이므로, 사용자마다 평문을 보여 줄지 말지는 응용에서 구현해야 한다.

| 상황 | 넣을 값 |
|---|---|
| 실제 서비스 | 로그인한 사용자의 식별자. **사람마다 달라야** 한다. 모두 `admin` 처럼 같은 값을 넣으면 감사 기록이 쓸모없어진다 |
| 배치 | 배치 전용 식별자(예: `batch.settle`). 사람과 구분한다 |
| 개발·시험 | 아무 이름이나 된다 |

값이 비어 있으면 `ORA-20541` 이다. 이 값은 감사 기록에 평문으로 남으므로 주민등록번호나 성명 같은 개인정보를 쓰지 마라.

| 흔한 실수 | 증상 | 고치는 법 |
|---|---|---|
| 세션을 등록한 연결과 **다른 연결**로 조회 | `ORA-20521` | 트랜잭션 경계 안에서 같은 연결 유지 |
| 연결을 **등록 해제 없이** 닫아 풀에 돌려줌 | 다음 사용자가 **앞 사용자의 등록을 이어받음**. 권한이 남의 것으로 판정 | `finally` 에서 반드시 `release` |
| 앱 서버와 DB 서버의 **시각 차이** | `ORA-20521`(증표 유효 시간 초과, 기본 300초) | 시각 동기화 |
| 증표 키가 DB의 키와 다름 | `ORA-20521`(증표 불일치) | 키 관리자에게 현재 키 확인. 재설치마다 새로 만드는 값 |

서비스마다 반복하지 말고 연결을 얻는 지점(데이터 소스 래퍼, AOP)에서 자동으로 호출되게 하라.

**주의.** `new OcsSessionSupport(null)` 은 증표 없이 세션 등록만 한다. **개발·시험 전용**이며 운영에서 쓰면 이 통제는 없는 것과 같다. 데이터베이스의 `APPCTX_MODE` 도 `SIMPLE` 이어야 동작하고, 운영 전환 점검이 이 설정을 확인한다.

### 6.2 한곳에 모아 두기

서비스마다 `try/finally` 를 반복하는 것은 현실적이지 않다. **연결을 얻는 지점을 한 곳으로 모으고** 거기서만 세션 등록과 해제를 하게 하라. 아래 도우미가 그 일을 한다. 업무 코드는 넘겨받은 연결 하나로 모든 조회와 갱신을 하면 된다.

```java
OcsWork work = new OcsWork(dataSource, session);   // 기동 시 한 번
int n = work.run("member.admin", con -> MemberExample.insertMember(con, 1L, "홍길동", "880101-1234567", "010-1234-5678", "Pw#12345"));
```

파일 위치는 `java/src/example/java/ocsecure/example/OcsWork.java` 이며 전체는 아래와 같다.

```java
package ocsecure.example;

import java.sql.Connection;
import java.sql.SQLException;
import javax.sql.DataSource;

import ocsecure.client.OcsSessionSupport;

/**
 * DB 연결을 얻고, 세션을 등록하고, 업무를 하고, 등록을 해제하고, 연결을 닫는 일을 한곳에 모은 도우미.
 *
 * <p>서비스마다 try/finally 를 반복하지 않도록 이 한 곳에서만 세션 등록을 다룬다. 업무 코드는 넘겨받은
 * 연결 하나로 모든 조회와 갱신을 하며, 같은 트랜잭션 안에서 다른 연결을 쓰지 않는다.
 *
 * <p>사용 예.
 * <pre>
 *   OcsWork work = new OcsWork(dataSource, session);
 *   int n = work.run("member.admin", con -> MemberExample.insertMember(con, 1L, "홍길동", "880101-1234567", "010-1234-5678", "Pw#12345"));
 * </pre>
 */
public final class OcsWork {

    /** 연결 하나로 하는 업무. */
    public interface Task<T> {
        T run(Connection con) throws SQLException;
    }

    private final DataSource dataSource;
    private final OcsSessionSupport session;

    public OcsWork(DataSource dataSource, OcsSessionSupport session) {
        this.dataSource = dataSource;
        this.session = session;
    }

    public <T> T run(String appUser, Task<T> task) throws SQLException {
        try (Connection con = dataSource.getConnection()) {
            con.setAutoCommit(false);
            session.establish(con, appUser);
            try {
                T result = task.run(con);
                con.commit();
                return result;
            } catch (SQLException | RuntimeException e) {
                // 삼키지 않는다. 되돌리고 다시 던진다.
                con.rollback();
                throw e;
            } finally {
                // 연결을 닫기 전에 반드시 등록을 해제한다. 해제하지 않으면 풀의 다음 사용자가 앞 사용자의 등록을 이어받는다.
                if (!session.release(con)) {
                    System.err.println("세션 등록을 해제하지 못하였다. 이 연결은 풀로 돌려보내지 말고 닫는 편이 안전하다.");
                }
            }
        }
    }
}
```

스프링을 쓰면 서비스 계층의 진입과 종료에 관점(AOP)으로 걸거나 데이터 소스를 감싸는 방식으로 같은 일을 한다. 어느 쪽이든 지켜야 할 것은 하나다. **세션을 등록한 그 연결에서 업무를 수행해야 한다.** 세션을 등록하고 연결을 닫은 뒤 다른 연결로 조회하면 아무 소용이 없다. 트랜잭션 경계 안에서 같은 연결이 유지되도록 구성하라.

### 6.3 증표 키

증표 키(`OcsAppProof` 에 넘기는 32바이트)는 **소스나 설정 파일에 평문으로 두지 마라.** 키 관리 제품이나 기동 시점에 주입되는 환경 값에서 읽는다. 운영에서는 이 키를 키 관리자나 보안 담당자가 응용 서버 담당자에게 전달한다. 재설치할 때마다 새로 만드는 값이므로 설치가 바뀌면 다시 받아야 한다.

### 6.4 증표가 만들어지는 방식

연동 모듈이 대신 하는 일이므로 알 필요는 없지만 오류를 이해하는 데 도움이 된다. 증표는 `HMAC-SHA256(증표 키, 응용사용자 || '|' || epoch || '|' || 세션식별자)` 이다. epoch 는 UTC 기준 초이고 세션 식별자는 `SYS_CONTEXT('USERENV','SID')` 이다. 증표에 세션이 묶여 있어 **다른 세션에서 만든 증표는 쓸 수 없고**, 앱 서버와 데이터베이스 서버의 시각 차이가 유효 시간(기본 300초)을 넘으면 거부된다.

## 7. 전자정부 표준프레임워크와 MyBatis

전자정부 표준프레임워크(스프링과 MyBatis 기반)로 업무 화면을 개발하는 사람을 위한 장이다. 호출 규격과 컬럼 다루기와 비밀번호의 설명은 앞 장에 있으며 이 환경에서도 같다. 이 장은 **이 환경에서 특히 부딪히는 것**만 모았다. 처음이라면 제1장부터 제5장까지를 먼저 읽어라.

### 7.1 표준프레임워크의 자체 암호화 서비스와 겹치지 않게 하라

전자정부 표준프레임워크는 실행환경 기반 계층에 자체 암호화 서비스를 제공하는 것으로 알려져 있다(정확도: 중간). 쓰는 버전의 개발자 가이드에서 정확한 클래스와 메서드 이름을 확인하시기 바라며, 이 매뉴얼은 특정 클래스 이름을 단정하지 않는다.

중요한 것은 역할 구분이다. 표준프레임워크의 암호화 서비스는 설정 파일의 비밀번호를 가리거나 전송 구간의 자료를 감싸는 것처럼 **애플리케이션 내부에서 끝나는 용도**에 적합하다. 반면 **테이블 컬럼에 저장되는 개인정보는 이 시스템을 통해야 한다.** 키 관리와 감사와 권한 판정이 여기에 묶여 있기 때문이다.

**한 컬럼을 두 방식으로 번갈아 암호화하는 일만은 반드시 피하라.** 어느 방식으로 암호화된 값인지 구분할 수 없게 되어 복호화가 불가능해진다. 이 시스템의 암호문은 맨 앞 바이트가 포맷 버전이라 식별이 가능하지만, 그 판별 코드를 업무 로직에 넣기 시작하면 감당할 수 없다.

### 7.2 MyBatis 매퍼 예시

앞 장의 예시와 같은 호출을 매퍼 XML 로 적은 것이다. 짧은 이름을 쓰며, 같은 동작의 긴 호출은 `OCS_OWNER.PKG_SECURE_API.<소문자 이름>` 이다.

**투명화 뷰 없이 직접 저장.** 암호문 컬럼과 색인 컬럼을 **함께** 채운다. 색인 컬럼을 빠뜨리면 그 행은 이후 검색되지 않는다.

```xml
<insert id="insertMemberEnc" parameterType="memberVO">
  INSERT INTO TB_MEMBER_ENC (
    mbr_id, mbr_name_enc, mbr_name_idx, mbr_rrn_enc, mbr_rrn_idx, mbr_phone_enc
  ) VALUES (
    #{mbrId},
    FN_ENC_NAME(#{mbrName}), FN_IDX_NAME(#{mbrName}),
    FN_ENC_RRN(#{mbrRrn}),   FN_IDX_RRN(#{mbrRrn}),
    FN_PROTECT('PHONE', #{mbrPhone})
  )
</insert>
```

**색인으로 검색.** 하이픈이 있든 없든 같은 행을 찾는다.

```xml
<select id="selectByRrn" resultType="memberVO">
  SELECT * FROM TB_MEMBER_ENC
   WHERE mbr_rrn_idx = FN_IDX_RRN(#{rrn})
</select>
```

**화면에서 권한을 먼저 묻기.** 복호화를 하지 않으므로 사용량에도 잡히지 않는다.

```xml
<select id="canRevealRrn" resultType="string">
  SELECT FN_ALLOWED('RRN') FROM DUAL
</select>
```

**비밀번호 등록, 검증, 점진 상향.** 검증은 불리언 대신 1과 0을 돌려준다. 갱신은 로그인에 성공한 직후, 평문이 손에 있는 그 순간에만 할 수 있다.

```xml
<insert id="insertUser" parameterType="userVO">
  INSERT INTO TB_USER (user_id, user_pwd)
  VALUES (#{userId}, FN_MAKE_PWD(#{userPwd}))
</insert>

<select id="checkPassword" resultType="int">
  SELECT FN_VERIFY_PWD(#{inputPwd}, user_pwd) FROM TB_USER WHERE user_id = #{userId}
</select>

<select id="pwdStale" resultType="int">
  SELECT FN_PWD_STALE(user_pwd) FROM TB_USER WHERE user_id = #{userId}
</select>

<update id="refreshPassword">
  UPDATE TB_USER SET user_pwd = FN_MAKE_PWD(#{inputPwd}) WHERE user_id = #{userId}
</update>
```

결과가 없는 경우(없는 사용자)와 비밀번호가 틀린 경우를 화면에서 구분해 알리지 마라(제5.2절).

### 7.3 화면을 만들 때 주의할 점

제10장의 금지 사항 가운데 화면 개발에서 특히 어기기 쉬운 것이다.

| 주의 | 이유 |
|---|---|
| 복호화한 값을 디버그 로그로 찍는 코드를 운영에 내보내지 않는다. 예외 때 파라미터 전체를 찍는 공통 처리가 있는지 확인한다 | 로그 파일은 암호화 대상이 아니어서 그 순간 암호화의 의미가 사라진다 |
| 상세 화면에서 읽은 평문(예: 주민등록번호)을 세션이나 화면 캐시에 담아 다음 화면에서 재사용하지 않는다 | 평문이 머무는 자리가 늘어난다. 필요할 때 다시 조회한다 |
| 검증 메시지에 정보를 흘리지 않는다. 이미 등록된 번호라고 알려 주지 않는다 | 특정인의 가입 여부를 알려 주는 것이 된다 |
| 개발 환경에 운영 데이터를 복제하지 않는다 | 복제 과정에서 평문이 지나갈 수 있다. 시험 자료는 만들어 쓴다 |

## 8. PL/SQL 프로그램 개발

### 8.1 세션 등록하기

자바 없이 직접 세울 때(시험이나 배치 도구)의 호출이다.
자바 없이 직접 세울 때(시험이나 배치 도구)의 호출이다.

```sql
BEGIN
  OCS_OWNER.PKG_SECURE_API.login('<업무사용자>', <epoch>, HEXTORAW('<증표>'));   -- PROOF 모드
  -- OCS_OWNER.PKG_SECURE_API.login('<업무사용자>');                           -- SIMPLE 모드(개발)
  -- ... 암복호화 ...
  OCS_OWNER.PKG_SECURE_API.logout;
END;
/
```

증표는 `HMAC-SHA256(증표 키, 응용사용자 || '|' || epoch || '|' || 세션식별자)` 이다. epoch 는 UTC 기준 초이고 세션 식별자는 `SYS_CONTEXT('USERENV','SID')` 이다. 증표에 세션이 묶여 있어 **다른 세션에서 만든 증표는 쓸 수 없다.** 증표 키는 데이터베이스 밖에 있으므로 PL/SQL 안에서 계산하지 않고 자바 등 앱 계층이 만들어 넘긴다.

**주의.** 이 설계상 **데이터베이스 안에서만 도는 PL/SQL 배치**(예: 스케줄러 작업)는 증표 키가 없어 `PROOF` 모드에서 스스로 세션을 등록할 수 없다. 이는 설계 주석에서 따른 추론이며 이 구성을 실제로 시험하지는 않았다. **데이터베이스 안 배치가 필요하면 설계 단계에서 키 관리자·보안 담당자와 방식을 합의하라.** 임의로 `SIMPLE` 로 바꾸지 마라.

### 8.2 기본 틀

**할 일.** 저장 프로시저에서 암복호화를 부르는 틀이다. 세션 등록은 **프로시저를 호출한 세션**에 이미 되어 있다고 전제한다(제6장).

```sql
CREATE OR REPLACE PROCEDURE SP_MEMBER_SAVE(p_id IN NUMBER, p_rrn IN VARCHAR2) IS
BEGIN
  IF FN_READY = 0 THEN
    RAISE_APPLICATION_ERROR(-20999, '암호 모듈을 쓸 수 없는 상태입니다.');   -- 값은 포함하지 말 것
  END IF;

  INSERT INTO TB_MEMBER_ENC (mbr_id, mbr_rrn_enc, mbr_rrn_idx)
  VALUES (p_id,
          FN_ENC_RRN(p_rrn),
          FN_IDX_RRN(p_rrn));
  -- EXCEPTION 절에서 WHEN OTHERS THEN NULL 로 삼키지 말 것
END;
/
```

### 8.3 PL/SQL 에서 주의할 것

| 항목 | 규칙 |
|---|---|
| 권한 | `PKG_SECURE_API` 실행 권한은 **계정에 직접** 있어야 컴파일된다(역할 권한은 저장 객체 안에서 불인정). 없으면 `PLS-00201` |
| SQL 안에서 호출 | 함수는 SQL 문에서 직접 쓸 수 있다. `verify_pwd`, `pwd_stale` 은 불리언 대신 `1`/`0` 을 돌려주는 이유 |
| 예외 | 삼키지 않는다. `WHEN OTHERS` 로 잡았다면 **반드시 다시 던진다** |
| 평문 | 로그 테이블, `DBMS_OUTPUT`, 예외 메시지에 평문을 넣지 않는다 |
| 대량 처리 | 행마다 호출하면 전환 비용이 누적된다. 묶어서 읽고 묶어서 기록 |
| 대상 테이블 권한 | 재암호화 같은 모듈 배치는 `OCS_OWNER` 권한으로 돈다. 업무 테이블 권한을 `OCS_OWNER` 에 **직접** 부여해야 하며 끝나면 회수(유지보수 매뉴얼 제8장) |

**주의.** 데이터베이스 안에서만 도는 배치의 세션 등록 문제는 제8.1절의 주의를 보라.

## 9. 오류와 예외 처리

### 9.1 예외 처리

키 저장소가 닫혀 있거나 권한이 없으면 모듈은 **예외를 낸다.** 널을 돌려주거나 평문을 그대로 저장하는 일은 없으며, 응용은 이 동작을 깨뜨리지 않아야 한다.

**할 일.**

```java
try {
    // 암복호화가 들어간 DB 작업
} catch (SQLException e) {
    // 로그만 남기고 넘어가지 말 것. 다시 던지거나 트랜잭션을 되돌린다.
    con.rollback();
    throw e;
}
```

**주의.** 예외를 넓게 잡아 삼키면 암호문이 들어갈 자리에 널이 들어가고 **한참 뒤에 드러난다.** 가장 흔한 사고이다.

멈춘 상태를 이용자에게 어떻게 보일지는 따로 챙기라. 화면 진입 전에 아래를 물어 갈라서 안내 화면을 내보내면 오류 추적이 그대로 노출되지 않는다.

```sql
SELECT FN_READY FROM DUAL   -- 1 가능, 0 불가
```

`0` 이 이어지면 키 저장소 유지 프로그램이 멈춘 것이므로 운영자에게 알리라. 감시 도구의 상태 점검에도 같은 값을 쓴다.

### 9.2 오류 번호

| 오류 | 뜻 | 개발자가 할 일 |
|---|---|---|

| `ORA-20522` | 사용량 임계치 초과 | 암호화 컬럼을 조건절에 쓴 쿼리가 있는지 확인, 6.1 로 수정 |

## 11. 참고: 호출 규격

### 11.1 일반형 함수

아래 표와 제11.2절의 함수 이름은 패키지 안의 이름이다. 쿼리에서는 **앞에 `FN_` 을 대문자로 붙인 짧은 이름**(예: `protect` 는 `FN_PROTECT`)을 기본으로 쓰라(제11.3절).

| 함수 | 용도 | 반환 | 세션 등록 | 복호화 자격 | 사용량 집계 |
|---|---|---|---|---|---|
| `protect(도메인, 평문)` | 암호화 | `RAW` | 필요 | 불필요 | 아님 |
| `search_of(도메인, 평문)` | 검색용 색인 생성 | `RAW` | 필요 | 불필요 | 아님 |
| `reveal(도메인, 암호문)` | 복호화 | `VARCHAR2` | 필요 | **필요**(없으면 예외) | **집계·임계치** |
| `masked(도메인, 암호문)` | 마스킹된 값 | `VARCHAR2` | **검사 안 함** | 불필요 | 아님 |
| `show(도메인, 암호문)` | 자격 있으면 평문, 없으면 마스킹 | `VARCHAR2` | 등록이 없으면 마스킹 | 있으면 평문 | 평문일 때만 |
| `allowed(도메인)` | 평문을 볼 자격이 있는가 | `'Y'` 또는 `'N'` | 없으면 `'N'` | 판정만 | 아님 |
| `ready` | 암복호화 가능 상태인가 | `1` 또는 `0` | 불필요 | 불필요 | 아님 |
| `login(사용자, 시각, 증표)` / `logout` | 세션 등록·해제 | — | — | — | — |

입력이 널이면 `protect`, `search_of`, `reveal`, `masked`, `show` 는 모두 널을 돌려준다.

> **설명.** `masked` 는 마스킹을 만들기 위해 내부에서 복호화하지만 평문은 함수 밖으로 나가지 않는다. 복호화 실패 시 예외 대신 `********` 를 돌려주고 감사 기록에 남기므로 **한 건의 손상이 목록 전체를 막지 않는다.** 대신 복호화 비용은 그대로 들므로, 대량 목록에서는 마스킹된 값을 별도 컬럼에 저장해 두는 편이 낫다. `show` 는 자격이 없으면 오류가 아니라 마스킹으로 처리하므로 화면마다 권한 분기를 두지 않아도 된다. 자격이 없을 때 **오류로 처리해야 하는 화면**이라면 `reveal` 을 직접 쓰라.

### 11.2 도메인 전용 함수

표준 도메인에는 이름으로 호출할 수 있는 함수가 있다. 호출 지점을 이름으로 검색하면 어느 화면이 평문을 쓰는지 바로 드러나도록 한 것이다.

| 도메인 | 암호화 | 복호화 | 마스킹 | 색인 |
|---|---|---|---|---|
| 주민등록번호 `RRN` | `enc_rrn` | `dec_rrn` | `mask_rrn` | `idx_rrn` |
| 성명 `NAME` | `enc_name` | `dec_name` | `mask_name` | `idx_name` |
| 계좌번호 `ACCOUNT` | `enc_account` | `dec_account` | `mask_account` | `idx_account` |
| 그 밖(`PHONE` 등) | `protect('PHONE', …)` | `reveal('PHONE', …)` | `masked('PHONE', …)` | `search_of('PHONE', …)` |

**주의.** 도메인 코드는 임의로 지을 수 없고 키 관리자가 등록한 것만 쓴다. 없는 코드를 넘기면 `ORA-20530` 이다.

### 11.3 짧은 함수 이름

패키지 이름 없이 쿼리에서 바로 쓰도록, `PKG_SECURE_API` 의 함수마다 `FN_` 으로 시작하는 같은 동작의 단독 함수가 있다. 이름은 `FN_` 뒤에 패키지 함수 이름을 대문자로 붙인 것이다. **이 매뉴얼의 쿼리 예시는 이 짧은 이름을 기본으로 쓴다.** 호출 지점을 `FN_` 으로 검색하면 평문을 쓰는 화면이 바로 드러난다. 패키지 이름을 붙인 긴 호출(`OCS_OWNER.PKG_SECURE_API.enc_rrn(...)`)도 같은 동작이며, 짧은 이름이 연결되어 있지 않은 환경의 보조 방법이다.

| 짧은 호출 (기본) | 긴 호출 (보조) |
|---|---|
| `FN_ENC_RRN(:v)` | `OCS_OWNER.PKG_SECURE_API.enc_rrn(:v)` |
| `FN_IDX_RRN(:v)` | `OCS_OWNER.PKG_SECURE_API.idx_rrn(:v)` |
| `FN_SHOW('RRN', c)` | `OCS_OWNER.PKG_SECURE_API.show('RRN', c)` |
| `FN_MASKED('RRN', c)` | `OCS_OWNER.PKG_SECURE_API.masked('RRN', c)` |

`login`, `logout` 은 프로시저이므로 짧은 이름이 없고 패키지 이름으로 부른다. 그 밖의 25개 함수는 모두 짧은 이름이 있다.

**쓰려면** 설치 담당자가 업무 계정을 암호 모듈에 연결해 두어야 한다. 설치 매뉴얼의 업무 계정 연결(`480_connect_app_schema.sql`)이 실행 권한과 시노님을 만든다. 열려 있지 않으면 `ORA-00904` 나 `ORA-00942` 가 나므로 키 관리자에게 알리라. 동작과 통제(문맥, 복호화 자격, 마스킹, 감사)는 패키지를 직접 부를 때와 같다. 전체 대응표는 설치 매뉴얼 제11.10절에 있다.

## 12. 참고: 자바에서 직접 암복호화하는 경우

일상 업무 개발에서 자바 연동 모듈(`ocsecure.client`)을 쓰는 곳은 **접속 증표와 세션 등록**(제6장)뿐이다. 암복호화는 제4장처럼 SQL 안에서 데이터베이스 함수로 한다.

| 클래스 | 용도 |
|---|---|
| `OcsAppProof` | 접속 증표 계산 |
| `OcsSessionSupport` | 세션 등록·해제 |
| `OcsCrypto` | 암호문 포맷, 비밀번호 계산. **데이터베이스를 거치지 않는 처리**용 |
| `OcsKeySet` | 키 묶음(`OcsCrypto` 직접 사용 시) |
| `OcsCryptoException` | 연동 모듈 예외 |

### 12.1 직접 쓰는 경우

외부 기관과 파일로 자료를 주고받는 연계처럼 **데이터베이스를 거치지 않는 처리**에만 `OcsCrypto` 를 직접 쓴다.

```java
OcsKeySet key = new OcsKeySet(keyId, OcsCrypto.ALG_AES256_CBC_HMAC_SHA256, encKey, macKey, idxKey);
byte[] cipher = OcsCrypto.encrypt("880101-1234567", key);
String plain  = OcsCrypto.decrypt(cipher, key);
```

이 코드가 만드는 암호문은 데이터베이스가 만드는 것과 **바이트 단위로 같다**(같은 고정 시험 벡터로 대조).

**주의.** 이 경로를 쓰면 **애플리케이션이 키를 다루게 되어** 데이터베이스 쪽 통제(세션 등록, 자격, 사용량, 감사)가 우회된다. 키를 어디에 두고 누가 접근하는지가 새 문제로 생기므로, 이 경로를 여는 것은 **예외적인 결정으로 보안 담당자의 승인**을 받아야 한다. 편의로 쓰기 시작하지 마라.

## 13. 참고: 기존 비밀번호 체계에서 옮겨 오기

### 13.1 기존 체계에서 옮겨 오기

기존 방식은 솔트 없는 단일 해시이다. 일괄 변환은 불가능하므로 **옛 비밀번호로 로그인시키되 그 자리에서 비밀번호 변경을 강제**한다. 임시 비밀번호 발급(강제 초기화)보다 나은 이유는 본인확인 채널이 따로 필요 없고 새 노출 경로가 생기지 않기 때문이다.

**할 일.**

| 단계 | 내용 |
|---|---|
| 1 | 컬럼을 `VARCHAR2(108)` 로 넓힘(옛 형식 Base64 44자, 새 형식 16진 108자가 섞임). 길이 확장은 서비스 중에도 가능 |
| 2 | **배포 전 관문**: `SELECT OCS_OWNER.PKG_LEGACY_PWD.self_check('아는 평문', '그 계정의 저장값') FROM DUAL;` 가 `일치` 여야 한다. `불일치` 면 배포 금지 |
| 3 | 로그인에 `check_pwd` 사용 |
| 4 | 결과 `2` 면 로그인시키되 **변경 화면으로 강제 이동**하고 다른 화면으로 못 나가게 막는다 |
| 5 | 변경 화면은 `make_pwd_str` 로 **새 형식으로만** 저장하고 복잡도 규칙을 함께 적용 |
| 6 | 이행이 끝나면 옛 검증 코드 제거(관리자와 시점 합의) |

| `check_pwd` 결과 | 뜻 | 처리 |
|---|---|---|
| `0` | 불일치(저장값이 비어 있는 경우 포함) | 로그인 실패 |
| `1` | 일치, 현재 형식 | 로그인 |
| `2` | 일치, **옛 형식** | 로그인시키되 변경 강제 |

저장값의 상태만 먼저 보려면 `pwd_state` 를 쓴다(`0` 미설정, `1` 현재 형식, `2` 옛 형식, `9` 알 수 없는 형식). 업무포털 단일 인증 이용자는 비밀번호가 비어 있으므로 `0` 이며, 로그인 실패와 구분해 **설정 절차로 보낸다.** `9` 는 통과시키지 말고 자료 이상으로 조사한다.

**주의.** 옛 형식으로 검증에 성공했을 때 **같은 비밀번호를 새 형식으로 다시 저장하고 끝내지 마라.** 옛 방식은 이미 유출되었을 수 있어, 형식만 바꿔 담으면 알려진 비밀번호를 그대로 쓰는 셈이다.

### 13.2 기존 방식 확인

옮겨 오려면 기존 방식을 정확히 알아야 한다. 방법은 세 갈래이며 **마지막 하나만 확정적**이다.

| 방법 | 하는 일 | 확실성 |
|---|---|---|
| 저장값의 생김새 | `@sql/04_admin/410_legacy_pwd_survey.sql` 을 기존 계정으로 실행. 자료형·길이 분포·문자 구성을 **세기만** 하고 저장값을 화면에 띄우지 않음 | 좁히기만 함 |
| 소스 코드 읽기 | 로그인 처리에서 비밀번호를 다루는 지점을 따라감. `encryptPassword`, `MessageDigest`, `PasswordEncoder` 로 검색 | 확실하나 시간이 걸림 |
| **실증 대조** | 평문과 그 저장값 한 쌍으로 후보 구성을 재현해 일치하는 것을 찾음 | **확정적** |

길이로 좁히는 기준이다.

| 표기 | MD5 | SHA-1 | SHA-256 | SHA-512 |
|---|---|---|---|---|
| 16진 | 32 | 40 | 64 | 128 |
| Base64 | 24 | 28 | 44 | 88 |

60자면 bcrypt, 54면 이미 이 시스템의 형식, 길이가 제각각이면 평문이거나 가변 길이 암호화이다. 조사 스크립트의 네 번째 항목(서로 다른 사용자가 같은 저장값을 갖는지)이 중요하다. **중복이 있으면 솔트가 없다**는 뜻이다.

**할 일.** 실증 대조는 시험계에 계정을 하나 만들어 비밀번호를 정해 등록한 뒤 그 계정의 저장값으로 한다.

```
python3 tools/legacy_pwd_probe.py --plain '정한비밀번호' --stored '조회한저장값' --id '아이디'
```

해시 알고리즘 여섯 가지, 표기 다섯 가지, 아이디를 섞는 네 가지 배치, 두 번 해싱하는 변형, 문자집합 두 가지(EUC-KR 포함)를 조합해 시도한다. 아이디를 함께 넣으라. 솔트를 따로 두지 않고 아이디를 솔트처럼 쓰는 구성이 드물지 않는다.

**주의.** **운영계 사용자의 비밀번호로 시도하지 마라.** 일치하는 것이 없어도 특별한 방식이라는 뜻은 아니다(흔한 구성만 시도함). 한글이 섞인 비밀번호는 문자집합이 다르면 결과가 완전히 달라지므로, 이를 놓치면 한글 비밀번호 사용자만 검증에 실패한다. 저장값이 **평문**으로 나오면 이행 문제가 아니라 사고에 가까우므로 보안 담당자에게 먼저 보고하라.

### 13.3 표준프레임워크로 개발된 시스템의 관행

전자정부 표준프레임워크로 개발된 시스템에서는 공통 유틸리티의 비밀번호 암호화 함수로 해시를 한 번 계산해 저장하는 방식이 널리 쓰이는 것으로 알려져 있다(정확도: 중간. 실제 사용 중인 코드를 확인하라). 해시를 한 번만 계산하는 방식은 계산이 매우 빨라 대량 대입에 취약한다.

이미 옛 방식으로 저장된 자료가 있다면 일괄 전환은 불가능하다. 원문을 모르기 때문이다. 현실적인 방법은 두 방식을 한동안 공존시키는 것이며, 그 절차는 제13.1절에, 기존 방식을 확인하는 방법은 제13.2절에 있다. 일정 기간이 지나면 남은 사용자에게 비밀번호 재설정을 요구하여 정리한다.

### 14.2 개발 모드로 빠르게 해 보기

개발자가 **시험 인스턴스에서** 증표 키 없이 암복호화를 바로 해 볼 수 있게 하는 방법이다. 운영의 통제(증표, 세션 등록, 자격, 감사)를 그대로 따르면 시험하기가 까다로우므로, 시험 인스턴스에서만 증표 검증을 잠시 끈다. **운영 인스턴스에서는 절대 쓰지 마라.** 켜 둔 채로는 운영 개통 판정(`320_golive_check.sql`)이 「불가」로 나온다.

**전제.** 설치 매뉴얼에서 마스터 키 주입, 도메인과 키, 증표용 키 등록, 업무 계정 연결(`480`)까지 끝난 시험 인스턴스이다. 실제 개인정보는 없어야 한다.

| 하고 싶은 일 | 어디를 보나 |
|---|---|
| 개발 모드를 켜고 끄기 | 제14.2.1절, 제14.2.5절 |
| SQL\*Plus에서 바로 암호화와 복호화 해 보기 | 제14.2.2절 |
| 자바 프로그램에서 해 보기 | 제14.2.3절 |
| 데이터 이관(평문을 암호문으로) 연습 | 제14.2.4절 |

#### 14.2.1 켜기

**접속.** `SYS`, 대상 PDB. 설치 패키지 폴더에서 `sqlplus` 를 시작한다.

**실행.**

```
@sql/09_test/910_dev_mode_on.sql
```

현재 설정이 나온 뒤 `DEV` 를 입력해야 켜진다. 켜지면 응용 인증 모드가 `SIMPLE` 이 된다.

**확인.** 「APPCTX_MODE = SIMPLE (개발 모드 켬)」이 나온다.

#### 14.2.2 SQL\*Plus에서 바로 해 보기

**접속.** 업무 계정. 이 계정에 `480_connect_app_schema.sql` 이 실행되어 있어야 한다.

**실행.** 세션을 등록한 같은 접속(같은 창)에서 호출한다. 아래 `개발자1` 은 시험용 응용 사용자 이름이며 아무 이름이나 된다.

```sql
EXEC OCS_OWNER.PKG_SECURE_API.login('개발자1');
SELECT FN_ENC_NAME('홍길동') FROM DUAL;
SELECT FN_IDX_NAME('홍길동') FROM DUAL;
SELECT FN_MASK_NAME(FN_ENC_NAME('홍길동')) FROM DUAL;
```

암호화(`FN_ENC_`), 색인(`FN_IDX_`), 마스킹(`FN_MASK_`)은 **복호화 자격이 없어도** 된다. 세션을 등록하지 않고 부르면 `ORA-20521` 이다.

**복호화(`FN_DEC_`)는 자격이 따로 필요하다.** 키 관리자(`OCS_KEYADM`)가 시험용으로 부여한다. `<업무계정>` 은 이름으로 바꾼다.

```sql
BEGIN
  OCS_OWNER.PKG_KEY_ADMIN.grant_reveal('NAME', '<업무계정>', 'USER', NULL, '개발 시험');
  COMMIT;
END;
/
```

그 뒤 같은 창에서 `SELECT FN_DEC_NAME(FN_ENC_NAME('홍길동')) FROM DUAL;` 이 평문을 돌려준다. 끝나면 `revoke_reveal('NAME', '<업무계정>', 'USER')` 로 거둔다.

#### 14.2.3 자바에서 해 보기

증표 키를 읽는 코드 없이 세션 등록만 하는 생성자를 쓴다. **개발·시험 전용이다.**

```java
OcsSessionSupport session = new OcsSessionSupport(null);   // 증표 없이 등록만
Connection con = dataSource.getConnection();
try {
    session.establish(con, "개발자1");
    // 이 연결로: INSERT ... VALUES (FN_ENC_NAME(?), FN_IDX_NAME(?)) 등
} finally {
    session.release(con);
    con.close();
}
```

운영으로 옮길 때는 `new OcsSessionSupport(new OcsAppProof(증표키))` 로 바꾸기만 하면 같은 코드가 증표 검증을 거친다(제6.1절).

설치 매뉴얼의 연동 확인(제4.2절)의 연동 확인 프로그램(`OcsConnectDemo`)은 운영 방식(증표 제출)을 확인하는 것이라, 개발 모드에서는 항목에 따라 결과가 달라질 수 있다. 이 부분은 확인하지 않았다.

#### 14.2.4 데이터 이관 연습

평문 컬럼을 암호문과 색인 컬럼으로 옮기는 연습이다. 제14.2.3절의 연결 안에서 일정 건수씩 묶어 처리하고 매번 커밋한다.

```java
PreparedStatement ps = con.prepareStatement(
  "UPDATE 내테이블 SET rrn_enc = FN_ENC_RRN(rrn_plain), rrn_idx = FN_IDX_RRN(rrn_plain) " +
  " WHERE rrn_enc IS NULL AND ROWNUM <= ?");
ps.setInt(1, 5000);
int n;
do { n = ps.executeUpdate(); con.commit(); } while (n > 0);
```

`WHERE rrn_enc IS NULL` 이 처리 완료 지점을 데이터에 남기므로 중간에 멈춰도 다시 실행하면 이어진다. 컬럼 이름은 현장에 맞게 바꾸라. 끝난 뒤에는 건수, 표본 복호화, 색인 검색 결과를 평문 검색과 견주어 검증한다(설계서 제13장). **시험 데이터는 실제 개인정보가 아닌 값**으로 하라.

## 15. 근거와 확인 범위

호출 규격, 세션 등록 요구, 마스킹과 자격과 임계치의 동작은 `200_pkg_secure_api.sql` 과 `190_pkg_crypto_policy.sql` 의 본문을 직접 읽은 결과다. 신뢰도: 높음. 암호문 길이 산식은 참조 구현으로 실측했다. 신뢰도: 높음.

| 구분 | 내용 |
|---|---|
| 확인된 것 | 제3장 예제 프로그램(`MemberExample`)의 가입, 상세, 목록, 검색, 수정, 비밀번호 확인, 삭제와 세션 등록·해제. 투명화 뷰 예시(`800`)와 사용 예시(`810`)의 객체 생성. 뷰로 넣고 꺼내고 색인으로 찾고 고치고 지우는 흐름과 컬럼 하나만 고칠 때 그 암호문만 바뀌는 것(연동 확인 프로그램의 `--data`, `--keep`, `--read`, `--staff`). 증표를 제출한 자바 세션에서의 `FN_` 호출(`OcsFnCheck`). 문맥 없는 호출의 거부. 복호화 자격이 없을 때의 거부와 자격 부여·회수의 즉시 반영. 개발 모드를 켜고 끄는 것과 `login` 한 줄 뒤의 암호화. 원본 테이블에 직접 저장, 자격이 없을 때의 `FN_REVEAL` 거부와 `FN_SHOW` 마스킹, 안쪽에서 먼저 자르는 페이징, 색인 검색, 색인끼리의 조인과 집계, 비밀번호 저장과 검증과 빈 값 거부, 저장 프로시저, 없는 도메인 코드의 거부와 되돌리기, 복호화 사용량 임계치의 차단(`OcsRecipeCheck`) |
| 확인되지 않은 것 | 제6.2절의 `OcsWork` 의 실행(컴파일만 확인했다). MyBatis 매퍼 XML 자체(같은 SQL 은 자바 `PreparedStatement` 로 확인했다). 비밀번호의 점진 상향과 기존 체계 이행. 데이터베이스 안에서만 도는 배치의 문맥. 전자정부 표준프레임워크 자체 암호화 서비스의 정확한 클래스 이름 |

확인되지 않은 호출문은 명세와 대조해 적었다(신뢰도: 중간). 처음 적용할 때 한 건씩 확인하라. 데이터베이스 안에서만 도는 배치가 `PROOF` 모드에서 세션을 등록할 수 없다는 서술은 설계 주석에서 따른 추론이다(정확도: 중간).

### 요약

호출할 것은 `OCS_OWNER.PKG_SECURE_API` 하나이며 암복호화는 데이터베이스가 한다. 가장 먼저 할 일은 세션을 등록하는 것으로, 암호화·색인·복호화 모두 등록이 필요하고 등록한 그 연결에서 써야 하며 연결을 닫기 전 `finally` 에서 등록을 해제해야 한다. 저장할 때는 암호문 컬럼(`RAW(256)`)과 색인 컬럼(`RAW(32)`)을 함께 채우고, 검색은 색인 컬럼으로 하며, 부분 일치와 범위 검색과 정렬은 지원하지 않으므로 업무 협의로 요건을 조정한다. 목록은 마스킹, 상세만 평문으로 나누고, 대량 추출은 승인된 별도 작업으로 분리한다. 트리거의 `UPDATING('컬럼')` 은 `UPDATE` 구문 안이 아니라 `IF` 에서 쓴다. 예외는 삼키지 말고 다시 던지며, 평문은 로그·세션·캐시에 남기지 않는다. 비밀번호는 별도 경로로, 복구할 수 없고 문맥이 필요 없으며 일부러 느리므로 로그인 한 번에 한 번만 검증하고, 없는 계정에도 같은 시간을 들이며, 로그인 성공 시점에 반복 횟수를 점진적으로 올린다.
