# DB 암호화 시스템 개발자 매뉴얼

## 0. 이 문서를 읽는 법

대상은 이 시스템을 이용해 **자바 프로그램 또는 PL/SQL 프로그램**을 개발하는 분입니다. 개인정보(주민등록번호, 성명, 연락처, 계좌번호 등)를 저장·조회·검색하는 일과 비밀번호를 다루는 일을 모두 포함합니다. 운영과 키 관리는 `유지보수_매뉴얼.md` 에 있습니다.

파일 이름에 「비밀번호」가 들어 있으나 이 문서는 암호화 전반을 다룹니다. 다른 문서가 참조하므로 이름은 바꾸지 않았습니다.

| 표시 | 뜻 |
|---|---|
| **할 일** | 개발할 때 실제로 해야 하는 것 |
| **확인** | 무엇이 나와야 정상인가 |
| **주의** | 어기면 사고가 나는 것 |
| 인용 표시(`>`) 「설명」 | 이유와 배경. **읽지 않아도 개발은 됩니다** |

**시험 인스턴스에서 바로 시험해 보려면** `docs/개발자/개발모드_빠른시작.md` 를 먼저 보십시오(증표 키 없이 `login` 한 줄로 문맥을 세우는 개발 모드이며 운영에서는 쓰지 않습니다).

처음에는 제1장과 제2장, 필요한 주제의 장만 보십시오. 오류가 났다면 제11장입니다.

## 1. 반드시 지킬 여덟 가지

| # | 규칙 | 어기면 |
|---|---|---|
| 1 | 호출할 패키지는 `OCS_OWNER.PKG_SECURE_API` **하나뿐**이다 | 하위 계층은 권한이 없어 호출 불가 |
| 2 | 암복호화는 **데이터베이스가 한다**. 애플리케이션은 키를 갖지 않는다 | 앱 서버가 침해되면 키까지 잃음 |
| 3 | 세션마다 **접속 문맥**을 세우고, 반납 전에 **`finally` 에서 거둔다** | 암호화·복호화 거부(`ORA-20521`) 또는 **남의 문맥을 물려받음** |
| 4 | 암호문 컬럼과 **색인 컬럼을 함께** 채운다 | 그 행은 이후 검색되지 않음 |
| 5 | 검색은 **색인 컬럼**으로 한다. 암호화 컬럼을 조건절에 쓰지 않는다 | 전 행 복호화 → 성능 붕괴, 임계치 차단 |
| 6 | 암복호화 호출의 **예외를 삼키지 않는다** | 암호문 자리에 널이 들어가고 뒤늦게 발견됨 |
| 7 | 로그·세션·캐시에 **평문을 남기지 않는다** | 암호화의 의미가 사라짐 |
| 8 | 비밀번호는 **양방향으로 암호화하지 않는다**. 전용 함수를 쓴다 | 복구 가능 = 누군가 꺼내 볼 수 있음 |

> **설명.** 규칙 1·2 는 설계의 토대입니다. 복호화 요청이 정책 계층(문맥, 자격, 사용량 판정)을 우회할 수 없는 것은 하위 계층에 어떤 계정도 실행 권한이 없기 때문입니다. 편의를 위해 이 구조를 우회하는 코드를 만들면 통제가 통째로 무너집니다.

## 2. 시작하기 전 준비

**할 일.** 개발을 시작하기 전에 아래를 확인하고, 없는 것은 해당 담당자에게 요청하십시오.

| 필요한 것 | 누구에게 | 확인 방법 |
|---|---|---|
| 응용 계정이 `PKG_SECURE_API` 를 **직접** 실행할 수 있음 | 키 관리자 | `SELECT OCS_OWNER.PKG_SECURE_API.ready FROM DUAL;` 가 `1` |
| 쓸 **도메인**이 등록되어 있음 | 키 관리자 | 도메인 코드(`RRN`, `NAME`, `PHONE`, `ACCOUNT` 등)를 문의 |
| 복호화가 필요하면 **복호화 자격** | 키 관리자 | 자격이 없으면 마스킹된 값만 나옴(오류 아님) |
| **증표 키**(운영) | 키 관리자·보안 담당자 | 앱 서버 설정에 안전하게 주입. 소스·설정 파일 평문 금지 |
| 개발 환경의 `APPCTX_MODE` | 키 관리자 | 개발은 `SIMPLE`(증표 없이 문맥 설정), 운영은 `PROOF` |

**주의.** 응용 계정이 PL/SQL 객체(뷰, 프로시저, 트리거)에서 `PKG_SECURE_API` 를 부르려면 실행 권한이 **역할이 아니라 계정에 직접** 부여되어 있어야 합니다. 역할로 받은 권한은 저장 객체 안에서 인정되지 않습니다. 설치 스크립트가 이를 이미 직접 부여합니다. 컴파일 오류 `PLS-00201` 이 나면 키 관리자에게 알리십시오.

## 3. 호출 규격

### 3.1 일반형 함수

| 함수 | 용도 | 반환 | 문맥 | 복호화 자격 | 사용량 집계 |
|---|---|---|---|---|---|
| `protect(도메인, 평문)` | 암호화 | `RAW` | 필요 | 불필요 | 아님 |
| `search_of(도메인, 평문)` | 검색용 색인 생성 | `RAW` | 필요 | 불필요 | 아님 |
| `reveal(도메인, 암호문)` | 복호화 | `VARCHAR2` | 필요 | **필요**(없으면 예외) | **집계·임계치** |
| `masked(도메인, 암호문)` | 마스킹된 값 | `VARCHAR2` | **검사 안 함** | 불필요 | 아님 |
| `show(도메인, 암호문)` | 자격 있으면 평문, 없으면 마스킹 | `VARCHAR2` | 문맥 없으면 마스킹 | 있으면 평문 | 평문일 때만 |
| `allowed(도메인)` | 평문을 볼 자격이 있는가 | `'Y'` 또는 `'N'` | 없으면 `'N'` | 판정만 | 아님 |
| `ready` | 암복호화 가능 상태인가 | `1` 또는 `0` | 불필요 | 불필요 | 아님 |
| `login(사용자, 시각, 증표)` / `logout` | 문맥 설정·해제 | — | — | — | — |

입력이 널이면 `protect`, `search_of`, `reveal`, `masked`, `show` 는 모두 널을 돌려줍니다.

> **설명.** `masked` 는 마스킹을 만들기 위해 내부에서 복호화하지만 평문은 함수 밖으로 나가지 않습니다. 복호화 실패 시 예외 대신 `********` 를 돌려주고 감사 기록에 남기므로 **한 건의 손상이 목록 전체를 막지 않습니다.** 대신 복호화 비용은 그대로 들므로, 대량 목록에서는 마스킹된 값을 별도 컬럼에 저장해 두는 편이 낫습니다. `show` 는 자격이 없으면 오류가 아니라 마스킹으로 처리하므로 화면마다 권한 분기를 두지 않아도 됩니다. 자격이 없을 때 **오류로 처리해야 하는 화면**이라면 `reveal` 을 직접 쓰십시오.

### 3.2 도메인 전용 함수

표준 도메인에는 이름으로 호출할 수 있는 함수가 있습니다. 호출 지점을 이름으로 검색하면 어느 화면이 평문을 쓰는지 바로 드러나도록 한 것입니다.

| 도메인 | 암호화 | 복호화 | 마스킹 | 색인 |
|---|---|---|---|---|
| 주민등록번호 `RRN` | `enc_rrn` | `dec_rrn` | `mask_rrn` | `idx_rrn` |
| 성명 `NAME` | `enc_name` | `dec_name` | `mask_name` | `idx_name` |
| 계좌번호 `ACCOUNT` | `enc_account` | `dec_account` | `mask_account` | `idx_account` |
| 그 밖(`PHONE` 등) | `protect('PHONE', …)` | `reveal('PHONE', …)` | `masked('PHONE', …)` | `search_of('PHONE', …)` |

**주의.** 도메인 코드는 임의로 지을 수 없고 키 관리자가 등록한 것만 씁니다. 없는 코드를 넘기면 `ORA-20530` 입니다.

### 3.2.1 짧은 함수 이름으로 부르기

패키지 이름 없이 쿼리에서 바로 쓰도록, `PKG_SECURE_API` 의 함수마다 `FN_` 으로 시작하는 같은 동작의 단독 함수가 있습니다. 이름은 `FN_` 뒤에 패키지 함수 이름을 대문자로 붙인 것입니다.

| 패키지 호출 | 짧은 호출 |
|---|---|
| `OCS_OWNER.PKG_SECURE_API.enc_rrn(:v)` | `FN_ENC_RRN(:v)` |
| `OCS_OWNER.PKG_SECURE_API.idx_rrn(:v)` | `FN_IDX_RRN(:v)` |
| `OCS_OWNER.PKG_SECURE_API.show('RRN', c)` | `FN_SHOW('RRN', c)` |
| `OCS_OWNER.PKG_SECURE_API.masked('RRN', c)` | `FN_MASKED('RRN', c)` |

**쓰려면** 설치 담당자가 업무 계정을 암호 모듈에 연결해 두어야 합니다. 설치 매뉴얼의 업무 계정 연결(`480_connect_app_schema.sql`)이 실행 권한과 시노님을 만듭니다. 열려 있지 않으면 `ORA-00904` 나 `ORA-00942` 가 나므로 키 관리자에게 알리십시오. 동작과 통제(문맥, 복호화 자격, 마스킹, 감사)는 패키지를 직접 부를 때와 같습니다. `login`, `logout` 은 프로시저이므로 패키지 이름으로 부릅니다. 전체 대응표는 설치 매뉴얼 제7.10절에 있습니다.

### 3.3 암호문과 색인의 크기

**할 일.** 컬럼 크기를 아래로 잡으십시오.

| 컬럼 | 형 | 근거 |
|---|---|---|
| 암호문 | `RAW(256)` | 평문 **191바이트(UTF-8)** 까지 담음 |
| 색인 | `RAW(32)` | 고정 32바이트 |
| 비밀번호 저장값 | `RAW(64)` | 고정 54바이트 |

암호문 길이는 `52 + 16 × (⌊n / 16⌋ + 1)` 바이트이며 `n` 은 평문의 UTF-8 바이트 수입니다(한글 한 글자는 3바이트). 주민등록번호 13자리는 68바이트입니다.

**주의.** 암호문은 **문자열 컬럼에 담지 마십시오.** 이진값이라 문자집합 변환에서 손상됩니다. 컬럼이 짧으면 암호문이 잘려 들어가고, 잘린 값은 영원히 복호화에 실패(`ORA-20511`)합니다. 개발 중 복호화가 계속 실패하면 컬럼 정의부터 보십시오.

> **설명.** 길이 산식은 파이썬 참조 구현으로 직접 확인했습니다(0, 13, 16, 207, 208바이트에서 68, 68, 84, 260, 276). 데이터베이스와 자바 구현은 같은 고정 시험 벡터로 대조되므로 같은 길이를 냅니다.

## 4. 세션 문맥

복호화뿐 아니라 **암호화와 색인 생성에도** 문맥이 필요합니다(`require_app_ctx = 'Y'` 인 도메인). 문맥 없이 호출하면 `ORA-20521` 입니다.

> **설명.** 색인은 같은 평문이면 항상 같은 값이 나옵니다. 응용 계정 접속 정보를 가진 사람이 후보 평문을 넣어 색인을 계산하고 저장된 색인과 맞춰 보면 평문을 알아낼 수 있으므로(주민등록번호는 생년월일을 알면 후보가 백만 개 수준), 복호화만 막고 색인을 열어 두면 통제가 성립하지 않습니다.

### 4.1 자바에서 세우기

**할 일.** 앱 기동 때 한 번 만들고, 연결을 빌릴 때마다 세우고, 반납 전에 `finally` 에서 거둡니다.

```java
// 기동 시 한 번. 증표 키는 소스·설정 파일에 평문으로 두지 말 것.
OcsAppProof proof = new OcsAppProof(loadAppCtxKeyFromSecureStore());   // 32바이트
OcsSessionSupport session = new OcsSessionSupport(proof);

Connection con = dataSource.getConnection();
try {
    session.establish(con, currentUserId());   // 업무 사용자 식별자(DB 계정이 아님)
    // ... 이 연결로 수행하는 모든 조회와 갱신 ...
} finally {
    boolean ok = session.release(con);          // 실패해도 업무를 되돌릴 수는 없으므로 로그만
    if (!ok) { log.warn("문맥 해제 실패"); }
    con.close();
}
```

**확인.** `session.establish` 가 예외 없이 돌아오고, 같은 연결에서 `SELECT OCS_OWNER.PKG_SECURE_API.allowed('RRN') FROM DUAL` 이 오류 없이 `Y` 또는 `N` 을 돌려줍니다.

| 흔한 실수 | 증상 | 고치는 법 |
|---|---|---|
| 문맥을 세운 연결과 **다른 연결**로 조회 | `ORA-20521` | 트랜잭션 경계 안에서 같은 연결 유지 |
| 연결 풀에 **거두지 않고** 반납 | 다음 사용자가 **앞 사람의 문맥을 물려받음**. 권한이 남의 것으로 판정 | `finally` 에서 반드시 `release` |
| 앱 서버와 DB 서버의 **시각 차이** | `ORA-20521`(증표 유효 시간 초과, 기본 300초) | 시각 동기화 |
| 증표 키가 DB의 키와 다름 | `ORA-20521`(증표 불일치) | 키 관리자에게 현재 키 확인. 재설치마다 새로 만드는 값 |

서비스마다 반복하지 말고 연결을 내어 주는 지점(데이터 소스 래퍼, AOP)에서 자동으로 호출되게 하십시오.

**주의.** `new OcsSessionSupport(null)` 은 증표 없이 문맥만 세웁니다. **개발·시험 전용**이며 운영에서 쓰면 이 통제는 없는 것과 같습니다. 데이터베이스의 `APPCTX_MODE` 도 `SIMPLE` 이어야 동작하고, 운영 전환 점검이 이 설정을 확인합니다.

### 4.2 PL/SQL에서 세우기

자바 없이 직접 세울 때(시험이나 배치 도구)의 호출입니다.

```sql
BEGIN
  OCS_OWNER.PKG_SECURE_API.login('<업무사용자>', <epoch>, HEXTORAW('<증표>'));   -- PROOF 모드
  -- OCS_OWNER.PKG_SECURE_API.login('<업무사용자>');                           -- SIMPLE 모드(개발)
  -- ... 암복호화 ...
  OCS_OWNER.PKG_SECURE_API.logout;
END;
/
```

증표는 `HMAC-SHA256(증표 키, 응용사용자 || '|' || epoch || '|' || 세션식별자)` 입니다. epoch 는 UTC 기준 초이고 세션 식별자는 `SYS_CONTEXT('USERENV','SID')` 입니다. 증표에 세션이 묶여 있어 **다른 세션에서 만든 증표는 쓸 수 없습니다.** 증표 키는 데이터베이스 밖에 있으므로 PL/SQL 안에서 계산하지 않고 자바 등 앱 계층이 만들어 넘깁니다.

**주의.** 이 설계상 **데이터베이스 안에서만 도는 PL/SQL 배치**(예: 스케줄러 작업)는 증표 키가 없어 `PROOF` 모드에서 스스로 문맥을 세울 수 없습니다. 이는 설계 주석에서 따른 추론이며 이 구성을 실제로 시험하지는 않았습니다. **데이터베이스 안 배치가 필요하면 설계 단계에서 키 관리자·보안 담당자와 방식을 합의하십시오.** 임의로 `SIMPLE` 로 바꾸지 마십시오.

## 5. 저장과 조회

### 5.1 투명화 뷰를 쓰는 경우 (권장)

기존 테이블 이름으로 뷰를 만들면 응용 쿼리를 거의 고치지 않아도 됩니다. 평문을 넣으면 트리거가 암호화와 색인 생성을 대신합니다.

**할 일.** 저장은 평소처럼 평문을 넣습니다.

```xml
<insert id="insertMember" parameterType="memberVO">
  INSERT INTO TB_MEMBER (mbr_id, mbr_name, mbr_rrn, mbr_phone)
  VALUES (#{mbrId}, #{mbrName}, #{mbrRrn}, #{mbrPhone})
</insert>
```

조회도 평소처럼 합니다. 평문 컬럼은 `show` 를 거치므로 **자격이 있으면 평문, 없으면 마스킹**입니다.

**주의.** 목록 화면은 뷰의 **마스킹 전용 컬럼**(`mbr_rrn_masked` 같은)을 쓰고, 상세 화면에서만 평문 컬럼을 읽도록 쿼리를 나누십시오. 평문 컬럼을 목록에서 읽으면 행마다 복호화가 일어납니다.

만드는 방법은 `sql/08_sample/800_sample_member.sql` 이 최소 구성, `sql/08_sample/810_usage_examples.sql` 이 더 완전한 본보기입니다. 업무 테이블에 적용할 때 바꿀 것은 테이블·컬럼 이름과 도메인 코드뿐입니다.

### 5.2 트리거를 직접 작성할 때

뷰의 `INSTEAD OF` 트리거를 손수 쓸 때는 아래 네 가지를 지키십시오.

| 규칙 | 이유 |
|---|---|
| 뷰에 보이는 컬럼은 **하나도 빠짐없이** `UPDATE` 분기에 둔다 | 빠진 컬럼은 오류 없이 **갱신이 조용히 사라짐**(한 행 갱신됨으로 나옴) |
| `UPDATING('컬럼명')` 은 **`IF` 같은 PL/SQL 조건식에서만** 쓴다. `UPDATE` 구문 안의 `CASE` 에 넣지 않는다 | `PLS-00231` 로 트리거가 컴파일되지 않음 |
| 바뀐 컬럼만 다시 암호화한다 | 조건 없이 전부 다시 암호화하면 값이 같아도 초기화 벡터가 새로 생겨 암호문이 바뀜 |
| 읽기 전용 컬럼(마스킹·색인 컬럼)은 일부러 빼고 주석으로 남긴다 | 의도를 구분 |

```sql
ELSIF UPDATING THEN
  UPDATE TB_MEMBER_ENC SET mbr_pwd = :NEW.mbr_pwd, join_dt = :NEW.join_dt
   WHERE mbr_id = :OLD.mbr_id;

  IF UPDATING('MBR_RRN') THEN
    UPDATE TB_MEMBER_ENC
       SET mbr_rrn_enc = OCS_OWNER.PKG_SECURE_API.enc_rrn(:NEW.mbr_rrn),
           mbr_rrn_idx = OCS_OWNER.PKG_SECURE_API.idx_rrn(:NEW.mbr_rrn)
     WHERE mbr_id = :OLD.mbr_id;
  END IF;
```

**주의.** 뷰는 원본 테이블에 대한 **직접 접근을 막지 못합니다.** 원본(`…_ENC`) 테이블의 권한을 필요한 계정에만 두십시오. 뷰를 제3자에게 넘기려 하면 `ORA-01720` 이 날 수 있는데, 응용 계정에 재부여 권한을 주지 않는 것이 맞으므로 **자료를 넣고 꺼내는 일은 조회 도구가 아니라 애플리케이션이 하도록** 하십시오.

### 5.3 투명화 뷰 없이 직접 쓰는 경우

실제 테이블에 직접 넣을 때는 함수를 명시적으로 부르고, **암호문과 색인을 함께** 채웁니다.

```xml
<insert id="insertMemberEnc" parameterType="memberVO">
  INSERT INTO TB_MEMBER_ENC (mbr_id, mbr_name_enc, mbr_name_idx, mbr_rrn_enc, mbr_rrn_idx, mbr_phone_enc)
  VALUES (#{mbrId},
          OCS_OWNER.PKG_SECURE_API.enc_name(#{mbrName}), OCS_OWNER.PKG_SECURE_API.idx_name(#{mbrName}),
          OCS_OWNER.PKG_SECURE_API.enc_rrn(#{mbrRrn}),   OCS_OWNER.PKG_SECURE_API.idx_rrn(#{mbrRrn}),
          OCS_OWNER.PKG_SECURE_API.protect('PHONE', #{mbrPhone}))
</insert>
```

바인드 변수를 쓰십시오. 문자열을 이어 붙이면 주입 통로가 되고, 평문이 실행 계획 캐시와 추적 파일에 남습니다.

복호화가 필요한 조회입니다. 자격이 없으면 예외입니다.

```xml
<select id="selectMemberRrn" resultType="string">
  SELECT OCS_OWNER.PKG_SECURE_API.dec_rrn(mbr_rrn_enc) FROM TB_MEMBER_ENC WHERE mbr_id = #{mbrId}
</select>
```

화면에서 미리 권한을 알고 분기하려면 `allowed` 로 판정만 물으십시오. 복호화하지 않으므로 사용량에도 잡히지 않습니다.

```sql
SELECT OCS_OWNER.PKG_SECURE_API.allowed('RRN') FROM DUAL
```

## 6. 암호화 컬럼 다루기

실제 개발에서 가장 많이 부딪히는 부분입니다. 암호문은 같은 평문이라도 **매번 다르게** 만들어지므로 예전처럼 다룰 수 없습니다.

| 하려는 일 | 지원 | 방법 |
|---|---|---|
| 일치 검색 | 가능 | **색인 컬럼** 사용(6.1) |
| 부분 일치(LIKE), 범위 검색 | **불가** | 업무 협의로 요건 조정(6.2) |
| 정렬 | **불가** | 다른 컬럼으로 정렬(6.2) |
| 조인 | 가능 | **같은 도메인**의 색인끼리(6.3) |
| 집계(`GROUP BY`) | 가능 | 색인 컬럼으로 묶기(6.3) |
| 합계·평균 | 대상 아님 | 그 컬럼이 암호화 대상인지 재검토 |

### 6.1 검색

**할 일.** 조건절의 평문 비교를 색인 비교로 바꿉니다.

```sql
-- 고치기 전: 전 행을 복호화한 뒤 비교. 성능이 무너지고 임계치에 걸린다.
SELECT * FROM TB_MEMBER WHERE mbr_rrn = '880101-1234567';

-- 고친 뒤: 인덱스를 타고 한 건만 찾는다.
SELECT * FROM TB_MEMBER_ENC WHERE mbr_rrn_idx = OCS_OWNER.PKG_SECURE_API.idx_rrn('880101-1234567');
```

색인값은 입력을 도메인별로 다듬은 뒤 계산하므로 **하이픈이 있든 없든 같은 행**을 찾습니다. 성명의 앞뒤 공백도 같습니다.

**주의.** 색인 컬럼에만 인덱스를 만드십시오. **암호문 컬럼에 인덱스를 만들지 마십시오**(값이 매번 달라 쓸 수 없고 비용만 듭니다).

### 6.2 부분 일치, 범위, 정렬

기술적 한계가 아니라 **그렇게 만들면 안 되는 것**입니다. 순서를 보존하면 순서 정보가 새고, 앞 몇 글자씩 따로 색인을 만들면 만든 만큼 노출이 늘어납니다.

| 요건 | 대안 |
|---|---|
| 성명 부분 검색 | 사번·회원번호 같은 다른 식별자로 검색 |
| 전체 목록에서 찾기 | 조회 범위를 부서·담당 건으로 좁힘 |
| 이름순 정렬 | 등록일시·식별자순. 꼭 필요하면 정렬용 컬럼을 따로 두되 **노출 범위를 문서로 남기고 승인** |

### 6.3 조인과 집계

```sql
-- 조인: 양쪽에 색인 컬럼을 두고 색인끼리 비교
SELECT a.*, b.* FROM TB_MEMBER_ENC a JOIN TB_ORDER_ENC b ON a.mbr_rrn_idx = b.ord_rrn_idx;

-- 집계: 색인으로 묶으면 복호화 없이 된다
SELECT mbr_rrn_idx, COUNT(*) FROM TB_ORDER_ENC GROUP BY mbr_rrn_idx;
```

**주의.** **도메인이 다르면 키가 달라 색인값이 맞지 않습니다.** 조인할 두 컬럼은 같은 도메인으로 등록되어야 하며, 컬럼 분류 단계에서 확인하십시오. 나중에 바꾸려면 재암호화가 필요합니다.

### 6.4 목록과 페이징

복호화·마스킹 함수를 건 채로 페이징하면 **전체 행에 함수가 적용된 뒤** 잘립니다. 안쪽 조회에서 먼저 자르고 바깥에서 함수를 거십시오.

```sql
SELECT OCS_OWNER.PKG_SECURE_API.masked('RRN', t.mbr_rrn_enc) AS mbr_rrn, t.*
  FROM ( SELECT * FROM TB_MEMBER_ENC WHERE dept_cd = :dept_cd
          ORDER BY mbr_id OFFSET :first ROWS FETCH NEXT :size ROWS ONLY ) t
```

### 6.5 대량 추출과 배치

복호화에는 **사용량 임계치**가 걸려 있습니다. 평소보다 현저히 많은 복호화는 차단(`ORA-20522`)되고 경보가 올라갑니다. 계정 탈취 시 피해를 줄이기 위한 장치입니다.

| 상황 | 해야 할 일 |
|---|---|
| 업무상 대량 추출·엑셀 내려받기 | 일반 조회 경로로 만들지 말고 **승인된 별도 작업**으로 분리, 키 관리자와 협의. 마스킹된 값으로 충분한지 먼저 검토 |
| 임계치에 걸림 | 대개 암호화 컬럼을 조건절에 쓴 쿼리가 전 행을 복호화 중. 6.1 로 고침. 정상 업무량이면 키 관리자와 협의 |
| 배치 | **배치 전용 사용자 식별자**로 문맥을 세워 감사 기록에서 사람과 구분. 행마다 호출하지 말고 묶어서 처리 |

## 7. 자바 프로그램 개발

### 7.1 대부분은 데이터베이스 함수를 부르면 됩니다

일상 업무 개발에서 자바 연동 모듈(`ocsecure.client`)을 쓰는 곳은 **접속 증표와 세션 문맥**(제4장)뿐입니다. 암복호화는 제5장처럼 SQL 안에서 데이터베이스 함수로 합니다.

| 클래스 | 용도 |
|---|---|
| `OcsAppProof` | 접속 증표 계산 |
| `OcsSessionSupport` | 문맥 설정·해제 |
| `OcsCrypto` | 암호문 포맷, 비밀번호 계산. **데이터베이스를 거치지 않는 처리**용 |
| `OcsKeySet` | 키 묶음(`OcsCrypto` 직접 사용 시) |
| `OcsCryptoException` | 연동 모듈 예외 |

### 7.2 자바에서 직접 암복호화하는 경우

외부 기관과 파일로 자료를 주고받는 연계처럼 **데이터베이스를 거치지 않는 처리**에만 `OcsCrypto` 를 직접 씁니다.

```java
OcsKeySet key = new OcsKeySet(keyId, OcsCrypto.ALG_AES256_CBC_HMAC_SHA256, encKey, macKey, idxKey);
byte[] cipher = OcsCrypto.encrypt("880101-1234567", key);
String plain  = OcsCrypto.decrypt(cipher, key);
```

이 코드가 만드는 암호문은 데이터베이스가 만드는 것과 **바이트 단위로 같습니다**(같은 고정 시험 벡터로 대조).

**주의.** 이 경로를 쓰면 **애플리케이션이 키를 다루게 되어** 데이터베이스 쪽 통제(문맥, 자격, 사용량, 감사)가 우회됩니다. 키를 어디에 두고 누가 접근하는지가 새 문제로 생기므로, 이 경로를 여는 것은 **예외적인 결정으로 보안 담당자의 승인**을 받아야 합니다. 편의로 쓰기 시작하지 마십시오.

### 7.3 예외 처리

키 저장소가 닫혀 있거나 권한이 없으면 모듈은 **예외를 냅니다.** 널을 돌려주거나 평문을 그대로 저장하는 일은 없으며, 응용은 이 동작을 깨뜨리지 않아야 합니다.

**할 일.**

```java
try {
    // 암복호화가 들어간 DB 작업
} catch (SQLException e) {
    // 로그만 남기고 넘어가지 말 것. 다시 던지거나 트랜잭션을 되돌린다.
    con.rollback();
    throw e;
}
```

**주의.** 예외를 넓게 잡아 삼키면 암호문이 들어갈 자리에 널이 들어가고 **한참 뒤에 드러납니다.** 가장 흔한 사고입니다.

멈춘 상태를 이용자에게 어떻게 보일지는 따로 챙기십시오. 화면 진입 전에 아래를 물어 갈라서 안내 화면을 내보내면 오류 추적이 그대로 노출되지 않습니다.

```sql
SELECT OCS_OWNER.PKG_SECURE_API.ready FROM DUAL   -- 1 가능, 0 불가
```

`0` 이 이어지면 키 저장소 유지 프로그램이 멈춘 것이므로 운영자에게 알리십시오. 감시 도구의 상태 점검에도 같은 값을 씁니다.

## 8. PL/SQL 프로그램 개발

### 8.1 기본 틀

**할 일.** 저장 프로시저에서 암복호화를 부르는 틀입니다. 문맥은 **프로시저를 호출한 세션**에 이미 서 있다고 전제합니다(제4장).

```sql
CREATE OR REPLACE PROCEDURE SP_MEMBER_SAVE(p_id IN NUMBER, p_rrn IN VARCHAR2) IS
BEGIN
  IF OCS_OWNER.PKG_SECURE_API.ready = 0 THEN
    RAISE_APPLICATION_ERROR(-20999, '암호 모듈을 쓸 수 없는 상태입니다.');   -- 값은 포함하지 말 것
  END IF;

  INSERT INTO TB_MEMBER_ENC (mbr_id, mbr_rrn_enc, mbr_rrn_idx)
  VALUES (p_id,
          OCS_OWNER.PKG_SECURE_API.enc_rrn(p_rrn),
          OCS_OWNER.PKG_SECURE_API.idx_rrn(p_rrn));
  -- EXCEPTION 절에서 WHEN OTHERS THEN NULL 로 삼키지 말 것
END;
/
```

### 8.2 PL/SQL에서 주의할 것

| 항목 | 규칙 |
|---|---|
| 권한 | `PKG_SECURE_API` 실행 권한은 **계정에 직접** 있어야 컴파일된다(역할 권한은 저장 객체 안에서 불인정). 없으면 `PLS-00201` |
| SQL 안에서 호출 | 함수는 SQL 문에서 직접 쓸 수 있다. `verify_pwd`, `pwd_stale` 은 불리언 대신 `1`/`0` 을 돌려주는 이유 |
| 예외 | 삼키지 않는다. `WHEN OTHERS` 로 잡았다면 **반드시 다시 던진다** |
| 평문 | 로그 테이블, `DBMS_OUTPUT`, 예외 메시지에 평문을 넣지 않는다 |
| 대량 처리 | 행마다 호출하면 전환 비용이 누적된다. 묶어서 읽고 묶어서 기록 |
| 대상 테이블 권한 | 재암호화 같은 모듈 배치는 `OCS_OWNER` 권한으로 돈다. 업무 테이블 권한을 `OCS_OWNER` 에 **직접** 부여해야 하며 끝나면 회수(관리자 매뉴얼 제8장) |

**주의.** 데이터베이스 안에서만 도는 배치의 문맥 문제는 제4.2절의 주의를 보십시오.

## 9. 비밀번호

비밀번호는 다른 개인정보와 **전혀 다른 경로**입니다.

| 비교 | 개인정보 | 비밀번호 |
|---|---|---|
| 복구 | 자격이 있으면 가능 | **불가능**(되돌릴 수 없음) |
| 문맥·자격 | 필요 | **불필요**(로그인 전에 검증해야 하므로) |
| 마스터 키 | 필요 | **쓰지 않음** |
| 감사 기록 | 남음 | 남지 않음 |
| 속도 | 빠름 | **일부러 느림**(반복 계산) |

따라서 **「비밀번호 찾기」는 알려 주는 기능이 아니라 새로 설정하게 하는 기능**이어야 합니다. 기획 단계에서 합의해 두지 않으면 개발 막바지에 문제가 됩니다.

### 9.1 함수와 저장

| 함수 | 용도 | 반환 |
|---|---|---|
| `make_pwd(평문)` | 저장값 생성 | `RAW`(54바이트) |
| `verify_pwd(평문, 저장값)` | 검증 | `1` 일치, `0` 불일치 |
| `pwd_stale(저장값)` | 반복 횟수가 현재 기준보다 낮은가 | `1` 갱신 필요, `0` 아님 |

**할 일.** 컬럼은 `RAW(64)` 로 잡고, 등록은 평문을 바인드 변수로 넘깁니다.

```xml
<insert id="insertUser" parameterType="userVO">
  INSERT INTO TB_USER (user_id, user_nm, user_pwd)
  VALUES (#{userId}, #{userNm}, OCS_OWNER.PKG_SECURE_API.make_pwd(#{userPwd}))
</insert>
```

**확인.** 저장 직후 `SELECT UTL_RAW.LENGTH(user_pwd) FROM TB_USER WHERE …` 가 `54` 여야 합니다. 검증이 계속 실패하면 컬럼 길이부터 의심하십시오(잘린 값은 절대 통과하지 못합니다).

| 규칙 | 이유 |
|---|---|
| 빈 값은 거부(`ORA-20541`). 화면·서버에서 **필수 입력 검증**을 둔다 | 공백만 입력된 경우처럼 걸러지지 않는 경우가 있다 |
| **복잡도 규칙은 이 시스템이 검사하지 않는다.** 응용에서 검사한 뒤 넘긴다 | 한 글자 비밀번호도 저장됨 |
| 저장값 안에 포맷·반복 횟수·솔트가 들어 있다 | 별도 컬럼 불필요, 반복 횟수를 올려도 기존 값 검증이 깨지지 않음 |

### 9.2 로그인 검증

**할 일.** 기본형입니다. 결과 `1` 일치, `0` 불일치, **조회 결과 없음은 존재하지 않는 사용자**입니다.

```xml
<select id="selectPasswordMatch" resultType="int">
  SELECT OCS_OWNER.PKG_SECURE_API.verify_pwd(#{inputPwd}, user_pwd) FROM TB_USER WHERE user_id = #{userId}
</select>
```

**주의.** **없는 계정에도 같은 시간을 들이십시오.** 존재하지 않는 계정은 즉시 끝나고 존재하는 계정은 반복 계산에 시간이 걸려, 응답 시간만으로 어떤 계정이 있는지 알아낼 수 있습니다. 기동 때 더미 저장값을 만들어 두고 없는 계정에 대해 그 값으로 검증한 뒤 실패로 처리합니다. **화면 메시지도 구분하지 마십시오**(없는 계정과 틀린 비밀번호를 같은 문구로).

```java
private final byte[] dummyStored = OcsCrypto.passwordHash("dummy-for-timing-only", currentIterations());

public boolean authenticate(String userId, String inputPwd) {
    byte[] stored = userMapper.selectPasswordBlob(userId);   // 없으면 null
    if (stored == null) {
        OcsCrypto.passwordVerify(inputPwd, dummyStored);     // 같은 시간을 들이고 결과는 버린다
        return false;
    }
    return OcsCrypto.passwordVerify(inputPwd, stored);
}
```

| 규칙 | 이유 |
|---|---|
| **로그인 한 번에 한 번만** 호출 | 일부러 느린 계산. 목록·반복문 안에서 부르면 즉시 문제 |
| 검증 **성공 후에** 세션 문맥을 세운다 | 로그인 전에는 사용자를 몰라 문맥을 세울 수 없음 |
| 로그인 실패 추적·계정 잠금은 **응용이 구현** | 이 시스템은 제공하지 않음 |

### 9.3 반복 횟수 점진 상향

관리자가 반복 횟수를 올려도 기존 사용자의 저장값은 옛 횟수 그대로입니다. 옮기는 방법은 **로그인에 성공한 그 순간**, 평문이 손에 있을 때 다시 계산해 저장하는 것입니다. 그 시점을 놓치면 영영 불가능합니다.

**할 일.**

```java
if (authenticate(userId, inputPwd)) {
    if (userMapper.selectPasswordStale(userId) == 1) {          // pwd_stale
        try {
            userMapper.updatePasswordBlob(userId, inputPwd);     // make_pwd 로 다시 저장
        } catch (Exception e) {
            log.warn("비밀번호 저장값 갱신 실패: userId={}", userId);   // 비밀번호는 로그에 찍지 않는다
        }
    }
}
```

갱신에 실패해도 **로그인을 막지 마십시오.** 다음 로그인에서 다시 시도하면 됩니다. 이 처리가 빠져 있으면 관리자 쪽 분포 확인에서 드러납니다.

### 9.4 변경과 초기화

| 상황 | 처리 |
|---|---|
| 사용자 변경 | **현재 비밀번호를 먼저 검증**한 뒤 새 값을 저장(화면을 열어 둔 채 자리를 비운 사이의 변경 방지) |
| 관리자 초기화 | 현재 비밀번호를 모르므로 검증 없음. **누가 초기화했는지는 응용이 기록**(이 시스템은 남기지 않음). 최초 로그인 때 변경 강제 |
| 임시 비밀번호 | 전자우편·문자로 보내면 평문이 경로에 남는다. **유효 시간이 짧은 재설정 링크**로 사용자가 직접 정하게 한다 |

### 9.5 자바 계층에서 계산하는 경우

기본은 데이터베이스 함수입니다. 반복 횟수를 크게 올렸는데 로그인이 몰리는 시간대에 DB 부하가 문제가 될 때만 계산을 앱 서버로 옮깁니다. **저장 형식이 같아 섞여 있어도 문제없습니다.**

```java
int iterations = configMapper.selectPwdIterations();            // 기동 시 SEC_CONFIG 에서 읽는다
byte[] stored = OcsCrypto.passwordHash(inputPwd, iterations);
```

**주의.** 반복 횟수를 앱이 따로 들면 DB 설정과 어긋날 수 있으므로 기동 시 DB에서 읽으십시오. `SEC_CONFIG` 조회 권한이 응용 계정에 없으면 키 관리자에게 읽기 권한을 요청하십시오(반복 횟수는 비밀이 아닙니다). 함수에 반복 횟수를 직접 지정하는 인자가 있으나 **시험용**이며, 업무 코드에서 임의로 낮추어 호출하지 마십시오.

### 9.6 기존 체계에서 옮겨 오기

기존 방식은 솔트 없는 단일 해시입니다. 일괄 변환은 불가능하므로 **옛 비밀번호로 로그인시키되 그 자리에서 비밀번호 변경을 강제**합니다. 임시 비밀번호 발급(강제 초기화)보다 나은 이유는 본인확인 채널이 따로 필요 없고 새 노출 경로가 생기지 않기 때문입니다.

**할 일.**

| 단계 | 내용 |
|---|---|
| 1 | 컬럼을 `VARCHAR2(108)` 로 넓힘(옛 형식 Base64 44자, 새 형식 16진 108자가 섞임). 길이 확장은 서비스 중에도 가능 |
| 2 | **배포 전 관문**: `SELECT OCS_OWNER.PKG_LEGACY_PWD.self_check('아는 평문', '그 계정의 저장값') FROM DUAL;` 가 `일치` 여야 한다. `불일치` 면 배포 금지 |
| 3 | 로그인에 `check_pwd` 사용 |
| 4 | 결과 `2` 면 로그인시키되 **변경 화면으로 강제 이동**하고 다른 화면으로 못 나가게 막는다 |
| 5 | 변경 화면은 `make_pwd_str` 로 **새 형식으로만** 저장하고 복잡도 규칙을 함께 적용 |
| 6 | 이행이 끝나면 옛 검증 코드 제거(관리자와 시점 합의) |

| `check_pwd` 결과 | 뜻 | 처리 |
|---|---|---|
| `0` | 불일치(저장값이 비어 있는 경우 포함) | 로그인 실패 |
| `1` | 일치, 현재 형식 | 로그인 |
| `2` | 일치, **옛 형식** | 로그인시키되 변경 강제 |

저장값의 상태만 먼저 보려면 `pwd_state` 를 씁니다(`0` 미설정, `1` 현재 형식, `2` 옛 형식, `9` 알 수 없는 형식). 업무포털 단일 인증 이용자는 비밀번호가 비어 있으므로 `0` 이며, 로그인 실패와 구분해 **설정 절차로 보냅니다.** `9` 는 통과시키지 말고 자료 이상으로 조사합니다.

**주의.** 옛 형식으로 검증에 성공했을 때 **같은 비밀번호를 새 형식으로 다시 저장하고 끝내지 마십시오.** 옛 방식은 이미 유출되었을 수 있어, 형식만 바꿔 담으면 알려진 비밀번호를 그대로 쓰는 셈입니다.

### 9.7 기존 방식 확인 (이행 준비)

옮겨 오려면 기존 방식을 정확히 알아야 합니다. 방법은 세 갈래이며 **마지막 하나만 확정적**입니다.

| 방법 | 하는 일 | 확실성 |
|---|---|---|
| 저장값의 생김새 | `@sql/04_admin/410_legacy_pwd_survey.sql` 을 기존 계정으로 실행. 자료형·길이 분포·문자 구성을 **세기만** 하고 저장값을 화면에 띄우지 않음 | 좁히기만 함 |
| 소스 코드 읽기 | 로그인 처리에서 비밀번호를 다루는 지점을 따라감. `encryptPassword`, `MessageDigest`, `PasswordEncoder` 로 검색 | 확실하나 시간이 걸림 |
| **실증 대조** | 평문과 그 저장값 한 쌍으로 후보 구성을 재현해 일치하는 것을 찾음 | **확정적** |

길이로 좁히는 기준입니다.

| 표기 | MD5 | SHA-1 | SHA-256 | SHA-512 |
|---|---|---|---|---|
| 16진 | 32 | 40 | 64 | 128 |
| Base64 | 24 | 28 | 44 | 88 |

60자면 bcrypt, 54면 이미 이 시스템의 형식, 길이가 제각각이면 평문이거나 가변 길이 암호화입니다. 조사 스크립트의 네 번째 항목(서로 다른 사용자가 같은 저장값을 갖는지)이 중요합니다. **중복이 있으면 솔트가 없다**는 뜻입니다.

**할 일.** 실증 대조는 시험계에 계정을 하나 만들어 비밀번호를 정해 등록한 뒤 그 계정의 저장값으로 합니다.

```
python3 tools/legacy_pwd_probe.py --plain '정한비밀번호' --stored '조회한저장값' --id '아이디'
```

해시 알고리즘 여섯 가지, 표기 다섯 가지, 아이디를 섞는 네 가지 배치, 두 번 해싱하는 변형, 문자집합 두 가지(EUC-KR 포함)를 조합해 시도합니다. 아이디를 함께 넣으십시오. 솔트를 따로 두지 않고 아이디를 솔트처럼 쓰는 구성이 드물지 않습니다.

**주의.** **운영계 사용자의 비밀번호로 시도하지 마십시오.** 일치하는 것이 없어도 특별한 방식이라는 뜻은 아닙니다(흔한 구성만 시도함). 한글이 섞인 비밀번호는 문자집합이 다르면 결과가 완전히 달라지므로, 이를 놓치면 한글 비밀번호 사용자만 검증에 실패합니다. 저장값이 **평문**으로 나오면 이행 문제가 아니라 사고에 가까우므로 보안 담당자에게 먼저 보고하십시오.

| 암복호화 예외를 삼키기 | 널이 저장되어 뒤늦게 발견 |
| 로그·세션·캐시·화면 메시지에 평문 남기기 | 암호화 대상 밖으로 평문이 나감. 공통 예외 처리가 파라미터 전체를 찍는지 확인 |
| 한 컬럼을 이 시스템과 **다른 방식으로 번갈아** 암호화 | 어느 방식인지 구분 불가 → 복호화 불가 |
| 키 관리 함수(`PKG_KEY_ADMIN` 등)를 업무 코드에서 호출 | 권한이 없고, 시도 기록이 남아 경보가 발생 |
| 비밀번호를 양방향으로 암호화 | 복구 가능 = 누가 꺼내 볼 수 있음 |
| 저장값을 비교해 같은 비밀번호인지 판별 | 같은 비밀번호도 저장값이 매번 다름(결함이 아니라 의도) |
| 검증 함수를 목록·반복문에서 호출 | 일부러 느린 계산 |
| 개발 환경에 운영 데이터 복제 | 복제 과정에 평문이 지나갈 수 있음. 시험 자료는 만들어 쓴다 |
| 운영에서 `new OcsSessionSupport(null)`, `APPCTX_MODE=SIMPLE` | 접속 통제가 없는 것과 같음 |

## 13. 근거와 신뢰도

호출 규격(제3장), 문맥 요구, 마스킹·자격·임계치 동작은 `200_pkg_secure_api.sql` 과 `190_pkg_crypto_policy.sql` 의 본문을 직접 읽은 결과입니다. 신뢰도: 높음. 암호문 길이 산식은 참조 구현으로 실측했습니다. 신뢰도: 높음.

자바 코드는 실제로 컴파일하고 시험한 것에서 가져왔습니다. 신뢰도: 높음. 다만 **본문의 SQL·MyBatis 호출문은 오라클에서 실행해 확인하지 않았습니다.** 함수 이름과 인자는 명세와 대조했습니다. 신뢰도: 중간. 처음 적용할 때 한 건씩 확인하십시오. 투명화 뷰 예시(`800`)는 인터넷망 시험 인스턴스에서 트리거 컴파일 오류가 한 번 나서 고쳤고, 고친 뒤 컴파일과 넣고 꺼내기를 확인하였습니다. `810` 은 제1장(표·뷰·트리거·프로시저·함수 생성)과 제2.1~2.2절(비밀번호 설정과 로그인 검증)을 `sqlplus` 로, 제2.3절(색인)과 제3장(넣기·꺼내기·고치기·지우기)을 연동 확인 프로그램의 `--staff` 로 오라클에서 확인하였습니다(복호화 자격이 없는 경로, 통과 16, 실패 0). 자격이 있는 경로의 평문 판정은 이 시험에서 확인하지 않았습니다.

데이터베이스 안에서만 도는 배치가 `PROOF` 모드에서 문맥을 세울 수 없다는 서술은 설계 주석에서 따른 추론이며 실측하지 않았습니다. 정확도: 중간. 전자정부 표준프레임워크의 자체 암호화 서비스와의 역할 구분은 `전자정부_사용설명서.md` 제2.3절을 보십시오. 정확한 클래스 이름은 확인하지 못했습니다.

## 14. 결론 요약

호출할 것은 `OCS_OWNER.PKG_SECURE_API` 하나이며 암복호화는 데이터베이스가 합니다. 가장 먼저 할 일은 세션 문맥을 세우는 것으로, 암호화·색인·복호화 모두 문맥이 필요하고 문맥은 세운 그 연결에서 써야 하며 반납 전 `finally` 에서 거두어야 합니다. 저장할 때는 암호문 컬럼(`RAW(256)`)과 색인 컬럼(`RAW(32)`)을 함께 채우고, 검색은 색인 컬럼으로 하며, 부분 일치와 범위 검색과 정렬은 지원하지 않으므로 업무 협의로 요건을 조정합니다. 목록은 마스킹, 상세만 평문으로 나누고, 대량 추출은 승인된 별도 작업으로 분리합니다. 트리거의 `UPDATING('컬럼')` 은 `UPDATE` 구문 안이 아니라 `IF` 에서 씁니다. 예외는 삼키지 말고 다시 던지며, 평문은 로그·세션·캐시에 남기지 않습니다. 비밀번호는 별도 경로로, 복구할 수 없고 문맥이 필요 없으며 일부러 느리므로 로그인 한 번에 한 번만 검증하고, 없는 계정에도 같은 시간을 들이며, 로그인 성공 시점에 반복 횟수를 점진적으로 올립니다.
