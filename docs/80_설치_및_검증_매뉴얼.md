# 설치 및 검증 매뉴얼

## 1. 이 문서의 범위

이 문서는 아무것도 없는 데이터베이스에 암호 모듈을 설치하고, 각 단계가 제대로 반영되었는지 확인하는 절차를 담았습니다. 개발 서버에서 오류를 고쳐 가며 진행한 과정을 정리한 것이므로, 여기 적힌 순서대로 하시면 같은 시행착오를 다시 겪지 않습니다.

읽는 분은 오라클 관리자이거나 그에 준하는 권한을 가진 담당자를 전제합니다. 설계 의도나 구조가 궁금하시면 `docs/10` 과 `docs/20` 을, 응용 개발 방법은 `docs/50` 과 `docs/61` 을 보시면 됩니다.

이 문서의 장 번호는 `docs/90_진행현황.md` 의 단계 번호와 다릅니다. 진행 현황 문서는 개발 과정의 순서를 적은 것이고, 이 문서는 설치 절차를 처음부터 다시 정리한 것이기 때문입니다. 이 문서 안에서 「제5장」이라고 하면 이 문서의 제5장, 곧 권한 부여를 가리킵니다.

각 장은 실행과 확인이 짝을 이룹니다. **확인에서 기대값이 나오지 않으면 다음 장으로 넘어가지 마십시오.** 뒤에서 드러나는 오류는 원인을 찾기가 훨씬 어렵습니다.

대상 환경은 오라클 19c 멀티테넌트이며 데이터베이스 문자집합이 `KO16MSWIN949` 인 경우를 기준으로 적었습니다. 다른 환경이라면 제2.1절과 제2.2절만 상황에 맞게 바꾸시면 됩니다.

## 2. 준비

### 2.1 파일 인코딩

저장소의 모든 스크립트는 UTF-8 로 저장되어 있고 주석과 오류 문구에 한글이 들어 있습니다. 데이터베이스 문자집합이 `KO16MSWIN949` 인 곳에서 이대로 실행하면 일부 패키지가 컴파일되지 않습니다. 한글 한 글자가 UTF-8 에서는 세 바이트인데 CP949 로 읽히면 두 바이트씩 끊기면서 남는 바이트가 뒤따르는 줄바꿈이나 따옴표를 삼켜 버리기 때문입니다. 한글이 짝수 개인 줄에서는 우연히 아무 일도 없으므로 전부가 아니라 몇몇 파일에서만 깨지는 것처럼 보입니다.

해결 방법은 둘이고 하나만 택해야 합니다. 섞으면 같은 문제가 반대 방향으로 생깁니다.

파일을 CP949 로 바꾸는 방법은 다음과 같습니다. `sql/` 을 읽어 `sql_cp949/` 를 만들며 내용은 같고 인코딩만 다릅니다. 이후에는 `sql_cp949/` 쪽을 실행하시면 됩니다.

```
python tools\to_cp949.py
```

파일을 그대로 두고 클라이언트에 알리는 방법은 다음과 같습니다. 명령 프롬프트를 새로 열 때마다 해 주셔야 합니다.

```
set NLS_LANG=KOREAN_KOREA.AL32UTF8
chcp 65001
```

자세한 사정은 `docs/70` 제6.1절에 적었습니다.

### 2.2 접속 대상 확인

멀티테넌트 환경에서는 `sqlplus / as sysdba` 로 붙으면 컨테이너 최상위(`CDB$ROOT`)에 접속됩니다. 암호 모듈은 업무 자료가 있는 PDB 에 설치해야 하므로, 설치 전에 어디에 붙었는지 반드시 확인해야 합니다.

```
SQL> @sql/01_schema/000_where_am_i.sql
```

컨테이너 이름과 문자집합이 나옵니다. `CDB$ROOT` 가 나오면 잘못 붙은 것이므로 대상 PDB 로 옮기셔야 합니다.

```sql
ALTER SESSION SET CONTAINER = <대상PDB>;
```

### 2.3 환경 점검

암호 연산에 필요한 것들이 갖추어져 있는지 봅니다.

```
SQL> @sql/01_schema/001_precheck.sql
```

해시와 암호화 결과를 미리 계산해 둔 기대값과 대조하므로, 전부 `OK` 로 나오면 암호 연산 기반이 정상이라는 뜻입니다. `DBMS_CRYPTO` 가 보이지 않는다는 메시지가 나오면 화면에 찍히는 `GRANT` 구문을 `SYS` 로 실행한 뒤 다시 돌리십시오.

## 3. 계정과 역할

`SYS` 또는 그에 준하는 권한으로 대상 PDB 에 접속하여 실행합니다. **일반 DBA 계정으로는 일부 부여가 조용히 실패할 수 있습니다.**

```
SQL> @sql/01_schema/010_users_roles.sql
```

네 계정의 비밀번호를 차례로 물어봅니다. 계정을 넷으로 나누는 것이 이 설계의 토대입니다. `OCS_OWNER` 는 패키지와 키 정보를 소유하고, `OCS_KEYADM` 은 키를 만들고 교체하며, `OCS_AUDITOR` 는 감사 기록만 읽고, `OCS_APP` 은 응용이 씁니다. 소유 계정이 혼자서 키까지 만들 수 있으면 계정을 나눈 의미가 없으므로, 소유 계정에는 관리 권한을 주지 않습니다.

스크립트 끝에 점검 조회 넷이 나옵니다. 빠진 SYS 객체 권한, 빠진 계정, 빠진 역할, 빠진 문맥을 각각 보여 주며 **넷 모두 결과가 비어 있어야 정상**입니다. 한 줄이라도 나오면 그 줄이 곧 다시 실행할 구문이거나 다시 만들어야 할 대상입니다.

SQL\*Plus 는 한 구문이 실패해도 다음 구문으로 넘어가므로, 긴 출력 속에서 실패 한 줄을 놓치기 쉽습니다. 점검 조회를 둔 이유가 그것이니 반드시 눈으로 확인하십시오.

확인은 두 조회입니다. 첫째는 한 건도 나오지 않아야 하고, 둘째는 기대값과 맞아야 합니다.

```sql
SELECT object_name, object_type, status FROM user_objects
 WHERE status <> 'VALID' ORDER BY 1;

SELECT object_type, COUNT(*) FROM user_objects GROUP BY object_type ORDER BY 1;
```

기대값은 패키지 명세 14, 패키지 본문 14, 테이블 8, 뷰 3, 시퀀스 3, 인덱스 14 입니다. 시퀀스가 3인 것은 명시적으로 만든 하나에 더해 `SEC_AUDIT_LOG` 와 `SEC_REKEY_JOB` 의 자동 증가 컬럼이 각각 내부 시퀀스를 하나씩 만들기 때문입니다. 인덱스 14는 직접 만든 다섯에 기본키 여덟과 유일키 하나를 더한 수입니다.

컴파일 오류가 나면 다음으로 상세를 봅니다.

```sql
SHOW ERRORS PACKAGE BODY <패키지이름>
```

주석이나 문자열 근처에서만 오류가 난다면 인코딩 문제이므로 제2.1절로 돌아가십시오.

## 5. 권한 부여

`OCS_OWNER` 로 실행합니다. **이 단계를 빠뜨리면 뒤의 거의 모든 단계가 막힙니다.** 개발 과정에서 실제로 이것을 빠뜨리고 한참을 헤맸으므로 특히 주의하십시오.

```
SQL> @sql/03_grants/300_grants.sql
```

이 스크립트는 최상위 인터페이스 패키지에만 실행 권한을 주고, 그 아래 계층에는 어떤 계정에도 주지 않습니다. 정책 계층을 우회한 복호화가 막히는 근거가 전적으로 이 원칙입니다. 아울러 관리 권한 대장에 초기 등록을 하고, 키 관리 계정이 키 현황 뷰를 읽을 수 있도록 직접 부여를 합니다. 역할로만 주면 소유자 권한 패키지 안에서 인정되지 않으므로 계정에 직접 주는 것입니다.

확인은 스크립트 끝의 점검 조회 둘이며 **둘 다 비어 있어야 정상**입니다. 하위 계층 패키지에 실행 권한이 새어 나갔는지, 키 테이블에 조회 외의 직접 권한이 있는지를 봅니다.

무엇이 누구에게 갔는지도 함께 확인하십시오.

```sql
SELECT grantee, table_name, privilege FROM USER_TAB_PRIVS_MADE
 WHERE grantee LIKE 'OCS%' ORDER BY 1, 2;
```

`OCS_APP` 과 `OCS_ROLE_APP` 에 `PKG_SECURE_API` 실행 권한이, `OCS_ROLE_KEYADM` 에 `PKG_KEY_ADMIN` 과 `PKG_REKEY` 와 `PKG_KEK_PROVIDER` 실행 권한이, `OCS_KEYADM` 에 `V_SEC_KEY_STATUS` 조회 권한이 보여야 합니다.

## 6. 자체 시험

`OCS_OWNER` 로 실행합니다. 고정 시험 벡터를 올리고 대조합니다.

```
SQL> @sql/09_test/900_kat_setup.sql
SQL> @sql/09_test/901_kat_data.sql
SQL> @sql/09_test/902_selftest.sql
```

마지막 줄에 통과와 실패 건수가 찍힙니다. **통과 68, 실패 0** 이 기대값입니다. 실패가 있으면 `[실패]` 로 시작하는 줄에 무엇이 어긋났는지 나옵니다.

이 시험의 핵심은 파이썬 참조 구현이 만들어 낸 값과 PL/SQL 의 계산 결과가 바이트 단위로 같은지 보는 것입니다. 둘이 같으면 암호문 형식이 규격대로 구현되었다고 볼 수 있고, 자바 연동 모듈이 같은 자료를 읽어야 할 때도 이 벡터가 기준이 됩니다. 접근 통제 항목도 함께 확인하므로, 문맥 없는 복호화 거부와 권한 없는 복호화 거부와 사용량 임계치가 모두 여기서 검증됩니다.

한 가지 반드시 알아 두셔야 할 것이 있습니다. **이 시험은 시험용 마스터 키를 주입했다가 끝에 키 저장소를 닫습니다.** 그러므로 돌리고 나면 운영 마스터 키가 사라진 상태가 되고 암복호화가 멈춥니다. 이미 운영 키를 주입한 뒤라면 다시 주입해야 하며, 시험이 끝날 때 화면에도 그렇게 알립니다.

## 7. 반복 횟수 측정과 설정

비밀번호 저장값을 만들 때 해시를 몇 번 반복할지를 정합니다. 높을수록 저장값이 유출되었을 때 대량 대입이 어려워지지만 로그인 응답도 그만큼 느려집니다. 장비 성능에 전적으로 달려 있어 실측 말고는 정할 방법이 없습니다.

```
SQL> @sql/04_admin/400_pwd_iteration_tune.sql
```

아무것도 묻지 않고 아무것도 바꾸지 않습니다. 5,000회부터 200,000회까지 재어 보여 줄 뿐입니다. 개발 서버 실측에서는 1,000회당 약 8.7밀리초였고, 50,000회면 한 번에 444밀리초였습니다.

로그인 한 건에 허용할 수 있는 시간을 먼저 정하고 그 안에 드는 가장 큰 값을 고르시면 됩니다. 업무포털 단일 인증이 주 경로여서 비밀번호 검증이 드물게 일어나는 환경이라면 여유가 많습니다. 정한 값은 다음으로 반영합니다.

```sql
UPDATE SEC_CONFIG SET cfg_value = '50000', updated_at = SYSTIMESTAMP
 WHERE cfg_key = 'PWD_ITERATIONS';
COMMIT;
```

한 번 올린 값을 내려서는 안 됩니다. 내리면 이미 저장된 값보다 약한 값이 새로 생깁니다.

여기서 솔직히 말씀드릴 것이 있습니다. 50,000회는 국제적으로 권고되는 수준에는 못 미칩니다. 원인은 PL/SQL 로 계산하기 때문이며, 같은 계산을 자바에서 하면 훨씬 빠릅니다. 자바 연동 모듈이 PL/SQL 과 바이트 단위로 같은 값을 내므로 계산을 응용 쪽으로 옮기는 선택지가 있습니다. 개통 전에 결정하시면 됩니다.

## 8. 마스터 키

마스터 키는 데이터 키를 감싸는 데만 쓰는 최상위 키입니다. 이것을 잃으면 암호화한 자료를 하나도 되살릴 수 없습니다.

`OCS_OWNER` 로 반입 방식을 정하고 키를 만듭니다.

```sql
UPDATE SEC_CONFIG SET cfg_value = 'GLOBAL_CTX', updated_at = SYSTIMESTAMP
 WHERE cfg_key = 'KEK_SOURCE';
COMMIT;

SET SERVEROUTPUT ON
DECLARE v RAW(32); BEGIN
  v := DBMS_CRYPTO.RANDOMBYTES(32);
  DBMS_OUTPUT.PUT_LINE('MASTER KEY = ' || RAWTOHEX(v));
END;
/
```

찍힌 64자리 16진 문자열을 **화면에서 지우기 전에 반드시 기록하십시오.** 열람 통제가 되는 곳에 두 벌 이상 보관하고, 누가 언제 꺼냈는지 남는 절차를 함께 두셔야 합니다.

`GLOBAL_CTX` 는 원래 개발과 시험 전용입니다. 키 관리 서버나 하드웨어 보안 모듈이 준비되면 `EXTERNAL` 로 바꾸고 `PKG_KEK_PROVIDER.load_from_external` 을 구현하면 되며, 그때 자료를 다시 암호화할 필요는 없습니다. 마스터 키는 데이터 키를 감싸는 데만 쓰이므로 감싼 값만 다시 만들면 됩니다. 되돌릴 수 있는 결정이므로 지금은 이대로 진행하셔도 됩니다.

이어서 `OCS_KEYADM` 으로 접속하여 주입합니다.

```sql
BEGIN OCS_OWNER.PKG_KEK_PROVIDER.set_master_key(HEXTORAW('<64자리>')); END;
/
```

주입한 값은 전역 문맥에 들어가며, 주입한 세션이 끝나도 남습니다. 다만 데이터베이스를 재기동하거나 누군가 키 저장소를 닫으면 사라집니다. 자체 시험이 끝에 닫으므로 시험을 돌린 뒤에는 다시 주입해야 합니다. 운영에서는 이 재주입을 사람이 하지 않도록 키 저장소 유지 프로그램을 두는 것이 좋으며, 제14장에 적었습니다.

## 9. 운영 도메인과 키

`OCS_KEYADM` 으로 실행합니다. 마스터 키가 주입되어 있어야 합니다.

```
SQL> @sql/04_admin/450_bootstrap_domains.sql
```

주민등록번호와 성명과 연락처와 계좌번호 네 도메인을 등록하고 각각 운영 키를 만들어 활성으로 올립니다. 도메인마다 정규화 방식과 마스킹 방식과 사용량 임계치가 다르며, 자세한 뜻은 파일 안의 주석에 적혀 있습니다. 여러 번 실행해도 안전하며, 활성 키가 이미 있으면 새로 만들지 않습니다.

확인은 스크립트 끝의 조회입니다. 네 도메인에 각각 `ACTIVE` 키가 하나씩 있어야 합니다.

## 10. 증표용 키

응용 계정의 접속 정보를 알아낸 사람이 조회 도구로 직접 붙더라도 아무것도 하지 못하게 하는 장치입니다. 애플리케이션이 이 키로 증표를 계산해 제출해야 문맥이 서고, 문맥이 서야 암호화와 복호화와 색인 생성이 됩니다.

이 키는 데이터베이스 **밖에서** 만들어 들여옵니다. 안에서 난수로 만들면 애플리케이션에 전달할 방법이 없고, 데이터베이스 관리자가 값을 보게 되어 장치의 취지가 무너집니다. 애플리케이션 담당자가 만들어 전달하는 것이 가장 낫습니다.

```
python -c "import secrets; print('\n'.join(secrets.token_hex(32) for _ in range(3)))"
```

세 줄이 나옵니다. 앞의 둘은 규격을 맞추기 위한 예비값이고, **세 번째가 실제 증표 계산에 쓰이는 값이며 애플리케이션 서버 설정에 들어갑니다. 반드시 기록해 두십시오.** 마스터 키와 달리 이 키는 설치할 때마다 새로 만드는 값이므로, 재설치한 뒤에 옛 키를 쓰면 증표가 맞지 않아 로그인이 막힙니다. `OCS_KEYADM` 으로 들여옵니다.

```
SQL> @sql/04_admin/460_appctx_key.sql
```

세 값을 차례로 물어봅니다. 데이터베이스 쪽에는 감싸인 형태로만 남으므로 이후에는 다시 꺼낼 수 없습니다.

## 11. 연동 확인

여기까지가 데이터베이스 쪽 설치이며, 이제 애플리케이션에서 실제로 쓰이는지 봅니다. 통제가 걸리는 쪽과 열리는 쪽을 모두 확인해야 합니다.

먼저 `OCS_APP` 으로 접속하여 접속 정보만으로는 아무것도 못 한다는 것을 확인합니다. **실패해야 정상입니다.**

```sql
SET SERVEROUTPUT ON
DECLARE c RAW(2000);
BEGIN
  c := OCS_OWNER.PKG_SECURE_API.enc_rrn('8001011234567');
  DBMS_OUTPUT.PUT_LINE('ENCRYPT=OK  <-- 통제가 새고 있다');
EXCEPTION
  WHEN OTHERS THEN
    DBMS_OUTPUT.PUT_LINE('거부됨 SQLCODE=' || SQLCODE || ' ' || SQLERRM);
END;
/
```

`SQLCODE=-20521` 과 「애플리케이션 인증 문맥 없음」이 나와야 합니다. `idx_rrn` 으로 바꾸어도 같아야 합니다. 색인은 결정적이어서 후보 평문을 넣어 가며 저장된 색인과 맞춰 보면 평문을 알아낼 수 있으므로, 복호화만 막고 색인을 열어 두면 통제가 성립하지 않습니다.

반대쪽은 자바 연동 확인 프로그램으로 봅니다. JDBC 드라이버가 필요하며 오라클 설치 폴더의 `jdbc/lib/ojdbc8.jar` 에 있습니다. 라이브러리 자체에는 외부 의존성이 없고 이 확인 프로그램만 JDBC 를 씁니다.

```
dir /s /b src\*.java > srcs.txt
javac -encoding UTF-8 -cp <경로>\ojdbc8.jar -d out @srcs.txt

java -cp out;<경로>\ojdbc8.jar ocsecure.client.OcsConnectDemo ^
     "jdbc:oracle:thin:@<호스트>:<포트>/<서비스명>" OCS_APP <암호> <증표키 16진 64자>
```

**통과 5, 실패 0** 이 기대값입니다. 문맥 없이는 거부되고, 증표를 제출하면 암호화가 되며, 같은 평문이 매번 다른 암호문이 되고, 구분자가 있든 없든 색인 값이 같으며, 복호화 권한이 없으면 거부된다는 것을 봅니다.

증표 키를 명령행에 적으면 명령 이력에 남습니다. 확인이 끝나면 창을 닫으시는 편이 낫고, 운영 코드에서는 키 관리 제품이나 기동 시점에 주입되는 값에서 읽어야 하며 소스나 설정 파일에 평문으로 두어서는 안 됩니다.

## 12. 업무 스키마 적용

실제 업무 테이블을 어떻게 바꾸어야 하는지는 `sql/08_sample/800_sample_member.sql` 이 본보기입니다. 암호문과 색인을 따로 두는 실제 저장 테이블을 만들고, 옛 이름을 그대로 쓰는 투명화 뷰를 올리고, 평문을 넣으면 트리거가 암호화와 색인 생성을 대신하게 하는 구조입니다. 조회 구문을 어떻게 고쳐야 하는지도 파일 끝에 적혀 있습니다.

예시를 돌려 보시려면 응용 계정에 표와 뷰와 트리거를 만들 권한이 필요합니다. 실제 사업에서는 업무 스키마에 이미 있을 권한입니다.

```sql
GRANT CREATE TABLE, CREATE VIEW, CREATE TRIGGER TO OCS_APP;
```

`OCS_APP` 으로 실행한 뒤 객체가 성한지 확인하십시오. 아무 행도 나오지 않으면 정상입니다. 제5장(권한 부여)을 빠뜨렸다면 뷰와 트리거가 깨져 나옵니다.

```sql
SELECT object_name, object_type, status FROM user_objects WHERE status <> 'VALID';
```

실제로 자료를 넣고 꺼내 보시려면 제11장에서 쓰신 연동 확인 명령의 맨 끝에 `--data` 를 덧붙이시면 됩니다. 그러면 투명화 뷰에 자료를 넣고 꺼내 보는 항목이 추가로 돕니다.

```
java -cp out;<경로>\ojdbc8.jar ocsecure.client.OcsConnectDemo ^
     "jdbc:oracle:thin:@<호스트>:<포트>/<서비스명>" OCS_APP <암호> <증표키 16진 64자> --data
```

**통과 9, 실패 0** 이 기대값이며, 평문을 넣으면 트리거가 암호화하여 저장하는지, 복호화 자격에 따라 평문과 마스킹이 갈리는지, 마스킹 전용 컬럼은 자격이 있어도 가려지는지, 색인으로 찾으면 구분자와 무관하게 같은 행이 나오는지를 봅니다. 시험 자료는 넣었다가 지우므로 남지 않습니다.

복호화 자격을 주는 쪽이 키 관리 계정이라는 것도 설계의 일부입니다. 소유 계정이 스스로에게 자격을 줄 수는 없고, 응용 계정이 스스로에게 줄 수도 없습니다. **아래는 반드시 `OCS_KEYADM` 으로 접속하여 실행하십시오.** 다른 계정으로 치면 `PLS-00201` 로 `PKG_KEY_ADMIN` 을 찾을 수 없다고 나옵니다.

```sql
BEGIN
  OCS_OWNER.PKG_KEY_ADMIN.grant_reveal('RRN', 'OCS_APP', 'USER', NULL, '연동 확인');
  COMMIT;
END;
/
```

확인이 끝나면 `revoke_reveal` 로 거두십시오.

## 13. 키 교체 리허설

한 번도 돌려 보지 않은 키 교체는 정작 필요한 순간에 반드시 실패합니다. 개통 전에 한 번은 실제로 해 보셔야 하며, 제12장의 시험 자료가 있을 때 하시면 됩니다.

`OCS_KEYADM` 으로 교체합니다.

```sql
SET SERVEROUTPUT ON
DECLARE v PLS_INTEGER; BEGIN
  v := OCS_OWNER.PKG_KEY_ADMIN.rotate('RRN', '교체 리허설');
  COMMIT;
  DBMS_OUTPUT.PUT_LINE('새 key_id = ' || v);
END;
/
```

옛 키가 `RETIRING`, 새 키가 `ACTIVE` 가 됩니다. 이 시점부터 새로 넣는 자료는 새 키로 암호화되고 기존 자료는 그대로 옛 키로 읽힙니다. **서비스를 멈추지 않는다는 것이 이 설계의 요점이므로, 교체 직후에 기존 자료가 그대로 읽히는지 반드시 확인하십시오.**

이어서 재암호화 배치로 옛 키 자료를 새 키로 옮깁니다. 이 패키지는 소유자 권한으로 돌므로 대상 업무 테이블의 조회와 갱신 권한을 **`OCS_OWNER` 에게 직접** 주어야 합니다. 역할로 준 권한은 인정되지 않습니다.

```sql
GRANT SELECT, UPDATE ON <업무스키마>.<테이블> TO OCS_OWNER;
```

```sql
BEGIN
  OCS_OWNER.PKG_REKEY.create_job('REHEARSAL', '<업무스키마>', '<테이블>',
                                 '<기본키컬럼>', '<암호문컬럼>', 'RRN', '<색인컬럼>', 1000);
  COMMIT;
END;
/

SET SERVEROUTPUT ON
BEGIN
  DBMS_OUTPUT.PUT_LINE('옮길 건수(전) = ' || OCS_OWNER.PKG_REKEY.remaining('REHEARSAL'));
  OCS_OWNER.PKG_REKEY.run_job('REHEARSAL');
  DBMS_OUTPUT.PUT_LINE('옮길 건수(후) = ' || OCS_OWNER.PKG_REKEY.remaining('REHEARSAL'));
END;
/
```

남은 건수가 0 이 된 뒤에만 옛 키를 폐기합니다. 폐기는 키 값을 지우는 것이 아니라 그 키로는 복호화도 못 하게 막는 것입니다.

```sql
SET SERVEROUTPUT ON
DECLARE v PLS_INTEGER; BEGIN
  SELECT key_id INTO v FROM OCS_OWNER.V_SEC_KEY_STATUS
   WHERE domain_code = 'RRN' AND key_state = 'RETIRING';
  OCS_OWNER.PKG_KEY_ADMIN.retire(v);
  COMMIT;
  DBMS_OUTPUT.PUT_LINE('폐기한 key_id = ' || v);
END;
/
```

폐기한 뒤에도 자료가 읽히면 모든 자료가 새 키로 옮겨졌다는 뜻이고 교체가 완결된 것입니다. 여기서 「사용할 수 없는 키」 오류가 나면 옮기지 못한 자료가 남아 있다는 뜻이므로 그것이 더 중요한 발견입니다.

배치가 끝나면 업무 테이블에 임시로 준 권한을 회수하십시오. 상시로 두면 암호 모듈 소유 계정이 업무 자료를 언제든 건드릴 수 있게 되어 계정을 나눈 뜻이 옅어집니다.

## 14. 개통 직전 조치

여기까지가 설치와 검증입니다. 개통 직전에 할 일이 따로 있습니다.

키 저장소 유지 프로그램을 띄우십시오. 전역 문맥의 마스터 키는 데이터베이스를 재기동하거나 누군가 키 저장소를 닫으면 사라집니다. 사람이 와서 다시 넣어 주어야 한다면 야간 재기동에 대응할 수 없습니다. `OcsKeystoreKeeper` 가 주기적으로 확인하여 닫혀 있으면 다시 넣습니다. 설정 파일에는 마스터 키와 계정 암호가 들어가므로 운영체제 권한으로 보호해야 합니다.

```
java -cp out;<경로>\ojdbc8.jar ocsecure.keeper.OcsKeystoreKeeper keeper.properties --once
java -cp out;<경로>\ojdbc8.jar ocsecure.keeper.OcsKeystoreKeeper keeper.properties
```

시험용 표를 지우십시오. `SEC_KAT` 은 고정 시험 벡터를 담는 표로 운영 배포 대상이 아닙니다.

```sql
DROP TABLE SEC_KAT PURGE;
```

소유 계정을 잠그십시오. 설치와 검증이 끝난 뒤에는 `OCS_OWNER` 로 접속할 일이 없어야 합니다.

```
SQL> @sql/03_grants/310_lockdown.sql
```

`APPCTX_MODE` 가 `PROOF` 인지 마지막으로 확인하십시오. 시험 과정에서 `SIMPLE` 로 바꾸었다면 되돌려야 하며, 이것을 잊으면 통제 하나가 통째로 사라집니다.

```sql
SELECT cfg_key, cfg_value FROM SEC_CONFIG
 WHERE cfg_key IN ('APPCTX_MODE', 'KEK_SOURCE', 'PWD_ITERATIONS');
```

## 15. 설치 점검표

한눈에 보시도록 각 장의 기대값만 모았습니다.

제2.2절에서는 대상 PDB 이름과 문자집합이 나와야 하고 `CDB$ROOT` 가 아니어야 합니다. 제2.3절에서는 점검 항목이 모두 `OK` 여야 합니다. 제3장에서는 점검 조회 넷이 모두 비어 있어야 합니다. 제4장에서는 잘못된 객체가 하나도 없고 패키지 명세 14와 본문 14, 테이블 8, 뷰 3, 시퀀스 3, 인덱스 14가 나와야 합니다. 제5장에서는 점검 조회 둘이 비어 있고 부여 내역에 네 계정과 세 역할이 보여야 합니다. 제6장에서는 통과 68에 실패 0 이어야 합니다. 제9장에서는 네 도메인에 각각 활성 키가 하나씩 있어야 합니다. 제11장에서는 응용 계정 직접 호출이 `-20521` 로 거부되고 자바 확인이 통과 5에 실패 0 이어야 합니다. 제12장에서는 자바 확인이 통과 9에 실패 0 이어야 합니다. 제13장에서는 옮길 건수가 0 이 되고 옛 키 폐기 뒤에도 자료가 읽혀야 합니다.

## 16. 자주 겪는 문제

몇몇 패키지에서만 컴파일 오류가 나고 오류 위치가 주석이나 문자열 근처라면 인코딩 문제입니다. 제2.1절로 돌아가십시오.

`ORA-01919` 로 역할이 존재하지 않는다고 나오거나 `ORA-00933` 으로 SQL 명령어가 올바르게 종료되지 않았다고 나오면, 앞선 구문이 조용히 실패한 것입니다. SQL\*Plus 는 최상위 구문을 세미콜론에서 끊으므로 그 뒤에 주석을 같은 줄로 붙이면 구문 전체가 실패하는데, 실패해도 다음 줄로 넘어가기 때문에 긴 출력 속에서 놓치기 쉽습니다. 저장소의 스크립트는 이 문제를 모두 고쳤고 정적 점검기가 다시 생기지 않도록 막습니다만, 스크립트를 손수 고치실 때는 주의하십시오.

`PLS-00201` 로 식별자를 찾을 수 없다고 나오면 두 가지 중 하나입니다. `PKG_SECURE_API` 를 찾을 수 없다면 제5장(권한 부여)을 빠뜨린 것입니다. `PKG_KEY_ADMIN` 이나 `PKG_REKEY` 를 찾을 수 없다면 계정을 잘못 고른 것입니다. 키와 자격을 다루는 패키지는 `OCS_KEYADM` 만 부를 수 있으며, 그것이 계정을 나눈 이유입니다. 개발 과정에서 실제로 겪은 일이며, 권한 대장에 행이 있는 것만 보고 권한 부여가 끝났다고 오해하기 쉽습니다.

`ORA-20521` 에 「증표 불일치」가 함께 나오면 데이터베이스가 가진 `_APPCTX` 키와 명령행에 넣은 키가 다른 것입니다. 이 키는 마스터 키와 달리 재설치할 때마다 새로 만들어 넣는 값이므로, 지우고 다시 설치했다면 옛 키를 쓰고 있을 가능성이 높습니다. 이번 설치에서 제10장에 넣으신 세 번째 값을 쓰십시오. 기억나지 않으면 기존 `_APPCTX` 키를 폐기하고 제10장을 다시 하시면 됩니다.

`ORA-20513` 으로 키 저장소가 열려 있지 않다고 나오면 마스터 키가 사라진 것입니다. 자체 시험을 돌린 직후이거나 데이터베이스를 재기동한 뒤입니다. 제8장의 주입을 다시 하십시오.

`ORA-20521` 로 애플리케이션 인증 문맥이 없다고 나오는 것은 대개 정상 동작입니다. 조회 도구로 직접 붙어 암복호화를 시도했을 때 나와야 하는 오류입니다.

`ORA-01720` 으로 허가 옵션이 없다고 나오면, 암호 모듈의 패키지를 부르는 뷰를 제3자에게 넘기려 한 것입니다. 그러려면 응용 계정이 패키지에 대해 재부여 권한까지 가져야 하는데, 그 권한을 주면 응용 계정이 아무에게나 이 API 를 넘길 수 있게 되므로 주지 않는 편이 맞습니다. 자료를 넣고 꺼내는 일은 조회 도구가 아니라 애플리케이션이 하도록 하십시오.

소유자 권한 패키지 안에서 `ORA-00942` 로 테이블이 없다고 나오면, 권한을 호출한 계정에 주고 소유 계정에는 주지 않은 것입니다. 소유자 권한 패키지 안의 조회와 갱신은 패키지 소유자의 권한으로 실행되며, 역할로 준 권한은 인정되지 않습니다.

## 17. 처음부터 다시 하기

설치 절차가 깨끗한 상태에서 제대로 도는지 확인하려면 모든 것을 지우고 제1장부터 다시 해 보아야 합니다. 고쳐 가며 쌓인 상태 위에서 도는 것과 아무것도 없는 상태에서 도는 것은 다르며, 후자를 확인하지 않으면 실제 반입 때 무엇이 빠졌는지 알 수 없습니다.

```
SQL> @sql/99_uninstall/990_drop_all.sql
```

`SYS` 로 실행하며 `DROP` 이라고 입력해야 진행됩니다. **이 스크립트는 암호 모듈과 그 아래의 모든 키와 감사 기록을 지웁니다. 키를 지우면 그 키로 암호화한 자료를 영구히 되살릴 수 없으므로 운영계에서는 절대 실행하지 마십시오.** 업무 스키마의 실제 표는 건드리지 않습니다.

끝에 남은 계정과 역할과 문맥을 보여 주며 셋 다 비어 있으면 설치 전 상태입니다.

## 18. 참고 근거와 신뢰도 자체 평가

이 문서에 적은 절차와 기대값은 모두 개발 서버의 오라클 19c 인스턴스에서 실제로 수행하고 확인한 결과입니다. 설치 순서, 각 단계의 기대값, 자주 겪는 문제는 전부 실측에 근거합니다. 신뢰도는 높음입니다.

반복 횟수 측정값(1,000회당 약 8.7밀리초)은 개발 서버 한 대에서 잰 값입니다. 운영 장비에서는 달라지므로 반드시 다시 재셔야 합니다. 정확도는 그 장비에 한해 높음이며, 다른 장비로 옮길 때는 참고치일 뿐입니다.

데이터베이스를 재기동하면 전역 문맥이 비워진다는 서술은 아직 실측하지 않았습니다. 메모리에만 있으므로 그렇게 보는 것이 타당하다는 수준이며 정확도는 중간입니다. 재기동 일정이 있을 때 확인하시기를 권합니다.

비밀번호 반복 횟수에 관한 국제 권고 수준을 언급한 부분은 해마다 바뀌는 수치이므로 정확도 중간으로 보시고, 인증 대응 시에는 최신 문서로 확인하셔야 합니다.

제17장의 「처음부터 다시 하기」는 제거 스크립트를 새로 만들어 넣은 것으로, **아직 실제로 전체 재설치를 수행해 보지는 않았습니다.** 이 문서를 쓰는 시점에서는 설치 절차만 검증된 상태이며, 제거 후 재설치가 끝까지 도는지는 다음 확인 대상입니다. 정확도는 중간입니다.

## 19. 결론 요약

설치는 환경 점검, 계정과 역할, 스키마와 패키지, 권한 부여, 자체 시험, 운영 설정, 마스터 키, 도메인과 키, 증표용 키, 연동 확인의 순서로 진행합니다. 각 단계마다 기대값이 정해져 있으며 맞지 않으면 다음으로 넘어가지 않는 것이 원칙입니다.

가장 빠뜨리기 쉬운 것은 제5장의 권한 부여입니다. 이것을 건너뛰면 뒤의 거의 모든 단계가 막히는데, 증상이 권한 문제로 보이지 않아 원인을 찾기 어렵습니다.

가장 중요한 것은 제8장의 마스터 키 보관입니다. 이것을 잃으면 암호화한 자료를 되살릴 방법이 없습니다.

개통 직전에는 키 저장소 유지 프로그램을 띄우고, 시험용 표를 지우고, 소유 계정을 잠그고, `APPCTX_MODE` 가 `PROOF` 인지 확인해야 합니다.

설치 절차가 깨끗한 상태에서 제대로 도는지는 제17장의 제거 스크립트로 모두 지운 뒤 제1장부터 다시 해 보아야 알 수 있습니다. 그 확인이 끝나야 실제 반입 절차를 믿을 수 있습니다.
