# 설치 및 검증 매뉴얼

## 0. 이 문서를 읽는 법

본문은 그대로 따라 하면 설치가 끝나도록 적었습니다. 각 장은 **접속**, **실행**, **확인**의 세 토막으로 이루어지고, 접속은 어느 계정으로 붙어야 하는지를, 실행은 무엇을 치는지를, 확인은 무엇이 나와야 하는지를 말합니다.

왜 그렇게 하는지를 적은 대목은 인용 표시로 묶어 「설명」이라고 달아 두었습니다. **설명은 읽지 않고 건너뛰어도 설치는 완료됩니다.** 처음 설치하실 때에는 건너뛰시고, 무엇이 어긋났을 때나 구조를 알아야 할 때 돌아와 보시면 됩니다.

> **설명.** 설명을 본문에서 떼어 낸 까닭은, 설치하는 사람이 지금 쳐야 할 것과 알아 두면 좋은 것을 눈으로 구별할 수 있어야 하기 때문입니다. 둘이 섞여 있으면 읽는 사람이 매번 어느 쪽인지 판단해야 하고, 그 판단이 한 번 어긋나면 단계를 건너뛰거나 하지 않아도 될 일을 하게 됩니다.

굵게 표시한 문장은 설명이 아니라 지시이므로 건너뛰지 마십시오. 확인에서 기대값이 나오지 않으면 **다음 장으로 넘어가지 말고** 제16장에서 해당 증상을 찾으십시오. 뒤에서 드러나는 오류는 원인을 찾기가 훨씬 어렵습니다.

## 1. 범위와 전제

이 문서는 아무것도 없는 데이터베이스에 암호 모듈을 설치하고 각 단계가 제대로 반영되었는지 확인하는 절차를 담았습니다. 읽는 분은 오라클 관리자이거나 그에 준하는 권한을 가진 담당자를 전제합니다.

대상 환경은 오라클 19c 멀티테넌트이며 데이터베이스 문자집합이 `KO16MSWIN949` 인 경우를 기준으로 적었습니다. 다른 환경이라면 제2.1절과 제2.2절만 상황에 맞게 바꾸시면 됩니다.

> **설명.** 설계 의도나 구조가 궁금하시면 `docs/10` 과 `docs/20` 을, 응용 개발 방법은 `docs/50` 과 `docs/61` 을 보시면 됩니다. 이 문서의 장 번호는 `docs/90_진행현황.md` 의 단계 번호와 다릅니다. 진행 현황 문서는 개발 과정의 순서를 적은 것이고 이 문서는 설치 절차를 따로 정리한 것입니다. 이 문서 안에서 「제5장」이라고 하면 이 문서의 제5장, 곧 권한 부여를 가리킵니다.

## 2. 준비

### 2.1 파일 인코딩

**실행.** 두 가지 방법 중 **하나만** 택하십시오. 섞으면 같은 문제가 반대 방향으로 생깁니다.

파일을 CP949 로 바꾸는 방법입니다. `sql/` 을 읽어 `sql_cp949/` 를 만들며 내용은 같고 인코딩만 다릅니다. 이후 모든 단계에서 `sql_cp949/` 쪽을 실행하십시오.

```
python tools\to_cp949.py
```

파일을 그대로 두고 클라이언트에 알리는 방법입니다. 명령 프롬프트를 새로 열 때마다 해 주셔야 합니다.

```
set NLS_LANG=KOREAN_KOREA.AL32UTF8
chcp 65001
```

> **설명.** 저장소의 모든 스크립트는 UTF-8 로 저장되어 있고 주석과 오류 문구에 한글이 들어 있습니다. 문자집합이 `KO16MSWIN949` 인 곳에서 이대로 실행하면 일부 패키지가 컴파일되지 않습니다. 한글 한 글자가 UTF-8 에서는 세 바이트인데 CP949 로 읽히면 두 바이트씩 끊기면서 남는 바이트가 뒤따르는 줄바꿈이나 따옴표를 삼켜 버리기 때문입니다. 한글이 짝수 개인 줄에서는 우연히 아무 일도 없으므로 전부가 아니라 몇몇 파일에서만 깨지는 것처럼 보입니다. 자세한 사정은 `docs/70` 제6.1절에 적었습니다.

### 2.2 접속 대상 확인

**접속.** `SYS` 또는 그에 준하는 권한으로 붙습니다.

**실행.**

```
SQL> @sql/01_schema/000_where_am_i.sql
```

**확인.** 컨테이너 이름과 문자집합이 나옵니다. 대상 PDB 이름이 나와야 하며 `CDB$ROOT` 가 나오면 잘못 붙은 것입니다. 그럴 때는 아래로 옮긴 뒤 다시 확인하십시오.

```sql
ALTER SESSION SET CONTAINER = <대상PDB>;
```

> **설명.** 멀티테넌트 환경에서 `sqlplus / as sysdba` 로 붙으면 컨테이너 최상위에 접속됩니다. 암호 모듈은 업무 자료가 있는 PDB 에 설치해야 하므로 설치 전에 어디에 붙었는지 확인해야 합니다.

### 2.3 환경 점검

**실행.**

```
SQL> @sql/01_schema/001_precheck.sql
```

**확인.** 점검 항목이 전부 `OK` 로 나와야 합니다. `DBMS_CRYPTO` 가 보이지 않는다는 메시지가 나오면 화면에 찍히는 `GRANT` 구문을 `SYS` 로 실행한 뒤 다시 돌리십시오.

> **설명.** 해시와 암호화 결과를 미리 계산해 둔 기대값과 대조하므로, 전부 `OK` 라면 암호 연산 기반이 정상이라는 뜻입니다.

## 3. 계정과 역할

**접속.** `SYS` 또는 그에 준하는 권한으로 대상 PDB 에 붙습니다. **일반 DBA 계정으로는 일부 부여가 조용히 실패할 수 있습니다.**

**실행.** 네 계정의 비밀번호를 차례로 물어봅니다.

```
SQL> @sql/01_schema/010_users_roles.sql
```

**확인.** 스크립트 끝에 점검 조회 넷이 나옵니다. 빠진 SYS 객체 권한, 빠진 계정, 빠진 역할, 빠진 문맥을 각각 보여 주며 **넷 모두 결과가 비어 있어야 정상**입니다. 한 줄이라도 나오면 그 줄이 곧 다시 실행할 구문이거나 다시 만들어야 할 대상입니다.

> **설명.** 계정을 넷으로 나누는 것이 이 설계의 토대입니다. `OCS_OWNER` 는 패키지와 키 정보를 소유하고, `OCS_KEYADM` 은 키를 만들고 교체하며, `OCS_AUDITOR` 는 감사 기록만 읽고, `OCS_APP` 은 응용이 씁니다. 소유 계정이 혼자서 키까지 만들 수 있으면 계정을 나눈 의미가 없으므로 소유 계정에는 관리 권한을 주지 않습니다. 점검 조회를 따로 둔 까닭은, SQL\*Plus 가 한 구문이 실패해도 다음 구문으로 넘어가기 때문에 긴 출력 속에서 실패 한 줄을 놓치기 쉬워서입니다.

**확인.** 첫째 조회는 한 건도 나오지 않아야 하고, 둘째 조회는 기대값과 맞아야 합니다.

```sql
SELECT object_name, object_type, status FROM user_objects
 WHERE status <> 'VALID' ORDER BY 1;

SELECT object_type, COUNT(*) FROM user_objects GROUP BY object_type ORDER BY 1;
```

기대값은 패키지 명세 14, 패키지 본문 14, 테이블 8, 뷰 3, 시퀀스 3, 인덱스 14 입니다.

> **설명.** 시퀀스가 셋인 것은 명시적으로 만든 하나에 더해 `SEC_AUDIT_LOG` 와 `SEC_REKEY_JOB` 의 자동 증가 컬럼이 각각 내부 시퀀스를 하나씩 만들기 때문입니다. 인덱스 열넷은 직접 만든 다섯에 기본키 여덟과 유일키 하나를 더한 수입니다.

## 5. 권한 부여

**접속.** `OCS_OWNER`.

**실행.** **이 단계를 빠뜨리면 뒤의 거의 모든 단계가 막힙니다.**

```
SQL> @sql/03_grants/300_grants.sql
```

**확인.** 스크립트 끝의 점검 조회 둘이 **모두 비어 있어야 정상**입니다. 하위 계층 패키지에 실행 권한이 새어 나갔는지, 키 테이블에 조회 외의 직접 권한이 있는지를 봅니다. 이어서 무엇이 누구에게 갔는지도 확인하십시오.

```sql
SELECT grantee, table_name, privilege FROM USER_TAB_PRIVS_MADE
 WHERE grantee LIKE 'OCS%' ORDER BY 1, 2;
```

`OCS_APP` 과 `OCS_ROLE_APP` 에 `PKG_SECURE_API` 실행 권한이, `OCS_ROLE_KEYADM` 에 `PKG_KEY_ADMIN` 과 `PKG_REKEY` 와 `PKG_KEK_PROVIDER` 실행 권한이, `OCS_KEYADM` 에 `V_SEC_KEY_STATUS` 조회 권한이 보여야 합니다.

> **설명.** 이 스크립트는 최상위 인터페이스 패키지에만 실행 권한을 주고 그 아래 계층에는 어떤 계정에도 주지 않습니다. 정책 계층을 우회한 복호화가 막히는 근거가 전적으로 이 원칙입니다. 키 관리 계정에 키 현황 뷰를 역할이 아니라 계정으로 직접 주는 까닭은, 역할로 준 권한이 소유자 권한 패키지 안에서는 인정되지 않기 때문입니다.

## 6. 자체 시험

**접속.** `OCS_OWNER`.

**실행.** **이 시험은 운영계에서 돌리지 마십시오.** 설정을 개발용으로 바꾸었다가 되돌리고, 끝에 키 저장소를 닫습니다.

```
SQL> @sql/09_test/900_kat_setup.sql
SQL> @sql/09_test/901_kat_data.sql
SQL> @sql/09_test/902_selftest.sql
```

**확인.** 마지막 줄에 **통과 68, 실패 0** 이 나와야 합니다. 실패가 있으면 `[실패]` 로 시작하는 줄에 무엇이 어긋났는지 나옵니다.

**시험이 끝나면 키 저장소가 닫힌 상태가 됩니다.** 이미 운영 마스터 키를 주입한 뒤였다면 제8장의 주입을 다시 하셔야 합니다. 시험이 끝날 때 화면에도 그렇게 알립니다.

> **설명.** 이 시험의 핵심은 파이썬 참조 구현이 만들어 낸 값과 PL/SQL 의 계산 결과가 바이트 단위로 같은지 보는 것입니다. 둘이 같으면 암호문 형식이 규격대로 구현되었다고 볼 수 있고, 자바 연동 모듈이 같은 자료를 읽어야 할 때도 이 벡터가 기준이 됩니다. 접근 통제 항목도 함께 확인하므로 문맥 없는 복호화 거부와 권한 없는 복호화 거부와 사용량 임계치가 모두 여기서 검증됩니다.

## 7. 비밀번호 반복 횟수

**접속.** `OCS_OWNER`.

**실행.** 먼저 장비 성능을 잽니다. 아무것도 묻지 않고 아무것도 바꾸지 않습니다.

```
SQL> @sql/04_admin/400_pwd_iteration_tune.sql
```

**확인.** 5,000회부터 200,000회까지의 소요 시간이 나옵니다. 로그인 한 건에 허용할 수 있는 시간을 먼저 정하고 그 안에 드는 가장 큰 값을 고르십시오. 고른 값을 반영합니다.

```sql
UPDATE SEC_CONFIG SET cfg_value = '50000', updated_at = SYSTIMESTAMP
 WHERE cfg_key = 'PWD_ITERATIONS';
COMMIT;
```

**한 번 올린 값을 내려서는 안 됩니다.** 내리면 이미 저장된 값보다 약한 값이 새로 생깁니다.

> **설명.** 높을수록 저장값이 유출되었을 때 대량 대입이 어려워지지만 로그인 응답도 그만큼 느려집니다. 장비 성능에 전적으로 달려 있어 실측 말고는 정할 방법이 없습니다. 개발 서버 실측에서는 1,000회당 약 8.7밀리초였고 50,000회면 한 번에 444밀리초였습니다. 업무포털 단일 인증이 주 경로여서 비밀번호 검증이 드물게 일어나는 환경이라면 여유가 많습니다.
>
> 솔직히 말씀드릴 것이 있습니다. 50,000회는 국제적으로 권고되는 수준에는 못 미칩니다. 원인은 PL/SQL 로 계산하기 때문이며 같은 계산을 자바에서 하면 훨씬 빠릅니다. 자바 연동 모듈이 PL/SQL 과 바이트 단위로 같은 값을 내므로 계산을 응용 쪽으로 옮기는 선택지가 있고, 개통 전에 결정하시면 됩니다.

## 8. 마스터 키

**접속.** 먼저 `OCS_OWNER`.

**실행.** 반입 방식을 정하고 키를 만듭니다.

```sql
UPDATE SEC_CONFIG SET cfg_value = 'GLOBAL_CTX', updated_at = SYSTIMESTAMP
 WHERE cfg_key = 'KEK_SOURCE';
COMMIT;

SET SERVEROUTPUT ON
DECLARE v RAW(32); BEGIN
  v := DBMS_CRYPTO.RANDOMBYTES(32);
  DBMS_OUTPUT.PUT_LINE('MASTER KEY = ' || RAWTOHEX(v));
END;
/
```

**찍힌 64자리 16진 문자열을 화면에서 지우기 전에 반드시 기록하십시오.** 열람 통제가 되는 곳에 두 벌 이상 보관하고, 누가 언제 꺼냈는지 남는 절차를 함께 두셔야 합니다. **이것을 잃으면 암호화한 자료를 하나도 되살릴 수 없습니다.**

**접속.** 이어서 `OCS_KEYADM`.

**실행.**

```sql
BEGIN OCS_OWNER.PKG_KEK_PROVIDER.set_master_key(HEXTORAW('<64자리>')); END;
/
```

**확인.** 「키 저장소 열림」이 나와야 합니다.

```sql
SET SERVEROUTPUT ON
BEGIN
  IF OCS_OWNER.PKG_KEK_PROVIDER.is_open THEN
    DBMS_OUTPUT.PUT_LINE('키 저장소 열림');
  ELSE
    DBMS_OUTPUT.PUT_LINE('키 저장소 닫힘');
  END IF;
END;
/
```

> **설명.** 마스터 키는 데이터 키를 감싸는 데만 쓰는 최상위 키입니다. 주입한 값은 전역 문맥에 들어가며 주입한 세션이 끝나도 남습니다. 다만 데이터베이스를 재기동하거나 누군가 키 저장소를 닫으면 사라집니다. 운영에서는 이 재주입을 사람이 하지 않도록 키 저장소 유지 프로그램을 두는 것이 좋으며 제14장에 적었습니다.
>
> `GLOBAL_CTX` 는 원래 개발과 시험 전용입니다. 키 관리 서버나 하드웨어 보안 모듈이 준비되면 `EXTERNAL` 로 바꾸고 `PKG_KEK_PROVIDER.load_from_external` 을 구현하면 되며, 그때 자료를 다시 암호화할 필요는 없습니다. 마스터 키는 데이터 키를 감싸는 데만 쓰이므로 감싼 값만 다시 만들면 됩니다. 되돌릴 수 있는 결정이므로 지금은 이대로 진행하셔도 됩니다.

## 11. 연동 확인

### 11.1 통제가 걸리는 쪽

**접속.** `OCS_APP`.

**실행.** **실패해야 정상입니다.**

```sql
SET SERVEROUTPUT ON
DECLARE c RAW(2000);
BEGIN
  c := OCS_OWNER.PKG_SECURE_API.enc_rrn('8001011234567');
  DBMS_OUTPUT.PUT_LINE('ENCRYPT=OK  <-- 통제가 새고 있다');
EXCEPTION
  WHEN OTHERS THEN
    DBMS_OUTPUT.PUT_LINE('거부됨 SQLCODE=' || SQLCODE || ' ' || SQLERRM);
END;
/
```

**확인.** `SQLCODE=-20521` 과 「애플리케이션 인증 문맥 없음」이 나와야 합니다. `enc_rrn` 을 `idx_rrn` 으로 바꾸어도 같아야 합니다.

> **설명.** 색인까지 막는 까닭은 색인이 결정적이기 때문입니다. 후보 평문을 넣어 가며 저장된 색인과 맞춰 보면 평문을 알아낼 수 있으므로, 복호화만 막고 색인을 열어 두면 통제가 성립하지 않습니다.

### 11.2 열리는 쪽

**실행.** 자바 연동 확인 프로그램을 컴파일하고 돌립니다. JDBC 드라이버가 필요하며 오라클 설치 폴더의 `jdbc/lib/ojdbc8.jar` 에 있습니다.

```
dir /s /b src\*.java > srcs.txt
javac -encoding UTF-8 -cp <경로>\ojdbc8.jar -d out @srcs.txt

java -cp out;<경로>\ojdbc8.jar ocsecure.client.OcsConnectDemo ^
     "jdbc:oracle:thin:@<호스트>:<포트>/<서비스명>" OCS_APP <암호> <증표키 16진 64자>
```

**확인.** **통과 5, 실패 0** 이 기대값입니다.

증표 키를 명령행에 적으면 명령 이력에 남습니다. 확인이 끝나면 창을 닫으시는 편이 낫습니다.

> **설명.** 문맥 없이는 거부되고, 증표를 제출하면 암호화가 되며, 같은 평문이 매번 다른 암호문이 되고, 구분자가 있든 없든 색인 값이 같으며, 복호화 자격이 없으면 거부된다는 것을 봅니다. 운영 코드에서는 증표 키를 키 관리 제품이나 기동 시점에 주입되는 값에서 읽어야 하며 소스나 설정 파일에 평문으로 두어서는 안 됩니다.

## 12. 업무 스키마 적용

### 12.1 예시 만들기

**접속.** `SYS` 또는 그에 준하는 권한.

**실행.** 응용 계정에 표와 뷰와 트리거를 만들 권한을 줍니다. 실제 사업에서는 업무 스키마에 이미 있을 권한입니다.

```sql
GRANT CREATE TABLE, CREATE VIEW, CREATE TRIGGER TO OCS_APP;
```

**접속.** `OCS_APP`. 마스터 키가 열려 있어야 합니다.

**실행.**

```
SQL> @sql/08_sample/800_sample_member.sql
```

**확인.**

```sql
SELECT object_name, object_type, status FROM user_objects
 WHERE object_name IN ('TB_MEMBER_ENC', 'TB_MEMBER', 'TRG_TB_MEMBER_IOD')
 ORDER BY 1;
```

**정확히 세 행이 나와야 하며 세 행 모두 `VALID` 여야 합니다.** 저장 테이블 `TB_MEMBER_ENC` 가 `TABLE` 로, 투명화 뷰 `TB_MEMBER` 가 `VIEW` 로, 트리거 `TRG_TB_MEMBER_IOD` 가 `TRIGGER` 로 한 행씩입니다. 세 행에 못 미치면 예시가 만들어지지 않은 것이고, `INVALID` 가 있으면 제5장을 빠뜨린 것입니다.

> **설명.** 이 예시는 실제 업무 테이블을 어떻게 바꾸어야 하는지의 본보기입니다. 암호문과 색인을 따로 두는 실제 저장 테이블을 만들고, 옛 이름을 그대로 쓰는 투명화 뷰를 올리고, 평문을 넣으면 트리거가 암호화와 색인 생성을 대신하게 하는 구조입니다. 조회 구문을 어떻게 고쳐야 하는지도 파일 끝에 적혀 있습니다. 확인에서 객체가 있는지와 성한지를 함께 보는 까닭은, 잘못된 객체만 세는 조회는 객체가 아예 없을 때에도 아무 행이 나오지 않아 통과처럼 보이기 때문입니다.

### 12.2 자격 없이 넣고 꺼내 보기

### 12.3 자격을 주고 반대쪽 보기

**접속.** `OCS_KEYADM`. **다른 계정으로 치면 `PLS-00201` 이 납니다.**

**실행.**


**실행.** 같은 확인을 `--data` 대신 `--keep` 으로 한 번 더 돌립니다.

```
java -cp out;<경로>\ojdbc8.jar ocsecure.client.OcsConnectDemo ^
     "jdbc:oracle:thin:@<호스트>:<포트>/<서비스명>" OCS_APP <암호> <증표키 16진 64자> --keep
```

**확인.** 이번에도 **통과 9, 실패 0** 입니다. 아까 거부되던 복호화가 평문을 돌려주고 마스킹이던 조회가 평문으로 바뀝니다. **마스킹 전용 컬럼만은 자격이 있어도 그대로 가려져야 하며, 가려지지 않으면 넘어가지 마십시오.** 마지막 줄에 시험 자료를 남겨 두었다는 안내가 나옵니다.

**자격은 지금 거두지 마십시오.** 제13장의 확인에 이 자격이 필요하며, 거두는 것은 제13.6절에서 합니다.

> **설명.** 자격을 주는 쪽이 키 관리 계정인 것도 설계의 일부입니다. 소유 계정이 스스로에게 줄 수 없고 응용 계정이 스스로에게 줄 수도 없습니다. `--keep` 은 하는 일이 `--data` 와 같되 시험 자료를 지우지 않고 남깁니다. 제13장에 옮길 자료가 있어야 하기 때문입니다.

## 13. 키 교체 리허설

여기서 쓰는 것은 실제 업무 테이블이 아니라 제12장에서 만든 예시 테이블입니다. 제12.3절에서 `--keep` 으로 남겨 둔 두 건이 옮길 자료입니다.

### 13.1 옮길 자료와 권한

**접속.** `OCS_APP`.

**확인.** 두 건이 나와야 합니다. 비어 있으면 제12.3절의 `--keep` 실행만 다시 하십시오.

```sql
SELECT mbr_id FROM TB_MEMBER_ENC ORDER BY 1;
```

**실행.** 같은 창에서 재암호화 배치가 쓸 권한을 줍니다.

```sql
GRANT SELECT, UPDATE ON TB_MEMBER_ENC TO OCS_OWNER;
```

> **설명.** 이 패키지는 소유자 권한으로 돌므로 대상 테이블의 조회와 갱신 권한을 `OCS_OWNER` 에게 직접 주어야 하고, 역할로 준 권한은 저장 프로시저 안에서 인정되지 않습니다. 실제 업무 테이블을 옮기실 때에는 스키마와 테이블, 기본 키와 암호문과 색인 컬럼 이름만 그 테이블의 것으로 바꾸시면 되고 절차는 그대로입니다. 다만 재암호화 배치는 숫자형 단일 기본 키를 가진 테이블만 지원하므로 대상 테이블이 이 조건을 만족하는지는 먼저 보셔야 합니다.

### 13.2 키 교체

**접속.** `OCS_KEYADM`.

**실행.**

```sql
SET SERVEROUTPUT ON
DECLARE
  v_old PLS_INTEGER;
  v_new PLS_INTEGER;
BEGIN
  SELECT key_id INTO v_old FROM OCS_OWNER.V_SEC_KEY_STATUS
   WHERE domain_code = 'RRN' AND key_state = 'ACTIVE';
  v_new := OCS_OWNER.PKG_KEY_ADMIN.rotate('RRN', '교체 리허설');
  COMMIT;
  DBMS_OUTPUT.PUT_LINE('옛 key_id = ' || v_old || ' , 새 key_id = ' || v_new);
END;
/
```

**여기 나오는 옛 key_id 를 적어 두십시오.** 제13.4절에서 폐기할 키가 이것입니다.

**실행.** 교체 직후에 기존 자료가 그대로 읽히는지 봅니다. `--read` 는 남은 자료를 읽기만 하고 넣지도 지우지도 않습니다.

```
java -cp out;<경로>\ojdbc8.jar ocsecure.client.OcsConnectDemo ^
     "jdbc:oracle:thin:@<호스트>:<포트>/<서비스명>" OCS_APP <암호> <증표키 16진 64자> --read
```

**확인.** **통과 6, 실패 0** 이며 두 건의 평문이 나와야 합니다.

> **설명.** 교체하면 옛 키가 `RETIRING`, 새 키가 `ACTIVE` 가 됩니다. 이 시점부터 새로 넣는 자료는 새 키로 암호화되고 기존 자료는 그대로 옛 키로 읽힙니다. 서비스를 멈추지 않는다는 것이 이 설계의 요점이므로 이 확인이 중요합니다. 폐기할 키를 상태로 찾지 않고 번호로 지목하는 까닭은, 폐기 대기 상태인 키가 도메인마다 여럿일 수 있어서 상태로 찾는 조회가 `ORA-01422` 로 멈출 수 있기 때문입니다. 조회 도구로 직접 읽지 않고 프로그램으로 읽는 까닭은 조회 도구에서는 응용 문맥을 세울 수 없기 때문입니다.

### 13.3 재암호화

**접속.** `OCS_KEYADM`.

**실행.**

```sql
BEGIN
  OCS_OWNER.PKG_REKEY.create_job('REHEARSAL', 'OCS_APP', 'TB_MEMBER_ENC',
                                 'MBR_ID', 'MBR_RRN_ENC', 'RRN', 'MBR_RRN_IDX', 1000);
  COMMIT;
END;
/

SET SERVEROUTPUT ON
BEGIN
  DBMS_OUTPUT.PUT_LINE('옮길 건수(전) = ' || OCS_OWNER.PKG_REKEY.remaining('REHEARSAL'));
  OCS_OWNER.PKG_REKEY.run_job('REHEARSAL');
  DBMS_OUTPUT.PUT_LINE('옮길 건수(후) = ' || OCS_OWNER.PKG_REKEY.remaining('REHEARSAL'));
END;
/
```

**확인.** **옮길 건수(전) = 2, 옮길 건수(후) = 0** 이 기대값입니다. `ORA-00942` 가 나면 제13.1절의 권한 부여를 빠뜨리셨거나 역할로 주신 것입니다.

> **설명.** 작업 이름은 한 번 쓰면 남으므로 리허설을 다시 하실 때에는 `REHEARSAL2` 처럼 다른 이름을 쓰셔야 합니다. 같은 이름으로 다시 만들려 하면 중복 오류가 나고, 이름을 되살려 쓰는 `reset_job` 은 진행 지점만 되돌릴 뿐 목표 키는 처음 만들 때 값 그대로이므로 새 교체에는 맞지 않습니다.

### 13.4 옛 키 폐기

**접속.** `OCS_KEYADM`.

**확인.** 폐기하기 전에 옛 키로 남아 있는 자료가 없는지 먼저 봅니다. **0 이 아니면 폐기하지 마십시오.** 0 이 아닌 채로 폐기하면 남은 자료를 영영 읽을 수 없게 됩니다.

```sql
SET SERVEROUTPUT ON
BEGIN
  DBMS_OUTPUT.PUT_LINE('남은 건수 = ' || OCS_OWNER.PKG_REKEY.remaining('REHEARSAL'));
END;
/
```

제13.3절의 「옮길 건수(후)」와 같은 값이며, 같은 함수를 한 번 더 부르는 것입니다. 0 이 아니면 제13.3절의 `run_job` 을 한 번 더 돌리십시오.

**실행.**

```sql
BEGIN
  OCS_OWNER.PKG_KEY_ADMIN.retire(<제13.2절에서 적어 둔 옛 key_id>);
  COMMIT;
END;
/
```

**실행.** 제13.2절의 `--read` 를 한 번 더 돌립니다.

**확인.** 다시 **통과 6, 실패 0** 이며 두 건의 평문이 그대로 나와야 합니다.

> **설명.** 남은 건수란 대상 테이블의 암호문을 하나씩 읽어 그 머리에 적힌 키 번호가 이번 작업의 목표 키와 다른 것을 센 값입니다. 곧 아직 옛 키로 남아 있는 행의 수이며, 이것이 0 이라는 것은 모든 행이 새 키로 옮겨졌다는 뜻입니다. 전부 읽어서 세므로 큰 테이블에서는 시간이 걸립니다. `run_job` 은 한 번 부를 때 정해진 묶음 수만 처리하고 돌아오므로, 실제 업무 테이블에서는 0 이 될 때까지 여러 번 불러야 할 수 있습니다.
>
> 폐기는 키 값을 지우는 것이 아니라 그 키로는 복호화도 못 하게 막는 것입니다. 폐기한 키로 읽어야 하는 자료가 한 건이라도 남아 있었다면 여기서 「사용할 수 없는 키」 오류가 났을 것이므로, 아무 일도 일어나지 않는 것이 바로 확인입니다. 반대로 오류가 난다면 옮기지 못한 자료가 남아 있다는 뜻이고 그것이 이 리허설에서 건질 수 있는 가장 중요한 발견입니다.

### 13.5 뒷정리

**접속.** `OCS_APP`.

**실행.**

```sql
DELETE FROM TB_MEMBER_ENC WHERE mbr_id IN (9001, 9002);
COMMIT;
REVOKE SELECT, UPDATE ON TB_MEMBER_ENC FROM OCS_OWNER;
```

이어서 제13.6절로 가십시오.

> **설명.** 지우는 대상이 뷰가 아니라 실제 저장 테이블인 것은 일부러입니다. 뷰로 지우려면 트리거를 거치게 되고 조회 도구에서는 응용 문맥이 없어 막힙니다. 임시로 준 권한을 상시로 두면 암호 모듈 소유 계정이 업무 자료를 언제든 건드릴 수 있게 되어 계정을 나눈 뜻이 옅어집니다.

### 13.6 복호화 자격 거두기

제12.3절에서 연동 확인을 위해 잠시 준 복호화 자격을 여기서 거둡니다. 설치의 마지막 손질입니다.

**접속.** `OCS_KEYADM`.

**실행.** 인자 셋은 줄 때 쓴 앞의 셋과 똑같아야 합니다.

```sql
BEGIN
  OCS_OWNER.PKG_KEY_ADMIN.revoke_reveal('RRN', 'OCS_APP', 'USER');
  COMMIT;
END;
/
```

**접속.** `OCS_AUDITOR`.

**확인.** 아무 행도 나오지 않아야 합니다.

```sql
SELECT domain_code, grantee_type, grantee_name, expires_at
  FROM OCS_OWNER.V_SEC_EFFECTIVE_REVEAL
 WHERE domain_code = 'RRN';
```

> **설명.** 이 자격은 연동이 제대로 되는지 보려고 잠시 준 것이고, 그대로 두면 응용 계정이 주민등록번호 평문을 언제든 꺼낼 수 있는 상태가 계속됩니다. 실제 사업에서는 사람이 아니라 업무 역할에 주고 기한을 함께 두는 것이 원칙이며, 여기서처럼 특정 계정에 기한 없이 주는 것은 확인 목적에 한합니다. 자격 대장은 키 관리 계정에게도 열어 두지 않았으므로 확인은 감사 계정이 유효 자격 뷰로 합니다. 주고 거둔 사실은 둘 다 감사 기록에 `REVEAL_GRANT` 와 `REVEAL_REVOKE` 로 남습니다.

## 14. 개통 직전 조치

여기까지가 설치와 검증이며, 개통 직전에 할 일이 따로 넷 있습니다.

### 14.1 전용 계정 만들기

유지 프로그램을 돌릴 전용 계정을 먼저 만듭니다. 사람이 쓰는 계정으로 돌리면 그 사람이 떠나거나 암호를 바꿀 때 암복호화가 함께 멈춥니다. 아래에서는 `ocskeeper` 라는 이름으로 적었습니다.

**실행(RHEL).** 로그인할 수 없고 홈 디렉터리도 없는 시스템 계정으로 만듭니다. 이어서 프로그램을 둘 디렉터리를 만들고 소유자를 넘깁니다.

```
useradd --system --no-create-home --shell /sbin/nologin ocskeeper
mkdir -p /opt/ocsecure/log
chown -R ocskeeper:ocskeeper /opt/ocsecure
chmod 750 /opt/ocsecure
```

**확인(RHEL).** 계정이 보이고, 로그인 셸이 `/sbin/nologin` 이어야 합니다.

```
id ocskeeper
getent passwd ocskeeper
```

**실행(윈도우).** 관리자 권한 명령 프롬프트에서 만듭니다. 별표를 적으면 암호를 물어보므로 명령 이력에 남지 않습니다. 암호는 길고 임의로 정하시고, 설정 파일의 암호와 마찬가지로 열람 통제가 되는 곳에 보관하십시오.

```
net user ocskeeper * /add /comment:"OCSecure 키 저장소 유지 프로그램 전용"
mkdir C:\ocsecure\log
```

이어서 암호 만료를 끕니다. **여기서부터는 창을 반드시 관리자 권한으로 띄우셔야 합니다.** 시작 단추를 누르고 `cmd` 또는 `powershell` 을 찾은 뒤 오른쪽 단추를 눌러 「관리자 권한으로 실행」을 고르십시오. 창 제목에 「관리자」가 붙어 있으면 맞습니다. 일반 권한으로 치면 계정을 고치지 못해 거부당하는데, 그 오류가 권한 문제로 보이지 않는 문구로 나오는 일이 있어 엉뚱한 데를 찾게 됩니다.

장비의 윈도우 판과 셸에 따라 되는 명령이 다르므로 세 가지를 적습니다. **화면으로 하는 첫 번째가 가장 확실하니 먼저 그쪽을 쓰시고, 명령으로 하셔야 할 때만 아래 둘을 보십시오.**

화면으로 하는 방법입니다. `lusrmgr.msc` 를 열어 사용자 목록에서 `ocskeeper` 의 속성을 열고 **「암호 사용 기간 제한 없음」에 체크**하신 뒤 확인을 누르십시오.

```
lusrmgr.msc
```

PowerShell 창에서 하는 방법입니다. 감싸지 말고 그대로 치십시오.

```
Set-LocalUser -Name ocskeeper -PasswordNeverExpires $true
```

명령 프롬프트에서 하는 방법입니다. 위 명령을 감싸거나, 그 명령이 없는 장비에서는 `wmic` 을 씁니다.

```
powershell -Command "Set-LocalUser -Name ocskeeper -PasswordNeverExpires $true"
wmic useraccount where "name='ocskeeper'" set PasswordExpires=FALSE
```

셋 다 실패한다면 먼저 창이 관리자 권한인지 다시 보십시오. 그것이 맞는데도 안 되는 경우라면 명령이 그 장비에 없는 것입니다. 세 가지를 두는 까닭도 어느 하나가 모든 장비에서 되지는 않기 때문입니다. `Set-LocalUser` 는 PowerShell 5.1 부터, 곧 Windows 10 과 Server 2016 부터 있고 그 이전 장비에는 없습니다. 반대로 `wmic` 은 오래된 장비에는 있으나 최근 윈도우에서는 빠졌습니다. `lusrmgr.msc` 는 서버 판에 대체로 있습니다. 또 `powershell -Command "... $true"` 형태는 **명령 프롬프트에서만 맞습니다.** 같은 줄을 PowerShell 창에서 치면 바깥 셸이 큰따옴표 안의 `$true` 를 `True` 라는 문자열로 먼저 바꿔 넣어, `'System.String'을 'PasswordNeverExpires' 매개 변수에 필요한 유형 'System.Boolean'으로 변환할 수 없습니다` 라는 오류가 납니다.

어느 쪽을 쓰셨든 결과는 `net user ocskeeper` 의 「암호 만료 날짜」로 확인하시면 됩니다.

암호 만료를 꺼 두는 까닭은, 만료되면 작업 스케줄러에 저장된 암호가 맞지 않게 되어 어느 날 재기동 뒤에 조용히 뜨지 않기 때문입니다. 대신 암호를 바꾸실 때에는 제14.4절의 작업 등록도 함께 다시 하셔야 합니다.

이어서 이 계정의 권한을 조입니다. `secpol.msc` 를 열어 로컬 정책의 사용자 권한 할당에서 셋을 손보십시오. **「일괄 작업으로 로그온」에 `ocskeeper` 를 더하고**, 「로컬 로그온 거부」와 「원격 데스크톱 서비스를 통한 로그온 거부」에도 `ocskeeper` 를 더하십시오. 앞의 하나는 작업 스케줄러가 이 계정으로 프로그램을 돌리기 위해 필요하고, 뒤의 둘은 이 계정으로 사람이 장비에 들어오지 못하게 막습니다.

**확인(윈도우).** 계정이 만들어졌고 활성 상태인지 봅니다. 「계정 활성」이 `Yes` 또는 「예」이고 **「암호 만료 날짜」가 「안 함」 또는 `Never`** 여야 합니다. 암호 만료 날짜에 실제 날짜가 보이면 위의 `Set-LocalUser` 가 먹지 않은 것입니다.

```
net user ocskeeper
```

> **설명.** 장비가 도메인에 속해 있으면 도메인 정책이 로컬 정책을 덮어쓸 수 있습니다. 위의 사용자 권한 할당이 적용되지 않는다면 도메인 관리자와 협의하셔야 합니다. 작업 스케줄러가 계정을 지정할 때 「일괄 작업으로 로그온」 권한을 알아서 주는 경우도 있습니다만, 보안을 조여 둔 장비에서는 그렇지 않으므로 미리 확인해 두는 편이 낫습니다.
>
> 이 계정은 데이터베이스 계정이 아니라 운영체제 계정입니다. 데이터베이스 쪽에서 쓰는 계정은 설정 파일에 적는 `OCS_KEYADM` 이며 둘은 별개입니다.

### 14.2 설정 파일 만들기

**실행.** 키 저장소 유지 프로그램의 설정 파일을 만듭니다. 예시가 `java/keeper.properties.sample` 에 있으니 이름을 `keeper.properties` 로 바꾸어 복사하고 값을 채우십시오. 둘 곳은 이 프로그램을 실행할 디렉터리이며, 실행할 때 경로를 넘기므로 어디에 두셔도 됩니다. 아래에서는 리눅스는 `/opt/ocsecure`, 윈도우는 `C:\ocsecure` 에 둔 것으로 적었습니다.

채울 값은 넷입니다. `jdbc.url` 에 접속 문자열을, `jdbc.user` 와 `jdbc.password` 에 `OCS_KEYADM` 의 계정과 암호를, `master.key` 에 제8장에서 기록해 두신 16진 64자를 넣으십시오. `check.seconds` 는 저장소가 열려 있는지 확인하는 주기이며 기본값 30 이면 충분합니다.

**이 파일에는 마스터 키와 계정 암호가 평문으로 들어갑니다.** 만드는 즉시 제14.3절로 잠그십시오. 형상 관리에는 값이 채워진 파일을 올리지 마십시오. 저장소의 `.gitignore` 가 `keeper.properties` 를 막아 두었습니다.

### 14.3 설정 파일 보호

제14.1절에서 만든 전용 계정만 읽을 수 있도록 막습니다.

**실행(RHEL).** 소유자를 전용 계정으로 바꾼 뒤 소유자만 읽도록 막습니다.

```
chown ocskeeper:ocskeeper /opt/ocsecure/keeper.properties
chmod 600 /opt/ocsecure/keeper.properties
```

**확인(RHEL).** `-rw-------` 와 `ocskeeper` 가 나와야 합니다.

```
ls -l /opt/ocsecure/keeper.properties
```

**실행(윈도우).** 관리자 권한 명령 프롬프트에서 `icacls` 로 접근 제어 목록을 다시 짭니다. **첫 줄의 상속 제거가 핵심입니다.** 이것을 빠뜨리면 상위 폴더에서 내려온 `Users` 읽기 권한이 그대로 남아 장비에 로그인할 수 있는 누구나 마스터 키를 읽습니다.

```
icacls C:\ocsecure\keeper.properties /inheritance:r
icacls C:\ocsecure\keeper.properties /grant:r "ocskeeper:(R)"
icacls C:\ocsecure\keeper.properties /grant:r "Administrators:(F)"
```

**확인(윈도우).** 두 줄만 나와야 합니다. `ocskeeper:(R)` 과 `BUILTIN\Administrators:(F)` 이며, `Users` 나 `Everyone` 이나 `Authenticated Users` 가 보이면 상속 제거가 되지 않은 것입니다.

```
icacls C:\ocsecure\keeper.properties
```

> **설명.** 윈도우에서는 프로그램이 이 보호를 대신 확인해 주지 못합니다. 유지 프로그램에 설정 파일이 남에게 읽히면 경고를 찍는 장치가 있습니다만, 그것은 POSIX 권한을 읽는 방식이라 윈도우에서는 아무 말 없이 지나갑니다. 그러므로 윈도우에서는 위 `icacls` 확인을 사람이 눈으로 해야 합니다.
>
> 접근 제어로 막아도 그 장비의 관리자는 소유권을 가져와 읽을 수 있습니다. 이것은 윈도우든 리눅스든 마찬가지이며 파일 권한으로 해결되는 문제가 아닙니다. 관리자 수를 줄이고 누가 언제 그 장비에 들어갔는지 남기는 쪽으로 다루셔야 합니다. 근본적으로는 제8장의 설명에 적은 대로 `EXTERNAL` 로 옮겨 키 관리 제품이 키를 쥐게 하는 것이 답이며, 이 설정 파일은 그때까지의 과도기 수단입니다.

### 14.4 상주 실행

**실행.** 어느 쪽 OS든 먼저 한 번만 돌려 보십시오. 설정이 틀렸으면 여기서 드러납니다.

```
java -cp out:ojdbc8.jar ocsecure.keeper.OcsKeystoreKeeper keeper.properties --once
```

**확인.** 저장소를 열고 바로 끝납니다. 이어서 제8장의 열림 확인이 「키 저장소 열림」으로 나와야 합니다.

**실행(RHEL).** `nohup` 으로도 돌아갑니다만 장비를 재기동하면 사라지므로 systemd 단위로 등록하시는 편이 낫습니다. `/etc/systemd/system/ocs-keeper.service` 에 아래를 두십시오.

```
[Unit]
Description=OCSecure Keystore Keeper
After=network-online.target

[Service]
Type=simple
User=ocskeeper
WorkingDirectory=/opt/ocsecure
ExecStart=/usr/bin/java -cp /opt/ocsecure/out:/opt/ocsecure/ojdbc8.jar ocsecure.keeper.OcsKeystoreKeeper /opt/ocsecure/keeper.properties
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

```
systemctl daemon-reload
systemctl enable --now ocs-keeper
systemctl status ocs-keeper
journalctl -u ocs-keeper -f
```

**실행(윈도우).** 윈도우에는 `nohup` 에 해당하는 것이 없고, 명령 프롬프트에서 띄운 프로그램은 로그아웃하면 함께 죽습니다. **작업 스케줄러에 등록하는 것이 추가 소프트웨어 없이 되는 유일한 방법입니다.** 먼저 실행할 내용을 배치 파일로 만드십시오. 명령에 경로와 재지정이 섞이면 스케줄러 등록이 번거로워지기 때문입니다. `C:\ocsecure\keeper.bat` 에 아래를 두십시오.

```
@echo off
cd /d C:\ocsecure
java -cp out;ojdbc8.jar ocsecure.keeper.OcsKeystoreKeeper keeper.properties >> log\keeper.log 2>&1
```

이 배치 파일과 `out` 폴더도 `keeper.properties` 와 같은 요령으로 전용 계정과 관리자만 접근하도록 막으십시오. 그런 다음 관리자 권한 명령 프롬프트에서 등록합니다. 암호를 묻거든 전용 계정의 암호를 넣으십시오.

```
schtasks /create /tn "OCSecure Keystore Keeper" /tr "C:\ocsecure\keeper.bat" ^
         /sc onstart /ru ocskeeper /rl HIGHEST /f
```

`/ru` 만 적고 `/rp` 를 적지 않으면 암호를 물어봅니다. 명령에 암호를 적으면 명령 이력에 남으므로 묻게 하는 편이 낫습니다. 등록이 「액세스가 거부되었습니다」로 막히면 전용 계정에 「일괄 작업으로 로그온」 권한이 없는 것이니 제14.1절의 사용자 권한 할당을 다시 보십시오.

`/sc onstart` 는 장비가 켜질 때 돌린다는 뜻이고, `/ru` 로 계정을 지정하면 **그 계정이 로그인해 있지 않아도 돌아갑니다.** 이것이 로그아웃해도 죽지 않는 근거입니다.

**등록한 뒤에 반드시 한 가지를 더 고치셔야 합니다.** 작업 스케줄러는 작업이 일정 시간 넘게 돌면 강제로 끝내는 설정을 기본으로 두는데, 이 프로그램은 끝나지 않고 계속 도는 것이 정상이므로 그대로 두면 며칠 뒤에 조용히 멈춥니다. 작업 스케줄러 화면에서 해당 작업의 설정 탭을 열어 「작업이 다음 시간 이상 실행되면 중지」의 **체크를 해제**하십시오. 같은 화면의 「작업이 실패하면 다시 시작」도 함께 켜 두시면 좋습니다.

**확인(윈도우).** 등록 상태를 보고, 장비를 재기동한 뒤에도 돌고 있는지까지 보셔야 합니다. 로그아웃만 해 보는 것으로는 부족합니다.

```
schtasks /query /tn "OCSecure Keystore Keeper" /v /fo list
type C:\ocsecure\log\keeper.log
```

로그에 주기적인 확인 기록이 쌓이고, 제8장의 열림 확인이 「키 저장소 열림」으로 나오면 됩니다.

> **설명.** 윈도우에서 이것을 진짜 서비스로 만들려면 자바 프로그램을 서비스로 감싸 주는 별도 도구가 필요합니다. 윈도우가 기본으로 주는 `sc.exe` 는 서비스 규약을 따르는 실행 파일만 등록할 수 있어서 일반 자바 프로그램을 바로 올리지 못합니다. 폐쇄망에 외부 도구를 들이는 것은 승인 절차가 따로 있을 것이므로, 추가 반입 없이 되는 작업 스케줄러 쪽을 본문으로 적었습니다. 운영 요건상 서비스로 등록해야 한다면 그때 도구 반입을 따로 협의하시면 됩니다.
>
> 로그 파일에는 키 값이 찍히지 않습니다. 열렸는지 닫혔는지와 다시 넣었다는 사실만 남으며, 상태가 바뀔 때만 기록하므로 파일이 빨리 자라지도 않습니다.

## 15. 설치 점검표

각 장의 기대값만 모았습니다.

제2.2절에서는 대상 PDB 이름과 문자집합이 나와야 하고 `CDB$ROOT` 가 아니어야 합니다. 제2.3절에서는 점검 항목이 모두 `OK` 여야 합니다. 제3장에서는 점검 조회 넷이 모두 비어 있어야 합니다. 제4장에서는 잘못된 객체가 하나도 없고 패키지 명세 14와 본문 14, 테이블 8, 뷰 3, 시퀀스 3, 인덱스 14가 나와야 합니다. 제5장에서는 점검 조회 둘이 비어 있고 부여 내역에 네 계정과 세 역할이 보여야 합니다. 제6장에서는 통과 68에 실패 0 이어야 합니다. 제8장에서는 「키 저장소 열림」이 나와야 합니다. 제9장에서는 네 도메인에 각각 활성 키가 하나씩 있어야 하고, 제10장에서는 `_APPCTX` 에 활성 키가 하나 있어야 합니다.

제11장에서는 응용 계정 직접 호출이 `-20521` 로 거부되고 자바 확인이 통과 5에 실패 0 이어야 합니다. 제12장에서는 예시 객체 세 개가 모두 `VALID` 로 나오고, 자격을 주기 전의 `--data` 와 자격을 준 뒤의 `--keep` 이 모두 통과 9에 실패 0 이어야 합니다. 통과 건수는 같되 자격이 생기면 거부되던 복호화가 평문을 돌려주고 마스킹 전용 컬럼만은 그대로 가려져 있어야 합니다.

제13장에서는 교체 직후 `--read` 가 통과 6에 실패 0 이고, 옮길 건수가 2에서 0 이 되며, 옛 키를 폐기한 뒤의 `--read` 도 다시 통과 6에 실패 0 이어야 합니다. 뒷정리와 제13.6절의 자격 회수를 마치면 감사 계정으로 본 유효 자격 조회가 비어 있어야 합니다. 제14장에서는 전용 계정이 로그인할 수 없는 상태로 만들어져 있어야 하고, 설정 파일에 전용 계정과 관리자 외의 권한이 남아 있지 않아야 하며, 장비를 재기동한 뒤에도 유지 프로그램이 돌고 있어야 하며, `APPCTX_MODE` 가 `PROOF` 여야 합니다.

## 16. 자주 겪는 문제

몇몇 패키지에서만 컴파일 오류가 나고 오류 위치가 주석이나 문자열 근처라면 인코딩 문제입니다. 제2.1절로 돌아가십시오.

`ORA-01919` 로 역할이 존재하지 않는다고 나오거나 `ORA-00933` 으로 SQL 명령어가 올바르게 종료되지 않았다고 나오면 앞선 구문이 조용히 실패한 것입니다. SQL\*Plus 는 최상위 구문을 세미콜론에서 끊으므로 그 뒤에 주석을 같은 줄로 붙이면 구문 전체가 실패하는데, 실패해도 다음 줄로 넘어가기 때문에 긴 출력 속에서 놓치기 쉽습니다. 저장소의 스크립트는 이 문제를 모두 고쳤고 정적 점검기가 다시 생기지 않도록 막습니다만, 스크립트를 손수 고치실 때는 주의하십시오.

`PLS-00201` 로 식별자를 찾을 수 없다고 나오면 둘 중 하나입니다. `PKG_SECURE_API` 를 찾을 수 없다면 제5장을 빠뜨린 것이고, `PKG_KEY_ADMIN` 이나 `PKG_REKEY` 를 찾을 수 없다면 계정을 잘못 고른 것입니다. 키와 자격을 다루는 패키지는 `OCS_KEYADM` 만 부를 수 있습니다.

`--data` 를 붙였을 때 「투명화 뷰 확인 중 오류」와 함께 `ORA-00942` 가 나오면 예시 표가 아직 없는 것입니다. 제12.1절을 먼저 하십시오. 제거 스크립트로 지운 뒤에는 응용 계정과 함께 예시 표도 사라지므로 다시 만들어야 합니다.

`--read` 에서 「시험 자료(9001, 9002)가 없다」고 나오면 제12.3절에 `--keep` 을 붙이지 않으신 것입니다. `--data` 는 확인이 끝나면 넣었던 자료를 지우므로 제13장에 옮길 자료가 남지 않습니다. 제12.3절의 `--keep` 실행만 다시 하시면 됩니다.

`ORA-20521` 에 「증표 불일치」가 함께 나오면 데이터베이스가 가진 `_APPCTX` 키와 명령행에 넣은 키가 다른 것입니다. 이 키는 재설치할 때마다 새로 만들어 넣는 값이므로 지우고 다시 설치했다면 옛 키를 쓰고 있을 가능성이 높습니다. 이번 설치에서 제10장에 넣으신 세 번째 값을 쓰십시오. 기억나지 않으면 기존 `_APPCTX` 키를 폐기하고 제10장을 다시 하시면 됩니다.

`ORA-01422` 로 요구보다 많은 행이 조회되었다고 나오면 폐기 대기 상태인 키가 둘 이상인 것입니다. 리허설을 두 번 하셨거나 자료 없이 교체부터 하신 경우이며, 부록 가로 정리하십시오.

`ORA-20513` 으로 키 저장소가 열려 있지 않다고 나오면 마스터 키가 사라진 것입니다. 자체 시험을 돌린 직후이거나 데이터베이스를 재기동한 뒤입니다. 제8장의 주입을 다시 하십시오.

`ORA-20521` 로 애플리케이션 인증 문맥이 없다고 나오는 것은 대개 정상 동작입니다. 조회 도구로 직접 붙어 암복호화를 시도했을 때 나와야 하는 오류입니다.

`ORA-01720` 으로 허가 옵션이 없다고 나오면 암호 모듈의 패키지를 부르는 뷰를 제3자에게 넘기려 한 것입니다. 그러려면 응용 계정이 패키지에 대해 재부여 권한까지 가져야 하는데, 그 권한을 주면 응용 계정이 아무에게나 이 API 를 넘길 수 있게 되므로 주지 않는 편이 맞습니다. 자료를 넣고 꺼내는 일은 조회 도구가 아니라 애플리케이션이 하도록 하십시오.

소유자 권한 패키지 안에서 `ORA-00942` 로 테이블이 없다고 나오면 권한을 호출한 계정에 주고 소유 계정에는 주지 않은 것입니다. 소유자 권한 패키지 안의 조회와 갱신은 패키지 소유자의 권한으로 실행되며 역할로 준 권한은 인정되지 않습니다.

## 부록 가. 키 교체 리허설 되돌리기

**접속.** `OCS_KEYADM`.

**확인.** 지금 키 상태를 봅니다.

```sql
SELECT key_id, key_state, created_at FROM OCS_OWNER.V_SEC_KEY_STATUS
 WHERE domain_code = 'RRN' ORDER BY key_id;
```

**접속.** `OCS_APP`.

**확인.** **반드시 먼저 하십시오.** 0 이 나와야 합니다.

```sql
SELECT COUNT(*) FROM TB_MEMBER_ENC;
```

**접속.** `OCS_KEYADM`.

**실행.** **위가 0 일 때에만 실행하십시오.** 자료가 있는데 폐기하면 그 자료는 영영 읽을 수 없게 됩니다.

```sql
BEGIN
  FOR r IN (SELECT key_id FROM OCS_OWNER.V_SEC_KEY_STATUS
             WHERE domain_code = 'RRN' AND key_state = 'RETIRING') LOOP
    OCS_OWNER.PKG_KEY_ADMIN.retire(r.key_id);
  END LOOP;
  COMMIT;
END;
/
```

**확인.** `ACTIVE` 키 하나만 남아야 합니다. 그 뒤에는 제12.3절의 `--keep` 으로 시험 자료 두 건을 다시 넣으시고 제13장을 처음부터 밟으시되, 재암호화 작업 이름만 `REHEARSAL2` 처럼 바꾸십시오.

## 부록 나. 참고 근거와 신뢰도 자체 평가

이 문서에 적은 절차와 기대값은 개발 서버의 오라클 19c 인스턴스에서 실제로 수행하고 확인한 결과입니다. 설치 순서, 각 단계의 기대값, 자주 겪는 문제는 전부 실측에 근거하며 신뢰도는 높음입니다.

반복 횟수 측정값(1,000회당 약 8.7밀리초)은 개발 서버 한 대에서 잰 값입니다. 운영 장비에서는 달라지므로 반드시 다시 재셔야 합니다. 정확도는 그 장비에 한해 높음이며 다른 장비로 옮길 때는 참고치일 뿐입니다.

데이터베이스를 재기동하면 전역 문맥이 비워진다는 서술은 아직 실측하지 않았습니다. 메모리에만 있으므로 그렇게 보는 것이 타당하다는 수준이며 정확도는 중간입니다. 재기동 일정이 있을 때 확인하시기를 권합니다.

비밀번호 반복 횟수에 관한 국제 권고 수준을 언급한 부분은 해마다 바뀌는 수치이므로 정확도 중간으로 보시고, 인증 대응 시에는 최신 문서로 확인하셔야 합니다.

제17장의 제거 스크립트와 부록 가의 되돌리기 절차는 전체 재설치를 끝까지 한 번 돌려 검증하는 중입니다. 정확도는 중간입니다.

설치는 환경 점검, 계정과 역할, 스키마와 패키지, 권한 부여, 자체 시험, 운영 설정, 마스터 키, 도메인과 키, 증표용 키, 연동 확인, 업무 스키마 적용, 키 교체 리허설의 순서로 진행합니다. 각 장마다 기대값이 정해져 있으며 맞지 않으면 다음으로 넘어가지 않는 것이 원칙입니다.

가장 빠뜨리기 쉬운 것은 제5장의 권한 부여입니다. 이것을 건너뛰면 뒤의 거의 모든 단계가 막히는데 증상이 권한 문제로 보이지 않아 원인을 찾기 어렵습니다.

가장 중요한 것은 제8장의 마스터 키 보관입니다. 이것을 잃으면 암호화한 자료를 되살릴 방법이 없습니다.

개통 직전에는 키 저장소 유지 프로그램을 띄우고, 시험용 표를 지우고, 소유 계정을 잠그고, `APPCTX_MODE` 가 `PROOF` 인지 확인해야 합니다.
