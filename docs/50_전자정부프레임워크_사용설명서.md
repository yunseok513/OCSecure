# 전자정부 표준프레임워크 연동 사용설명서

## 1. 이 설명서의 대상과 범위

전자정부 표준프레임워크로 업무 화면을 개발하시는 분이 OCSecure 암복호화 모듈을 쓰는 방법을 다룹니다. 양방향 암복호화와 단방향 암호화를 각각 어떻게 호출하는지, 그리고 암호화된 컬럼을 조회와 검색과 집계에서 어떻게 다루는지가 본문의 내용입니다.

모듈의 내부 구조와 설계 근거는 `10_암호화모듈_개발설계.md`에, 통제 체계는 `20_보안관리_접근통제설계.md`에 있습니다. 이 설명서는 그것들을 읽지 않아도 업무를 개발할 수 있도록 쓰되, 왜 그렇게 해야 하는지가 중요한 지점에서는 이유를 함께 적었습니다. 이유를 모르면 편한 쪽으로 우회하게 되고, 그 우회가 대개 통제를 무너뜨리기 때문입니다.

본문의 코드는 모두 실제로 컴파일하고 시험한 것입니다. 다만 데이터베이스 쪽 호출문은 오라클 인스턴스에서 실행해 확인하지 못하였으므로, 처음 적용하실 때 한 건씩 확인하며 진행하시기를 권합니다.

## 2. 시작하기 전에 알아야 할 세 가지

### 2.1 암복호화는 데이터베이스가 합니다

기본 구도는 애플리케이션이 평문을 넘기면 데이터베이스가 암호화하여 저장하고, 조회할 때 데이터베이스가 복호화하여 돌려주는 것입니다. 애플리케이션은 키를 갖지 않으며 알 필요도 없습니다. 키를 애플리케이션이 들고 있으면 애플리케이션 서버가 침해될 때 키까지 함께 잃기 때문입니다.

따라서 업무 개발자가 다룰 것은 `OCS_OWNER.PKG_SECURE_API` 하나뿐입니다. 이 패키지 아래에 여러 계층이 더 있으나 응용 계정에는 실행 권한이 없으므로 호출할 수 없고, 호출할 필요도 없습니다.

자바 쪽 연동 모듈(`ocsecure-client`)은 세 가지 경우에만 씁니다. 접속 증표를 만들 때, 데이터베이스를 거치지 않는 외부 연계 자료를 다룰 때, 그리고 연동 시험에서 결과를 대조할 때입니다. 일상적인 업무 개발에서는 쓸 일이 없습니다.

### 2.2 세션마다 접속 문맥을 세워야 합니다

복호화는 정당한 애플리케이션 경로를 거친 세션에서만 동작합니다. 응용 계정의 접속 정보를 알아낸 사람이 조회 도구로 직접 붙어 데이터를 긁어 가는 일을 막기 위한 장치입니다.

이 문맥은 트랜잭션이 아니라 세션에 붙습니다. 연결 풀을 쓰는 환경에서는 연결을 빌릴 때마다 세우고 돌려줄 때 반드시 거두어야 합니다. 거두지 않고 반납하면 그 연결을 다음에 빌린 다른 사용자가 앞 사람의 문맥을 그대로 물려받습니다. 권한이 남의 것으로 판정되는 사고가 여기서 납니다. 구체적인 방법은 제3.1절에 있습니다.

### 2.3 표준프레임워크의 자체 암호화 서비스와 겹치지 않게 하십시오

전자정부 표준프레임워크는 실행환경 기반 계층에 자체 암호화 서비스를 제공하는 것으로 알려져 있습니다. 정확도: 중간이며, 쓰시는 버전의 개발자 가이드에서 정확한 클래스와 메서드 이름을 확인하시기 바랍니다. 제가 확인할 수 없어 이 설명서에서는 특정 클래스 이름을 단정하지 않겠습니다.

중요한 것은 이름이 아니라 역할 구분입니다. 표준프레임워크의 암호화 서비스는 설정 파일의 비밀번호를 가리거나 전송 구간의 자료를 감싸는 것처럼 애플리케이션 내부에서 끝나는 용도에 적합합니다. 반면 테이블 컬럼에 저장되는 개인정보는 OCSecure를 통해야 합니다. 키 관리와 감사와 권한 판정이 여기에 묶여 있기 때문입니다.

한 컬럼을 두 방식으로 번갈아 암호화하는 일만은 반드시 피하십시오. 어느 방식으로 암호화된 값인지 구분할 수 없게 되어 복호화가 불가능해집니다. OCSecure의 암호문은 맨 앞 바이트가 포맷 버전이라 식별이 가능하지만, 그 판별 코드를 업무 로직에 넣기 시작하면 감당할 수 없습니다.

## 3. 양방향 암호화 사용법

### 3.1 세션 문맥 세우기

가장 먼저 할 일이며, 이것이 빠지면 조회가 전부 실패합니다.

연동 모듈의 `OcsSessionSupport`가 이 일을 합니다. 증표 생성기를 넣어 만들고, 업무 처리 전후로 호출하면 됩니다.

```java
import ocsecure.client.OcsAppProof;
import ocsecure.client.OcsSessionSupport;

// 애플리케이션 기동 시 한 번 만들어 둡니다.
// 증표 키는 소스나 설정 파일에 평문으로 두지 마십시오.
// 키 관리 제품이나 기동 시점에 주입되는 환경 값에서 읽어야 합니다.
OcsAppProof proof = new OcsAppProof(loadAppCtxKeyFromSecureStore());
OcsSessionSupport session = new OcsSessionSupport(proof);
```

업무 처리에서는 다음과 같이 감쌉니다. 거두는 일을 반드시 `finally`에 두는 것이 요점입니다. 업무가 예외로 끝나도 문맥은 남기지 않아야 합니다.

```java
Connection con = dataSource.getConnection();
try {
    session.establish(con, currentUserId());   // 업무 사용자 식별자
    // ... 이 연결로 수행하는 모든 조회와 갱신 ...
} finally {
    session.release(con);
    con.close();
}
```

서비스마다 이 코드를 반복하는 것은 현실적이지 않으므로, 실제로는 연결을 내어 주는 지점을 한 번 감싸 자동으로 호출되게 하는 편이 낫습니다. 표준프레임워크는 스프링 기반이므로 관점 지향 방식으로 서비스 계층 진입과 종료에 걸거나, 데이터 소스를 감싸는 방식 중 무엇을 택해도 됩니다. 어느 쪽이든 지켜야 할 것은 하나입니다. **문맥을 세운 그 연결에서 업무를 수행해야 합니다.** 문맥을 세우고 연결을 반납한 뒤 다른 연결로 조회하면 아무 소용이 없습니다. 트랜잭션 경계 안에서 같은 연결이 유지되도록 구성하셔야 합니다.

개발 단계에서 증표 준비가 아직 안 되었다면 증표 없이 문맥만 세우는 방식을 쓸 수 있습니다. 생성자에 `null`을 넣으면 되고, 데이터베이스 쪽 설정도 함께 바꾸어야 합니다. 다만 이 방식은 통제가 사실상 없는 것과 같으므로 운영에서는 쓰지 마십시오. 운영 전환 점검 구문이 이 설정을 확인합니다.

### 3.2 저장하기

투명화 뷰를 적용한 테이블이라면 평소처럼 평문을 넣으시면 됩니다. 뷰에 붙은 트리거가 암호화와 색인 생성을 대신합니다.

```xml
<insert id="insertMember" parameterType="memberVO">
  INSERT INTO TB_MEMBER (mbr_id, mbr_name, mbr_rrn, mbr_phone)
  VALUES (#{mbrId}, #{mbrName}, #{mbrRrn}, #{mbrPhone})
</insert>
```

투명화 뷰를 쓰지 않고 실제 테이블에 직접 넣는다면 함수를 명시적으로 호출합니다. 암호문 컬럼과 색인 컬럼을 **함께** 채워야 한다는 점에 주의하십시오. 색인 컬럼을 빠뜨리면 그 행은 이후 검색되지 않습니다.

```xml
<insert id="insertMemberEnc" parameterType="memberVO">
  INSERT INTO TB_MEMBER_ENC (
    mbr_id, mbr_name_enc, mbr_name_idx, mbr_rrn_enc, mbr_rrn_idx, mbr_phone_enc
  ) VALUES (
    #{mbrId},
    OCS_OWNER.PKG_SECURE_API.enc_name(#{mbrName}),
    OCS_OWNER.PKG_SECURE_API.idx_name(#{mbrName}),
    OCS_OWNER.PKG_SECURE_API.enc_rrn(#{mbrRrn}),
    OCS_OWNER.PKG_SECURE_API.idx_rrn(#{mbrRrn}),
    OCS_OWNER.PKG_SECURE_API.protect('PHONE', #{mbrPhone})
  )
</insert>
```

표준으로 마련된 도메인에는 전용 함수가 있고, 그 밖의 도메인은 `protect`에 도메인 코드를 넘겨 씁니다. 도메인 코드는 임의로 지어 쓸 수 없고 키 관리자가 미리 등록해 둔 것이라야 합니다. 없는 도메인을 넘기면 오류가 납니다.

### 3.3 조회하기

투명화 뷰를 쓰면 기존 조회문을 거의 그대로 둘 수 있습니다.

```xml
<select id="selectMember" resultType="memberVO">
  SELECT mbr_id, mbr_name, mbr_rrn, mbr_phone, join_dt
    FROM TB_MEMBER
   WHERE mbr_id = #{mbrId}
</select>
```

뷰에서 평문 컬럼은 `show` 함수를 거치므로, 복호화 자격이 있으면 평문이 나오고 없으면 마스킹된 값이 나옵니다. 화면마다 권한을 판단하는 분기를 넣지 않아도 되도록 한 구성입니다.

자격이 없을 때 마스킹이 아니라 오류로 처리해야 하는 화면이라면 `reveal`을 직접 호출하십시오. 권한이 없으면 예외가 납니다.

```xml
<select id="selectMemberRrn" resultType="string">
  SELECT OCS_OWNER.PKG_SECURE_API.dec_rrn(mbr_rrn_enc)
    FROM TB_MEMBER_ENC
   WHERE mbr_id = #{mbrId}
</select>
```

화면에서 미리 권한을 알고 분기하고 싶다면 판정만 물어볼 수 있습니다. 복호화를 수행하지 않으므로 사용량에도 잡히지 않습니다.

```xml
<select id="canRevealRrn" resultType="string">
  SELECT OCS_OWNER.PKG_SECURE_API.allowed('RRN') FROM DUAL
</select>
```

### 3.4 자바 계층에서 직접 암복호화가 필요한 경우

외부 기관과 파일로 자료를 주고받는 연계처럼 데이터베이스를 거치지 않는 처리가 있습니다. 이때만 연동 모듈의 `OcsCrypto`를 직접 씁니다.

```java
import ocsecure.client.OcsCrypto;
import ocsecure.client.OcsKeySet;

OcsKeySet key = new OcsKeySet(keyId, OcsCrypto.ALG_AES256_CBC_HMAC_SHA256,
                              encKey, macKey, idxKey);

byte[] cipher = OcsCrypto.encrypt("880101-1234567", key);
String plain  = OcsCrypto.decrypt(cipher, key);
```

이 코드가 만드는 암호문은 데이터베이스가 만드는 것과 바이트 단위로 같습니다. 세 구현이 같은 고정 시험 벡터를 통과하는 것으로 확인하였습니다.

다만 여기서 키를 다루게 되므로, 이 경로를 여는 것은 예외적인 결정이어야 합니다. 키를 어디에 두고 누가 접근할 수 있는지가 새로 생기는 문제이며, 그 답 없이 편의로 이 경로를 쓰기 시작하면 데이터베이스 쪽에 세워 둔 통제가 통째로 우회됩니다.

## 4. 단방향 암호화 사용법

### 4.1 무엇을 단방향으로 하는가

원문을 다시 읽을 필요가 없고 일치 여부만 확인하면 되는 값, 곧 비밀번호가 대상입니다. 주민등록번호나 계좌번호처럼 업무상 원문 출력이 필요한 값은 단방향으로 하면 안 됩니다. 복구할 방법이 없기 때문입니다.

### 4.2 등록과 변경

```xml
<insert id="insertUser" parameterType="userVO">
  INSERT INTO TB_USER (user_id, user_pwd)
  VALUES (#{userId}, OCS_OWNER.PKG_SECURE_API.make_pwd(#{userPwd}))
</insert>
```

저장 결과는 54바이트의 이진값이며 컬럼은 `RAW(64)` 정도로 잡으면 넉넉합니다. 이 값 안에 반복 횟수와 솔트가 함께 들어 있으므로 별도 컬럼을 둘 필요가 없습니다.

빈 비밀번호는 거부됩니다. 오라클에서 빈 문자열은 널과 같으므로, 화면에서 필수 입력 검증이 빠지면 여기서 오류로 드러납니다.

### 4.3 검증

불리언을 SQL에서 직접 쓸 수 없으므로 1과 0을 돌려줍니다.

```xml
<select id="checkPassword" resultType="int">
  SELECT OCS_OWNER.PKG_SECURE_API.verify_pwd(#{inputPwd}, user_pwd)
    FROM TB_USER
   WHERE user_id = #{userId}
</select>
```

결과가 1이면 일치입니다. 조회 결과가 아예 없는 경우, 곧 없는 사용자 식별자인 경우와 비밀번호가 틀린 경우를 화면에서 구분하여 알리지 마십시오. 어느 식별자가 존재하는지를 알려 주는 셈이 됩니다.

### 4.4 반복 횟수를 점진적으로 올리기

비밀번호 저장값은 일부러 계산이 느리도록 만들어져 있습니다. 유출되었을 때 대량 대입을 어렵게 하기 위함이며, 반복 횟수가 그 세기를 결정합니다.

초기값은 만 회로 두었으나 이 값은 임시입니다. 실제 장비에서 로그인 응답 시간을 측정한 뒤 허용 범위 안에서 최대한 올리셔야 합니다. 값은 `SEC_CONFIG` 테이블의 `PWD_ITERATIONS` 항목이며 키 관리자가 바꿉니다.

반복 횟수를 올려도 기존 사용자의 저장값은 옛 횟수로 그대로 남습니다. 저장값 안에 횟수가 들어 있으므로 검증은 계속 정상 동작합니다. 다만 그대로 두면 옛 사용자만 약한 상태로 남으므로, 로그인에 성공한 시점에 다시 계산하여 갱신하는 처리를 넣는 것이 좋습니다.

```xml
<select id="pwdStale" resultType="int">
  SELECT OCS_OWNER.PKG_SECURE_API.pwd_stale(user_pwd)
    FROM TB_USER WHERE user_id = #{userId}
</select>

<update id="refreshPassword">
  UPDATE TB_USER
     SET user_pwd = OCS_OWNER.PKG_SECURE_API.make_pwd(#{inputPwd})
   WHERE user_id = #{userId}
</update>
```

로그인 성공 직후, 곧 입력받은 평문이 아직 손에 있는 그 순간에만 갱신할 수 있습니다. 나중에는 원문을 알 수 없으므로 불가능합니다.

### 4.5 기존 비밀번호 체계에서 옮겨 오기

전자정부 표준프레임워크로 개발된 시스템에서는 공통 유틸리티의 비밀번호 암호화 함수를 써서 해시를 한 번 계산해 저장하는 방식이 널리 쓰이는 것으로 알려져 있습니다. 정확도: 중간이며 실제 사용 중인 코드를 확인하셔야 합니다.

해시를 한 번만 계산하는 방식은 계산이 매우 빨라 대량 대입에 취약합니다. 새로 만드는 시스템이라면 처음부터 반복 기반 방식으로 가는 편이 옳습니다. 이미 옛 방식으로 저장된 자료가 있다면 일괄 전환은 불가능합니다. 원문을 모르기 때문입니다. 현실적인 방법은 두 방식을 한동안 공존시키는 것으로, 저장값의 길이나 형식으로 어느 방식인지 판별하여 옛 방식이면 옛 방식으로 검증하고 성공한 그 자리에서 새 방식으로 다시 저장하는 것입니다. 일정 기간이 지나면 남은 사용자에게 비밀번호 재설정을 요구하여 정리합니다.

이 전환 코드는 업무 시스템마다 사정이 달라 모듈에 넣지 않았습니다. 필요하시면 기존 저장 형식을 알려 주시면 작성해 드리겠습니다.

## 5. 암호화 컬럼 활용 방법

이 장이 실제 개발에서 가장 많이 부딪히는 부분입니다. 암호화된 컬럼은 예전처럼 다룰 수 없고, 그 차이를 모르고 짠 쿼리가 개통 직전에 한꺼번에 문제를 일으킵니다.

### 5.1 검색은 색인 컬럼으로 합니다

암호문은 같은 값이라도 매번 다르게 만들어지므로 암호문끼리 비교하는 것이 성립하지 않습니다. 그래서 검색용 색인 컬럼을 따로 둡니다. 같은 평문이면 항상 같은 색인 값이 나오고, 비밀 키가 결합되어 있어 색인 값만으로는 원문을 알아낼 수 없습니다.

고치기 전의 쿼리는 이렇습니다. 이렇게 두면 전체 행을 복호화한 뒤 비교하므로 성능이 무너지고, 복호화 사용량 임계치에도 걸립니다.

```sql
SELECT * FROM TB_MEMBER WHERE mbr_rrn = '880101-1234567'
```

고친 뒤에는 색인 컬럼을 씁니다. 인덱스를 타고 한 건만 찾습니다.

```xml
<select id="selectByRrn" resultType="memberVO">
  SELECT * FROM TB_MEMBER
   WHERE mbr_rrn_idx = OCS_OWNER.PKG_SECURE_API.idx_rrn(#{rrn})
</select>
```

색인 값은 입력을 다듬은 뒤에 계산되므로, 하이픈이 있든 없든 같은 행을 찾습니다. 성명처럼 앞뒤 공백이 섞여 들어오기 쉬운 값도 마찬가지입니다. 어떤 다듬기를 적용할지는 도메인마다 정해져 있습니다.

### 5.2 부분 일치와 범위 검색은 되지 않습니다

이름의 일부로 찾는다거나 특정 구간의 값을 찾는 조회는 암호화된 컬럼에서 지원하지 않습니다. 기술적 한계가 아니라 그렇게 만들면 안 되는 것에 가깝습니다. 순서를 보존하는 방식으로 암호화하면 검색은 되지만 데이터의 순서 정보가 그대로 새어 나가고, 앞 몇 글자씩 따로 색인을 만들면 만든 만큼 노출 면적이 늘어납니다.

현실적인 대응은 업무 협의로 요건을 바꾸는 것입니다. 성명 부분 검색은 사번이나 회원번호 같은 다른 식별자로 대체할 수 있는 경우가 많고, 전체 목록에서 찾는 대신 조회 범위를 부서나 담당 건으로 좁히면 부분 검색이 필요 없어지는 경우도 많습니다. 정 필요하다면 별도 색인을 추가할 수는 있으나, 그때는 무엇을 얼마나 노출하기로 했는지를 문서로 남기고 승인을 받아야 합니다.

### 5.3 정렬도 되지 않습니다

이름순 정렬 같은 요건이 여기에 걸립니다. 암호문으로 정렬하면 무의미한 순서가 나오고, 복호화한 뒤 정렬하면 전체를 복호화해야 합니다.

가장 무난한 대안은 정렬 기준을 다른 컬럼으로 바꾸는 것입니다. 등록일시나 식별자순으로 충분한 화면이 대부분입니다. 이름순이 업무상 반드시 필요하다면 정렬용 컬럼을 따로 두는 방법이 있습니다. 성의 첫 글자만 담는다거나 초성만 담는 식으로 노출 범위를 좁힌 값을 두고 그것으로 정렬하는 것인데, 이 역시 부분 노출이므로 승인 대상입니다.

### 5.4 조인

암호화된 컬럼으로 두 테이블을 잇는 경우에는 양쪽 모두에 색인 컬럼을 두고 색인끼리 조인합니다. 같은 도메인이라면 같은 키로 계산되므로 값이 일치합니다.

```sql
SELECT a.*, b.*
  FROM TB_MEMBER_ENC a
  JOIN TB_ORDER_ENC  b ON a.mbr_rrn_idx = b.ord_rrn_idx
```

도메인이 다르면 키가 달라 값이 맞지 않습니다. 조인이 필요한 두 컬럼은 반드시 같은 도메인으로 등록해야 하며, 이 점을 컬럼 분류 단계에서 미리 확인해야 합니다. 나중에 도메인을 바꾸려면 재암호화가 필요합니다.

### 5.5 집계와 통계

암호화된 컬럼을 그룹 기준으로 쓸 때는 색인 컬럼으로 묶으면 복호화 없이 집계됩니다. 값 자체는 필요 없고 같은 값끼리 묶기만 하면 되는 경우가 대부분이기 때문입니다.

```sql
SELECT mbr_rrn_idx, COUNT(*)
  FROM TB_ORDER_ENC
 GROUP BY mbr_rrn_idx
```

결과를 화면에 보여 줄 때만 대표값을 복호화하면 됩니다. 전체를 복호화하는 것과 비교하면 호출 횟수가 크게 줄어듭니다.

합계나 평균처럼 값 자체를 계산해야 하는 경우에는 애초에 그 컬럼을 암호화 대상에서 빼는 것이 맞는지 다시 검토해 보십시오. 금액처럼 통계가 본질인 컬럼은 개인정보가 아닌 경우가 많습니다.

### 5.6 목록 화면과 페이징

목록 화면에서는 마스킹된 값을 기본으로 쓰십시오. 성능과 정보 노출을 동시에 줄이는 가장 효과적인 방법입니다. 목록 한 번에 수십 건씩 발생하던 복호화가 사용자가 실제로 열어 본 건수만큼으로 줄어듭니다.

투명화 뷰에는 마스킹 전용 컬럼을 함께 두었으므로 목록에서는 그것을 쓰고, 상세 화면에서만 평문 컬럼을 읽도록 쿼리를 나누십시오.

페이징에서 주의할 점이 하나 있습니다. 복호화나 마스킹 함수를 걸어 둔 채로 페이징하면 전체 행에 함수가 적용된 뒤 잘리는 일이 생깁니다. 페이징을 안쪽 조회에서 먼저 끝내고 바깥에서 함수를 거는 구조로 짜야 합니다.

```sql
SELECT OCS_OWNER.PKG_SECURE_API.masked('RRN', t.mbr_rrn_enc) AS mbr_rrn, t.*
  FROM ( SELECT * FROM TB_MEMBER_ENC
          WHERE dept_cd = #{deptCd}
          ORDER BY mbr_id
          OFFSET #{first} ROWS FETCH NEXT #{size} ROWS ONLY ) t
```

### 5.7 대량 추출과 엑셀 내려받기

복호화에는 사용량 임계치가 걸려 있습니다. 평소보다 현저히 많은 복호화가 한꺼번에 일어나면 차단되고 경보가 발생합니다. 정상 업무를 방해하려는 장치가 아니라, 계정이 탈취되었을 때 피해 범위를 줄이기 위한 장치입니다.

따라서 업무상 대량 추출이 필요한 화면은 일반 조회 경로로 만들지 마십시오. 사전에 승인된 작업으로 분리하고 키 관리자와 협의하여 별도 처리하는 것이 옳습니다. 임계치를 그냥 올려 달라고 요청하는 것은 통제를 없애는 것과 같습니다.

내려받은 엑셀 파일에 평문 개인정보가 담기는 순간 그 파일은 암호화 대상 밖으로 나갑니다. 내려받기 기능 자체가 필요한지, 마스킹된 값으로 충분하지 않은지를 먼저 검토하시기 바랍니다.

### 5.8 배치

배치에서도 문맥을 세워야 하는 것은 같습니다. 배치 전용 사용자 식별자를 정해 두고 그것으로 문맥을 세우면, 감사 기록에서 사람의 조회와 배치의 조회가 구분됩니다.

행마다 함수를 호출하면 전환 비용이 누적되므로, 대량 처리에서는 일정 건수씩 묶어 읽고 묶어 기록하는 구조로 작성하십시오. 재암호화처럼 모듈이 제공하는 배치는 이미 그렇게 되어 있습니다.

## 6. 화면을 만들 때 주의할 점

로그에 평문을 남기지 마십시오. 복호화한 값을 디버그 로그로 찍는 코드가 개발 중에 들어갔다가 그대로 운영에 나가는 일이 흔합니다. 로그 파일은 암호화 대상이 아니므로 그 순간 암호화의 의미가 사라집니다. 예외가 발생했을 때 파라미터 전체를 찍는 공통 처리가 있다면 특히 확인하셔야 합니다.

화면 캐시와 세션에도 평문을 담지 마십시오. 상세 화면에서 읽은 주민등록번호를 세션에 담아 두고 다음 화면에서 재사용하는 방식은 편리하지만, 그만큼 평문이 머무는 자리가 늘어납니다. 필요할 때 다시 조회하는 편이 낫습니다.

검증 메시지로 정보를 흘리지 마십시오. 이미 등록된 주민등록번호라고 알려 주면, 그 자체가 특정인의 가입 여부를 알려 주는 것이 됩니다.

개발 환경에는 운영 데이터를 복제하지 마십시오. 운영 키는 개발 환경에 배포되지 않으므로 복제해 와도 복호화되지 않지만, 복제 과정에서 평문이 지나갈 수 있습니다. 시험용 자료는 만들어 쓰십시오.

## 7. 오류가 났을 때

모듈이 내는 오류는 번호로 구분됩니다. 자주 보시게 될 것만 추리면 다음과 같습니다.

`ORA-20521`은 애플리케이션 인증 문맥이 없다는 뜻입니다. 가장 흔한 원인은 문맥을 세우지 않았거나, 세운 연결과 조회한 연결이 다른 경우입니다. 트랜잭션 경계 안에서 같은 연결이 유지되는지 확인하십시오. 증표 유효 시간이 지난 경우에도 같은 번호가 나는데, 이때는 애플리케이션 서버와 데이터베이스 서버의 시각이 어긋나 있을 가능성을 먼저 보십시오.

`ORA-20520`은 복호화 권한이 없다는 뜻입니다. 해당 도메인에 대한 권한이 대장에 등록되어 있는지, 한시 권한이라면 만료되지 않았는지 확인하십시오. 권한 부여는 키 관리자가 합니다.

`ORA-20522`는 사용량 임계치를 넘었다는 뜻입니다. 대개는 암호화 컬럼을 조건절에 그대로 쓴 쿼리가 전체 행을 복호화하고 있는 경우입니다. 제5.1절을 따라 색인 컬럼을 쓰도록 고치십시오. 정상 업무인데도 걸린다면 임계치를 조정해야 하므로 키 관리자와 협의하십시오.

`ORA-20511`은 무결성 검증 실패입니다. 암호문이 변조되었거나 키가 맞지 않는 경우입니다. 개발 중이라면 컬럼 길이가 모자라 암호문이 잘렸을 가능성이 가장 큽니다. 컬럼 정의를 확인하십시오. 운영에서 이 오류가 나면 조용히 넘기지 말고 즉시 보안 담당자에게 알려야 합니다.

`ORA-20512`와 `ORA-20513`은 키를 쓸 수 없는 상태라는 뜻입니다. 업무 개발자가 해결할 수 있는 문제가 아니므로 키 관리자에게 알리십시오. 특히 `ORA-20513`은 마스터 키가 반입되지 않았다는 뜻으로, 데이터베이스를 재기동한 뒤 키를 다시 넣지 않은 경우에 납니다.

`ORA-20530`은 정의되지 않은 도메인을 썼다는 뜻입니다. 도메인 코드의 철자를 확인하고, 없는 도메인이라면 키 관리자에게 등록을 요청하십시오.

## 8. 하지 말아야 할 것

암호문 컬럼에 인덱스를 만들지 마십시오. 값이 매번 달라지므로 쓸 수 없고 공간과 갱신 비용만 듭니다.

암호문을 문자열로 변환해 비교하거나 이어 붙이지 마십시오. 이진값이므로 문자집합 변환 과정에서 손상됩니다.

복호화 함수를 조건절에 쓰지 마십시오. 제5.1절에서 설명한 그대로입니다.

키 관리 함수를 업무 코드에서 호출하지 마십시오. 응용 계정에는 권한이 없으므로 호출되지도 않지만, 시도한 기록은 남고 경보가 발생합니다.

암호화된 컬럼을 그대로 복사하여 다른 테이블에 옮기는 일은 가능하지만, 그 테이블의 컬럼 길이가 충분한지 반드시 확인하십시오. 잘리면 복구할 수 없습니다.

## 9. 참고 근거와 신뢰도 자체 평가

본문의 자바 코드와 암호문 포맷에 관한 서술은 신뢰도 높음입니다. 연동 모듈을 실제로 컴파일하고 고정 시험 벡터 마흔아홉 건을 통과시켜 확인하였으며, 파이썬 참조 구현과 바이트 단위로 결과가 같습니다.

데이터베이스 쪽 호출문에 관한 서술은 신뢰도 중간입니다. 함수 이름과 인자는 실제 구현과 대조하였으나 오라클 인스턴스에서 실행해 확인하지는 못하였습니다.

암호화 컬럼의 검색과 정렬 제약에 관한 서술은 신뢰도 높음입니다. 확률적 암호화의 성질에서 곧바로 따라 나오는 결과입니다.

전자정부 표준프레임워크의 자체 암호화 서비스와 비밀번호 처리 관행에 관한 서술은 신뢰도 중간입니다. 제도와 관행의 큰 얼개는 알려져 있으나 정확한 클래스 이름과 메서드 서명은 확인하지 못하였으므로, 쓰시는 버전의 개발자 가이드에서 확인하시기 바랍니다.

해시를 한 번만 계산하는 방식이 대량 대입에 취약하다는 서술은 신뢰도 높음입니다. 널리 확립된 사실입니다.

## 10. 결론 요약

업무 개발자가 다룰 것은 `OCS_OWNER.PKG_SECURE_API` 하나이며, 암복호화는 데이터베이스가 수행하고 애플리케이션은 키를 갖지 않습니다. 가장 먼저 할 일은 세션마다 접속 문맥을 세우고 반납 전에 거두는 것으로, 문맥을 세운 그 연결에서 업무를 수행해야 하고 거두는 일은 반드시 `finally`에 두어야 합니다. 양방향 암호화는 저장할 때 암호문 컬럼과 색인 컬럼을 함께 채우는 것이 요점이고, 조회는 투명화 뷰를 쓰면 기존 코드를 거의 그대로 둘 수 있습니다. 단방향 암호화는 비밀번호에만 쓰며, 저장값 안에 반복 횟수가 들어 있으므로 나중에 세기를 올려도 기존 사용자와 공존합니다. 암호화된 컬럼에서 가장 크게 달라지는 것은 검색으로, 조건절에 평문을 쓰던 쿼리는 모두 색인 컬럼을 쓰도록 고쳐야 하며 부분 일치와 범위 검색과 정렬은 지원하지 않으므로 업무 협의로 요건을 조정하는 편이 낫습니다. 목록 화면은 마스킹을 기본으로 하여 복호화 호출 자체를 줄이는 것이 성능과 보호를 함께 얻는 길이고, 대량 추출은 일반 조회 경로가 아니라 승인된 별도 작업으로 분리해야 합니다.
