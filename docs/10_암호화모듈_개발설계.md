# 암복호화 모듈 개발 설계서

## 1. 이 문서의 범위

이 문서는 오라클 데이터베이스 테이블 컬럼을 대상으로 하는 양방향 암복호화 모듈과 일방향 암호화 모듈의 개발 설계를 다룹니다. 접근권한 통제와 모듈 보호에 관한 사항은 `20_보안관리_접근통제설계.md`에서 별도로 다루며, 이 문서에서는 그쪽 설계가 요구하는 인터페이스만 정의합니다.

## 2. 양방향과 일방향의 분류 기준

두 방식은 기술적 선택지가 아니라 데이터의 용도에 따라 결정되는 사항입니다. 원문을 다시 읽어야 하는 데이터는 양방향으로, 원문을 다시 읽을 필요가 없고 일치 여부만 확인하면 되는 데이터는 일방향으로 처리합니다.

일방향 암호화의 대표적 대상은 비밀번호입니다. 시스템은 사용자가 입력한 비밀번호가 등록된 것과 같은지만 판정하면 되고, 등록된 비밀번호가 무엇인지 알아낼 필요는 없습니다. 오히려 알아낼 수 있어서는 안 됩니다. 국내 개인정보 보호 법령은 비밀번호를 복호화되지 않는 일방향 암호화로 저장하도록 요구하는 것으로 알려져 있습니다. 정확도: 높음.

양방향 암호화의 대상은 주민등록번호를 비롯한 고유식별정보와 계좌번호, 신용카드번호, 그리고 업무상 원문 출력이 필요한 연락처와 주소 등입니다. 이들은 고지서 발송이나 결제 처리처럼 원문 자체가 필요한 업무가 존재하므로 복호화가 가능해야 합니다. 개인정보의 안전성 확보조치 기준은 고유식별정보와 계좌번호, 신용카드번호 등을 암호화 저장 대상으로 규정하고 있는 것으로 알려져 있습니다. 정확도: 중간.

경계에 있는 사례가 있습니다. 주민등록번호는 양방향 암호화 대상이면서 동시에 조회 키로 자주 사용됩니다. 조회를 위해 암호문을 그대로 비교하려면 결정적 암호화가 필요한데, 결정적 암호화는 같은 값이 같은 암호문이 되므로 빈도 분석에 취약해집니다. 이 문제의 권장 해법은 암호문 컬럼과 검색용 해시 컬럼을 분리하는 것으로, 저장은 확률적 양방향 암호화로 하고 검색은 키가 결합된 일방향 해시 컬럼으로 수행합니다. 상세한 방식은 제9절에 서술하였습니다.

분류 결과는 표가 아니라 대장 형태의 별도 산출물로 관리하며, 컬럼별로 소속 테이블, 데이터 성격, 분류 결과, 분류 근거가 되는 법령 조항 또는 업무 요건, 그리고 복호화가 필요한 업무의 목록을 기재합니다. 복호화가 필요한 업무 목록을 반드시 기재하도록 하는 이유는, 이 목록이 비어 있는 양방향 컬럼은 사실 일방향으로 전환할 수 있다는 신호이기 때문입니다.

## 3. 아키텍처 대안과 권고

세 가지 대안이 있으며 각각의 성립 조건이 다릅니다.

첫 번째 대안은 오라클의 투명 데이터 암호화를 사용하는 방식입니다. 데이터베이스가 저장 시점에 자동으로 암호화하고 조회 시점에 자동으로 복호화하므로 애플리케이션을 전혀 수정하지 않아도 됩니다. 대신 이 방식이 방어하는 대상은 저장 매체입니다. 데이터 파일이나 백업 테이프가 유출되었을 때를 막아 줄 뿐, 정상적으로 접속한 데이터베이스 사용자에게는 평문이 그대로 보입니다. 즉 내부자에 의한 조회를 막지 못합니다. 또한 Advanced Security Option이라는 유상 옵션이 필요하며 Enterprise Edition에서만 사용할 수 있는 것으로 알려져 있습니다. 정확도: 중간. 컬럼 단위 투명 데이터 암호화에는 외래 키 제약이나 인덱스 사용에 제한이 있는 것으로 알려져 있습니다. 정확도: 중간.

두 번째 대안은 데이터베이스 내부에 자체 암호화 패키지를 구현하는 방식입니다. 오라클이 기본 제공하는 DBMS_CRYPTO 패키지를 이용해 PL/SQL 패키지를 작성하고, 뷰와 트리거를 이용해 애플리케이션에서는 기존과 동일한 이름으로 테이블을 사용하도록 만듭니다. 별도 라이선스 비용이 없고 애플리케이션 수정을 최소화할 수 있다는 점이 장점입니다. 단점은 암호화와 복호화 연산이 데이터베이스 서버의 자원을 소비한다는 점과, 키가 어떤 형태로든 데이터베이스 내부를 거치므로 최고 권한 관리자에 대한 방어가 완전하지 않다는 점입니다. DBMS_CRYPTO는 Oracle 10g부터 제공되고 있습니다. 정확도: 높음.

세 번째 대안은 애플리케이션 계층에서 암호화하고 데이터베이스에는 암호문만 저장하는 방식입니다. 키가 데이터베이스에 존재하지 않으므로 데이터베이스 관리자에 대한 방어가 가장 강합니다. 그러나 데이터베이스 단독으로는 해당 컬럼에 대해 어떤 연산도 할 수 없게 되어, 기존의 통계 쿼리와 배치 작업과 보고서가 모두 재작성 대상이 됩니다. 또한 여러 애플리케이션이 같은 테이블을 사용한다면 모든 애플리케이션에 동일한 암호화 로직을 이식해야 하며, 이식 누락이 발생하는 순간 평문이 섞여 들어갑니다.

권고는 두 번째 대안을 기본 골격으로 하되, 실제 암호 연산을 수행하는 부분만 교체 가능한 제공자로 분리하고 키 보관은 데이터베이스 외부로 분리하는 절충안입니다. 암호 연산은 데이터베이스 내부 패키지가 수행하여 애플리케이션 영향과 개발 비용을 억제하고, 마스터 키는 하드웨어 보안 모듈이나 외부 키 관리 서버에 두어 데이터베이스 파일과 백업만 확보한 공격자가 복호화하지 못하도록 합니다. 데이터베이스 관리자에 대한 방어는 암호 설계가 아니라 권한 분리와 감사로 처리하며, 그 방법은 보안관리 설계서에 서술하였습니다.

이 사업의 대상이 관공서 시스템으로 확정되었으므로, 최종 형상에서는 암호 연산을 검증필 암호모듈이 수행해야 할 가능성이 높습니다. 그러나 검증 획득은 별도 과업으로 분리하였으므로, 이 사업에서는 암호 연산 계층을 제공자 교체가 가능한 구조로 설계하고 개발과 시험 단계에서는 오라클 내장 기능을 임시 제공자로 사용합니다. 이 구조를 택하면 검증필 모듈이 확보된 시점에 제공자 구현체 하나만 추가하고 설정을 바꾸는 것으로 전환이 완료되며, 정책 계층과 인터페이스 계층과 애플리케이션은 손대지 않아도 됩니다.

제공자 교체 방식의 후보는 세 가지입니다. 첫째는 오라클의 외부 프로시저 호출 기능을 이용하여 검증필 공유 라이브러리를 직접 호출하는 방식으로, 애플리케이션 영향이 가장 적으나 별도 프로세스를 경유하므로 성능과 장애 전파 특성을 반드시 실측해야 합니다. 둘째는 데이터베이스 내장 자바를 이용하여 검증필 자바 모듈을 호출하는 방식입니다. 셋째는 암호 연산만 애플리케이션 계층으로 옮겨 검증필 자바 모듈이 수행하도록 하고 데이터베이스는 암호문만 취급하는 방식으로, 이 경우 검색용 색인 값의 생성 위치도 함께 이동해야 합니다. 세 후보의 성능과 안정성 비교는 제3단계 개념 검증의 핵심 과제이며, 어느 쪽을 택하더라도 상위 계층의 인터페이스는 동일하게 유지되도록 설계합니다.

## 4. 모듈 구조

모듈은 네 개의 계층으로 나눕니다. 계층을 나누는 목적은 두 가지인데, 하나는 각 계층마다 부여되는 실행 권한을 다르게 하기 위함이고 다른 하나는 검증필 암호모듈로의 교체가 최하위 한 겹에서만 일어나도록 격리하기 위함입니다. 이 구조가 보안관리 설계와 인증 대응의 공통 전제가 됩니다.

최하위 계층은 암호 제공자 계층입니다. 실제 암호 연산을 수행하는 유일한 계층이며, 동일한 호출 규약을 따르는 여러 구현체가 공존할 수 있도록 설계합니다. 개발과 시험 단계에서는 오라클 내장 기능을 사용하는 구현체를 두고, 검증필 모듈이 확보되면 같은 규약을 따르는 구현체를 추가합니다. 이 계층이 지켜야 할 규약은 평문과 키 식별자를 받아 암호문 본문을 반환하고 그 역을 수행하는 것, 그리고 해시와 메시지 인증 코드를 계산하는 것으로 한정하며, 암호문 포맷 조립과 키 조회와 정책 판단은 이 계층의 책임이 아닙니다. 이 경계를 지키지 않으면 제공자 교체 시 상위 계층까지 함께 고쳐야 하므로, 설계 검토에서 가장 엄격히 확인해야 할 항목입니다.

그 위의 계층은 암호 연산 계층입니다. 키를 조회하고 초기화 벡터를 생성하며 암호문 포맷을 조립하고 무결성 태그를 검증합니다. 어떤 제공자를 호출할지는 이 계층이 암호문 헤더의 알고리즘 식별자와 설정값을 보고 결정합니다. 이 계층과 그 아래 제공자 계층에는 어떤 일반 계정에도 실행 권한을 부여하지 않습니다.

중간 계층은 정책 계층입니다. 호출자가 해당 컬럼을 복호화할 자격이 있는지 판정하고, 자격이 없으면 마스킹된 값을 반환하며, 호출 사실을 감사 기록으로 남깁니다. 복호화 요청이 정책 계층을 우회할 수 없도록 하는 것이 이 설계의 핵심이며, 우회 차단은 암호 연산 계층에 대한 실행 권한을 회수함으로써 달성합니다.

최상위 계층은 인터페이스 계층입니다. 애플리케이션과 배치가 실제로 호출하는 함수들로 구성되며, 업무 의미를 가진 이름을 사용합니다. 이 계층만 응용 계정에 실행 권한을 부여합니다.

패키지 명세의 골격은 다음과 같습니다. 실제 구현 시 명명 규칙은 기관 표준을 따르십시오.

```sql
-- 최하위: 암호 제공자 계층 (교체 지점, 실행 권한 비공개)
-- 모든 구현체가 동일한 규약을 따른다. 포맷 조립과 키 조회는 하지 않는다.
CREATE OR REPLACE PACKAGE SEC_OWNER.PKG_PROVIDER_DBMS AS   -- 임시 구현체
  FUNCTION block_encrypt (p_plain IN RAW, p_key IN RAW, p_iv IN RAW, p_alg IN NUMBER) RETURN RAW;
  FUNCTION block_decrypt (p_cipher IN RAW, p_key IN RAW, p_iv IN RAW, p_alg IN NUMBER) RETURN RAW;
  FUNCTION mac           (p_msg IN RAW, p_key IN RAW, p_alg IN NUMBER) RETURN RAW;
  FUNCTION digest        (p_msg IN RAW, p_alg IN NUMBER) RETURN RAW;
  FUNCTION random_bytes  (p_len IN NUMBER) RETURN RAW;
END;
-- 향후 추가: PKG_PROVIDER_KCMVP (검증필 모듈 연동, 동일 규약)

-- 암호 연산 계층 (키 조회·IV 생성·포맷 조립·태그 검증, 실행 권한 비공개)
CREATE OR REPLACE PACKAGE SEC_OWNER.PKG_CRYPTO_CORE AS
  FUNCTION encrypt_raw (p_plain IN VARCHAR2, p_key_id IN NUMBER) RETURN RAW;
  FUNCTION decrypt_raw (p_cipher IN RAW) RETURN VARCHAR2;
  FUNCTION hmac_index  (p_plain IN VARCHAR2, p_key_id IN NUMBER) RETURN RAW;
  FUNCTION hash_oneway (p_plain IN VARCHAR2, p_salt IN RAW) RETURN RAW;
END;

-- 중간: 정책 계층 (실행 권한 비공개)
CREATE OR REPLACE PACKAGE SEC_OWNER.PKG_CRYPTO_POLICY AS
  FUNCTION protect  (p_domain IN VARCHAR2, p_plain  IN VARCHAR2) RETURN RAW;
  FUNCTION reveal   (p_domain IN VARCHAR2, p_cipher IN RAW)      RETURN VARCHAR2;
  FUNCTION index_of (p_domain IN VARCHAR2, p_plain  IN VARCHAR2) RETURN RAW;
END;

-- 최상위: 인터페이스 계층 (응용 계정에 EXECUTE 부여)
CREATE OR REPLACE PACKAGE SEC_OWNER.PKG_SECURE_API AS
  FUNCTION enc_rrn      (p_rrn IN VARCHAR2)    RETURN RAW;
  FUNCTION dec_rrn      (p_cipher IN RAW)      RETURN VARCHAR2;
  FUNCTION idx_rrn      (p_rrn IN VARCHAR2)    RETURN RAW;
  FUNCTION verify_pwd   (p_input IN VARCHAR2, p_stored IN RAW) RETURN NUMBER;
  FUNCTION make_pwd     (p_input IN VARCHAR2)  RETURN RAW;
END;
```

`p_domain`이라는 인자를 둔 이유는 컬럼마다 다른 키와 다른 정책을 적용하기 위함입니다. 주민등록번호와 계좌번호에 같은 키를 쓰면 한 키의 유출이 전체 유출로 번지므로, 도메인 단위로 키를 분리하는 것이 바람직합니다.

## 5. 암호문 포맷

암호문에는 암호문 자체 외에 복호화에 필요한 메타 정보가 함께 담겨야 합니다. 이 설계를 생략하고 순수 암호문만 저장하면 키를 교체하는 순간 기존 데이터를 복호화할 수 없게 되어 키 교체가 사실상 불가능해집니다. 실무에서 가장 흔히 발견되는 설계 결함입니다.

권장 포맷은 다음의 연속된 바이트열입니다. 첫 1바이트는 포맷 버전이고, 다음 1바이트는 알고리즘 식별자이며, 다음 2바이트는 키 식별자입니다. 그 뒤로 16바이트의 초기화 벡터가 오고, 그 뒤에 가변 길이의 암호문 본문이 이어지며, 마지막에 32바이트의 무결성 검증 태그가 붙습니다.

무결성 검증 태그를 두는 이유는 암호문이 변조되었을 때 이를 탐지하기 위함입니다. 암호화만 하고 무결성 검증을 하지 않으면, 공격자가 암호문 일부를 조작하여 복호화 결과를 예측 가능한 방향으로 바꾸는 공격이 성립할 수 있습니다. 태그는 버전부터 암호문 본문까지 전체에 대해 별도의 무결성 키로 계산한 HMAC-SHA256 값을 사용하며, 복호화 시 태그를 먼저 검증하고 검증에 실패하면 복호화를 수행하지 않고 예외를 발생시킵니다. 이 순서를 지키는 것이 중요합니다.

인증 암호화 방식인 GCM을 사용하면 이 구조를 알고리즘 자체가 제공하므로 더 간결합니다. 다만 오라클의 DBMS_CRYPTO 패키지가 GCM 운영 모드를 지원하는지는 버전에 따라 다르며, 19c 기준으로는 CBC와 CFB, OFB, ECB 계열만 제공되는 것으로 알고 있습니다. 정확도: 중간이며 반드시 대상 버전 문서로 확인이 필요합니다. 지원되지 않는다면 위에 서술한 대로 암호화 후 별도 MAC을 붙이는 구조를 사용하십시오.

저장 데이터형은 RAW를 권장합니다. 암호문을 Base64로 변환하여 VARCHAR2에 담는 방식도 널리 쓰이나, 길이가 약 1.33배로 늘고 문자 집합 변환 과정에서 손상 위험이 있으므로 특별한 제약이 없다면 RAW가 낫습니다. RAW의 최대 길이 제약을 넘는 경우에만 BLOB을 사용합니다.

길이 산정의 예를 들면, 13자리 주민등록번호를 AES-256 CBC로 암호화할 경우 평문 13바이트가 패딩을 거쳐 16바이트가 되고 여기에 헤더 4바이트와 초기화 벡터 16바이트와 태그 32바이트가 더해져 총 68바이트가 됩니다. 컬럼은 여유를 두어 RAW(128) 정도로 정의하는 것이 안전합니다. 정확도: 높음. 다만 실제 구현에서 반드시 실측 확인하십시오.

## 6. 알고리즘 선정

대상이 관공서 시스템이므로 최종 형상의 양방향 암호화 알고리즘은 국산 블록 암호를 기본으로 삼습니다. ARIA와 SEED, LEA가 국내 표준으로 지정되어 있는 것으로 알려져 있으며, 공공 부문에서는 이들 중 하나를 검증필 모듈이 제공하는 형태로 사용하는 것이 일반적인 것으로 알려져 있습니다. 정확도: 중간이며 발주 기관의 보안 지침으로 확인이 필요합니다. 오라클 내장 패키지는 국산 알고리즘을 지원하지 않으므로, 이 알고리즘은 제공자 계층의 검증필 구현체가 확보된 이후에 적용됩니다.

개발과 시험 단계에서는 오라클 내장 기능이 지원하는 AES-256을 임시로 사용하며 운영 모드는 CBC 또는 가능하다면 GCM을 사용합니다. 이때의 암호문에는 알고리즘 식별자가 함께 기록되므로, 이후 국산 알고리즘으로 전환할 때 기존 데이터를 읽지 못하게 되는 일은 발생하지 않습니다. 전환은 키 교체와 동일한 절차, 곧 새 알고리즘을 활성으로 지정하고 재암호화 배치를 나누어 수행하는 방식으로 처리합니다. 다만 임시 구현체로 암호화된 실제 개인정보가 운영계에 남아서는 안 되므로, 시험계와 운영계의 경계를 분명히 하고 운영 개통 전에 검증필 구현체로의 전환을 완료하는 것을 원칙으로 삼습니다.

ECB 모드는 같은 평문 블록이 같은 암호문 블록이 되어 패턴이 그대로 드러나므로 어떤 알고리즘을 쓰든 사용해서는 안 됩니다. 정확도: 높음.

초기화 벡터는 암호화할 때마다 새로 생성한 난수를 사용합니다. 같은 평문이 같은 암호문이 되지 않도록 하기 위함이며, 이를 확률적 암호화라고 합니다. 난수는 암호학적으로 안전한 생성기에서 얻어야 하며 오라클에서는 DBMS_CRYPTO의 난수 생성 기능을 사용합니다. 일반 난수 함수를 사용해서는 안 됩니다.

일방향 해시는 SHA-256 이상을 사용합니다. MD5와 SHA-1은 충돌 공격이 실증되어 있으므로 사용하지 않습니다. 정확도: 높음. 오라클의 DBMS_CRYPTO에서 SHA-2 계열 상수는 12c부터 제공되는 것으로 알고 있습니다. 정확도: 중간. 11g 이하 환경이라면 외부 모듈 연동이 필요합니다.

## 7. 키 관리 설계

키는 두 단계로 구성합니다. 실제 데이터를 암호화하는 데이터 암호화 키가 있고, 그 데이터 암호화 키를 다시 암호화하여 보관하는 키 암호화 키가 있습니다. 이 구조를 택하는 이유는 키 교체 때문입니다. 키 암호화 키를 교체할 때는 데이터 암호화 키만 다시 암호화하면 되므로 수억 건의 데이터를 재암호화할 필요가 없습니다.

키 암호화 키는 데이터베이스 외부에 보관합니다. 하드웨어 보안 모듈이나 오라클 키 볼트 같은 전용 제품을 사용하는 것이 바람직하며, 여의치 않다면 최소한 데이터베이스와 분리된 별도 서버의 보호된 저장소에 두고 데이터베이스 기동 시점에 반입하는 구조로 설계합니다. 키 암호화 키를 데이터베이스 테이블에 평문으로 저장하는 것은 암호화를 하지 않은 것과 실질적으로 동일합니다.

데이터 암호화 키는 도메인별로 분리하며, 각 키에 식별자와 생성 일시와 상태를 부여하여 이력으로 관리합니다. 상태는 활성과 폐기 예정과 폐기로 구분하되, 폐기 예정 상태의 키는 복호화에만 사용하고 신규 암호화에는 사용하지 않습니다. 이 상태 구분이 있어야 무중단 키 교체가 가능합니다.

키 교체 절차는 다음과 같이 진행합니다. 새 키를 생성하여 활성으로 지정하고 기존 키를 폐기 예정으로 변경하면, 그 시점 이후의 신규 데이터는 새 키로 암호화되고 기존 데이터는 암호문 헤더의 키 식별자를 보고 옛 키로 복호화됩니다. 이어서 재암호화 배치를 여유 시간대에 나누어 수행하여 기존 데이터를 점진적으로 새 키로 전환하고, 옛 키로 암호화된 데이터가 남지 않았음이 확인되면 옛 키를 폐기 상태로 변경합니다. 이 절차는 서비스 중단 없이 수행 가능하며, 개통 전에 반드시 한 번은 실제로 수행하여 검증해야 합니다.

세션 내에서 데이터 암호화 키를 반복 조회하면 성능이 저하되므로 패키지 변수에 캐시하되, 캐시된 키는 세션 종료 시 소멸되도록 하고 키 상태가 변경되면 캐시를 무효화하는 경로를 마련합니다. 키를 담은 변수에는 결과 캐시나 함수 결과 캐시 기능을 적용하지 않습니다.

## 8. 일방향 암호화 설계

일방향 암호화는 용도에 따라 두 가지로 나뉘며 설계가 서로 다릅니다. 이 둘을 구분하지 않고 같은 방식으로 구현하는 것이 흔한 오류입니다.

첫째는 비밀번호 저장입니다. 여기서는 의도적으로 느린 연산이 필요합니다. 공격자가 유출된 해시 값에 대해 대량의 후보를 대입하는 공격을 어렵게 만들기 위함이며, 단순 SHA-256 한 번으로는 초당 수억 건의 대입이 가능하므로 충분한 보호가 되지 않습니다. 반복 수행 기반의 키 유도 함수를 사용하고 사용자마다 다른 난수 솔트를 부여하며, 반복 횟수를 충분히 크게 설정합니다. 오라클의 DBMS_CRYPTO에 PBKDF2 기능이 12.2 이후 포함된 것으로 알고 있습니다. 정확도: 중간이며 버전 확인이 필요합니다. 가용하지 않다면 비밀번호 검증만은 애플리케이션 계층에서 수행하고 데이터베이스에는 결과만 저장하는 편이 낫습니다. 저장 형식에는 솔트와 반복 횟수와 알고리즘 식별자를 함께 담아, 향후 반복 횟수를 상향할 때 기존 사용자와 신규 사용자가 공존할 수 있도록 합니다.

둘째는 검색용 색인 값 생성입니다. 여기서는 반대로 빠른 연산이 필요하며 같은 입력이 항상 같은 출력이 되어야 합니다. 그래야 암호화된 컬럼에 대해 완전 일치 검색을 수행할 수 있기 때문입니다. 이때 단순 해시를 사용해서는 안 됩니다. 주민등록번호처럼 가능한 값의 범위가 제한된 데이터는 전수 대입으로 원문을 복원할 수 있기 때문입니다. 반드시 비밀 키가 결합된 HMAC을 사용하여, 키를 모르는 공격자는 색인 값으로부터 원문을 유추할 수 없도록 합니다. 이 비밀 키는 데이터 암호화 키와 동일한 수준으로 보호되어야 하며, 데이터베이스 테이블에 노출되어서는 안 됩니다.

## 9. 검색과 인덱스 설계

암호화된 컬럼은 인덱스를 이용한 검색이 원칙적으로 불가능합니다. 확률적 암호화를 사용하면 같은 값도 매번 다른 암호문이 되므로 암호문 비교 자체가 성립하지 않고, 설령 결정적 암호화를 쓰더라도 범위 검색이나 부분 일치 검색은 불가능합니다. 따라서 검색 요건별로 서로 다른 해법이 필요합니다.

완전 일치 검색은 앞 절에서 설명한 HMAC 기반 색인 컬럼으로 해결합니다. 원본 테이블에 색인용 컬럼을 추가하고 여기에 유일 인덱스 또는 일반 인덱스를 생성하면, 검색 시 입력값을 같은 방식으로 변환하여 인덱스 탐색이 가능합니다. 다만 이 색인 컬럼은 같은 값이 같은 색인 값이 되므로 빈도 분석의 여지가 남습니다. 성별과 생년월일처럼 분포가 치우친 데이터에는 신중히 적용해야 합니다.

부분 일치 검색은 근본적으로 어렵습니다. 앞자리 일부를 별도로 해시하여 보조 색인을 만드는 방법이 있으나, 보조 색인이 늘어날수록 정보 노출 면적도 함께 늘어납니다. 실무적으로는 부분 일치 검색 요건 자체를 재검토하여, 다른 식별자로 대체하거나 검색 대상을 사용자 본인의 데이터로 제한하는 방향의 업무 협의를 먼저 시도하는 것이 낫습니다.

범위 검색과 정렬은 암호화된 컬럼에서 지원하지 않는 것을 원칙으로 합니다. 순서를 보존하는 암호화 기법이 존재하나 그 대가로 데이터의 순서 정보가 그대로 노출되므로, 보호 대상 컬럼에는 적합하지 않습니다.

집계와 통계 업무에서 암호화 컬럼이 그룹 기준으로 사용되는 경우가 있습니다. 이때는 색인 컬럼을 그룹 기준으로 사용하면 복호화 없이 집계가 가능합니다. 결과를 화면에 표시할 때만 대표값을 복호화하면 되므로 복호화 호출 횟수를 크게 줄일 수 있습니다.

## 10. 애플리케이션 투명화 전략

기존 애플리케이션의 수정 범위를 줄이기 위해 뷰를 이용한 투명화를 적용합니다. 원본 테이블의 이름을 변경하고 원래 이름으로 뷰를 생성하여, 애플리케이션의 조회 구문은 수정 없이 동작하도록 하는 방식입니다.

구체적으로는 원본 테이블 `TB_MEMBER`를 `TB_MEMBER_ENC`로 변경하고 암호화 컬럼을 RAW형으로 전환한 뒤, `TB_MEMBER`라는 이름의 뷰를 생성하여 암호화 컬럼 자리에 복호화 함수 호출을 넣습니다. 삽입과 수정을 지원하려면 뷰에 INSTEAD OF 트리거를 부착하여 입력된 평문을 암호화한 뒤 실제 테이블에 기록하도록 합니다.

이 방식의 한계를 분명히 해 둘 필요가 있습니다. 첫째, 조회 성능이 저하됩니다. 뷰를 통한 조회는 반환되는 모든 행에 대해 복호화 함수를 호출하므로, 대량 조회 구문에서는 호출 횟수가 그대로 비용이 됩니다. 이를 완화하려면 화면에서 실제로 필요한 컬럼만 조회하도록 애플리케이션 쿼리를 정리하는 작업이 병행되어야 합니다. 둘째, 암호화 컬럼을 조건절에 사용하는 기존 쿼리는 반드시 수정해야 합니다. 뷰 위에서 복호화된 값을 조건으로 걸면 전체 행을 복호화한 뒤 비교하게 되어 성능이 붕괴합니다. 이러한 쿼리는 색인 컬럼을 사용하도록 명시적으로 고쳐야 하며, 수정 대상 쿼리의 식별이 제1단계 현황 분석의 핵심 작업입니다. 셋째, 뷰는 원본 테이블에 대한 직접 접근을 막지 못합니다. 원본 테이블에 대한 권한을 회수하지 않으면 애플리케이션 계정이 암호문에 직접 접근할 수 있으며, 이는 보안관리 설계에서 다룹니다.

## 11. 성능 설계

암복호화는 호출 횟수에 비례하여 비용이 발생합니다. 따라서 성능 설계의 요체는 연산을 빠르게 만드는 것이 아니라 호출 횟수를 줄이는 데 있습니다.

첫째 원칙은 필요한 시점에만 복호화하는 것입니다. 목록 화면에서는 마스킹된 값을 보여 주고 상세 화면에서만 복호화하는 방식으로 설계하면, 목록 조회 한 번에 수십 건씩 발생하던 복호화가 사용자가 실제로 열람한 건수만큼으로 줄어듭니다. 이는 성능 대책인 동시에 정보 노출 최소화 대책이기도 하므로 우선적으로 적용할 가치가 있습니다.

둘째 원칙은 대량 처리 시 집합 단위로 처리하는 것입니다. 행마다 PL/SQL 함수를 호출하면 SQL 엔진과 PL/SQL 엔진 사이를 오가는 전환 비용이 누적됩니다. 전환 배치나 재암호화 배치처럼 대량 처리가 필요한 경우에는 일정 건수씩 묶어 읽고 배열 단위로 처리한 뒤 묶어 기록하는 구조로 작성합니다.

셋째 원칙은 키 조회를 반복하지 않는 것입니다. 앞서 서술한 세션 단위 키 캐시가 이에 해당합니다.

성능 목표는 개념 검증 단계에서 실측한 값을 근거로 설정합니다. 일반적으로 단일 행 복호화의 추가 비용은 크지 않으나 수만 행 단위 조회에서는 체감 가능한 저하가 발생합니다. 구체적인 수치는 하드웨어와 데이터 규모에 따라 크게 달라지므로 이 문서에서 예측치를 제시하지 않겠습니다. 근거 없는 수치를 제시하는 것보다 실측 계획을 명시하는 편이 유용하다고 판단하였습니다.

## 12. 오류 처리 원칙

암호 모듈의 오류 처리에는 두 가지 원칙이 적용됩니다.

첫째, 실패 시 안전한 방향으로 실패해야 합니다. 키를 조회할 수 없거나 무결성 검증에 실패했을 때 평문을 반환하거나 빈 문자열을 반환하는 구현은 위험합니다. 예외를 발생시켜 처리가 중단되도록 하고, 호출한 업무가 그 실패를 인지하도록 해야 합니다. 다만 조회성 화면에서 한 건의 복호화 실패가 전체 화면 오류로 이어지면 운영에 부담이 되므로, 정책 계층에서 복호화 실패를 마스킹된 고정 문자열로 치환하고 동시에 경고 로그를 남기는 방식을 선택할 수 있습니다. 이 경우 경고 로그가 실제로 점검되는 체계가 함께 갖추어져야 합니다.

둘째, 오류 메시지에 정보를 담지 않아야 합니다. 복호화 실패 사유를 상세히 반환하면 공격자에게 유용한 단서가 됩니다. 호출자에게는 일반화된 메시지를 반환하고 상세 사유는 내부 로그에만 기록합니다. 어떤 경우에도 예외 메시지나 로그에 평문과 키를 기록해서는 안 되며, 이는 코드 검토의 필수 점검 항목으로 지정해야 합니다.

## 13. 데이터 전환 절차

기존 평문 데이터를 암호문으로 전환하는 작업은 사업에서 가장 위험한 구간입니다. 서비스 중단이 가능하다면 절차가 단순해지므로 가능한 한 중단 시간을 확보하는 편을 권합니다. 중단이 불가능한 경우를 기준으로 절차를 서술하겠습니다.

먼저 원본 테이블에 암호문 컬럼과 색인 컬럼을 추가합니다. 이 시점에는 기존 평문 컬럼이 그대로 사용되고 있으므로 서비스에 영향이 없습니다.

다음으로 이중 기록을 시작합니다. 삽입과 수정 시 평문 컬럼과 암호문 컬럼 양쪽에 기록하도록 트리거나 애플리케이션을 변경합니다. 이 시점부터 신규 데이터는 양쪽에 모두 존재하게 됩니다.

이어서 기존 데이터에 대한 전환 배치를 수행합니다. 배치는 반드시 재시작 가능하도록 설계하며, 처리 완료 지점을 별도 관리 테이블에 기록하여 중단 시 이어서 수행할 수 있도록 합니다. 일정 건수마다 커밋하여 되돌리기 구간을 짧게 유지하고, 업무 시간대를 피하여 나누어 수행합니다.

전환이 완료되면 검증합니다. 전체 건수가 일치하는지, 임의 표본에 대해 복호화 결과가 원본 평문과 일치하는지, 색인 컬럼으로 검색한 결과가 평문으로 검색한 결과와 일치하는지를 확인합니다. 이 검증을 통과하기 전에는 다음 단계로 넘어가지 않습니다.

검증 후 읽기 경로를 전환합니다. 조회가 암호문 컬럼을 복호화하여 사용하도록 뷰를 교체하고, 일정 기간 병행 운영하며 이상 여부를 관찰합니다.

마지막으로 평문 컬럼을 제거합니다. 컬럼을 단순히 삭제하는 것으로는 데이터 블록에 잔존 데이터가 남을 수 있으므로, 삭제 전에 값을 임의 데이터로 덮어쓰는 절차를 두거나 테이블을 재구성하는 것이 바람직합니다. 아울러 전환 이전에 생성된 백업에는 평문이 그대로 남아 있다는 점을 반드시 인지하고, 해당 백업의 보관 정책과 폐기 시점을 별도로 결정해야 합니다. 이 항목은 실무에서 자주 누락되며, 암호화를 완료했다고 보고한 이후에도 평문이 백업 매체에 수년간 남아 있는 사례가 드물지 않습니다.

## 14. 시험 계획

기능 시험은 암호화한 값이 복호화하여 원문과 일치하는지, 같은 평문을 두 번 암호화하면 서로 다른 암호문이 나오는지, 색인 값은 같은 평문에 대해 항상 같은지, 암호문 한 바이트를 변조했을 때 복호화가 거부되는지, 키를 교체한 후에도 기존 데이터가 정상 복호화되는지를 확인합니다. 경계값 시험으로 빈 문자열과 최대 길이 값, 한글과 특수 문자, 널 값의 처리를 포함합니다.

성능 시험은 단일 행 조회와 대량 목록 조회, 색인 검색, 대량 삽입, 전환 배치의 다섯 가지 유형에 대해 암호화 적용 전후를 비교 측정합니다. 측정은 운영과 동등한 데이터 규모에서 수행해야 하며, 소량 데이터에서의 측정치는 의미가 없습니다.

통제 유효성 시험은 보안관리 설계서에 정의된 시나리오에 따라 수행하며, 개발 트랙이 아닌 제3자가 수행합니다.

## 15. 참고 근거와 신뢰도 자체 평가

오라클 DBMS_CRYPTO 패키지의 제공 시점과 기본 기능에 관한 서술은 신뢰도 높음입니다. 다만 SHA-2 계열 지원 시점과 PBKDF2 지원 시점, GCM 운영 모드 지원 여부에 관한 서술은 신뢰도 중간이며, 대상 데이터베이스 버전의 공식 문서로 반드시 확인하셔야 합니다.

투명 데이터 암호화의 라이선스 조건과 컬럼 단위 적용 제약에 관한 서술은 신뢰도 중간입니다. 버전과 계약에 따라 달라집니다.

암호 알고리즘 선정에 관한 서술은 신뢰도 높음입니다. ECB 모드 회피, MD5와 SHA-1 회피, 확률적 암호화를 위한 난수 초기화 벡터 사용, 비밀번호에 대한 반복 기반 키 유도 함수 적용, 저엔트로피 데이터의 색인에 키 결합 해시 사용은 모두 널리 확립된 원칙입니다.

국내 법령상 비밀번호의 일방향 암호화 요구에 관한 서술은 신뢰도 중간에서 높음입니다. 고유식별정보 등의 암호화 저장 요구에 관한 서술은 신뢰도 중간이며, 구체적 조문과 적용 대상은 법무 검토를 거치시기 바랍니다.

국산 암호 알고리즘의 표준 지정과 공공 부문 적용 요건에 관한 서술은 신뢰도 중간입니다.

성능에 관한 정량적 수치는 제시하지 않았으며, 이는 근거가 없기 때문입니다.

## 16. 결론 요약

양방향과 일방향의 선택은 원문을 다시 읽어야 하는지 여부로 결정하며, 비밀번호는 일방향, 고유식별정보와 계좌 정보는 양방향으로 처리합니다. 아키텍처는 데이터베이스 내부 PL/SQL 패키지로 암호 연산을 수행하되 마스터 키만 외부에 분리 보관하는 절충안을 권고하며, 이는 라이선스 부담과 애플리케이션 영향을 억제하면서 저장 매체 유출에 대한 방어를 확보하는 선택입니다. 모듈은 암호 제공자 계층과 암호 연산 계층과 정책 계층과 인터페이스 계층의 네 겹으로 나누어, 계층별로 실행 권한을 다르게 부여하는 동시에 검증필 암호모듈로의 교체가 최하위 한 겹에서만 일어나도록 격리합니다. 암호문에는 버전과 알고리즘과 키 식별자와 초기화 벡터와 무결성 태그를 함께 담아야 하며, 이를 생략하면 키 교체가 불가능해집니다. 암호화된 컬럼은 검색이 불가능하므로 키가 결합된 HMAC 색인 컬럼을 별도로 두어 완전 일치 검색을 지원하고, 부분 일치와 범위 검색 요건은 업무 협의로 축소하는 것을 우선합니다. 성능 설계의 요체는 연산 최적화가 아니라 복호화 호출 횟수 자체를 줄이는 데 있으며, 목록 화면 마스킹이 가장 효과적인 수단입니다. 데이터 전환은 이중 기록 구간을 둔 단계적 방식으로 수행하고, 전환 이전에 생성된 백업에 평문이 남아 있다는 점을 반드시 별도로 처리해야 합니다.
