# 진행 현황

이 파일이 기준입니다. 대화가 길어져 맥락을 놓쳤을 때 여기만 보면 됩니다.
한 단계씩 진행하며, 단계가 끝날 때마다 갱신합니다.

## 작업 방식

작업 환경이 폐쇄망이라 스크립트를 고쳐 다시 반입하는 절차가 무겁습니다.
그래서 문제가 생기면 두 가지를 함께 합니다.

첫째, 저장소의 스크립트를 고칩니다. 다음 반입분과 기록을 위한 것입니다.

둘째, 폐쇄망에서 지금 바로 칠 수 있는 명령을 함께 드립니다. 반입을 기다리지
않고 진행할 수 있어야 하기 때문입니다. 대개는 붙여넣을 수 있는 짧은 SQL 이거나
고칠 한 줄입니다.

반입은 고칠 것이 여러 건 쌓였을 때 한 번에 하는 편이 낫습니다.

최종 갱신: 2026-09-30 (단계 3 진행 중)

## 지금 할 일

**단계 3. 스키마 객체와 패키지 설치** (진행 중)

먼저 인코딩을 맞춥니다. 저장소 스크립트는 UTF-8 이고 대상 데이터베이스는
`KO16MSWIN949` 이므로, 그냥 실행하면 주석과 문자열의 한글이 어긋나 일부
패키지가 컴파일되지 않습니다. 둘 중 하나만 하십시오.

```
rem (가) 파일을 CP949 로 바꾼다. 이후 sql_cp949/ 를 쓴다.
python tools\to_cp949.py

rem (나) 파일은 그대로 두고 클라이언트에 알린다. 창을 새로 열 때마다 해야 한다.
set NLS_LANG=KOREAN_KOREA.AL32UTF8
chcp 65001
```

자세한 사정은 `docs/70` 제6.1절에 있습니다.

`OCS_OWNER` 로 `SFISPDB949` 에 접속하여 순서대로 실행합니다. 번호가 곧 의존
관계이므로 순서를 지켜야 합니다.

```
sqlplus OCS_OWNER/<암호>@<호스트>:<포트>/SFISPDB949

SQL> @sql/01_schema/020_tables.sql
SQL> @sql/01_schema/030_views.sql
SQL> @sql/02_packages/090_pkg_sec_err.sql
SQL> @sql/02_packages/100_pkg_provider_dbms.sql
SQL> @sql/02_packages/110_pkg_crypto_fmt.sql
SQL> @sql/02_packages/120_pkg_audit.sql
SQL> @sql/02_packages/130_pkg_kek_provider.sql
SQL> @sql/02_packages/140_pkg_key_store.sql
SQL> @sql/02_packages/150_pkg_crypto_core.sql
SQL> @sql/02_packages/160_pkg_authz.sql
SQL> @sql/02_packages/170_pkg_app_context.sql
SQL> @sql/02_packages/180_pkg_key_admin.sql
SQL> @sql/02_packages/190_pkg_crypto_policy.sql
SQL> @sql/02_packages/195_pkg_legacy_pwd.sql
SQL> @sql/02_packages/200_pkg_secure_api.sql
SQL> @sql/02_packages/210_pkg_rekey.sql
SQL> COMMIT;
```

확인은 다음 한 줄입니다. 잘못된 객체가 하나도 나오지 않아야 합니다.

```sql
SELECT object_name, object_type, status FROM user_objects
 WHERE status <> 'VALID' ORDER BY 1;

SELECT object_type, COUNT(*) FROM user_objects GROUP BY object_type ORDER BY 1;
```

패키지 명세 14개와 본문 14개, 테이블 8개, 뷰 3개, 시퀀스 1개가 기대값입니다.

컴파일 오류가 나면 해당 패키지 이름과 오류 내용을 알려 주십시오. 오류 상세는
다음으로 봅니다.

```sql
SHOW ERRORS PACKAGE BODY <패키지이름>
```

### 단계 3 에서 나온 것

인코딩 문제를 확인했습니다. 위에 적었고 `docs/70` 제6.1절에 자세히 적었습니다.
변환 도구 `tools/to_cp949.py` 를 새로 두었고, 반입 꾸러미에도 CP949 사본을
함께 담도록 고쳤습니다.

`PKG_REKEY` 본문에서 `SQLERRM` 을 `UPDATE` 문 안에 직접 쓴 곳을 찾아 고쳤습니다.
오라클은 SQL 문 안에서 `SQLERRM` 과 `SQLCODE` 를 직접 쓰는 것을 허용하지 않으므로
PL/SQL 변수로 먼저 받아서 넘겨야 합니다. 같은 실수가 다시 나오지 않도록 정적
점검기에 검사 항목을 더했습니다.

폐쇄망에서는 반입을 기다리지 말고 `210_pkg_rekey.sql` 을 다음과 같이 고쳐서
다시 올리면 됩니다. 고칠 곳은 두 군데입니다. 선언부의 `v_done NUMBER := 0;`
바로 아래에 한 줄을 넣고,

```
    v_err     VARCHAR2(400);
```

마지막 `WHEN OTHERS THEN` 예외부를 다음과 같이 바꿉니다.

```
    WHEN OTHERS THEN
      v_err := SUBSTR(SQLERRM, 1, 400);
      ROLLBACK;
      UPDATE SEC_REKEY_JOB
         SET status = 'ERROR', last_error = v_err,
             updated_at = SYSTIMESTAMP
       WHERE job_name = p_job_name;
```

## 미결 사항

- 검증필 암호모듈 인증은 별도 과업으로 분리 (docs/30). 이 사업 범위 밖입니다.
- 에디션과 유상 옵션 보유 현황 미확인. 현재 설계는 유상 옵션을 쓰지 않으므로
  당장 막히지는 않습니다.
- TO-BE 문자집합이 MSWIN949 이므로, 기존 비밀번호가 어느 문자집합으로
  해싱되었는지 확인할 때 이 점을 함께 보아야 합니다. 단계 6 에서 다룹니다.
- 오라클 스크립트는 아직 실제 인스턴스에서 돌려 본 적이 없습니다. 단계 2 부터
  하나씩 확인됩니다. 정적 점검기는 컴파일을 대신하지 못하므로, 단계 3 에서
  나온 `SQLERRM` 같은 오류는 실제 컴파일에서만 드러납니다.
- 주민등록번호 기존 키를 찾지 못하면 해당 자료를 되살릴 수 없습니다. 최대 위험.
