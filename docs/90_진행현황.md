# 진행 현황

이 파일이 기준입니다. 대화가 길어져 맥락을 놓쳤을 때 여기만 보면 됩니다.
한 단계씩 진행하며, 단계가 끝날 때마다 갱신합니다.

## 작업 방식

작업 환경이 폐쇄망이라 스크립트를 고쳐 다시 반입하는 절차가 무겁습니다.
그래서 문제가 생기면 두 가지를 함께 합니다.

첫째, 저장소의 스크립트를 고칩니다. 다음 반입분과 기록을 위한 것입니다.

둘째, 폐쇄망에서 지금 바로 칠 수 있는 명령을 함께 드립니다. 반입을 기다리지
않고 진행할 수 있어야 하기 때문입니다. 대개는 붙여넣을 수 있는 짧은 SQL 이거나
고칠 한 줄입니다.

반입은 고칠 것이 여러 건 쌓였을 때 한 번에 하는 편이 낫습니다.

최종 갱신: 2026-09-30 (단계 4 완료)

## 지금 할 일

**단계 9. 운영 마스터 키 준비와 도메인·키 등록**

지금까지는 자체 시험용 고정 키로만 돌았습니다. 실제로 쓸 키는 아직 하나도
없습니다. 이 단계가 끝나야 응용에서 쓸 수 있는 상태가 됩니다.

세 부분으로 나뉘고 계정이 갈립니다. 계정이 갈리는 것이 설계 의도입니다.
스키마를 소유한 계정과 키를 만드는 계정을 나누어 두어야 한 계정이 새더라도
혼자서는 자료를 풀 수 없습니다.

### 9의1. 마스터 키 생성과 보관 (OCS_OWNER)

```sql
UPDATE SEC_CONFIG SET cfg_value = 'GLOBAL_CTX', updated_at = SYSTIMESTAMP
 WHERE cfg_key = 'KEK_SOURCE';
COMMIT;

SET SERVEROUTPUT ON
DECLARE v RAW(32); BEGIN
  v := DBMS_CRYPTO.RANDOMBYTES(32);
  DBMS_OUTPUT.PUT_LINE('MASTER KEY = ' || RAWTOHEX(v));
END;
/
```

찍힌 64자리 16진 문자열이 **이 시스템 전체의 마스터 키**입니다. 이것을 잃으면
암호화한 자료를 하나도 되살릴 수 없습니다. 화면에서 지우기 전에 반드시
기록하십시오. 열람 통제가 되는 곳에 두 벌 이상 보관하고, 누가 언제 꺼냈는지
남는 절차를 함께 두어야 합니다.

`GLOBAL_CTX` 는 원래 개발·시험 전용입니다. 키 관리 서버나 하드웨어 보안 모듈이
준비되면 `EXTERNAL` 로 바꾸고 `PKG_KEK_PROVIDER.load_from_external` 을 구현하면
됩니다. 그때 자료를 다시 암호화할 필요는 없습니다. 마스터 키는 데이터 키를
감싸는 데만 쓰이므로, 감싼 값만 다시 만들면 됩니다. **되돌릴 수 있는 결정입니다.**

### 9의2. 주입과 등록 (OCS_KEYADM)

```sql
BEGIN OCS_OWNER.PKG_KEK_PROVIDER.set_master_key(HEXTORAW('위에서 받은 64자리')); END;
/
```

이어서 `sql/04_admin/450_bootstrap_domains.sql` 을 실행합니다. 도메인 넷(RRN,
NAME, PHONE, ACCOUNT)을 등록하고 각각 운영 키를 만들어 활성으로 올립니다. 여러
번 실행해도 안전합니다. 활성 키가 이미 있으면 새로 만들지 않습니다.

### 단계 9 에서 나온 것

`450_bootstrap_domains.sql` 이 「복호화 권한 없음」으로 멈췄습니다. 두 가지가
겹쳐 있습니다.

첫째는 메시지가 잘못된 것입니다. 실제로 막힌 것은 복호화가 아니라 **관리 권한**
인데, `PKG_AUTHZ.require_admin` 이 복호화 권한 오류 코드를 그대로 쓰고 있었습니다.
원인을 잘못 짚게 만드는 메시지였습니다. `e_no_admin`(-20523) 을 따로 두어
고쳤습니다. 급하지 않으니 다음 반입 때 `090` 과 `160` 을 함께 가져가시면 됩니다.

둘째가 진짜 원인입니다. `SEC_ADMIN_GRANT` 에 관리 권한이 등록되어 있지 않은
것으로 보입니다. 그 등록은 `300_grants.sql` 이 합니다. 단계 4 에서 이 파일을
실행하지 않고 자체 시험만 돌리셨다면 대장이 비어 있습니다. 자체 시험은 자기
권한을 스스로 넣었다가 끝나면 지우므로 통과했어도 대장에는 남지 않습니다.

`OCS_OWNER` 로 다음을 확인하십시오. 결과가 비어 있으면 `300_grants.sql` 을
실행하시면 됩니다.

```sql
SELECT privilege, grantee_type, grantee_name FROM SEC_ADMIN_GRANT ORDER BY 1;
SELECT granted_role FROM DBA_ROLE_PRIVS WHERE grantee = 'OCS_KEYADM';
```

`OCS_KEYADM` 으로 다시 실행하니 이번에는 `OCS_OWNER.V_SEC_KEY_STATUS` 를 찾을 수
없다는 오류가 났습니다. 뷰에 대한 조회 권한이 역할로만 부여되어 있었기 때문으로
보입니다. 역할로 받은 권한은 저장 프로시저 안에서 인정되지 않고, 익명 블록에서도
기본 역할 설정에 따라 달라질 수 있습니다. 계정에 직접 부여하도록 `300_grants.sql`
을 고쳤습니다. 읽기 전용이고 키 값은 이 뷰에 나오지 않으므로 위험이 없습니다.

폐쇄망에서는 `OCS_OWNER` 로 이 한 줄만 치시면 됩니다.

```sql
GRANT SELECT ON V_SEC_KEY_STATUS TO OCS_KEYADM;
```

### 9의3. 증표용 키 등록 (OCS_KEYADM)

첫 확인에서 `ORA-20521` 「애플리케이션 인증 문맥 없음」이 났습니다. 마스터 키
문제가 아닙니다. 자료 도메인 넷을 `require_app_ctx='Y'` 로 등록했으므로 암호화든
복호화든 애플리케이션 인증 문맥이 먼저 서 있어야 하는데, 그 문맥을 세우는 데
쓰이는 `_APPCTX` 키를 `450_bootstrap_domains.sql` 이 만들지 않았습니다.
설치 절차에서 빠진 것이며 제 잘못입니다.

`460_appctx_key.sql` 을 새로 두었습니다. 이 키는 데이터베이스 밖에서 만들어
들여옵니다. 안에서 난수로 만들면 애플리케이션에 줄 방법이 없고, 데이터베이스
관리자가 값을 보게 되어 장치의 취지가 무너지기 때문입니다. 애플리케이션 담당자가
만들어 전달하는 것이 가장 낫습니다.

```
python -c "import secrets; print('\n'.join(secrets.token_hex(32) for _ in range(3)))"
```

세 번째 값이 실제 증표 계산에 쓰이며 애플리케이션 서버 설정에 넣습니다.
데이터베이스 쪽에서는 이 값을 다시 꺼낼 수 없습니다.

### 9의4. 확인 (다른 세션의 OCS_OWNER)

여기가 핵심입니다. 키를 주입한 세션이 아닌 **다른 세션**에서 암복호화가 되는지
보아야 합니다. 마스터 키 문맥이 인스턴스 전체에 걸리는지, 아니면 주입한 세션에만
걸리는지가 여기서 갈립니다. 세션마다 주입해야 한다면 운영에서 쓸 수 없는
구조이므로 설계를 고쳐야 합니다. 아직 확인하지 않았습니다.

- [x] 출력: 소문자 16진 32자. Base64 가 아니다.
- [x] `sha256Encoder` 는 SHA-256 을 16진 64자로 돌려준다. 솔트 없음, 반복 없음.
- [x] 로그인 경로는 `SecurityUserDetailsService`. 넘어온 값을 Base64 로 풀고

  돌려 보고서야 드러났습니다. 남은 단계에서도 같은 태도로 봅니다.
- 소유 계정 잠금(310_lockdown.sql)은 아직 하지 않았습니다. 개통 직전에 합니다.
- 시험용 표 SEC_KAT 은 남아 있습니다. 운영 배포 대상이 아니므로 개통 전에
  지워야 합니다.
- 주민등록번호 기존 키는 `SeedCryptoManagement.seedEncrypting` 안에
  `pbUserKey` 16바이트 배열로 원본에 박혀 있습니다. 소재 파악은 끝났습니다.
  키 값은 현장에만 두며 이 저장소에 들어오지 않습니다. 이행 도구는 키를
  실행 시점에 받도록 만듭니다.
- 비밀번호가 해시가 아니라 SEED 암호화일 가능성이 생겼습니다. 단계 5의2 에서
  가립니다. 만약 그렇다면 이행 방식을 변경 강제에서 무중단 전환으로 바꿀 수
  있습니다.
- 기존 시스템이 오라클 9.2.0.5 입니다. 19c 는 9i 와 직접 연결되지 않으므로
  (19c 가 지원하는 최저 상대 판은 11.2), 데이터베이스 링크로 자료를 옮길 수
  없습니다. 내보내기 파일이나 평문 파일을 거쳐야 하며, 어느 경로가 실제로
  되는지는 단계 9 에서 확인해야 합니다. 아직 확인하지 않았습니다.
- 9i 에는 `DBMS_CRYPTO` 가 없습니다. 따라서 기존 시스템 쪽에서는 이번에 만든
  모듈을 쓸 수 없고, 이행 작업은 TO-BE 인 19c 에서 하거나 애플리케이션 쪽에서
  해야 합니다.
