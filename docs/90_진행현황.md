# 진행 현황

이 파일이 기준입니다. 대화가 길어져 맥락을 놓쳤을 때 여기만 보면 됩니다.
한 단계씩 진행하며, 단계가 끝날 때마다 갱신합니다.

## 작업 방식

작업 환경이 폐쇄망이라 스크립트를 고쳐 다시 반입하는 절차가 무겁습니다.
그래서 문제가 생기면 두 가지를 함께 합니다.

첫째, 저장소의 스크립트를 고칩니다. 다음 반입분과 기록을 위한 것입니다.

둘째, 폐쇄망에서 지금 바로 칠 수 있는 명령을 함께 드립니다. 반입을 기다리지
않고 진행할 수 있어야 하기 때문입니다. 대개는 붙여넣을 수 있는 짧은 SQL 이거나
고칠 한 줄입니다.

반입은 고칠 것이 여러 건 쌓였을 때 한 번에 하는 편이 낫습니다.

최종 갱신: 2026-09-30 (단계 4 완료)

## 지금 할 일

**단계 11. 키 저장소 유지 프로그램 적용**

마스터 키 보관 방식을 **별도 상주 프로그램**으로 정했습니다. 응용과 분리되어
역할이 깔끔하고, 응용을 재기동해도 영향이 없으며, 제품을 사지 않아도 됩니다.

`java/src/main/java/ocsecure/keeper/OcsKeystoreKeeper.java` 를 만들었습니다. 하는
일은 넷뿐입니다. 설정에서 마스터 키를 읽고, 키 관리 계정으로 접속하여 주입하고,
주기적으로 저장소가 열려 있는지 확인하고, 끊기거나 닫혀 있으면 다시 붙어 다시
주입합니다. 업무 처리는 하지 않으며 자료를 읽지도 쓰지도 않습니다.

### 11의1. 설정 파일 만들기

`java/keeper.properties.sample` 을 `keeper.properties` 로 복사하고 값을 채웁니다.
이 파일에는 마스터 키와 계정 암호가 들어가므로 운영체제 권한으로 보호해야 합니다.
리눅스는 `chmod 600`, 윈도우는 서비스 계정만 읽도록 접근 제어를 겁니다. 프로그램이
시작할 때 남이 읽을 수 있으면 경고를 냅니다.

### 11의2. 설정 점검

```
java -cp out;<경로>\ojdbc8.jar ocsecure.keeper.OcsKeystoreKeeper keeper.properties --once
```

`저장소가 열렸다. 설정이 올바르다.` 가 나오면 됩니다. 한 번 주입하고 확인한 뒤
끝내므로, 설정이 맞는지 보는 데 씁니다.

### 11의3. 상주 실행과 확인

인자 없이 띄우면 계속 돕니다. 이 창을 띄워 둔 채로, **다른 창**에서 자바 연동
확인을 다시 돌려 `통과 5 / 실패 0` 이 나오는지 보십시오. 그 다음 상주 프로그램을
끄고 다시 돌려 실패하는지도 보시면 역할이 분명해집니다.

```
java -cp out;<경로>\ojdbc8.jar ocsecure.keeper.OcsKeystoreKeeper keeper.properties
```

운영에서는 윈도우 서비스나 리눅스 데몬으로 등록하여 장비 기동 시 함께 뜨게
합니다. 출력은 날짜와 시각이 붙은 한 줄짜리이므로 파일로 돌려 두면 그대로
운영 기록이 됩니다. 상태가 바뀔 때만 남기므로 같은 오류가 주기마다 쌓이지
않습니다.

### 함께 더한 것: 상태 확인 함수

키 저장소가 닫히면 모든 호출이 예외를 냅니다. 안전한 동작이지만 이용자에게
오류 추적이 그대로 보이는 것은 좋지 않습니다. `PKG_SECURE_API.ready` 를 열었습니다.
1 이면 가능, 0 이면 불가이며 키 값은 드러나지 않습니다. 화면 진입 전에 물어
안내로 가르고, 감시 도구의 상태 점검에도 같은 값을 씁니다. 자체 시험 항목도
하나 늘어 **68건**이 됩니다.

응용 쪽에서 챙길 것도 하나 적어 두었습니다. 암복호화 호출을 감싸는 `catch` 가
예외를 삼키면 암호문 자리에 널이 들어갑니다. 반드시 다시 던지거나 트랜잭션을
되돌려야 하며, `docs/61` 부록에 적었습니다.

### 남는 제약

데이터베이스를 재기동하면 전역 문맥이 비워지므로, 이 프로그램이 다시 붙어 주입할
때까지 암복호화가 멈춥니다. 확인 주기가 30초면 공백도 그만큼입니다. 이 공백을
없애려면 선택지 셋째인 키 관리 서버나 하드웨어 보안 모듈로 가야 하며, 그것은
별도 과업으로 남깁니다.

## 미결 사항

- 검증필 암호모듈 인증은 별도 과업으로 분리 (docs/30). 이 사업 범위 밖입니다.
- 에디션과 유상 옵션 보유 현황 미확인. 현재 설계는 유상 옵션을 쓰지 않으므로
  당장 막히지는 않습니다.
- TO-BE 문자집합이 MSWIN949 이므로, 기존 비밀번호가 어느 문자집합으로
  해싱되었는지 확인할 때 이 점을 함께 보아야 합니다. 단계 6 에서 다룹니다.
- 오라클 스크립트는 단계 4 까지 실제 인스턴스에서 확인되었습니다. 정적 점검기는
  컴파일과 실행을 대신하지 못하므로, 단계 3~4 에서 나온 세 건의 오류는 실제로
  돌려 보고서야 드러났습니다. 남은 단계에서도 같은 태도로 봅니다.
- 소유 계정 잠금(310_lockdown.sql)은 아직 하지 않았습니다. 개통 직전에 합니다.
- 시험용 표 SEC_KAT 은 남아 있습니다. 운영 배포 대상이 아니므로 개통 전에
  지워야 합니다.
- 주민등록번호 기존 키는 `SeedCryptoManagement.seedEncrypting` 안에
  `pbUserKey` 16바이트 배열로 원본에 박혀 있습니다. 소재 파악은 끝났습니다.
  키 값은 현장에만 두며 이 저장소에 들어오지 않습니다. 이행 도구는 키를
  실행 시점에 받도록 만듭니다.
- 비밀번호가 해시가 아니라 SEED 암호화일 가능성이 생겼습니다. 단계 5의2 에서
  가립니다. 만약 그렇다면 이행 방식을 변경 강제에서 무중단 전환으로 바꿀 수
  있습니다.
- 기존 시스템이 오라클 9.2.0.5 입니다. 19c 는 9i 와 직접 연결되지 않으므로
  (19c 가 지원하는 최저 상대 판은 11.2), 데이터베이스 링크로 자료를 옮길 수
  없습니다. 내보내기 파일이나 평문 파일을 거쳐야 하며, 어느 경로가 실제로
  되는지는 단계 9 에서 확인해야 합니다. 아직 확인하지 않았습니다.
- 9i 에는 `DBMS_CRYPTO` 가 없습니다. 따라서 기존 시스템 쪽에서는 이번에 만든
  모듈을 쓸 수 없고, 이행 작업은 TO-BE 인 19c 에서 하거나 애플리케이션 쪽에서
  해야 합니다.
