# 진행 현황

이 파일이 기준입니다. 대화가 길어져 맥락을 놓쳤을 때 여기만 보면 됩니다.
한 단계씩 진행하며, 단계가 끝날 때마다 갱신합니다.

## 작업 방식

작업 환경이 폐쇄망이라 스크립트를 고쳐 다시 반입하는 절차가 무겁습니다.
그래서 문제가 생기면 두 가지를 함께 합니다.

첫째, 저장소의 스크립트를 고칩니다. 다음 반입분과 기록을 위한 것입니다.

둘째, 폐쇄망에서 지금 바로 칠 수 있는 명령을 함께 드립니다. 반입을 기다리지
않고 진행할 수 있어야 하기 때문입니다. 대개는 붙여넣을 수 있는 짧은 SQL 이거나
고칠 한 줄입니다.

반입은 고칠 것이 여러 건 쌓였을 때 한 번에 하는 편이 낫습니다.

최종 갱신: 2026-10-02 (클린 재설치 진행 중, 제13장에서 멈춤)

## 지금 할 일

모듈 자체는 단계 14 까지 실 인스턴스에서 확인을 마쳤습니다. 지금 하고 있는 일은
**아무것도 없는 상태에서 설치 매뉴얼대로 다시 깔아 보는 것**이고, 그 과정에서
매뉴얼과 스크립트의 결함을 찾아 고치고 있습니다.

### 클린 재설치가 어디까지 갔나

제12장까지 마쳤고 **제13장(키 교체 리허설)에서 멈추어 있습니다.** 멈춘 까닭은
제12장의 `--data` 가 시험 자료를 넣었다 지우는 바람에 제13장에 옮길 자료가 한
건도 없었기 때문입니다. 매뉴얼의 결함이었고 아래와 같이 고쳐 두었습니다.

이어서 할 일은 `docs/80` 의 **부록 가(키 교체 리허설 되돌리기)** 로 빈 폐기 대기
키를 정리하고, 제12.3절의 `--keep` 으로 시험 자료 두 건을 다시 넣은 뒤, 제13장을
처음부터 밟는 것입니다. 재암호화 작업 이름만 `REHEARSAL2` 처럼 바꾸면 됩니다.

제14장(개통 직전 조치)은 **선생님 뜻에 따라 잠시 미루어 둔 상태**입니다. 전용
계정과 설정 파일 보호까지는 손보았고 상주 실행은 아직 해 보지 않았습니다.

### 이번에 클린 재설치가 찾아낸 것들

`010_users_roles.sql` 에서 `DBMS_LOCK` 실행 권한 부여와 `CREATE ROLE` 세 줄이
전부 실패했습니다. 원인은 **세미콜론 뒤에 같은 줄로 붙인 주석**입니다. SQL*Plus 는
최상위 구문을 세미콜론에서 끊으므로 그 뒤의 주석이 구문에 섞여 들어가 구문 전체가
실패합니다. 실패해도 다음 줄로 넘어가므로 긴 출력 속에서 놓치기 쉽습니다. 해당하는
다섯 줄을 고쳤고 같은 실수를 잡는 항목을 정적 점검기에 넣었습니다.

제12장의 확인이 **잘못된 객체만 세고 있어서**, 객체가 아예 없을 때에도 아무 행이
나오지 않아 통과처럼 보였습니다. 있는지와 성한지를 함께 보도록 고쳤습니다.

`800_sample_member.sql` 의 `UPDATE` 분기가 `join_dt` 를 다루지 않아 그 컬럼만
고치는 갱신이 오류 없이 사라지고 있었습니다. 빠진 컬럼을 넣고 `UPDATING('컬럼명')`
으로 갈라 바뀐 컬럼만 다시 암호화하도록 했습니다.

반입 꾸러미가 `java/keeper.properties.sample` 을 담지 않고 있었습니다. 꾸러미
도구가 디렉터리 단위로 복사하는데 이 파일만 그 바깥에 있었기 때문입니다.

### 설치 매뉴얼을 다시 썼습니다

작업 기록처럼 쓰여 있던 것을 **그대로 따라 하면 끝나는 절차서**로 고쳤습니다. 각
장이 접속과 실행과 확인의 세 토막으로 고정되고, 왜 그렇게 하는지는 인용 표시로
묶어 「설명」으로 떼어 냈습니다. 설명은 건너뛰어도 설치가 완료됩니다.

작업 디렉터리를 제2.4절에 정하고 **`OCS_HOME` 환경 변수 하나로 묶었습니다.**
꾸러미를 어디에 풀었든 고칠 곳은 변수에 넣는 한 줄뿐입니다. 자바 작업은 모두
`%OCS_HOME%\java` 에서 한다는 것도 못 박았습니다.

제14장을 운영체제별로 갈라 전용 계정 만들기, 프로그램 가져다 두기, 설정 파일
만들기, 설정 파일 보호, 상주 실행, 나머지 정리의 여섯 절로 나누었습니다. 윈도우
쪽은 `icacls` 상속 제거와 작업 스케줄러 등록이 핵심이며, **제가 실제 윈도우
장비에서 돌려 본 것이 아니므로 현장 확인이 필요합니다.**

### 응용 개발자에게 건넬 것

### 가. 개통 전 정리 (우리가 할 일, 급하지 않음)

「향후 과제」 항목을 보십시오. 유지 프로그램 설치, 재기동 시 전역 문맥 실측,
소유 계정 잠금, 시험용 표 제거, `EXTERNAL` 전환, 비밀번호 계산 위치 결정입니다.
개통 일정이 잡히면 역순으로 당겨 오면 됩니다.

### 나. 발주처가 정해야 할 것 (먼저 물어 두어야 함)

하나, 단일 인증을 쓸 수 없는 이용자가 처음 비밀번호를 정할 때 본인임을 어떻게
확인할 것인가. 정해진 것이 없으면 담당자가 대장에 근거해 확인한 뒤 1회용 설정
링크를 발급하는 방식으로 설계하겠습니다.

둘, 화면이나 출력물에 주민등록번호를 실제로 보여 주는 곳이 있는가. 없다면
평문 복원이 아예 필요 없어지고 이 사업 최대 위험이 사라집니다.

셋, 주민등록번호를 되살리지 못할 경우 어떻게 할 것인가. 본인 확인을 다시 받을
것인지 해당 항목을 비울 것인지입니다.

### 다. 기존 시스템 이행 (조사가 필요한 일)

`RESIDE_NO` 44자의 해시 방식을 확정해야 합니다. 비밀번호와 달리 **주민등록번호는
본인이 다 기억하므로** 협조해 주실 분 한 분이면 실측으로 끝납니다. 그분의
`USER_ID` 로 행을 찾아 `RESIDE_NO` 값을 꺼낸 뒤 다음을 돌리면 됩니다.

```
python tools\legacy_pwd_probe.py --plain "<본인 주민등록번호>" --stored "<RESIDE_NO 값>" --id "<USER_ID 값>"
```

그리고 앞서 보셨던 Base64 24자 컬럼이 어느 테이블에 있는지 찾아야 합니다. SEED
한 블록이므로 실제 복호화 대상일 가능성이 높습니다.

- [x] 치환표 검증 완료. SS0~SS3 각 256개, SS2·SS3 는 SS0·SS1 의 16비트 회전,
      규격 마스크로 분해했을 때 나오는 8비트 S-box 두 개가 모두 전단사,
      KC 는 0x9e3779b9 에서 시작하는 1비트 회전 수열. 손댄 흔적 없음.
- [x] 운용 방식: ECB 한 블록. 초기 벡터 없음. 결정적.
- [x] 패딩: **영 채움**. `new byte[16]` 에 앞에서부터 채우므로 남는 자리가 0x00.
      PKCS5 가 아니므로 복호화하면 뒤에 널 바이트가 남는다. 잘라내야 한다.
- [x] 입력 제한: 16자 이하. 16자를 넘으면 null 을 돌려준다.
- [x] 입력 인코딩: 한 글자씩 `getBytes()[0]`. 플랫폼 기본 문자집합의 첫 바이트만
      쓰므로 **한글은 애초에 깨진다.** 이 방식으로 넣은 값은 전부 ASCII 다.
- [x] 출력: 소문자 16진 32자. Base64 가 아니다.
- [x] `sha256Encoder` 는 SHA-256 을 16진 64자로 돌려준다. 솔트 없음, 반복 없음.
- [x] 로그인 경로는 `SecurityUserDetailsService`. 넘어온 값을 Base64 로 풀고
      `seedEncrypting` 을 돌리지만, 정작 조회에는 원래 값을 그대로 쓴다.
      계산 결과를 버리는 코드이며 기존 시스템의 결함으로 보인다.

### 기존 시스템 조사

- [x] 규모: 최근 1년 접속자 약 2만 3천 명, 전원 공무원

## 향후 과제 (급하지 않으나 개통 전에는 해야 하는 것)

- 키 저장소 유지 프로그램(`OcsKeystoreKeeper`) 설치와 상주 시험. 만들어 두었고
  컴파일과 자체 시험은 통과했으나 실환경에 올려 보지는 않았습니다. 데이터베이스
  재기동과 자체 시험 뒤에 사람 손 없이 복구되는지가 확인 대상입니다.
- 데이터베이스 재기동 시 전역 문맥이 비워지는지 실측. 재기동 일정이 있을 때
  자바 연동 확인을 다시 돌려 보면 됩니다.
- 소유 계정 잠금(`310_lockdown.sql`). 개통 직전에 합니다.
- 시험용 표 `SEC_KAT` 제거. 운영 배포 대상이 아닙니다.
- 마스터 키를 `EXTERNAL` 로 전환. 키 관리 서버나 하드웨어 보안 모듈이 준비되면
  합니다. 자료를 다시 암호화할 필요는 없습니다.
- 비밀번호 계산을 자바 쪽으로 옮길지 결정. 옮기면 반복 횟수를 크게 올릴 수
  있습니다. 지금은 50,000 회입니다.

## 미결 사항

- 검증필 암호모듈 인증은 별도 과업으로 분리 (docs/30). 이 사업 범위 밖입니다.
- 에디션과 유상 옵션 보유 현황 미확인. 현재 설계는 유상 옵션을 쓰지 않으므로
  당장 막히지는 않습니다.
- TO-BE 문자집합이 MSWIN949 이므로, 기존 비밀번호가 어느 문자집합으로
  해싱되었는지 확인할 때 이 점을 함께 보아야 합니다. 단계 6 에서 다룹니다.
- 오라클 스크립트는 단계 4 까지 실제 인스턴스에서 확인되었습니다. 정적 점검기는
  컴파일과 실행을 대신하지 못하므로, 단계 3~4 에서 나온 세 건의 오류는 실제로
  돌려 보고서야 드러났습니다. 남은 단계에서도 같은 태도로 봅니다.
- 소유 계정 잠금(310_lockdown.sql)은 아직 하지 않았습니다. 개통 직전에 합니다.
- 시험용 표 SEC_KAT 은 남아 있습니다. 운영 배포 대상이 아니므로 개통 전에
  지워야 합니다.
- 주민등록번호 기존 키는 `SeedCryptoManagement.seedEncrypting` 안에
  `pbUserKey` 16바이트 배열로 원본에 박혀 있습니다. 소재 파악은 끝났습니다.
  키 값은 현장에만 두며 이 저장소에 들어오지 않습니다. 이행 도구는 키를
  실행 시점에 받도록 만듭니다.
- 비밀번호가 해시가 아니라 SEED 암호화일 가능성이 생겼습니다. 단계 5의2 에서
  가립니다. 만약 그렇다면 이행 방식을 변경 강제에서 무중단 전환으로 바꿀 수
  있습니다.
- 기존 시스템이 오라클 9.2.0.5 입니다. 19c 는 9i 와 직접 연결되지 않으므로
  (19c 가 지원하는 최저 상대 판은 11.2), 데이터베이스 링크로 자료를 옮길 수
  없습니다. 내보내기 파일이나 평문 파일을 거쳐야 하며, 어느 경로가 실제로
  되는지는 단계 9 에서 확인해야 합니다. 아직 확인하지 않았습니다.
- 9i 에는 `DBMS_CRYPTO` 가 없습니다. 따라서 기존 시스템 쪽에서는 이번에 만든
  모듈을 쓸 수 없고, 이행 작업은 TO-BE 인 19c 에서 하거나 애플리케이션 쪽에서
  해야 합니다.
