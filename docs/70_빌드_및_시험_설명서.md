# 빌드 및 시험 설명서

## 1. 이 문서의 범위

저장소에 들어 있는 파이썬 코드와 자바 코드를 어떻게 준비하고 돌리고 배포하는지를 다룹니다. 지금까지의 설명서들이 "무엇을 어떻게 쓰는가"를 다루었다면 이 문서는 "그것을 어떻게 만들어 내는가"를 다룹니다.

본문의 모든 명령은 실제로 실행하여 결과를 확인한 것입니다. 확인하지 못한 것은 그렇다고 적어 두었습니다.

## 2. 준비물

자바는 8 이상이면 됩니다. 연동 모듈이 8을 대상으로 컴파일되도록 해 두었기 때문이며, 그 이유는 전자정부 표준프레임워크 3.x 환경까지 고려했기 때문입니다. 개발 환경의 자바가 더 높아도 상관없습니다.

파이썬은 3.6 이상이면 동작할 것으로 보이나, 확인은 3.11에서만 하였습니다. 정확도: 중간.

파이썬 쪽에는 외부 패키지가 하나 필요합니다. 자바 쪽에는 없습니다. 자세한 것은 각 장에서 다루겠습니다.

오라클 쪽 자체 시험을 돌리려면 인스턴스와 접속 도구가 필요하나, 그것 없이도 파이썬과 자바 점검은 전부 돌아갑니다.

## 3. 한 번에 점검하기

평소에는 이것 하나면 됩니다.

```
./tools/run_checks.sh
```

네 가지를 차례로 수행합니다. 참조 구현 시험을 돌리고, 고정 시험 벡터가 참조 구현과 여전히 일치하는지 확인하고, PL/SQL 정적 점검을 하고, 자바 모듈을 컴파일하여 자체 시험을 돌립니다. 하나라도 실패하면 거기서 멈추고 실패 이유를 알려 줍니다.

마지막 줄에 `모든 점검 통과`가 나와야 합니다. 커밋하기 전에 돌리는 습관을 들이시면 좋습니다.

여기서 확인하지 못하는 것이 하나 있습니다. **오라클에서의 컴파일과 실행입니다.** 이 점검은 인스턴스를 필요로 하지 않으므로, PL/SQL은 정적 점검까지만 이루어집니다. 실 인스턴스 확인은 제6장을 보십시오.

## 4. 파이썬 쪽

### 4.1 무엇이 들어 있는가

`tools/refimpl/ocsecure_ref.py`가 참조 구현입니다. 암호문 포맷의 실행 가능한 정의이며, 문서의 서술과 실제 구현이 어긋나는 것을 막는 역할을 합니다. PL/SQL과 자바가 이것과 같은 값을 내는지로 정확성을 판정하므로, 이 파일이 세 구현의 기준점입니다.

`tools/refimpl/gen_vectors.py`는 참조 구현이 만들어 낸 값을 고정 시험 벡터로 떨어뜨립니다. 세 가지 형식으로 나오는데, JSON은 범용, `.properties`는 자바용, `.sql`은 오라클용입니다.

`tools/legacy_pwd_probe.py`는 기존 비밀번호 저장 방식을 식별합니다. 이 도구만은 외부 패키지 없이 돌아갑니다.

`tools/lint_plsql.py`는 오라클 없이 잡을 수 있는 PL/SQL 오류를 걸러 냅니다.

`tests/`에는 참조 구현 시험과 식별기 시험이 있습니다. `tests/vectors/`에는 생성된 고정 시험 벡터가 있으며, 이 둘은 손으로 고치지 않습니다.

### 4.2 준비

외부 패키지 하나가 필요합니다.

```
pip install -r requirements.txt
```

`cryptography` 하나뿐이며 AES 연산에만 씁니다. 해시와 키 유도는 표준 라이브러리만으로 되므로, 저장 방식 식별기는 이것 없이도 돌아갑니다.

폐쇄망이라 내려받을 수 없다면 참조 구현 시험만 건너뛰시면 됩니다. PL/SQL 정적 점검과 자바 컴파일은 영향을 받지 않습니다. 다만 고정 시험 벡터를 새로 만들 수 없으므로, 저장소에 들어 있는 벡터를 그대로 쓰셔야 합니다. 그것으로 충분합니다.

`ModuleNotFoundError: No module named '_cffi_backend'` 오류가 나면 `pip install cffi`를 함께 하십시오. 배포판에 따라 `cryptography`가 설치되어 있어도 이 부분이 빠져 있는 경우가 있습니다.

### 4.3 시험 실행

전부 돌리려면 이렇게 합니다. 저장소 최상위에서 실행합니다.

```
python3 -m unittest discover -s tests -q
```

무엇이 통과했는지 하나씩 보고 싶으면 `-q` 대신 `-v`를 씁니다. 시험 이름을 한글로 달아 두었으므로 무엇을 확인하는 시험인지 이름만 보아도 알 수 있습니다.

파일 하나만 돌리려면 이렇게 합니다.

```
python3 -m unittest discover -s tests -p "test_refimpl.py"
```

시험 묶음 하나만 돌리려면 `tests` 디렉터리로 들어가서 실행합니다.

```
cd tests && python3 -m unittest test_refimpl.TestPassword
```

### 4.4 시험 벡터 다시 만들기

참조 구현을 고쳤다면 벡터를 다시 만들어야 합니다.

```
python3 tools/refimpl/gen_vectors.py
```

세 파일이 함께 갱신됩니다. **반드시 참조 구현 수정과 같은 커밋에 넣으십시오.** 벡터만 옛것으로 남아 있으면 PL/SQL과 자바 쪽 시험이 엉뚱한 기준과 대조하게 됩니다.

이 사고를 막으려고 `run_checks.sh`가 벡터를 다시 만들어 기존 파일과 바이트 단위로 비교합니다. 어긋나면 거기서 멈추므로, 잊고 커밋하는 일은 생기지 않습니다.

벡터를 손으로 고치지 마십시오. 생성 파일이며, 다음 생성 때 덮어써집니다.

### 4.5 저장 방식 식별기

기존 시스템의 비밀번호 저장 방식을 알아낼 때 씁니다. 자세한 사용법은 `61_비밀번호시스템_개발자설명서.md` 제10.1절에 있습니다.

```
python3 tools/legacy_pwd_probe.py --plain '평문' --stored '저장값' --id '아이디'
```

### 4.6 PL/SQL 정적 점검기

```
python3 tools/lint_plsql.py
```

패키지 명세와 본문의 대응, 종결자 누락, 그리고 패키지 사이의 호출이 실제로 존재하는 이름을 가리키는지를 확인합니다. 오타로 인한 컴파일 실패를 미리 잡아 주지만 컴파일을 대신하지는 못합니다.

## 5. 자바 쪽

### 5.1 무엇이 들어 있는가

`java/src/main/java/ocsecure/client/` 아래가 연동 모듈의 본체입니다. `OcsCrypto`가 암호문 포맷 구현이고, `OcsKeySet`이 키 묶음, `OcsAppProof`가 접속 증표 생성기, `OcsSessionSupport`가 세션 문맥 확립 도우미, `OcsLegacyPassword`가 이행 기간용 기존 방식 검증, `OcsCryptoException`이 예외 정의입니다.

`java/src/test/java/ocsecure/client/OcsSelfTest.java`가 자체 시험입니다. 고정 시험 벡터와 대조하여 참조 구현과 바이트 단위로 같은 값을 내는지 확인합니다.

`java/pom.xml`이 빌드 정의입니다.

### 5.2 의존성이 없다는 것

외부 라이브러리를 하나도 쓰지 않습니다. JDK 표준 라이브러리만으로 만들었습니다.

의도한 설계입니다. 암호 모듈이 다른 라이브러리를 끌고 들어오면 그 라이브러리의 취약점이 곧 암호 모듈의 취약점이 되고, 대상 프로젝트가 이미 쓰고 있는 것과 버전이 충돌하면 적용 자체가 막힙니다. 전자정부 표준프레임워크 프로젝트는 의존성이 이미 촘촘하게 얽혀 있는 경우가 많아 이 점이 특히 중요합니다.

덕분에 빌드 도구 없이 `javac`만으로도 컴파일되고, 소스를 그대로 복사해 넣어도 동작합니다.

### 5.3 빌드 도구 없이 컴파일하기

가장 간단한 방법입니다. 저장소 최상위에서 실행합니다.

```
javac -encoding UTF-8 -d out $(find java/src -name '*.java')
java -Dstdout.encoding=UTF-8 -cp out ocsecure.client.OcsSelfTest tests/vectors/kat.properties
```

`-encoding UTF-8`을 빠뜨리면 주석의 한글이 깨지면서 컴파일에 실패할 수 있습니다. `-Dstdout.encoding=UTF-8`을 빠뜨리면 시험 결과의 한글이 물음표로 나옵니다. 둘 다 환경의 기본 문자집합에 따라 달라지므로 명시하는 편이 안전합니다.

이 두 줄을 묶어 둔 것이 `tools/build_java.sh`입니다. 경고까지 모두 켜고 컴파일하므로 평소에는 이것을 쓰시면 됩니다.

```
./tools/build_java.sh
```

### 5.4 Maven 으로 빌드하기

배포용 jar를 만들 때 씁니다.

```
cd java && mvn -B package
```

`java/target/ocsecure-client-1.0.0.jar`가 나옵니다. 처음 실행할 때는 Maven이 플러그인을 내려받으므로 시간이 걸리고 망 접속이 필요합니다.

이 명령과 산출물은 실제로 확인하였습니다. 만들어진 jar를 사용해 자체 시험을 돌려 68건이 모두 통과하는 것까지 확인하였습니다.

```
javac -encoding UTF-8 -cp java/target/ocsecure-client-1.0.0.jar \
      -d out-test java/src/test/java/ocsecure/client/OcsSelfTest.java
java -Dstdout.encoding=UTF-8 \
     -cp "java/target/ocsecure-client-1.0.0.jar:out-test" \
     ocsecure.client.OcsSelfTest tests/vectors/kat.properties
```

`target/` 디렉터리는 형상 관리에서 제외해 두었습니다. 빌드 산출물이므로 커밋하지 마십시오.

Gradle 빌드 스크립트는 제공하지 않습니다. 필요하시면 만들어 드릴 수 있으나, 의존성이 없으므로 굳이 필요하지 않을 것입니다.

### 5.5 자바 8 을 대상으로 하는 이유

전자정부 표준프레임워크 3.x 환경이 자바 8을 쓰는 경우가 있어 그에 맞추었습니다. 정확도: 중간이며 실제 대상 환경을 확인하셔야 합니다.

더 낮은 버전을 대상으로 컴파일하려면 다음과 같이 확인할 수 있습니다. 실제로 확인한 명령입니다.

```
javac --release 8 -encoding UTF-8 -d out $(find java/src/main -name '*.java')
```

`source value 8 is obsolete` 경고가 나오지만 컴파일은 정상입니다. 최근 JDK가 옛 대상 버전에 대해 내는 경고이며 결과에는 영향이 없습니다.

### 5.6 업무 프로젝트에 반입하기

세 가지 방법이 있습니다.

첫째는 jar를 직접 넣는 방법입니다. 만들어진 jar를 프로젝트의 라이브러리 디렉터리에 두고 클래스패스에 추가합니다. 폐쇄망 환경에서 가장 간단합니다.

둘째는 사내 저장소에 올려 두고 의존성으로 선언하는 방법입니다. Maven을 쓰는 프로젝트라면 이 편이 관리하기 좋습니다.

```xml
<dependency>
  <groupId>ocsecure</groupId>
  <artifactId>ocsecure-client</artifactId>
  <version>1.0.0</version>
</dependency>
```

셋째는 소스를 그대로 복사해 넣는 방법입니다. 의존성이 없으므로 `ocsecure/client` 패키지를 통째로 옮기면 그대로 동작합니다. 빌드 절차를 하나 더 두고 싶지 않을 때 쓸 만합니다. 다만 나중에 모듈이 고쳐졌을 때 반영이 누락되기 쉬우므로, 복사해 넣었다는 사실과 어느 판을 가져왔는지를 기록해 두십시오.

어느 방법이든 반입한 뒤에는 그 환경에서 자체 시험을 한 번 돌려 보시기를 권합니다. 문자집합이나 보안 정책이 달라 결과가 달라지는 일이 드물게 있습니다.

## 6. 오라클 쪽 시험

인스턴스가 필요합니다. 설치 직후와 변경 배포 직후에 반드시 돌립니다.

```
sqlplus OCS_OWNER/…@대상DB
SQL> @sql/09_test/900_kat_setup.sql
SQL> @sql/09_test/901_kat_data.sql
SQL> @sql/09_test/902_selftest.sql
```

`901_kat_data.sql`은 생성 파일입니다. 참조 구현을 고쳤다면 `gen_vectors.py`를 먼저 돌려 갱신한 뒤에 올리십시오.

자체 시험은 설정을 개발 모드로 잠시 바꾸었다가 되돌립니다. **운영계에서 실행하지 마십시오.**

## 7. 무엇을 고치면 무엇을 다시 돌려야 하는가

참조 구현을 고쳤다면 벡터를 다시 만들고, 세 구현의 시험을 모두 돌려야 합니다. 포맷이 바뀐 것이므로 PL/SQL과 자바가 따라오지 못하면 거기서 드러납니다.

PL/SQL만 고쳤다면 정적 점검을 돌리고 인스턴스에서 자체 시험을 돌립니다.

자바만 고쳤다면 `build_java.sh` 하나면 됩니다.

문서만 고쳤다면 아무것도 돌릴 필요가 없습니다. 다만 문서에 적은 명령을 바꾸었다면 그 명령이 실제로 동작하는지 한 번 실행해 보십시오.

어느 경우든 커밋 전에 `run_checks.sh`를 돌리면 위 판단을 대신해 줍니다.

## 8. 자주 겪는 문제

한글이 물음표로 나오면 `-Dstdout.encoding=UTF-8`을 붙이십시오. 컴파일 단계에서 한글이 깨진다면 `-encoding UTF-8`이 빠진 것입니다.

`ModuleNotFoundError: No module named 'cryptography'`는 파이썬 패키지가 없는 것입니다. `pip install -r requirements.txt`로 해결됩니다. `_cffi_backend`를 찾지 못한다는 오류라면 `pip install cffi`를 함께 하십시오.

`시험 벡터가 참조 구현과 어긋난다`는 참조 구현을 고치고 벡터를 다시 만들지 않은 것입니다. `gen_vectors.py`를 돌리고 결과를 함께 커밋하십시오.

Maven 빌드가 멈춰 있다면 플러그인을 내려받는 중일 수 있습니다. 폐쇄망이라면 `javac`로 컴파일하거나 사내 저장소를 거울로 두셔야 합니다.

`target/`이나 `out/`이 형상 관리에 올라왔다면 제외 설정을 확인하십시오. 빌드 산출물은 커밋하지 않습니다.

## 9. 폐쇄망에서

관공서 환경은 망이 분리되어 있는 경우가 많으므로 정리해 두겠습니다.

자바 쪽은 문제가 없습니다. 의존성이 없으므로 JDK만 있으면 `javac`로 컴파일됩니다. Maven을 쓰실 거라면 플러그인을 미리 받아 두거나 사내 저장소를 거울로 두셔야 합니다.

파이썬 쪽은 `cryptography` 하나만 반입하면 됩니다. 반입이 어렵다면 참조 구현 시험을 건너뛰고 저장소에 들어 있는 벡터를 그대로 쓰시면 됩니다. 저장 방식 식별기와 PL/SQL 정적 점검기는 표준 라이브러리만 쓰므로 그대로 동작합니다.

오라클 쪽은 애초에 망 접속이 필요 없습니다.

## 10. 참고 근거와 신뢰도 자체 평가

본문의 명령은 모두 실제로 실행하여 확인하였습니다. 파이썬 시험 실행, 벡터 생성, 정적 점검, `javac` 컴파일, 자바 8 대상 컴파일, Maven 패키징, 산출된 jar로 자체 시험 실행까지 모두 확인하였으므로 신뢰도 높음입니다.

파이썬 3.6 이상에서 동작한다는 서술은 신뢰도 중간입니다. 3.11에서만 확인하였습니다.

전자정부 표준프레임워크 3.x가 자바 8을 쓴다는 서술은 신뢰도 중간입니다. 대상 환경을 확인하셔야 합니다.

오라클 쪽 자체 시험 실행 절차는 신뢰도 중간입니다. 스크립트의 내용은 확인하였으나 인스턴스에서 실행해 보지는 못하였습니다.

## 11. 결론 요약

평소에는 `./tools/run_checks.sh` 하나면 됩니다. 참조 구현 시험과 벡터 최신 여부, PL/SQL 정적 점검, 자바 컴파일과 자체 시험을 한 번에 수행하며, 오라클 인스턴스 없이 돌아갑니다. 파이썬 쪽은 `cryptography` 하나만 있으면 되고 없으면 참조 구현 시험만 건너뛰면 됩니다. 자바 쪽은 외부 의존성이 전혀 없어 `javac`만으로 컴파일되고, 배포용 jar가 필요하면 `cd java && mvn -B package`로 만듭니다. 업무 프로젝트에는 jar를 넣거나 사내 저장소를 거치거나 소스를 복사해 넣는 세 가지 방법이 있으며, 어느 쪽이든 반입 후 그 환경에서 자체 시험을 한 번 돌려 보시기 바랍니다. 참조 구현을 고쳤다면 시험 벡터를 다시 만들어 같은 커밋에 넣어야 하고, 잊더라도 점검 스크립트가 잡아 줍니다.
