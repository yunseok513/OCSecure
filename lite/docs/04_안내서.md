# OCS-LITE 간이 암호화 모듈 안내서

## 0. 이 문서에 대하여

이 문서는 재정통합시스템의 오라클 데이터베이스에 설치된 간이 암호화 모듈(이하 OCS-LITE)을 설치하고 사용하고 유지보수하는 담당자를 위한 안내서입니다. 모듈의 목적은 주민등록번호와 계좌번호 같은 식별번호를 암호화해 저장하고, 비밀번호를 되돌릴 수 없는 해시로 저장하는 것입니다. 전문 암호화 솔루션을 대체하는 제품이 아니며, 방어할 수 있는 범위가 좁다는 점을 제10장에 분명히 적었습니다. 계약 상대방에게 모듈을 인계할 때는 제10장을 함께 전달하시기 바랍니다.

이 문서가 설명하는 절차 가운데 오라클 인스턴스에서 직접 실행해 확인한 것은 아직 없습니다. 개발 환경에는 오라클이 없어서, 암호문 형식이 기준 구현과 일치하는지, 스크립트의 정적 점검, 안내서와 코드의 일치를 보는 파이썬 시험만 통과한 상태입니다. 다음 표는 확인된 것과 확인되지 않은 것을 구분합니다. 시험 인스턴스에서 제3장의 절차를 한 번 실행해 본 뒤에 이 표를 갱신하여 인계하십시오.

| 항목 | 상태 |
|---|---|
| 암호문 형식, 키 유도, 비밀번호 해시가 파이썬 기준 구현과 같은 바이트를 낸다 | 파이썬 기준값으로 계산, 오라클 실행은 미확인 |
| SQL 코드(주석 밖)가 ASCII 만 쓰고, 주석이 CP949 로 표현되며, 패키지 명세와 본문이 짝을 이룬다 | 정적 점검 통과 |
| 패키지가 오라클에서 오류 없이 컴파일된다 | 미확인 |
| 문자집합 점검(`05_check_charset.sql`)이 NLS_LANG 이 어긋난 창에서 설치를 멈추고, 맞는 창에서는 통과한다 | 미확인 |
| 자체 시험(`50_selftest.sql`)이 전부 통과한다 | 미확인 |
| 비밀번호 해시의 반복 횟수 10000이 허용 응답 시간 안에 든다 | 미측정 |
| 대량 전환(수십만 행 이상)의 소요 시간 | 미측정 |

## 1. 한눈에 보기

OCS-LITE는 오라클 데이터베이스 안의 객체만으로 이루어집니다. 별도의 서버나 상주 프로그램, 서버 파일, 자바 라이브러리가 없습니다. 소유 계정 `SFC_OWNER` 하나가 키 테이블 `SFC_KEY`, 봉인값 패키지 `SFC_SEAL`, 본체 패키지 `PKG_SFC`, 응용이 부르는 함수 여섯 개를 가집니다. 업무 계정은 이 함수 여섯 개의 실행 권한만 받으며, 키 테이블과 패키지에는 접근하지 못합니다.

| 함수 | 하는 일 |
|---|---|
| `FN_SFC_ENC(평문)` | 식별번호를 암호화해 16진 문자열로 돌려줍니다. 같은 평문도 호출마다 다른 값이 나옵니다. |
| `FN_SFC_DEC(암호문)` | 암호문을 평문으로 되돌립니다. |
| `FN_SFC_MASK(암호문, 유형)` | 복호화한 값을 가려서 돌려줍니다. 유형은 `RRN`, `ACCOUNT`, `ALL`입니다. |
| `FN_SFC_PWD_HASH(비밀번호)` | 비밀번호를 해시한 108자 16진 문자열을 돌려줍니다. |
| `FN_SFC_PWD_VERIFY(비밀번호, 저장값)` | 일치하면 1, 아니면 0입니다. |
| `FN_SFC_READY` | 암호화를 쓸 수 있으면 1, 아니면 0입니다. 감시에 쓰십시오. |

양방향 암호화는 AES-256-CBC에 HMAC-SHA256 태그를 붙인 형식이며, 오라클 내장 `DBMS_CRYPTO`로 계산합니다. 복호화할 때는 태그를 먼저 검증하므로 암호문이 변조되면 복호화 전에 거부됩니다. 비밀번호는 PBKDF2-SHA256으로 해시하고, 솔트와 반복 횟수를 저장값 안에 함께 담습니다.

## 2. 설치 전에 확인할 것

설치하려면 `SYS` 권한으로 `SFC_OWNER` 계정을 만들고 `DBMS_CRYPTO` 실행 권한을 주어야 합니다. 이 권한을 발급받을 수 없는 환경이면 모듈을 설치할 수 없으므로 가장 먼저 확인하십시오. 오라클 버전은 `DBMS_CRYPTO`가 SHA-256 계열 HMAC을 지원해야 하며, 19c에서는 지원합니다. 다른 버전은 확인되지 않았습니다.

컬럼 길이를 미리 잡아 두십시오. 암호문은 16진 문자열로 저장하므로 평문보다 훨씬 깁니다. 주민등록번호는 하이픈 포함 여부와 관계없이 136자, 20자 이내의 계좌번호는 168자, 32자 이내는 200자, 비밀번호 해시는 108자이며 UTF-8에서 한글 한 글자는 3바이트로 셈합니다. 한 값의 평문이 1900바이트를 넘으면 `-20601` 오류로 거부됩니다. 이미 운영 중인 테이블이면 컬럼을 새로 추가해야 하므로 제4.3절을 먼저 읽으십시오.

## 3. 설치

설치 패키지를 받으면 먼저 파일이 온전한지 확인하십시오. 패키지 최상위 폴더에서 다음 명령을 실행해 모든 줄이 `OK`로 끝나야 하며, 하나라도 `FAILED`가 나오면 파일이 옮겨지는 도중 손상된 것이므로 설치하지 말고 패키지를 다시 받으십시오. 파이썬이 있는 장비라면 `python3 tools/verify_manifest.py`로도 같은 확인을 하며, 이쪽은 목록에 없는 파일이 끼어 있는지도 알려 줍니다.

```
sha256sum -c MANIFEST.sha256
```

설치 파일은 패키지의 `sql/` 폴더에 있고(저장소에서는 `lite/sql/`) 번호 순서대로 실행합니다. 명령이 `@10_sys_setup.sql`처럼 파일 이름만 쓰므로, 반드시 `sql/` 폴더로 이동한 다음 SQL*Plus를 실행하십시오. 아래 명령에서 `@`는 SQL*Plus의 실행 명령입니다.

패키지의 SQL 파일은 한글 주석이 있어서 **CP949로 저장**되어 있습니다(저장소의 원본은 UTF-8이고 패키지를 만들 때 변환합니다). SQL*Plus를 실행하는 창에서 클라이언트 문자집합을 파일에 맞춰야 합니다. 리눅스는 `export NLS_LANG=KOREAN_KOREA.KO16MSWIN949`, 윈도우는 `set NLS_LANG=KOREAN_KOREA.KO16MSWIN949`를 먼저 실행하십시오. 어긋나면 한글 주석이 줄바꿈을 삼켜 뒤따르는 줄이 조용히 사라질 수 있으므로, 모든 스크립트가 첫 줄에서 `05_check_charset.sql`로 점검하고 어긋났으면 `Client character set does not match the file encoding` 메시지(`ORA-20999`)와 함께 중단합니다. 파일을 UTF-8로 바꿔 쓰는 경우에는 `KOREAN_KOREA.AL32UTF8`로 맞추며, 두 방식을 섞어 쓰면 안 됩니다.

| 순서 | 접속 계정 | 명령 | 하는 일 |
|---|---|---|---|
| 1 | `SYS` | `@10_sys_setup.sql "암호" USERS` | 소유 계정 생성과 권한 부여. 인자는 소유 계정 암호와 테이블스페이스입니다. |
| 2 | `SFC_OWNER` | `@20_key_table.sql` | 키 테이블과 시퀀스 생성 |
| 3 | `SFC_OWNER` | `@21_seal.sql` | 봉인값 패키지 생성. 두 번째 실행은 스스로 거부합니다. |
| 4 | `SFC_OWNER` | `@22_pkg_sfc.sql`, `@23_functions.sql` | 본체 패키지와 응용 함수 생성 |
| 5 | `SFC_OWNER` | `@30_init_key.sql` | 첫 키 생성과 사용 가능 여부 확인 |
| 6 | `SFC_OWNER` | `@50_selftest.sql` | 자체 시험 |
| 7 | `SYS` | `@40_connect_app.sql 업무스키마` | 업무 스키마에 함수 실행 권한과 시노님 부여 |

4번이 끝나면 다음 조회로 컴파일 상태를 확인하십시오. 결과가 한 줄이라도 나오면 `SHOW ERRORS`로 원인을 보고 멈추십시오.

```sql
SELECT object_name, object_type, status FROM user_objects WHERE status <> 'VALID';
```

6번의 마지막 줄이 `OCS-LITE SELFTEST OK`가 아니면 배포하지 마십시오. `FAIL`이 찍힌 항목 이름을 개발팀에 전달하면 원인을 좁힐 수 있습니다. 6번 B부는 실제 키를 쓰지만 어떤 테이블에도 쓰지 않습니다.

5번이 끝난 직후 **데이터베이스 전체를 백업**하십시오. 이 시점부터 키와 봉인값이 데이터베이스에 존재하며, 이 둘을 잃으면 암호화한 자료를 되살릴 방법이 없습니다. 백업과 복구의 주의는 제8장에 있습니다.

7번 이후 업무 스키마에서 다음 조회가 `1`을 돌려주면 연결이 끝난 것입니다.

```sql
SELECT FN_SFC_READY FROM DUAL;
```

마지막으로 소유 계정을 잠그기를 권합니다. 잠가도 업무 계정의 함수 호출은 그대로 동작하고, 로그인만 막힙니다. 키 교체 때 일시적으로 풀면 됩니다.

```sql
ALTER USER SFC_OWNER ACCOUNT LOCK;
```

## 4. 응용에서 쓰기

### 4.1 저장과 조회

업무 스키마에서는 접두어 없이 함수 이름을 그대로 쓸 수 있습니다.

```sql
INSERT INTO member (id, rrn_enc, pw_hash)
VALUES (1, FN_SFC_ENC('9001011234567'), FN_SFC_PWD_HASH('사용자가-입력한-비밀번호'));

SELECT FN_SFC_DEC(rrn_enc)          AS rrn,
       FN_SFC_MASK(rrn_enc, 'RRN')  AS rrn_masked
  FROM member WHERE id = 1;
```

마스킹 규칙은 다음과 같습니다. `RRN`은 숫자 13자리일 때 앞 여섯 자리와 하이픈만 보여 주고(`900101-*******`) 13자리가 아니면 전부 가립니다. `ACCOUNT`는 앞 네 자리만 보여 주고 나머지를 `*`로 채우며 네 자리 이하이면 전부 가립니다. `ALL`은 항상 `********`입니다. 입력이 NULL이면 결과도 NULL입니다. 유형을 생략하면 `ALL`로 처리합니다.

### 4.2 비밀번호

로그인 검사는 저장된 해시와 대조합니다. 1이면 일치, 0이면 불일치입니다. 저장값이 깨졌거나 비어 있어도 오류가 아니라 0이 나옵니다.

```sql
SELECT FN_SFC_PWD_VERIFY(:입력한_비밀번호, pw_hash) FROM member WHERE id = :id;
```

비밀번호 해시는 일부러 느리게 계산합니다. 한 번 계산하는 데 걸리는 시간을 설치 후에 반드시 재어 보십시오.

```sql
SET TIMING ON
SELECT FN_SFC_PWD_HASH('measure') FROM DUAL;
```

0.3초를 넘으면 로그인이 몰릴 때 문제가 될 수 있습니다. 반복 횟수는 `22_pkg_sfc.sql` 맨 위의 `c_pwd_iterations` 상수(기본 10000)입니다. 줄이면 안전성이 떨어지므로 한꺼번에 많이 줄이지 말고 합의된 값으로 바꾼 뒤 이 패키지를 다시 컴파일하십시오. 이미 저장된 해시는 자기 안에 반복 횟수를 담고 있어 영향을 받지 않습니다. 이 모듈은 비밀번호 복잡도, 만료, 로그인 시도 제한, 계정 잠금을 제공하지 않습니다. 모두 응용이 맡아야 합니다.

### 4.3 이미 평문이 들어 있는 테이블을 전환하는 방법

운영 중인 테이블이라면 컬럼 형식을 바꾸지 말고 새 컬럼을 추가해 옮기는 방식이 안전합니다. 원본이 남아 있으므로 문제가 생겨도 되돌릴 수 있습니다. 여기서는 `member.rrn`을 예로 듭니다.

```sql
ALTER TABLE member ADD (rrn_enc VARCHAR2(136));

-- 나누어 전환한다. 한 번에 수십만 건을 처리하지 않는다.
UPDATE member SET rrn_enc = FN_SFC_ENC(rrn)
 WHERE rrn_enc IS NULL AND rrn IS NOT NULL AND ROWNUM <= 10000;
COMMIT;
-- 건수가 0이 될 때까지 반복

-- 검증: 복호화한 값이 원본과 다른 행이 없어야 한다.
SELECT COUNT(*) FROM member WHERE rrn IS NOT NULL AND FN_SFC_DEC(rrn_enc) <> rrn;
```

검증 결과가 0이고 응용이 새 컬럼을 읽도록 바뀐 것을 확인한 뒤에야 원본 컬럼을 지우십시오. 원본 컬럼을 지우는 순간부터 평문은 어디에도 없게 되므로, 그 전에 백업을 한 번 더 받으십시오. 전환 소요 시간은 측정되지 않았습니다. 시험 인스턴스에서 대표 건수로 먼저 재어 본 뒤 작업 시간대를 정하십시오. 암호화 한 번마다 키 테이블을 한 번 조회하므로 대량 작업은 느릴 수 있습니다.

### 4.4 쓰지 말아야 할 곳

암호화된 컬럼으로는 검색하지 못합니다. 같은 평문도 매번 다른 암호문이 되므로 `WHERE rrn_enc = FN_SFC_ENC('...')`는 결코 일치하지 않습니다. 검색이 없다는 것이 이 모듈의 전제였습니다. 나중에 검색 요건이 생기면 이 모듈을 그대로 쓸 수 없고 설계를 다시 해야 합니다. 복호화 값을 로그나 화면 출력, 임시 테이블에 남기지 마십시오. 복호화하는 쿼리를 뷰로 만들어 일반 사용자에게 열면 암호화의 의미가 없어집니다.

## 5. 평소 운영

정기적으로 해야 할 일은 거의 없도록 설계하였습니다. 감시 시스템이 있다면 업무 스키마에서 `SELECT FN_SFC_READY FROM DUAL`을 주기적으로 실행해 1이 아닐 때 알리도록 하십시오. 이 함수는 오류를 던지지 않고 0을 돌려줍니다.

분기에 한 번 다음을 확인하십시오. 키 테이블에 활성 키가 정확히 하나 있는지, 업무 계정이 아닌 계정이 `SFC_OWNER`의 객체에 권한을 받은 적이 없는지 봅니다. 이를 위해 `SYS`로 접속해 확인합니다.

```sql
SELECT key_id, key_state, created_at FROM SFC_OWNER.SFC_KEY ORDER BY key_id;
SELECT grantee, table_name, privilege FROM dba_tab_privs WHERE owner = 'SFC_OWNER';
```

두 번째 조회 결과에는 업무 스키마에 부여한 함수 여섯 개의 실행 권한만 나와야 합니다. 그 밖의 행, 특히 `SFC_KEY`, `PKG_SFC`, `SFC_SEAL`이 보이면 즉시 권한을 회수하고 원인을 조사하십시오.

## 6. 키 교체

키는 정해진 주기가 없지만, 담당자가 바뀌었거나 키 유출이 의심될 때는 교체해야 합니다. 교체해도 서비스를 멈출 필요가 없습니다. 이전 키는 `OLD` 상태로 남아 기존 자료를 계속 복호화하고, 새 자료는 새 키로 암호화합니다.

```sql
-- SFC_OWNER 로 접속 (잠겨 있으면 SYS 에서 ALTER USER SFC_OWNER ACCOUNT UNLOCK)
EXEC PKG_SFC.rotate_key
SELECT key_id, key_state FROM SFC_KEY ORDER BY key_id;
```

교체 직후 새로 만들어지는 암호문부터 새 키를 씁니다. 기존 자료를 새 키로 바꾸려면 다시 암호화해야 합니다. 어떤 키로 만들어진 값인지는 암호문 문자열의 5번째부터 8번째 글자(키 번호를 16진 네 자리로 쓴 것)로 알 수 있습니다.

```sql
SELECT SUBSTR(rrn_enc, 5, 4) AS key_hex, COUNT(*)
  FROM member GROUP BY SUBSTR(rrn_enc, 5, 4);

UPDATE member SET rrn_enc = FN_SFC_ENC(FN_SFC_DEC(rrn_enc))
 WHERE SUBSTR(rrn_enc, 5, 4) <> '새키번호4자리' AND ROWNUM <= 10000;
COMMIT;
```

모든 행이 새 키로 바뀐 뒤에도 이전 키 행은 지우지 마십시오. 이 모듈은 키를 삭제하는 기능을 제공하지 않으며, 지우면 그 키로 만든 값은 복구할 수 없습니다. 교체가 끝나면 데이터베이스를 백업하십시오. 소유 계정은 다시 잠가 두십시오.

## 7. 오류가 났을 때

모든 오류는 `ORA-206xx` 형식의 예외로 나옵니다. 오류 번호를 보고 아래 표에서 원인을 찾으십시오.

| 번호 | 메시지 | 의미와 조치 |
|---|---|---|
| `-20601` | bad argument 계열 | 인자가 잘못되었습니다. 평문이 1900바이트를 넘거나, 빈 비밀번호를 해시하려 했거나, 마스킹 유형이 `RRN`, `ACCOUNT`, `ALL`이 아닌 경우입니다. 호출한 쪽을 고치십시오. |
| `-20602` | no active key 또는 key id not found | 활성 키가 없거나 암호문 헤더의 키 번호가 키 테이블에 없습니다. 첫 설치라면 `30_init_key.sql`을 실행하십시오. 키 테이블이 다른 환경에서 복사된 경우일 수 있습니다. |
| `-20602` | stored key does not match the seal | 키 테이블의 키가 현재 봉인값으로 열리지 않습니다. 봉인값 패키지가 다시 만들어졌거나 키 테이블만 다른 데이터베이스에서 가져온 경우입니다. 제8장을 보십시오. 이 상태에서는 모든 복호화가 실패합니다. |
| `-20603` | integrity check failed | 암호문이 변조되었거나 잘렸거나, 다른 키로 만든 값입니다. 해당 행만 실패하는지 전체가 실패하는지 확인하십시오. 일부만이면 데이터 손상, 전체이면 키 문제입니다. |
| `-20604` | ciphertext too short 또는 not a valid hex string | 암호문 컬럼에 평문이나 잘린 값이 들어 있습니다. 컬럼 길이가 모자라 암호문이 잘렸을 가능성이 가장 큽니다. 컬럼 길이를 제2장 표와 비교하십시오. |
| `-20605` | keys already exist 또는 no active key | `init_key`를 두 번 실행했거나, 키가 없는데 `rotate_key`를 실행했습니다. 대부분 정상 방어 동작입니다. |
| `ORA-20999` | Client character set does not match the file encoding | 문자집합 점검(`05_check_charset.sql`)이 설치를 멈춘 것입니다. SQL*Plus 창의 `NLS_LANG`이 파일 저장 형식(CP949)과 다릅니다. 제3장의 설정을 한 뒤 같은 스크립트를 다시 실행하십시오. |
| `PLS-00201` | identifier 'DBMS_CRYPTO' must be declared | 설치 중 `SFC_OWNER`에 `DBMS_CRYPTO` 실행 권한이 없습니다. `10_sys_setup.sql`의 부여 문을 `SYS`로 다시 실행하십시오. |
| `ORA-04063` 또는 `ORA-06508` | package body has errors | 패키지가 컴파일되지 않았습니다. `SHOW ERRORS`로 원인을 확인하고 개발팀에 전달하십시오. |

암호화 전체가 멈췄는지 의심될 때 먼저 `SELECT FN_SFC_READY FROM DUAL`을 실행하십시오. 0이면 키 문제, 1인데 일부 행만 실패하면 그 행의 자료 문제입니다.

## 8. 백업, 복구, 환경 복제

키 테이블 `SFC_KEY`와 봉인값 패키지 `SFC_SEAL`은 한 쌍입니다. 둘 중 하나만 옮기거나 하나만 다시 만들면 저장된 키가 열리지 않습니다. 데이터베이스 전체를 백업하고 복구하는 경우에는 둘이 함께 움직이므로 문제가 없습니다. 문제가 되는 것은 일부 스키마만 옮기는 경우입니다.

업무 스키마만 `expdp` 등으로 개발이나 시험 환경에 복제하면, 그 환경에는 키가 없으므로 암호문은 읽을 수 없는 채로 남습니다. 이것은 의도된 보호입니다. 시험에서 복호화가 꼭 필요하다면 업무 스키마와 `SFC_OWNER`를 함께 복제해야 하는데, 이 경우 그 환경에서는 데이터와 키가 함께 있게 되므로 운영과 같은 수준으로 관리하십시오. 복제한 환경에서 새 키를 쓰고 싶다면 그 환경에서 `SFC_OWNER`를 제거하고 제3장을 처음부터 다시 수행한 뒤 시험용 자료를 새로 암호화하십시오.

다음 객체는 어떤 경우에도 지우거나 다시 만들지 마십시오. `SFC_KEY` 테이블, `SFC_SEAL` 패키지, `SFC_KEY_SEQ` 시퀀스입니다. `PKG_SFC`와 여섯 개 함수는 다시 컴파일해도 안전합니다. 그리고 복구 시험을 개통 전에 한 번은 해 보십시오. 백업에서 복구한 시험 인스턴스에서 `SELECT FN_SFC_READY FROM DUAL`이 1이고, 이전에 암호화한 값이 복호화되는지 확인하는 것으로 충분합니다.

## 9. 제거

제거하면 키가 사라지므로 암호화된 자료는 영원히 읽을 수 없게 됩니다. 반드시 먼저 모든 암호문 컬럼을 평문으로 되돌리고(`UPDATE ... SET col = FN_SFC_DEC(col)`), 백업을 받고, 연결된 업무 스키마마다 `41_disconnect_app.sql 스키마`를 실행한 다음에야 `90_uninstall.sql`을 실행하십시오.

## 10. 이 모듈이 막아 주는 것과 막지 못하는 것

키와 봉인값이 모두 데이터베이스 안에 있으므로, 이 모듈이 막아 주는 것은 암호화한 컬럼이 SQL로 복사되어 다른 곳으로 나가는 경우입니다. 개발이나 시험 데이터베이스로의 스키마 복제, 조회 결과의 파일 반출, 화면이나 로그로의 노출이 이에 해당합니다.

막지 못하는 것은 다음과 같습니다. 데이터 파일이나 백업 파일을 통째로 입수한 공격자는 키 테이블과 봉인값을 함께 얻을 수 있습니다. 데이터베이스 관리자는 키 테이블과 봉인값 패키지를 볼 수 있고, 업무 스키마로 접속한 사람은 자기에게 허용된 함수로 복호화할 수 있어서, 복호화 권한이 있는 계정이 탈취되면 평문이 노출됩니다. 이 모듈은 누가 언제 복호화했는지 기록하는 감사 기능이 없습니다. 검증필 암호모듈이 요구되는 환경이라면 이 모듈은 그 요건을 충족하지 못합니다.

계약 상대방에게는 다음 취지의 문장을 서면으로 전달하십시오. 본 모듈은 암호화 키를 데이터베이스 내부에 보관합니다. 따라서 데이터 파일이나 백업 전체가 외부로 유출되는 경우에는 암호화가 데이터를 보호하지 못할 수 있으며, 데이터베이스 관리자의 접근에 대한 방어도 제공하지 않습니다. 더 높은 수준이 필요하면 별도의 키 관리 체계를 도입해야 합니다. 설계 근거는 패키지의 `설계결정.md`(저장소에서는 `lite/docs/02_설계결정.md`)에 있습니다.

## 12. 참고 근거와 신뢰도 자체 평가

이 안내서는 저장소의 `lite/sql/`에 있는 구현, `lite/docs/01`부터 `03`까지의 요구 확정과 설계 문서, 그리고 `lite/tests/`의 기준 구현을 읽은 내용에 근거합니다. 오류 번호, 함수 이름, 컬럼 길이, 키 번호의 위치(암호문 5번째부터 8번째 글자)는 코드와 일치하도록 작성했으며 정확도는 높음입니다. 오라클이 소유 계정을 잠가도 그 계정이 소유한 정의자 권한 프로그램은 그대로 실행된다는 서술은 일반적인 오라클 동작에 근거하며 정확도는 높음이지만, 이 환경에서 확인한 것은 아닙니다. `DBMS_CRYPTO`의 버전별 지원 범위는 정확하지 않을 수 있으므로 설치 환경의 공식 문서로 확인하십시오. 신뢰도는 중간입니다.

요약하면, OCS-LITE는 식별번호를 AES-256으로 암호화하고 비밀번호를 해시하는 여섯 개의 함수를 제공하며 유지보수할 대상이 적습니다. 키가 데이터베이스 안에 있어 파일과 백업 유출은 막지 못하고, 암호화한 컬럼으로 검색할 수 없습니다. 설치 직후의 백업과 봉인값·키 테이블을 한 쌍으로 다루는 것이 가장 중요한 운영 규칙이며, 이 안내서의 절차는 오라클에서 아직 실행해 확인하지 않았습니다.
